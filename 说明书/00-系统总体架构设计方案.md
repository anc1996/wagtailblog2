# wagtailblog2 系统总体架构设计方案

## 1. 系统定位与架构愿景

### 1.1 系统定位

`wagtailblog2`（Django 应用包名 `wagtailblog3`）是一套高可用、企业级的**中文知识库与内容出版管理系统**。系统融合了 Wagtail 8.0 CMS 的树状权限与可视化编辑能力，针对大规模技术文章、公文材料、理论学习、政治要件等多类型内容，构建了关系数据、文档数据库、全文搜索引擎与智能大模型协同工作的现代内容中台。

### 1.2 核心架构设计原则

1. **多库分层，权责单一**：关系库保元数据与权限，文档库保多版本正文大文本，搜索引擎保高性能检索与分词，各司其职，坚决避免跨库数据混杂。
2. **正文资产绝对保护**：正文、修订版本指针（Revision Pointer）与草稿快照受严格一致性保护，数据库迁移、删页、清理操作必须具备强事务隔离与可回滚保证。
3. **最终一致性与异步解耦**：搜索同步、删除级联、文件解析等耗时或跨系统操作全面采用 Outbox/Delivery 事务性发件箱模式与 Celery 异步队列驱动，避免主线程长事务阻塞。
4. **统一设计体系与无障碍**：前端基于企业级六层架构与语义 Token 规范构建，全面适配亮/暗主题与移动响应式，符合 WCAG 2.1 AA 级可访问性。

| 架构层级 | 核心选型与版本 | 职责与定位 |
| :--- | :--- | :--- |
| **基础运行环境** | Python 3.13.2 | 现代 Python 运行时，全面启用静态类型检查与编译字节码优化 |
| **核心业务框架** | Django 5.2.8 LTS<br>Wagtail 8.0 | Web 核心引擎，提供 ORM、中间件、安全防御及 Wagtail 8.0 现代 CMS 树状内容管理与工作流 |
| **关系型主数据库** | MySQL 8.4 LTS | 权威元数据中心：页面树、发布状态、标签分类、权限组、Outbox 事件及搜索分析明细 |
| **文档型正文存储** | MongoDB 7.0 | 正文与多版本中心：存放大文本 StreamField、历史 Revision 快照与未发布草稿 |
| **全文检索分析引擎** | Elasticsearch 7.17 | 内容搜索与分析中心：自建独立中文分词内容索引（v005+）、热词聚合与时序统计 |
| **高速缓存与消息中继** | Redis 7.0 | 缓存层、限流计数器、Celery Broker 消息队列及分布式并发锁 |
| **对象与多媒体存储** | MinIO（S3 兼容） | 私有化对象存储：文章插图、封面图、附件文档、视频资源及多尺寸派生图 |
| **异步任务与定时调度** | Celery 5.4<br>Celery Beat | 异步执行器：处理 `maintenance` 维护队列任务（索引投递、正文安全清理、权限刷新）及定时补偿 |
| **Web 容器与网关** | uWSGI + Nginx | uWSGI 管理 Python 多进程与协程池（6051 端口/Sock）；Nginx 负责反向代理、静态分发与 SSL 终止 |
| **日志与可观测体系** | Filebeat 8.x + Docker | 结构化 JSON 业务日志抽取、集中聚合至 Elasticsearch 日志索引，集成健康检查 |

## 3. 数据权威与多库职责划分矩阵

系统彻底打破传统 CMS 将几十兆富文本直接塞入 SQL 单表的粗暴模式，实施精细化的多库隔离：

```text
[用户浏览器 / 管理员编辑后台]
       │
       ▼ (Wagtail 8.0 Form / Admin)
 ┌─────────────────────────────────────────────────────────────┐
 │                      Django 应用层                          │
 └──────┬──────────────────────┬──────────────────────┬────────┘
        │                      │                      │
        ▼                      ▼                      ▼
┌────────────────┐   ┌────────────────────┐   ┌────────────────┐
│  MySQL 8.4 主库 │   │   MongoDB 7.0 集合 │   │ Elasticsearch  │
├────────────────┤   ├────────────────────┤   ├────────────────┤
│ · 页面树路径   │   │ · 正式发布正文     │   │ · 独立内容搜索 │
│ · live/has_edit│   │ · 历史Revision快照 │   │ · 权限Scope过滤│
│ · Tag与分类关系│   │ · 临时草稿文档     │   │ · 热词与分析大盘│
│ · Outbox/投递表│   │ (body为空不入MySQL)│   │ (纯派生索引)   │
└────────────────┘   └────────────────────┘   └────────────────┘
```

- **MySQL 8.4（权威元数据与权限中心）**：
  - 保存 `wagtailcore_page`、`blog_blogpage` 等模型，记录页面标题、作者、发布状态、时间戳及层级路径。
  - **核心约束**：`BlogPage.body` 在 MySQL 表结构中**保持为空数组**，真实内容由底层信号与生命周期拦截器委托给 MongoDB 存取。
- **MongoDB 7.0（正文大文本与版本中心）**：
  - 划分为三大标准集合：
    - `blog_page_formal_contents`：存放当前公开已发布状态的权威正文。
    - `blog_page_revision_contents`：存放历次发布与草稿生成的不可变历史快照（绑定 Revision ID）。
    - `blog_page_draft_contents`：存放正在编辑中、尚未正式发布的草稿正文。
- **Elasticsearch 7.17（派生搜索与分析大盘）**：
  - 维护独立的 `wagtailblog-prod-content-v*` 物理索引，通过 `wagtailblog-prod-content-read` Alias 对外提供读服务。
  - 数据必须由 MySQL Outbox 事务日志通过 Celery 投递产生，任何情况下禁止业务代码直连 ES 执行未授权写入。

## 4. 物理拓扑与多环境配置隔离

系统严格区分三套物理/虚拟环境，通过环境变量实现代码无差别的确定性运行：

### 4.1 节点环境分布

1. **Windows 11 开发机 (`192.168.20.1`)**：
   - 负责工作区文件编辑（`F:\openclaw\workspace\wagtail\wagtailblog2`）。
   - 不承担 Conda 运行时，不直接启动本地 Python 进程。
2. **WSL2 测试环境 (`192.168.20.5`, Hyper-V Gen2 VM)**：
   - 与 Windows 共享底层 NTFS 目录挂载（`/mnt/f/openclaw/workspace/wagtail/wagtailblog2`），单一 `.git` 库。
   - 运行 Debian 系统，搭载专用 Conda 环境：`/root/anaconda3/envs/wagtailblog-test`。
   - 负责运行全套自动化测试、代码编译检查、pre-commit 门禁及 Git 提交发布入口。
3. **生产服务器 (`192.168.20.2`, 主机名 `ziliao`)**：
   - 独立 Hyper-V Gen1 Linux 虚拟机，专用 Conda 环境：`/root/anaconda3/envs/wagtailblog`。
   - 生产项目主目录：`/home/source/Django/wagtail/wagtailblog3`。
   - 运行受 systemd 守护的四大核心服务：uWSGI、maintenance Worker、Beat、Filebeat。

### 4.2 严格的环境变量驱动边界

所有入口统一引用 `wagtailblog3.settings.dev`，由底层 `WAGTAILBLOG_ENV` 安全选择唯一环境文件，禁止跨环境复制凭据：

- **测试环境**：`WAGTAILBLOG_ENV=test`，加载 `wagtailblog3/settings/.env.test`。
- **生产环境**：`WAGTAILBLOG_ENV=production`，加载 `wagtailblog3/settings/.env.production`（权限固定为 `600`）。
