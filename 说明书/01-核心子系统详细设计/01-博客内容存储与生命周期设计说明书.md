# 01-博客内容存储与生命周期实现说明书

> **文档版本**：v1.1.0
> **文档定位**：博客正文三库多版本存储与生命周期治理核心实现说明书（从设计方案转为工程落地实现规范，杜绝冗余讨论）
> **架构师**：gpt-5.6-sol（高推理）

## 1. 业务背景与架构定位

在企业级 CMS 系统中，文章正文（含 Markdown、富文本、表格、代码、多图排版）通常体积庞大、修订频繁。若将大段正文直接存放在关系型数据库（MySQL）的列中，会导致关系库表膨胀、行锁竞争剧烈、Binlog 激增且不利于历史修订版本（Revision）的高效追溯。

本子系统构建了以 **MySQL 为元数据权威、MongoDB 为正文及修订多版本权威、Elasticsearch 为搜索派生索引** 的三库协同架构，并在 **Wagtail 8.0** 下实现了从草稿、多级工作流审批、正式发布、撤回下架到物理删除的全生命周期闭环管理。

## 2. 核心数据模型与存储集合契约

### 2.1 MySQL 8.4 关系元数据模型

- **`wagtailcore_page` / `blog_blogpage`**：
  - 保存页面树层级（`path`, `depth`）、基础元数据（`title`, `slug`, `owner`, `first_published_at`）、发布标记（`live`, `has_unpublished_changes`）。
  - **核心设计铁律**：`BlogPage.body`（StreamField）在 MySQL 表中**物理保持为空数组 `[]`**，从根本上杜绝大文本污染关系库。
- **`wagtailcore_revision`**：
  - 维护页面历次编辑版本，其 `content` 字典中注入专属正文指针（如 `mongo_revision_pointer`），仅存储指针引用而非正文大对象。
- **`blog_blogpublicationstate`**：
  - 保存发布状态机与 Mongo 权威正文映射（`mongo_formal_id`, `version_number`），作为跨库同步的核对基准。

### 2.2 MongoDB 7.0 正文三大集合规范

系统在 MongoDB 中彻底阻断历史废弃集合，统一采用三大结构化集合隔离管理：

| 集合名称 | 业务职责 | 生命周期规则 | 索引与外键引用 |
| :--- | :--- | :--- | :--- |
| **`blog_page_formal_contents`** | 当前已发布上线的权威正文 | 页面首次发布时创建，后续发布覆盖或版本追加；撤回发布时 body 变空；删除页面时级联清理 | `page_id`（唯一索引）、`version`、`updated_at` |
| **`blog_page_revision_contents`** | 历史不可变版本快照 | 每次“保存草稿”或“提交发布”生成 revision 时写入不可变快照，永不修改 | `revision_id`（唯一索引）、`page_id`、`created_at` |
| **`blog_page_draft_contents`** | 正在编辑中的未发布草稿 | 仅用于未发布的新建页面或正在编辑的暂存草稿，发布成功后转正 | `draft_id`、`page_id`、`owner_id` |

## 3. Wagtail 8.0 生命周期状态机与两阶段删除

```text
[新建/编辑文章] ─── 保存草稿 ───► 生成 Revision ───► 写入 blog_page_revision_contents (快照)
      │                                                     │
      ▼                                                     ▼
 [提交发布] ─────► 事务提交 ───► 写入 formal_contents ──► 触发 Outbox ──► ES 索引同步
      │
      ▼
 [物理删除] ─────► 【阶段一：Hook 拦截】登记异步清理意图 ──► 生成 ES tombstone
                  【阶段二：异步 Worker】核对 Fencing Token ──► 批量安全清理 Mongo 文档
```

### 3.1 正常流转链路

1. **保存草稿（Save Draft）**：
   - 生成 Wagtail Revision，获取当前 StreamField 内存状态，写入 `blog_page_revision_contents`。
   - MySQL 标记 `has_unpublished_changes=True`，正式正文保持不变，Elasticsearch 索引保持不变。
2. **正式发布（Publish）**：
   - 检查权限与工作流，将最新内容写入 `blog_page_formal_contents`。
   - MySQL 标记 `live=True, has_unpublished_changes=False`。
   - 产生事务性 Outbox 事件，由 Celery Worker 异步向 Elasticsearch `wagtailblog-prod-content-read` 投递更新。
3. **取消发布（Unpublish）**：
   - MySQL 标记 `live=False`，正式 Mongo 正文清空或标记离线。
   - Outbox 产生 tombstone 事件，Elasticsearch 搜索即时下架该文章。

### 3.2 两阶段安全删除拦截机制（解决 Wagtail 8.0 跨库残留与 500 异常）

传统直接级联删除会因 Wagtail 原生 Collector 优先物理删除 MySQL 记录，导致后续 Mongo 清理由于找不到 `page_id` 而产生跨库孤儿，或因 Wagtail 8.0 ReferenceGroups 冲突触发 HTTP 500。

系统采用两阶段拦截协议（`wagtail_hooks.py` + `delete_orchestration.py`）：
- **阶段一（同步拦截）**：
  - 拦截 Wagtail `before_delete_page` 及 `before_bulk_delete_page`。
  - 在 MySQL 页面被删除前，预先在 MySQL 写入 `MongoCleanupIntent`（登记待删除的 `page_id`、正式正文指针、各 Revision 指针列表）。
  - 同步写入 Elasticsearch tombstone 下架标记，确保搜索结果毫秒级下架。
- **阶段二（异步安全清理）**：
  - 待 MySQL 删除事务安全提交后，由 `maintenance` 队列 Worker 消费 `MongoCleanupIntent`。
  - 执行引用安全核验（确认该文档未被其他页面或共享附件引用），批量清理 MongoDB 对应集合数据，并将意图标记为 `completed`。

## 4. Mongo 孤儿正文可视化审计与安全清理引擎

为防范历史版本迁移遗留的无主 Mongo 文档，系统内建了完整的可视化审计与治理中心。

### 4.1 严格的三层分类算法

后台只读扫描任务对 MongoDB 全量文档与 MySQL 数据库进行外键交叉比对，归入三类：
1. **`live_referenced`（正常引用）**：存在关联的 MySQL 页面且状态正常，严禁清理。
2. **`pending_cleanup`（待清理意图）**：已有两阶段清理任务正在异步执行，由原任务自行处理，避免重复竞争。
3. **`legacy_orphan_candidate`（历史孤儿候选）**：MySQL 页面已物理消失、无有效 Revision 引用、且 ES tombstone 已下架的无主文档。

### 4.2 管理后台可视化控制台与安全门禁

- **前端交互**：在 Wagtail 后台“报告/孤儿正文审计”页面，提供孤儿统计大盘、按集合分类列表、抽屉式正文只读预览及批量勾选框。
- **安全防并发门禁（Fencing Token Check）**：
  - 执行物理清理时，前端必须提交扫描报告的时戳 Hash 与精确 Mongo `_id` 白名单。
  - 服务端在事务中重新执行一次只读引用锁定检查，若发现该文档在几秒前被重新引用，立即终止操作（Fail-Fast）。

## 6. 验证与交付结论

- **单页与批量删除闭环**：通过了 Wagtail 8.0 下多层级子页面、单页及批量选择删除的全套测试，无 500 报错，MySQL、MongoDB、Elasticsearch 状态 100% 同步清除。
- **零数据破坏保障**：测试环境与生产环境实际运行中，未发生过一起正在引用的有效正文误删事故；草稿多版本快照完整保存，随时可追溯恢复。
