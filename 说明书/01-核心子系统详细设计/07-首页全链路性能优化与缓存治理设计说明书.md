# 《首页全链路性能优化与缓存治理实施方案》

## 1. 现状与根因证据

### 1.1 当前性能基线

目标页面：

`http://192.168.20.2:6050/zh-hans/`

实测结果：

| 指标 | 当前值 | 说明 |
|---|---:|---|
| `loadEventEnd` | 15.49 秒 | 页面完成加载时间严重超标 |
| TTFB | 1.65～2.82 秒 | 后端首字节响应偏慢 |
| HTML 大小 | 166.5 KB，未压缩 | 动态 HTML 传输体积较大 |
| SQL 查询数 | 231 次 | 存在明显 N+1 查询 |
| Google Fonts 单文件下载 | 约 11.75 秒 | 境外字体请求阻塞页面关键链路 |

当前首页性能问题不是单点故障，而是由以下链路共同叠加：

```text
外部字体阻塞
    +
首页服务端 N+1 查询
    +
菜单递归重复查询
    +
热门内容未预取关联对象
    +
模板片段未缓存
    +
动态 HTML 未启用 Gzip
    =
TTFB 高、首屏阻塞、loadEventEnd 极慢
```

### 1.2 根因一：Google Fonts 外部依赖阻塞前端

文件：

`wagtailblog3/static/gretzia/css/style.css`

现状：

```css
@import url("https://fonts.googleapis.com/...");
```

该导入包含：

- 4 个字体族；
- 42 个字重；
- 境外 `fonts.gstatic.com` 的多个 `woff2` 文件；
- 单个字体资源最长耗时约 11.75 秒。

问题在于：

1. CSS `@import` 会增加关键渲染链路；
2. 字体服务器受到国内网络、DNS、跨境链路和连接复用影响；
3. 42 个字重远超首页实际需要；
4. `font-display` 即使设置为 `swap`，也不能消除外部请求本身对页面加载事件和 CSS 依赖的影响；
5. 首页对外部字体没有可用性和超时兜底治理。

### 1.3 根因二：`top_tags_sidebar` 存在 N+1 查询

文件：

`blog_tags.py`

当前逻辑在模板标签中循环遍历所有 `BlogPage.tags.all()`，导致：

- 每个页面或每组标签触发额外查询；
- 首页总计约 160 次相关 SQL；
- 标签统计与页面遍历没有下沉到数据库；
- 查询结果没有缓存。

已验证的优化方向是直接对标签关联表进行聚合：

```python
Tag.objects.filter(
    blog_blogpagetag_items__content_object__live=True
).annotate(
    num_times=Count("blog_blogpagetag_items")
).order_by("-num_times")[:6]
```

该方案实测约 14ms、1 次查询，明显优于逐页面遍历。

实施时需要进一步确认计数语义：

- 只统计 live 的 `BlogPage`；
- 是否只统计当前站点；
- 是否需要限定当前语言；
- 是否需要排除重复关联；
- 是否应使用带过滤条件的 `Count(..., filter=Q(...))`。

### 1.4 根因三：菜单递归和热门文章查询缺少预取

#### 菜单

`generate_menu_items` 的现有行为包含：

- 递归遍历菜单节点；
- 重复执行 `exists()`；
- 重复执行 `specific()`；
- 同一菜单节点在不同层级或不同调用中重复读取；
- 约产生 19 次 SQL。

问题不只是查询数量，还包括递归过程中每个节点的数据库访问无法共享。

#### 热门文章

`popular_posts` 当前缺少：

```python
prefetch_related("categories")
select_related("banner_image", "featured_image")
```

这会导致：

- 文章分类在模板展示时触发额外查询；
- 横幅图、特色图在访问时触发额外查询；
- 模板循环内隐式访问关联对象；
- SQL 数量随文章数量增长。

### 1.5 根因四：模板片段没有缓存

首页以下高复用、低实时性的内容当前没有片段缓存：

- 热门标签；
- 侧边栏；
- 主菜单；
- 热门文章列表或其关联组件。

这导致每次匿名访问都重复执行相同计算和查询。

### 1.6 根因五：动态 HTML 未启用 Nginx Gzip

当前动态 HTML 未配置：

```nginx
gzip_proxied any;
```

结果是：

- 166.5 KB HTML 以明文传输；
- 首次加载受网络吞吐影响；
- 即使后端查询优化完成，传输体积仍然偏大；
- HTML、CSS、JSON、SVG 等文本资源未获得压缩收益。

需要注意：Gzip 主要降低传输时间，不会直接消除应用层 TTFB。TTFB 的核心改善仍来自查询优化和服务端缓存。

## 2. 优化目标与量化指标

### 2.1 总体目标

以 `zh-hans` 首页匿名访问为主验收场景，在缓存预热、正常生产网络和固定测试环境下达到：

| 指标 | 当前基线 | 目标 |
|---|---:|---:|
| TTFB | 1.65～2.82 秒 | `< 200ms` |
| DOMReady | 待补充实测 | `< 800ms` |
| `loadEventEnd` | 15.49 秒 | `< 1s` |
| SQL 次数 | 231 次 | `< 15 次` |
| HTML 传输 | 166.5 KB 未压缩 | 启用 Gzip，目标压缩后显著下降 |
| 外部字体请求 | 多个境外请求 | 0 个境外字体请求 |
| 首页缓存命中率 | 无治理 | 匿名首页核心片段 `> 90%` |
| 首页错误率 | 待补充 | 不高于当前基线 |

### 2.2 指标口径

为了避免测试结果失真，指标需要明确口径：

- TTFB：浏览器 Network Timing 中的响应首字节时间；
- DOMReady：`domContentLoadedEventEnd`；
- Load：`loadEventEnd`；
- SQL：Django 请求级 SQL 统计；
- SQL `< 15`：以匿名首页、缓存命中和缓存未命中分别记录；
- P0 完成后，`loadEventEnd` 不能再被外部字体请求主导；
- TTFB `< 200ms` 应定义为至少 P95 或固定测试环境下的稳定目标，而不是单次最好值；
- 需要同时测试冷缓存和热缓存，不能只用热缓存结果。

建议最终采用：

```text
固定测试环境
固定并发：1、5、20
每组至少 30 次请求
分别统计 P50、P95、最大值
```

## 3. 分阶段实施设计

## P0：斩断 Google Fonts 外部依赖

### 3.1 实施目标

优先解除 11.75 秒级别的外部阻塞，确保首页在没有境外资源可用时仍能正常完成加载。

### 3.2 推荐方案

修改：

`wagtailblog3/static/gretzia/css/style.css`

移除所有外部 `@import`，改为本地系统字体栈：

```css
:root {
    --font-sans:
        -apple-system,
        BlinkMacSystemFont,
        "Segoe UI",
        "Microsoft YaHei",
        "PingFang SC",
        Arial,
        sans-serif;
}
```

正文和标题统一使用本地字体栈，例如：

```css
body {
    font-family: var(--font-sans);
}
```

### 3.3 字体策略

优先级建议：

1. 首页直接使用系统字体；
2. 如果品牌字体是硬性要求，只保留实际使用的 1～2 个字体族；
3. 只保留必要字重，例如 `400`、`500`、`700`；
4. 字体文件放入本地静态目录；
5. 使用 `woff2`；
6. 使用 `font-display: swap`；
7. 不允许运行时依赖 `fonts.googleapis.com` 或 `fonts.gstatic.com`。

不建议仅添加以下配置来“缓解”问题：

```css
font-display: swap;
```

因为这只是调整字体显示策略，不能去除境外网络依赖。

### 3.4 P0 验证

确认以下内容：

- 首页请求瀑布流中不存在 Google Fonts 请求；
- 页面加载不依赖 `fonts.gstatic.com`；
- CSS 无外部 `@import`；
- 视觉上标题、正文、导航没有明显排版退化；
- 中文、英文、数字、粗体均能正常显示；
- `loadEventEnd` 不再出现 11 秒级别的外部资源等待。

## P1：消除 N+1 与关联对象预取

P1 是 TTFB 和 SQL 数量优化的核心阶段。

### 4.1 重写热门标签统计

文件：

`blog_tags.py`

将逐页面遍历方式改为数据库聚合。

基础实现：

```python
from django.db.models import Count

top_tags = (
    Tag.objects
    .filter(blog_blogpagetag_items__content_object__live=True)
    .annotate(num_times=Count("blog_blogpagetag_items"))
    .order_by("-num_times")[:6]
)
```

如果项目 Django 版本支持条件聚合，并且需要严格保证只统计 live 内容，建议使用：

```python
from django.db.models import Count, Q

top_tags = (
    Tag.objects
    .filter(blog_blogpagetag_items__content_object__live=True)
    .annotate(
        num_times=Count(
            "blog_blogpagetag_items",
            filter=Q(
                blog_blogpagetag_items__content_object__live=True
            ),
        )
    )
    .order_by("-num_times")[:6]
)
```

实施时需要通过实际模型关系确认反向查询名是否确实为：

```text
blog_blogpagetag_items
```

同时建议增加稳定排序，避免同数量标签在不同请求中随机变化：

```python
.order_by("-num_times", "name")[:6]
```

如存在重复关联，应评估是否需要：

```python
Count("blog_blogpagetag_items", distinct=True)
```

是否使用 `distinct=True` 必须基于数据模型和索引情况验证，不能无条件添加。

### 4.2 优化 `popular_posts`

将查询优化放在生成热门文章 QuerySet 的位置，而不是在模板中补救：

```python
popular_posts = (
    BlogPage.objects
    .live()
    .select_related("banner_image", "featured_image")
    .prefetch_related("categories")
    .order_by("-first_published_at")[:N]
)
```

实际字段和排序规则应沿用现有业务逻辑。

原则：

- `ForeignKey`、`OneToOneField` 使用 `select_related`；
- 多对多和反向关系使用 `prefetch_related`；
- 只预取模板实际使用的关联；
- 不在模板内访问未预取的 QuerySet；
- 不将整个首页 QuerySet 强制转换成无必要的大列表；
- 对图片关联确认是否存在空值；
- 确认 `banner_image` 和 `featured_image` 是否属于同一继承层级。

如果模板只使用分类名称，可考虑定制 Prefetch 和字段裁剪，但第一阶段不建议过早复杂化。

### 4.3 优化菜单生成

文件位置需要根据项目实际代码确认，通常可能位于：

- `templatetags/` 下的菜单模板标签；
- `context_processors.py`；
- 首页视图；
- 独立的菜单服务模块。

改造原则：

1. 菜单树在一次请求中只生成一次；
2. 递归过程只操作内存中的节点；
3. 用 `select_related` 或 `prefetch_related` 一次加载所需字段；
4. 避免递归中的 `exists()`；
5. 避免对同一节点重复调用 `specific()`；
6. 如果必须调用 `specific()`，在进入递归前批量处理并复用结果；
7. 明确菜单深度，避免无界递归；
8. 对没有子节点的节点直接使用已加载结果。

推荐结构：

```text
数据库查询菜单节点
    -> 构建 parent_id 到 children 的内存映射
    -> 单次递归组装菜单树
    -> 模板只遍历已构建对象
```

不要采用每次递归调用都重新执行 QuerySet 的方式。

### 4.4 P1 查询目标

P1 完成后的预期结果：

| 模块 | 当前估算 | 目标 |
|---|---:|---:|
| 热门标签 | 约 160 次 | 1 次 |
| 菜单 | 约 19 次 | 1～3 次 |
| 热门文章关联 | 随文章数增长 | 固定少量查询 |
| 首页总 SQL | 231 次 | 冷缓存尽量 `< 15` |

首页总查询数应使用实际请求统计确认。对于 Wagtail 的页面树、站点、用户、翻译和图片等固定查询，可以接受少量基础 SQL，但必须避免随内容数量线性增长。

### 4.5 P1 测试要求

增加或完善以下测试：

- 首页请求 SQL 数量测试；
- `top_tags_sidebar` 结果数量和排序测试；
- 非 live 页面不会影响热门标签统计；
- `popular_posts` 访问分类和图片不产生额外 SQL；
- 菜单多层级结构结果正确；
- 菜单无子节点、已删除节点、未发布节点行为正确；
- 中文站点和其他语言站点结果隔离；
- 没有图片或分类时模板不报错。

## P2：Redis 模板片段缓存与失效机制

### 5.1 缓存范围

建议先缓存匿名首页的高复用片段：

| 片段 | 建议 TTL | 说明 |
|---|---:|---|
| 主菜单 | 10 分钟 | 低频变化，按站点和语言隔离 |
| 热门标签 | 5 分钟 | 内容变化后可延迟更新 |
| 侧边栏 | 5 分钟 | 与热门标签、热门文章相关 |
| 热门文章列表 | 5 分钟 | 根据发布频率调整 |
| 页面级公共组件 | 5～10 分钟 | 仅限不含用户个性化内容的片段 |

不要把包含以下信息的片段直接做公共缓存：

- 登录用户信息；
- 用户名、头像；
- 权限相关按钮；
- CSRF Token；
- 个性化推荐；
- 用户购物车、通知、私有数据。

### 5.2 模板缓存示例

在对应模板中加载缓存标签：

```django
{% load cache %}
```

主菜单：

```django
{% cache 600 "home-main-menu" request.site.hostname LANGUAGE_CODE %}
    {% include "..." %}
{% endcache %}
```

热门标签：

```django
{% cache 300 "home-top-tags" request.site.hostname LANGUAGE_CODE %}
    {% include "..." %}
{% endcache %}
```

实际项目中应使用稳定的站点标识和语言标识，不建议只使用一个全局字符串，避免以下问题：

- 中文站和英文站互相污染；
- 测试环境和生产环境键值冲突；
- 多站点菜单相互覆盖。

如果模板上下文中没有 `LANGUAGE_CODE`，应使用项目已有的语言变量或显式传入。

### 5.3 缓存后端

建议确认 Django 已配置 Redis：

```python
CACHES = {
    "default": {
        "BACKEND": "django_redis.cache.RedisCache",
        "LOCATION": "redis://127.0.0.1:6379/1",
        "OPTIONS": {
            "CLIENT_CLASS": "django_redis.client.DefaultClient",
        },
        "KEY_PREFIX": "wagtailblog2",
        "TIMEOUT": 300,
    }
}
```

生产环境必须确认：

- Redis 是否为独立实例或独立逻辑库；
- 是否配置密码和网络访问控制；
- 是否有最大内存和淘汰策略；
- 是否存在多应用共用同一 Redis DB；
- 是否启用持久化；
- Redis 不可用时应用是否应降级为直读数据库。

### 5.4 缓存键设计

推荐统一命名：

```text
wagtailblog2:{environment}:home:{site}:{language}:{fragment}:{version}
```

示例：

```text
wagtailblog2:prod:home:main:zh-hans:menu:v1
wagtailblog2:prod:home:main:zh-hans:top-tags:v1
wagtailblog2:prod:home:main:zh-hans:sidebar:v1
```

建议至少包含：

- 环境；
- 站点；
- 语言；
- 片段名称；
- 版本号。

版本号用于低成本全量失效。模板或数据结构发生变化时，只需将 `v1` 改为 `v2`，避免旧结构继续命中。

### 5.5 失效机制

缓存不能只依赖 TTL。建议采用“事件失效 + TTL 兜底”的方式。

#### 内容发布相关

在 Wagtail 页面发布、取消发布、删除、编辑后触发：

- 热门标签缓存失效；
- 热门文章缓存失效；
- 侧边栏缓存失效；
- 必要时失效对应语言和站点的首页片段。

可使用项目已有的 Wagtail hooks，例如：

- `after_publish_page`
- `after_unpublish_page`
- `after_delete_page`
- 页面编辑完成后的现有业务钩子

#### 标签变更相关

Tag 或 `BlogPage` 标签关联发生变化时触发：

- `top-tags` 失效；
- `sidebar` 失效。

应覆盖：

- 标签新增；
- 标签删除；
- 页面标签关联修改；
- 页面从 live 变为 draft；
- 页面从 draft 发布为 live。

#### 菜单变更相关

菜单节点、菜单排序、菜单标题、菜单可见性发生变化时触发：

- `menu` 失效；
- 相关首页公共片段失效。

### 5.6 防止缓存击穿

首页高峰期建议补充以下治理：

- 对缓存重建增加短时 Redis 锁；
- 只有一个请求负责重建；
- 其他请求等待或读取旧值；
- 不调用 `cache.clear()`；
- 不因单个页面发布而清空全站缓存；
- Redis 故障时允许回源数据库，但需要监控回源量。

P2 第一版可以先使用 Django 模板片段缓存，待命中率和失效正确性验证后，再增加统一缓存服务或锁机制，避免一次引入过多抽象。

## P3：Nginx 动态 Gzip

### 6.1 推荐配置

在 Nginx 的 `http` 或对应 `server` 配置中加入：

```nginx
gzip on;
gzip_proxied any;
gzip_vary on;
gzip_comp_level 5;
gzip_min_length 1024;

gzip_types
    text/plain
    text/css
    text/html
    application/json
    application/javascript
    application/x-javascript
    application/xml
    application/rss+xml
    image/svg+xml;
```

建议：

- `gzip_comp_level 5` 作为 CPU 和压缩率的折中；
- 不压缩 JPEG、PNG、WebP、WOFF2 等已经压缩的资源；
- 保留 `gzip_vary on`，便于代理按 `Accept-Encoding` 正确缓存；
- 确认上游响应没有错误设置 `Content-Encoding`；
- 确认 Nginx 不会对已压缩响应重复压缩。

## 5. 数据与服务影响

### 8.1 数据库影响

正向影响：

- 标签统计从约 160 次查询降为 1 次聚合查询；
- 菜单递归查询数量固定化；
- 热门文章关联查询由逐条访问变为批量加载；
- 数据库连接占用和 ORM 对象构造数量下降；
- 首页 TTFB 明显改善。

潜在影响：

- 聚合查询会增加单次 SQL 的聚合工作；
- 缺少适当索引时，首次聚合可能扫描较多关联记录；
- `Count` 的过滤条件和重复关联处理不正确时，统计结果可能偏大；
- `prefetch_related` 会增加单次返回数据量，但通常远低于 N+1 查询成本。

建议检查并确认已有索引：

- `content_type_id`；
- `object_id`；
- `tag_id`；
- `live`；
- 发布日期排序字段；
- 菜单父节点和排序字段。

是否新增索引必须基于 `EXPLAIN` 和实际数据量决定，本次不预设数据库迁移。

### 8.2 Redis 影响

新增：

- 首页菜单缓存；
- 热门标签缓存；
- 侧边栏缓存；
- 热门文章缓存；
- 失效事件相关操作；
- 可能的缓存重建锁。

必须监控：

- Redis 内存使用；
- 缓存命中率；
- 缓存未命中率；
- Redis 连接错误；
- 缓存重建耗时；
- 缓存键数量；
- 页面发布后的失效延迟。

### 8.3 Nginx 和网络影响

正向影响：

- 动态 HTML 传输体积明显下降；
- 首屏网络传输时间下降；
- 带宽消耗下降；
- 移动网络下收益更明显。

潜在影响：

- Gzip 会增加少量 CPU 使用；
- 压缩等级过高可能抵消收益；
- 代理配置错误可能导致缓存内容与 `Accept-Encoding` 不匹配；
- 上游已经压缩时可能出现重复压缩问题。

建议从压缩等级 5 开始，并在压测中观察 Nginx CPU。

## 7. 回滚方案与残余风险

### 10.1 P0 回滚

回滚方式：

- 恢复 CSS 中原有字体声明；
- 或通过配置开关切换到本地字体栈；
- 不需要数据库回滚。

风险：

- 恢复后会重新引入境外网络依赖；
- 应仅作为视觉回归临时回滚，不应作为长期方案。

### 10.2 P1 回滚

回滚方式：

- 恢复 `top_tags_sidebar` 原有逻辑；
- 移除新增 `select_related` 和 `prefetch_related`；
- 保留测试代码，修正测试期望；
- 不涉及数据库结构回滚。

风险：

- 原逻辑会重新产生 N+1；
- 如果聚合查询的关联路径配置错误，可能出现标签统计不准确，因此必须先做结果对比测试。

### 10.3 P2 回滚

回滚方式：

- 暂时移除模板 `{% cache %}`；
- 将缓存版本号切换；
- 停用失效 hook；
- 不执行 Redis 全库清理；
- 如需清理，只删除 `wagtailblog2:*:home:*` 命名空间键。

风险：

- 缓存失效不完整会导致内容短时间过期；
- 缓存键未包含语言或站点时会造成内容串站；
- 公共片段误包含个性化字段会造成隐私问题；
- Redis 不可用时可能导致数据库回源压力突增；
- 缓存击穿可能在内容发布或 TTL 同时到期时出现。

### 10.4 P3 回滚

回滚方式：

```bash
nginx -t
nginx -s reload
```

若出现异常：

- 删除 Gzip 配置；
- 执行 `nginx -t`；
- reload；
- 确认上游响应恢复。

风险：

- Gzip 参数配置错误；
- 代理层未正确处理 `Vary: Accept-Encoding`；
- CPU 压缩开销高于预期；
- 上游响应已压缩导致重复压缩。

### 10.5 残余风险

即使完成 P0～P3，仍可能存在以下问题：

- TTFB `< 200ms` 对冷缓存请求不一定稳定；
- Wagtail 页面树和 `specific()` 仍可能存在固定开销；
- 首页 HTML 本身仍可能过大；
- 第三方统计、广告或图片资源仍可能影响最终 load；
- 图片尺寸和格式未优化时，页面视觉完成时间仍可能较高；
- 服务器 CPU、数据库连接池或 Redis 网络抖动会影响 P95；
- 真实用户网络与内网测试环境差异较大。

因此目标应以 P95、真实网络和分阶段数据为准，不以单次测试结果作为唯一验收依据。
