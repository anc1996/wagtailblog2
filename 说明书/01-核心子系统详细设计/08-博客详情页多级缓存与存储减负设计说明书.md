## 1. 业务背景与现状调用链路实测剖析（Why Cache is Critical）

### 1.1 现状完整调用链路拆解（基于 models.py 与 blog_page.html）
目前读者在前台访问任意一篇已发布的博客文章详情页（`BlogPage`）时，在无缓存保护下，完整执行以下 6 个阶段的计算与 I/O 链路：

```text
[HTTP GET /blog/article-slug/]
         │
         ▼ 阶段 1: Wagtail 路由与页面模型加载 (MySQL 1~2 次 SQL)
   wagtailcore_page / blog_blogpage 状态与树节点解析
         │
         ▼ 阶段 2: BlogPage.serve() 核心装配 (MySQL 1 次 SQL + MongoDB 1 次物理网络 I/O)
   1. 查询 MySQL BlogPublicationState 获取 published_body_version_id
   2. 向 MongoDB 发起 find_one 物理查询 (数十 KB ~ 数百 KB 正文 JSON)
   3. 在 Python 内存中执行 MongoDBStreamFieldAdapter.from_mongodb() 反序列化与校验
   4. 执行 self.gallery_images.exists() (MySQL 1 次 SQL)
         │
         ▼ 阶段 3: BlogPage.get_context() 页面上下文装配 (MySQL 10~14 次高开销 SQL)
   1. BlogTagIndexPage.objects.live().first() (1 次 SQL)
   2. get_related_posts_by_tags(): 获取 tags -> 提取 tag_ids -> 多表 JOIN 跨表聚合过滤 Count('tagged_items') 排序 (3~4 次复杂 SQL)
   3. get_prev_post() & get_next_post(): 分类存在性核验 + 基于 first_published_at 双向排序 (2~4 次 SQL)
   4. get_view_count(): PageViewCount 聚合统计 (2 次 SQL)
   5. get_reactions(): ReactionType 列表 + Reaction 分组聚合 (2 次 SQL)
         │
         ▼ 阶段 4: Django 模板渲染触发的延迟查询 (MySQL 2~4 次 SQL)
   featured_image、authors.all()、tags.all() 关联模型按需抓取
         │
         ▼ 阶段 5: StreamField 模板 CPU 密集型编译渲染 (高 CPU 开销)
   遍历 page.body，逐块执行 Wagtail Block 渲染：Vditor Markdown 解析、Pygments 代码高亮、KaTeX 公式转义、Mermaid 语法占位
         │
         ▼ 阶段 6: 动态交互组件与读写事务 (L3 旁路)
   1. {% render_comments page %}: 评论树结构与作者头像渲染 (1~2 次 SQL)
   2. {% include 'blog/reactions_block.html' %}: 点赞点踩高亮状态
   3. PageViewMiddleware / PageViewCounter.record(): 异步/同步写入访客审计日志与递增聚合
   4. CSRF Token 随用户 Session 动态生成
```

### 1.2 现状瓶颈与痛点根因分析
1. **MongoDB 物理读取 100% 击穿**：
   - 每次读者访问，uWSGI 进程必向 MongoDB 发起网络读取。即便文章多年未更新，数十 KB 的 JSON 仍重复从磁盘拉取，造成 MongoDB 连接池竞争与网络延迟（5ms ~ 20ms）。
2. **为什么单纯套 Django 模板 `{% cache %}` 无法解决问题**：
   - `BlogPage.serve()` 与 `get_context()` 在模板渲染**之前**就已经完整执行。即便正文块被 `{% cache %}` 包裹，`get_content_from_mongodb()` 的 Mongo 读取已发生，相关文章的 4 次多表聚合 SQL 已发出，上下篇的 4 次 SQL 已执行。因此仅改模板片段无法从根源降低 MySQL 压力。
3. **CPU 密集型序列化与渲染**：
   - StreamField 反序列化校验（Python 遍历处理块结构）以及 Markdown/代码高亮解析在每个请求中重复运算，单进程吞吐量（RPS）受限于 CPU 瓶颈，冷温请求 TTFB 常年徘徊在 120ms ~ 280ms。

### 1.3 现状实测指标基线（Baseline）
- **MongoDB 物理读取**：**100% 击穿**（每次访问必触发 1 次网络与集合查询）；
- **MySQL 查询次数**：单次请求执行 **15 ~ 22 次 SQL 查询**（静态上下文占 10~14 次，动态组件与页面基础占 5~8 次）；
- **首字节响应时间 (TTFB)**：冷/温请求通常在 **120ms ~ 280ms** 之间；
- **单核 RPS 承载能力**：约 **30 ~ 50 req/s**。

## 2. 需求目标与边界原则（Goals & Non-Goals）

### 2.1 核心目标
1. **L2 服务层正文零 Mongo 读**：对公开正式访问，正文直接从 Redis 高速读取反序列化好的 Clean Payload，热缓存场景下 MongoDB 物理读取降为 **0 次**（命中率 > 95%）；
2. **L2.5 上下文静态查询减负**：为“相关推荐”与“上下篇导航”引入轻量 DTO 代次缓存，消除多表 Count 跨表 JOIN，使页面静态装配 SQL 下降 **70% 以上**；
3. **L1 模板片段按需减负**：稳定后通过代次片段缓存，跳过重复的 Markdown 与代码高亮 CPU 计算；
4. **实时性与精准代次失效（Zero-Stale Invalidation）**：后台发布、编辑、取消发布或删除时，通过精确版本标识与代次递增实现毫秒级自然换代，绝不使用危险的 Redis 通配符扫描；
5. **动态交互绝对安全（L3 旁路）**：评论区提交、点赞反应、实时阅读统计、登录态、CSRF Token 100% 旁路，零串读、零污染、零缓存。

### 2.2 非目标（明确不做的事）
1. **不做整页 HTTP 强缓存（No `cache_page`）**：严禁对文章页整体套用 HTTP 页面缓存，否则会破坏 CSRF Token、破坏当前用户点赞状态、导致评论树用户态串标；
2. **后台预览与历史 Revision 绝对穿透（Bypass Drafts & Previews）**：管理员在 Wagtail 后台预览未发布草稿、对比历史 Revision 时，100% 绕过所有公开缓存，直读 MongoDB 原始数据，且绝不把草稿写回 Redis；
3. **不改变存储权威契约**：MongoDB 依然是不可变正文版本的唯一权威归宿，MySQL 是页面关系元数据唯一权威；Redis 仅定位为**易失性只读加速层**；
4. **不做无法证实的虚假指标承诺**：坚决摒弃未经验证的“全场景 30ms TTFB”或“全局 400 RPS”口头承诺，一切指标以真实压测数据为准。

## 3. 多级缓存协同架构体系设计（Multi-Tier Architecture）

系统采用“**L1 渲染片段缓存 + L2.5 上下文导航 DTO 缓存 + L2 服务层正文 Payload 缓存 + L3 动态交互旁路**”的四层协同架构：

```text
               [用户浏览器访问 GET /blog/article-slug/]
                                  │
                                  ▼
      ┌────────────────────────────────────────────────────────┐
      │ 核心前置判定: 是否属于管理后台预览 / 历史 Revision 审计? │
      └───────────────────────────┬────────────────────────────┘
                   ┌──────────────┴──────────────┐
              [是: 预览/草稿]               [否: 公开正常访问]
                   │                             │
                   ▼                             ▼
       ┌──────────────────────┐      ┌──────────────────────────────────────────────┐
       │ 强制安全旁路穿透      │      │ L2: 服务层正文 Clean Payload 缓存             │
       │ 1. 绕过 Redis 缓存   │      │ Key: blog-detail:v1:body:{site}:{loc}:{pk}:..│
       │ 2. 直读 Mongo 目标快照│      │ 命中: 返回干净正文字典 (跳过 Mongo 网络 I/O) │
       │ 3. 严禁写回公共缓存  │      │ 未命中: 单飞互斥回源 Mongo 并写入 Redis      │
       └──────────────────────┘      └──────────────────────┬───────────────────────┘
                                                            │
                                                            ▼
                                     ┌──────────────────────────────────────────────┐
                                     │ L2.5: 上下文推荐与导航 DTO 缓存               │
                                     │ Key: blog-detail:v1:nav:{site}:{loc}:{pk}:.. │
                                     │ 命中: 直接返回轻量文章列表字典 (免 8~10次SQL)│
                                     │ 未命中: 执行过滤并缓存纯净 DTO (非 QuerySet) │
                                     └──────────────────────┬───────────────────────┘
                                                            │
                                                            ▼
                                     ┌──────────────────────────────────────────────┐
                                     │ L1: 模板正文渲染片段缓存 (Template Fragment) │
                                     │ Key: blog-detail:v1:html:{site}:{loc}:{pk}:..│
                                     │ 命中: 直接输出预编译 HTML (跳过 CPU 运算)    │
                                     │ 未命中: 执行 Markdown/KaTeX 渲染并写入       │
                                     └──────────────────────┬───────────────────────┘
                                                            │
                                                            ▼
                                     ┌──────────────────────────────────────────────┐
                                     │ L3: 动态交互旁路通道 (100% 动态实时计算)     │
                                     │ · {% render_comments page %}: 实时审核与头像 │
                                     │ · {% include 'reactions_block.html' %}: 点赞 │
                                     │ · PageViewCounter: 实时读写统计审计          │
                                     │ · CSRF Token 与用户 Session 菜单             │
                                     └──────────────────────────────────────────────┘
```

### 3.1 L2：服务层正文 Payload 缓存（Service-Level Clean Payload Cache）
在 `BlogPage.get_content_from_mongodb()` 拦截，通过独立服务 `DetailCacheService` 进行调度。

- **Key 命名契约**：
  ```text
  blog-detail:v1:body:{site_id}:{locale_id}:{page_id}:{body_version_id}:{body_schema_version}
  ```
- **存储内容契约（Strict Clean Payload）**：
  只缓存纯净的、不可变的正文内容结构，禁止混入易变元数据：
  ```python
  {
      "body": [...],                   # 经过 MongoDBStreamFieldAdapter 校验的块列表
      "body_version_id": "uuid_hex",   # 当前发布的不可变正文版本 ID
      "body_sha256": "sha256_hex",     # 正文哈希校验码
      "body_schema_version": 1         # 块结构协议版本
  }
  ```
- **纯净性隔离原则**：
  - 严禁将 `title`、`intro`、`featured_image`、`has_gallery` 写入此缓存；
  - `has_gallery` 必须由当前请求的模型关系判定（或由下文独立轻量代次维护），杜绝“后台删除了画廊图片，前端依然渲染画廊容器”的陈旧状态。
- **TTL 策略**：86,400 秒（24 小时）。因为 key 与不可变 `body_version_id` 强绑定，版本变更天然切换新 Key，旧 Key 自然按 TTL 过期回收。

### 3.2 L2.5：上下文推荐与导航 DTO 缓存（Context DTO Cache）
针对 `get_context()` 中引发 8~10 次复杂 SQL 查询的 `get_related_posts_by_tags()`、`get_prev_post()` 和 `get_next_post()` 进行减负。

- **Key 命名契约**：
  ```text
  blog-detail:v1:nav:{site_id}:{locale_id}:{page_id}:{publication_generation}
  ```
- **存储内容契约（Lightweight DTO Dict）**：
  严格禁止缓存 Django ORM `QuerySet` 或 `BlogPage` 模型实例（防止包含已关闭的数据库连接或 Session 闭包）：
  ```python
  {
      "related_posts": [
          {"id": 12, "title": "文章标题", "url": "/blog/slug-1/", "date": "2026-08-01", "image_url": "..."},
          ...
      ],
      "prev_post": {"id": 10, "title": "上一篇", "url": "/blog/slug-prev/"} or None,
      "next_post": {"id": 15, "title": "下一篇", "url": "/blog/slug-next/"} or None
  }
  ```
- **公开权限强约束**：
  查询时必须显式增加 `.public()` 与隐私限制过滤（`PageViewRestriction` 检查），禁止非公开/受限文章进入共享导航缓存。
- **TTL 策略**：14,400 秒（4 小时），受 `publication_generation` 强约束。

### 3.3 L1：模板/渲染层 HTML 片段缓存（Template Fragment Cache）
在 `wagtailblog3/templates/blog/blog_page.html` 中引入 Django 原生 `{% cache %}` 标签，包裹高 CPU 消耗的正文块遍历区域。

- **Key 命名契约**：
  ```text
  blog-detail:v1:html:{site_id}:{locale_id}:{page_id}:{publication_generation}:{render_version}
  ```
- **模板标签语法**：
  ```django
  {% load cache %}
  {% cache 3600 blog_detail_body_html page.id page_generation render_version %}
      <div class="article-body-content">
          <div class="content-blocks" data-reading-content data-content-image-gallery>
              {% for block in page.body %}
                  <div class="content-block-wrapper {% if block.block_type == 'rich_text' or block.block_type == 'markdown_block' %}markdown-body{% endif %}" data-block-type="{{ block.block_type }}">
                      {% if block.block_type == 'image_block' %}
                          {% include "blog/streams/image_block.html" with value=block.value only %}
                      {% else %}
                          {% include_block block %}
                      {% endif %}
                  </div>
              {% endfor %}
          </div>
      </div>
  {% endcache %}
  ```
- **核心约束**：
  - `render_version` 作为应用级全局常量（如 `DETAIL_RENDER_VERSION = "20260906-v1"`），用于在更新了 Markdown 渲染器逻辑、CSS 主题或安全过滤规则时实现全站 HTML 瞬间换代；
  - 动态组件绝不进包裹区。

### 3.4 L3：动态交互绝对旁路通道（Dynamic Bypass）
以下组件与数据严禁加入任何缓存：
1. **`{% render_comments page %}`**：包含实时审核通过的评论树、当前登录用户头像、评论点赞态；
2. **`{% include 'blog/reactions_block.html' %}`**：用户个性化反应按钮与当前高亮态；
3. **`{{ page.get_view_count }}` 与 `PageViewMiddleware`**：实时读者浏览量、滚动深度追踪、IP 审计入库；
4. **CSRF Token 与用户鉴权状态**：页面中的 `data-csrf-token` 及导航栏登录态。

## 4. 预览隔离与安全穿透设计（Preview & Draft Isolation）

为了彻底杜绝“编辑在后台预览草稿，结果草稿被存入 Redis 导致线上公开读者提前看见未发布内容”，必须建立严格的**物理穿透与隔离契约**：

### 4.1 预览态确定性判定
在 `BlogPage.serve()` 及缓存拦截器中，通过以下优先级判定当前请求是否处于预览/历史审计模式：
```python
is_preview = (
    getattr(request, "in_preview_panel", False)
    or getattr(request, "is_preview", False)
    or request.resolver_match.url_name in {"preview", "preview_revision"}
    or not self.live
)
```

### 4.2 行为隔离守则
1. **读取时**：
   - 当 `is_preview=True` 时，直接绕过 `DetailCacheService`，强制调用底层的 `MongoManager.get_body_version()` 读取草稿或对应 `Revision` 的快照；
2. **写入时**：
   - 预览链路下，**严禁**调用 `DetailCacheService.set_body()` 或 `set_nav_dto()`，禁止向 Redis 写入任何 Key；
3. **历史 Revision 审计防污染**：
   - 查看历史 Revision 时，读取的是 `blog_page_revision_bodies` 集合中的只读快照，其数据生命周期完全独立，绝不触碰正式缓存通道。

## 5. 精准失效与代次生命周期闭环（Invalidation & Generation Lifecycle）

### 5.1 彻底废止通配符删除（Pattern Deletion Deprecation）
- **严重隐患**：旧方案中设想的 `cache.delete("blog_mongo_payload_*")` 是无效或极度危险的。标准 Django 缓存后端根本不支持通配符删除；即便在 `django-redis` 中使用 `delete_pattern()`，在生产环境中对数万个 Key 进行 `KEYS/SCAN` 操作也会造成 Redis 阻塞与严重的延迟毛刺。
- **取而代之的架构方案**：**不可变版本键绑定（Version-Immunity）+ 代次指针自然淘汰（Generation Bump）**。

### 5.2 版本键与代次闭环机制
1. **正文内容变更**：
   - 文章发布新版本时，MySQL `BlogPublicationState.published_body_version_id` 被更新为全新 UUID，Key 天然切换，旧 Key 自动等待 TTL 回收，零扫描开销、零脏读并发；
2. **页面元数据与关系变更（代次推进）**：
   - 依赖页面级的 `publication_generation`（正整数或 UUID hex）。一旦触发元数据变更，递增该代次，所有引用该代次的 HTML 片段与上下文 DTO 在下一次访问时自然未命中，重新生成并覆盖最新代次；
3. **事务安全兜底（Mandatory `transaction.on_commit`）**：
   - 所有的缓存失效与代次推进动作，**必须**包裹在 `transaction.on_commit(...)` 中执行。若当前事务因为数据库异常回滚，绝对不触发缓存失效，保持缓存与数据库原子一致。

### 5.3 生命周期事件与失效覆盖矩阵

| 事件触发源 | 涉及行为 | 失效范围与动作 | 触发时机与机制 |
| :--- | :--- | :--- | :--- |
| **文章正常发布 (`page_published`)** | 首次发布或更新内容 | 1. 正文切换全新 `version_id` 天然换代<br>2. 推进当前文章 `generation`<br>3. 推进前一篇与后一篇文章的 `generation`（使相邻导航同步刷新）<br>4. 触发首页片段失效 `_invalidate_home_fragments()` | `page_published` 信号，强制 `on_commit` |
| **文章取消发布 (`page_unpublished`)** | 下线文章 | 1. 推进当前文章 `generation`<br>2. 推进相邻文章 `generation`<br>3. 触发首页失效 | `page_unpublished` 信号，强制 `on_commit` |
| **创建删除意图 (`PageDeletionIntent`)** | 受控删除开始 | 1. 立即推进该页 `generation`<br>2. 推进相邻文章 `generation`，使其它文章不再链接到待删除文章 | 删除意图入库事务提交后，强制 `on_commit` |
| **页面移动 / 权限变更 (`post_page_move`)** | 移动父节点或调整隐私权限 | 推进当前节点及子节点的 `generation`，清空受限 DTO 缓存 | Wagtail 信号，强制 `on_commit` |
| **全局静态资源/清洗规则发布** | 模板样式升级或 Markdown 增强 | 全局递增 `DETAIL_RENDER_VERSION` 常量，全站 HTML 片段毫秒级平滑过渡 | 代码部署生效，零 Redis 停机时间 |

## 6. 高并发容灾、防击穿与降级设计（Resilience & Concurrency）

### 6.1 并发互斥回源（Single-Flight Mutex Lock）
在超高并发场景下，如果某篇热门文章的 L2 缓存同时失效（或首次冷启动），数十个 uWSGI 工作进程可能同时向 MongoDB 发起查询，导致 Mongo 物理连接池瞬间打满（击穿效应）。

- **防击穿互斥锁算法**：
  ```python
  lock_key = f"blog-detail:lock:body:{page_id}:{body_version_id}"
  # 尝试获取短租约锁 (租约 5 秒，防止进程宕机死锁)
  acquired = cache.add(lock_key, "locked", timeout=5)
  if acquired:
      try:
          # 独占回源 MongoDB 拉取正文
          payload = fetch_from_mongodb(...)
          # 写入 Redis
          cache.set(cache_key, payload, timeout=86400)
          return payload
      finally:
          cache.delete(lock_key)
  else:
      # 未抢到锁的并发进程，短暂自旋等待 50ms 后重新读取 Redis
      time.sleep(0.05)
      cached = cache.get(cache_key)
      if cached:
          return cached
      # 若重试仍无，说明回源较慢，降级直接直查 Mongo，绝不无界等待
      return fetch_from_mongodb(...)
  ```

### 6.2 坚不可摧的 Fail-Open 降级策略
- **黄金法则**：缓存是性能加速手段，绝对不能成为可用性单点瓶颈。
- **异常捕获范围**：
  - Redis 服务停止、网络连接超时；
  - 序列化/反序列化 JSON 损坏；
  - `body_sha256` 校验不匹配；
- **降级动作**：
  - 一旦发生上述任何异常，`DetailCacheService` 立即捕获并在日志中记录 `logger.warning("detail_cache_read_failed ...")`；
  - 立即降级回退到原生的 `MongoManager` 与 `MySQL ORM` 物理查询，确保返回正确的页面给读者，**严格杜绝返回 HTTP 500**。

### 6.3 负缓存（Negative Caching）
- 若某文章的不可变版本在 MongoDB 中确实缺失或已损坏（触发 `PublicationBodyUnavailableError`），在 Redis 中记录一个特殊的标记值（TTL 设定为 30 秒），防止恶意流量针对不存在的非法版本频繁发起穿透攻击。

## 8. 验证指标、测试策略与性能量化标准（Verification & Metrics）

### 8.1 四类运行场景验证矩阵
所有缓存落地必须通过以下 4 类核心场景的严格比对：

| 场景标识 | 场景名称 | 外部环境条件 | 预期行为与判定依据 |
| :--- | :--- | :--- | :--- |
| **场景 A** | **冷缓存 (Cold Cache)** | Redis 中无目标 Key | 1. 成功回源 Mongo 读取正文<br>2. 成功执行必要的 DTO 构造<br>3. 正确将 Clean Payload 写入 Redis<br>4. 页面 200 正常呈现 |
| **场景 B** | **热缓存 (Hot Cache)** | Redis 已存在有效 Key | 1. **MongoDB 读取 0 次** (Mongo 查询捕获断言)<br>2. **MySQL 查询次数大幅下降 70%+**<br>3. 正文内容与冷态 100% 一致 |
| **场景 C** | **Redis 故障 (Fail-Open)** | 模拟 Redis 断开或异常抛错 | 1. 记录 warning 日志<br>2. **绝不报 500**，优雅透明回退到 MongoDB 直读<br>3. 页面渲染完全正常 |
| **场景 D** | **草稿预览 (Draft Preview)** | 后台携带 preview 参数访问 | 1. **不读取任何 Redis 缓存**<br>2. **不写入任何 Redis 缓存**<br>3. 渲染出最新未发布的编辑中草稿 |

### 8.2 自动化契约测试清单（必须实现的单测）
在 `test_blog_page_cache.py` 中必须落地的测试方法：
1. `test_l2_cache_hit_bypasses_mongo_read`：验证热缓存状态下，`MongoManager.get_body_version` 调用的执行次数为 0；
2. `test_context_dto_cache_reduces_sql_queries`：使用 `CaptureQueriesContext` 断言冷态与热态下的 SQL 查询次数差异；
3. `test_preview_mode_completely_bypasses_and_never_writes_cache`：模拟预览请求，断言其直接读取草稿，且检查 Redis 对应 Key 不存在；
4. `test_fail_open_on_redis_connection_error`：模拟 Redis 抛出 `ConnectionError`，断言页面依然返回 200 且正确呈现正文；
5. `test_corrupted_payload_triggers_fallback_and_recovery`：向 Redis 存入损坏的 JSON 或错误的 Hash，断言系统安全弃用并回源；
6. `test_page_publish_bumps_generation_atomically`：断言页面发布后，通过 `on_commit` 正确推进代次，旧导航 DTO 不再被读取；
7. `test_unpublish_and_deletion_intent_invalidates_access`：断言取消发布或进入删除状态后，公共访问立即阻断，无陈旧内容残留；
8. `test_single_flight_mutex_prevents_dogpile_effect`：并发多线程模拟同时访问冷 Key，断言只有一个线程真正穿透到 Mongo。

## 9. 风险评估与安全回滚方案（Risks & Rollback）

### 9.1 核心风险与防御对策
- **风险 1：缓存穿透/击穿** $\to$ **对策**：内置 Single-Flight 分布式锁，辅以 30s 损坏版本负缓存；
- **风险 2：草稿内容泄漏** $\to$ **对策**：预览与历史 Revision 逻辑强制置于缓存拦截器之前，代码与单测层面对 preview 实施零容忍旁路；
- **风险 3：版本混淆与幽灵数据** $\to$ **对策**：Key 必须绑定 `published_body_version_id`，版本变更 Key 天然隔离，无法产生串版；
- **风险 4：Redis 内存膨胀** $\to$ **对策**：L2 Payload 仅存紧凑 JSON，单篇约 10~50KB，10,000 篇热门文章仅需数百 MB，且配置 24 小时 TTL 自动驱逐。

### 9.2 原子化安全回滚预案
- 本次改造属于**纯应用代码与模板层加速优化**，不增加数据库字段，不执行数据库迁移（零 Schema Migration），不修改 MongoDB 原有物理集合；
- **回滚操作**：若上线后遇到任何不可预期的异常，直接通过 Git 将代码回退到上一稳定 commit，并重载 uWSGI（`systemctl reload wagtailblog3`）即可在 5 秒内 100% 恢复原有直读直查链路，对数据库与用户资产**零残留影响**。
