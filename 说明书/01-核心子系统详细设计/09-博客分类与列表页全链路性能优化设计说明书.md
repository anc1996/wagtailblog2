## 1. 设计结论

生产分类页的主要问题不是单个慢查询，而是同一份列表数据在页面、模板标签和侧边栏中被重复计算。优化必须把请求拆成三个边界：

1. **公开列表数据**：由列表装配引擎一次批量读取，允许 Redis 缓存；
2. **实时互动写入**：浏览量、匿名访客、反应写入仍走现有事务和唯一约束，不被列表缓存阻断；
3. **正文与发布一致性**：MongoDB 正文、`StreamField body`、Revision、`mongo_content_id` 和发布指针不进入本方案的缓存载荷，也不改变其持久化顺序。

目标是将默认 20 篇列表页的应用 SQL 从基线 182 次压缩到**冷缓存不超过 10 次，热缓存不超过 2 次**；将归档挂件 HTML 从 91.2 KB 压缩到 **18 KB 以下**；删除人为白屏，使首屏以服务端 HTML 到达即开始渐进渲染。

本说明书是性能架构与落地契约，不等同于已经完成的代码变更。任何生产发布必须经过 WSL2 定向测试、Maker-Checker 复核和用户终审。

### 2.2 性能基线

以下数字来自本案前期生产/WSL2 实测，作为验收前的固定基线，不把目标数字当作已经验证的结果：

| 指标 | 基线 | 主要原因 |

| 首屏白屏 | 0.8 至 1.5 秒 | `.preloader` 覆盖内容直到 `window.load` |

### 2.3 范围与非目标

**本次范围**：`BlogIndexPage` HTML 页面、`blog_index_results_api`、列表卡片数据装配、归档和随机作者侧边栏、分类页 CSS/JS 阻塞路径、内容生命周期失效和可观测性。

**明确非目标**：

- 不修改 Markdown 原文格式、`markdown_block` 存储 key、MongoDB 文档、Revision 或正文指针；
- 不把浏览量、反应写入迁移到 Redis，也不因为读列表缓存而跳过 `PageViewCounter` 的数据库事务；
- 不使用 `cache.clear()`、Redis `FLUSHDB`、MySQL `TRUNCATE`、MongoDB `drop` 或未授权批量修复；
- 不把预览、草稿、后台权限页面写入公开缓存；
- 不为了本案顺手重构全站前端资源或详情页业务。

## 3. 总体架构

### 3.1 请求链路

```text
Wagtail 路由解析
      │ 取得 site_id、locale_id、BlogIndexPage.pk
      ▼
规范化 query_params + 读取 listing_generation
      │
      ├─ L0：当前请求 memo（同一请求只装配一次）
      ├─ L1：Redis 结构化 ListingPayload
      ├─ L2：Redis 渲染后的 HTML/JSON 片段
      └─ 未命中：Single-Flight Mutex，批量查询并回填 L1/L2
                         │
                         ├─ BlogPage 元数据、图片、作者、标签
                         ├─ PageViewCount 条件聚合
                         └─ Reaction 条件聚合
      ▼
HTML 首屏或 JSON 渐进增强响应
      │
      ├─ 统计写入仍由现有 middleware / PageViewCounter 异步记录
      └─ 发布、下线、删除、批量导入完成后推进 generation
```

### 3.2 缓存层定义

| 层级 | 内容 | 生命周期 | 允许的数据 |
|---|---|---:|---|
| L0 | 请求级字典和已规范化的分页结果 | 单请求 | 任何公开列表 DTO |
| L1 | 可序列化 `ListingPayload` | 默认 120 秒，带随机抖动 | 标题、日期、URL、作者/标签展示值、图片 URL、统计快照、分页元数据 |
| L2 | 服务端渲染 HTML 或 JSON 片段 | 默认 90 秒，允许 stale-while-revalidate | 仅由 L1 生成的公开无用户差异结果 |
| 旁路聚合 | 归档聚合、作者候选集合、反应类型字典 | 10 分钟至 6 小时 | 不含正文和权限信息 |

L1/L2 使用现有 Redis cache alias 和与详情页一致的错误处理原则：Redis 故障时记录指标并回源数据库，不能让读者请求失败。禁止缓存 Django QuerySet、Page 实例、数据库连接和包含 request/user 的对象。

## 4. 列表缓存契约

### 4.1 规范化请求参数

只允许以下参数进入缓存身份：

```text
page          正整数，非法值归一为 1，设置最大页深度保护
search        去首尾空白，长度上限 100，按 Unicode 原文排序后编码
start_date    YYYY-MM-DD，非法值丢弃
end_date      YYYY-MM-DD，非法值丢弃
sort_primary  date_asc/date_desc/title_asc/title_desc
sort_secondary 与 primary 组合匹配的合法值
```

规范化结果按固定字段顺序生成 canonical query string，例如：

```text
page=1&search=&start_date=&end_date=&sort_primary=date_desc&sort_secondary=title_asc
```

再使用 SHA-256 得到 `query_hash`。原始 query string 不得直接拼接到 Redis key，避免空格、重复参数和超长输入制造大量等价 key。查询参数也必须经过长度、日期和排序白名单校验，防止把缓存当作绕过查询约束的入口。

### 4.2 Key 拓扑

所有键使用 schema 版本，便于无损切换。`generation` 是不透明字符串，推荐复用详情页的发布代次语义，但列表代次按受影响的索引页维护。

```text
wblog:list:v2:payload:{site_id}:{locale_id}:{page_id}:{query_hash}:{generation}
wblog:list:v2:html:{site_id}:{locale_id}:{page_id}:{query_hash}:{generation}
wblog:list:v2:json:{site_id}:{locale_id}:{page_id}:{query_hash}:{generation}
wblog:list:v2:lock:{site_id}:{locale_id}:{page_id}:{query_hash}:{generation}
wblog:list:v2:generation:{site_id}:{locale_id}:{page_id}
```

键拓扑强制包含 `site_id`、`locale`、`page_id`、规范化 `query_params` 的摘要和 `version_generation`。`site_id` 与 `locale_id` 不能只用语言名称替代：相同语言可存在多个站点，站点根页面和发布范围可能不同。

`ListingPayload` 至少包含：

```json
{
  "schema_version": 2,
  "site_id": 1,
  "locale_id": 1,
  "page_id": 368,
  "generation": "publication-generation",
  "filters": {"search": "", "start_date": "", "end_date": "", "sort_primary": "date_desc", "sort_secondary": "title_asc"},
  "pagination": {"page": 1, "page_size": 20, "total_results": 122, "total_pages": 7},
  "cards": []
}
```

`cards` 中只保存模板所需的公开 DTO。不要保存 `body`、Mongo 文档、Revision 内容、用户反应身份、session key 或 IP。

### 4.3 防击穿、防雪崩和并发语义

采用与 `DetailCacheService` 相同的 Single-Flight 思路：

1. 先读 L2，再读 L1；命中后直接返回；
2. 未命中时用 `cache.add(lock_key, random_token, timeout=5)` 争抢锁；
3. 获锁者再次检查 L1，避免锁建立前已有回源结果；确认仍未命中后执行批量查询并写入 L1/L2；
4. 未获锁请求最多随机等待 25 至 250 ms，随后再次读缓存；仍未命中则执行一次受控回源，不得无限自旋；
5. 存在未过期 stale 数据时优先返回 stale，并由获锁者异步刷新；没有 stale 时才允许短暂等待；
6. 锁释放必须校验 token，Redis 环境使用 compare-and-delete Lua 脚本，禁止请求 A 删除已过期后由请求 B 取得的新锁；
7. TTL 必须加入 0 至 20% 的随机抖动。大批量导入不得循环删除每个查询 key，只推进 generation；旧 key 自然过期。

缓存异常是 Fail-Open：锁服务异常时直接回源，但通过每进程并发信号量限制同一 worker 的回源并发，并打出 `listing_cache.fail_open` 指标。不得用全局缓存清空作为异常补偿。

### 4.4 HTTP 契约

只有 `GET`、公开、无用户个性化的列表请求允许缓存。缓存响应应包含：

```text
Cache-Control: public, max-age=30, stale-while-revalidate=90
ETag: "{generation}-{query_hash}-{payload_hash}"
X-Blog-Listing-Cache: HIT|MISS|STALE|BYPASS
```

ETag 命中返回 304 时不得重新渲染模板。预览、登录后有权限差异、非 GET、异常参数和明确 `no-store` 请求保持 `private, no-store`。异步 API 的 JSON 结构继续保留现有 `ok/data/error` 外层和 canonical URL 字段，只改变其内部从缓存读取，不能让前端同时适配第二种格式。

## 5. 列表高性能装配引擎

### 5.1 查询模型选择

默认路径直接查询 `BlogPage` 具体模型的公开子页面，使用 `date` 和 `title` 字段排序，消除当前对 `BlogPage`、`BlogIndexPage` 的逐行日期子查询：

```python
BlogPage.objects.live().public().child_of(index_page)
```

若现网仍存在允许列出 `BlogIndexPage` 子节点的历史数据，必须先用观测查询确认数量；在兼容开关开启期间保留旧多态查询作为降级路径，并单独计数 `listing.compat_query`。确认没有历史混合节点后，才关闭兼容开关。不能未经数据盘点直接改变列表语义。

日期排序使用 `BlogPage.date`，稳定次序追加 `pk`；标题排序使用数据库可用的大小写归一表达式和 `pk`。搜索、日期范围和排序必须在分页前完成。深页和超长搜索需要限制最大页数或转入异步受控回源，不能让任意请求扫描无限结果。

### 5.2 Batch Prefetch Engine 契约

新增 `apps/blog/services/listing.py`（最终命名以代码现状复核为准）作为唯一装配入口，接受 `site_id`、`locale_id`、索引页和规范化参数，返回不可变的 `ListingPayload`。推荐的查询顺序如下：

| 步骤 | 查询 | 目标次数 | 说明 |
|---|---|---:|---|
| 1 | `COUNT` 或已缓存的 `total_results` | 0/1 | 只在 L1 未命中时执行；不得携带日期子查询 |
| 2 | 当前页 BlogPage + `select_related('featured_image')` | 1 | 仅取卡片字段，保留稳定排序 |
| 3 | 作者批量预取 | 1 | `Prefetch(..., to_attr='listing_authors')` |
| 4 | 标签及 through 关系批量预取 | 1 至 2 | 使用 `to_attr='listing_tags'`，模板不再访问 manager |
| 5 | 浏览量条件聚合 | 1 | `PageViewCount` 对 page_id 集合一次 `Sum`，条件聚合今日与总量 |
| 6 | 反应聚合 | 1 | `Reaction` 按 `page_id、reaction_type_id` 一次 `Count`；反应类型字典单独缓存 |
| 7 | 图片 rendition DTO | 0/1 | 使用固定 filter spec 批量预取已有 rendition；禁止在列表请求循环创建图片切片 |
| 8 | 列表页自身必需的公开元数据 | 0/1 | 只在未由 Wagtail 上下文提供时读取 `BlogTagIndexPage` |

冷缓存的业务查询预算为上述最多 9 次，加上 Wagtail 路由/站点解析最多 1 次，总计不超过 10 次。图片切片首次生成、数据库连接初始化、监控探针和未纳入列表渲染的中间件必须单独计量，不能把它们隐藏在预算之外；验收时同时报告业务 SQL 与总 SQL。

浏览量聚合必须保持现有新旧口径分离：`view_count_v2` 与 `count` 不得相加。反应结果要按所有 `ReactionType` 补齐 0 值，保持详情页和列表页的展示契约。

### 5.3 运行时属性与兼容兜底

批量装配后给当前请求中的 `BlogPage` 实例注入只读语义的运行时字段，例如：

```text
_listing_view_count
_listing_reactions
listing_authors
listing_tags
listing_image_url
```

现有 `BlogPage.get_view_count()` 和 `get_reactions()` 保留作为详情页及第三方模板的兼容入口：

- 属性存在时直接返回批量结果，不产生 SQL；
- 属性不存在时继续调用现有 `PageViewCounter` 或原聚合逻辑，保障详情页和非列表调用不被破坏；
- 运行时属性只附着于当前请求实例，不写回数据库、不放入 Redis、不跨请求复用；
- 任何缓存 DTO 反序列化都必须重新构造成普通字典或专用 dataclass，禁止反序列化任意 Python 对象。

推荐逐步让模板使用 `listing_*` 字段，稳定后再移除列表模板对 manager 的访问。这样即使某个旧模板仍调用 `get_view_count()`，也只会命中注入的批量值。

### 5.4 模板重入消除

`_blog_index_results.html` 必须接收已装配的 `cards` 或已注入字段的 BlogPage，不得在循环中访问：

- `post.specific`；
- `post.authors.all`、`post.tags.all`；
- `post.get_view_count` 两次；
- `post.get_reactions`；
- 未预取的 featured image rendition。

统计块改为一次绑定后的纯字段渲染，例如 `card.view_count.total`、`card.view_count.today`、`card.reactions`。模板标签只能格式化传入数据，不得包含 QuerySet、聚合、随机选择或 `reverse()` 循环。`with` 只用于避免同一字段重复解析，不作为数据加载机制。

### 5.5 数据库与索引验收

实施前后必须保存脱敏后的 `EXPLAIN` 结果，重点核验：

- Wagtail 页面树过滤命中 `path/depth` 相关索引；
- `BlogPage.date` 现有索引覆盖日期排序和范围过滤；
- `PageViewCount` 的 `(page_id, date)` 唯一约束支持今日聚合；
- `Reaction` 至少能按 `(page_id, reaction_type_id)` 过滤聚合；
- 标题 `icontains` 在 MySQL 8.4 上的执行计划和中文数据选择性不足时，先评估全文检索或搜索服务，不在本案无测量地添加索引。

任何索引迁移必须单独设计、生成并检查 migration，不得把性能文档中的建议直接当作生产迁移命令执行。

## 6. 侧边栏缓存与 DOM 瘦身

### 6.1 归档聚合缓存

归档数据拆成 Redis 聚合和模板片段两层：

```text
wblog:sidebar:v2:archive:aggregate:{site_id}:{locale_id}:{archive_generation}:{policy_version}
wblog:sidebar:v2:archive:fragment:{site_id}:{locale_id}:{archive_generation}:{current_year}:{current_month}:{policy_version}
wblog:sidebar:v2:archive:lock:{site_id}:{locale_id}:{archive_generation}:{policy_version}
```

聚合 payload 只包含年份、月份、数量和已生成的同源 URL，不包含 Page 对象。`archive_generation` 由公开 BlogPage 的发布、取消发布、发布日期变更和受控删除推进。聚合缓存默认 6 小时，片段默认 1 小时并带抖动；代次推进后旧 key 不再被读取，自然过期。

归档树策略：

1. 当前年份和过去两年展开月份，最多 36 个有数据月份；
2. 更早年份只输出年份、文章数和一个可访问的年份入口，不输出 12 个空月份节点；
3. 历史月份通过公开 GET 的按年异步接口加载，接口参数包含 `site_id/locale/year` 的服务端派生值，不能信任客户端传入站点；
4. 当前年份不是自然年而是数据最新年份时，以最新公开文章年份为准，避免新年无数据导致树折叠错误；
5. 链接在缓存构建阶段一次生成，模板不执行 216 次 `reverse()`。

在 18 年历史、每年 12 月份的基线下，初始 DOM 从约 216 个月份节点降至 36 个左右，加上年份摘要后，挂件 HTML 目标低于 18 KB，较基线至少减少 80%。异步历史请求也必须复用聚合缓存，不能把扫描从首屏转移成每次点击全表扫描。

### 6.2 随机作者缓存

移除 `order_by('?')`。候选集合按当前站点公开 BlogPage 的作者关系构建：

```text
wblog:sidebar:v2:author:candidates:{site_id}:{locale_id}:{generation}
wblog:sidebar:v2:author:pick:{site_id}:{locale_id}:{generation}:{time_bucket}
wblog:sidebar:v2:author:lock:{site_id}:{locale_id}:{generation}
```

候选集合默认缓存 30 分钟，选择结果按小时 bucket 缓存。Redis 可用时使用 `SRANDMEMBER` 或在应用层对已缓存 ID 做受控随机选择；Redis 不可用时使用 `generation + 当前小时` 的确定性 hash 选择，禁止回退到 `ORDER BY RAND()`。作者详情只读取一次，片段命中时不访问数据库。没有公开文章作者时返回空状态，不制造异常。

作者集合只在公开关系变更时失效。草稿中修改作者关系不应清除公开挂件，直到页面发布。

### 6.3 片段缓存的模板边界

模板片段 key 必须包含站点、语言、代次和展示策略版本。不得只使用 `request.LANGUAGE_CODE`，也不得把当前登录用户、CSRF token 或完整 request 放进缓存结果。推荐将缓存读写放在 inclusion tag 的服务层或视图上下文装配层，模板只负责输出 HTML。

侧边栏缓存失败时返回最小安全结构：归档为空树、作者为空，不阻断主列表。必须记录 `sidebar_cache.fail_open`，并在监控中区分“缓存空结果”和“查询异常”。

## 7. Wagtail 生命周期与精准失效

### 7.1 失效原则

列表缓存采用“推进代次而非枚举删除”的策略。发布事务成功提交后推进代次，后续请求使用新 key；旧 key 不会被新代次读取。这样避免搜索条件、分页页数和多站点缓存 key 的笛形枚举，也避免批量导入造成 Redis 删除风暴。

所有失效动作通过 `transaction.on_commit()` 执行。事务回滚时不得推进代次，否则会制造无效缓存 miss；缓存系统不可用时只记录日志和指标，不能回滚已成功提交的内容事务。

### 7.2 事件矩阵

| 事件 | 失效范围 | 时机 | 双存储要求 |
|---|---|---|---|
| BlogPage 首次发布/重新发布 | 所有包含该页的父级 `BlogIndexPage` generation、归档 generation、作者候选 generation、相关首页片段 | 发布事务 `on_commit` | 必须先沿用 `BlogPublicationService` 完成 Mongo 正文与 MySQL 发布指针契约 |
| BlogPage 取消发布 | 同上 | `page_unpublished` 后 `on_commit` | 先保证公开指针/墓碑状态，再让新列表隐藏文章 |
| 已发布页的日期、标题、作者、标签、图片变更 | 该页父级列表 + 归档/作者相关 generation | 仅在变更真正发布后 | 草稿保存不清公开缓存 |
| BlogIndexPage 发布/编辑 | 自身页面缓存和其列表 generation | 发布/编辑提交后 | 不触碰子文章正文 |
| 受控单页删除 | 删除前捕获站点、语言、父级列表和作者/日期范围；删除完成后推进 | `pre_delete` 记录范围，事务提交后执行 | 严禁绕过 `PageDeletionIntent`、Mongo 引用检查和墓碑流程 |
| 批量导入草稿 | 不失效公开列表 | 草稿批次完成 | 不得因为写入草稿而改变公开代次 |
| 批量导入并发布 | 先收集受影响的唯一 index/site/locale 集合，提交后每个 generation 只推进一次 | 批次事务 `on_commit` | 不循环删除所有分页 key |
| Author/Tag 独立公开关系变更 | 受影响作者集合、相关列表 generation | 公开关系确认后 | 不清理正文缓存 |
| 失效事件丢失 | 由定时 reconciler 对发布状态和 generation 做核对 | 只做观测和补偿 | 补偿工具必须 dry-run 默认、禁止批量删数据 |

现有 `wagtail.signals.page_published/page_unpublished`、`apps/blog/signals.py` 的 Feed 和详情缓存失效必须继续执行；列表失效是并行副作用，不能替换或吞掉既有信号。删除场景必须结合现有 `before_delete_page`/`pre_delete` 保护逻辑，因为 Wagtail 删除并不等价于普通取消发布。

### 7.3 失效服务接口

建议提供窄接口 `ListingInvalidationService`：

```text
schedule_page_publication(page, event) -> None
schedule_index_refresh(index_page, reason) -> None
schedule_bulk_refresh(scopes) -> None
capture_delete_scope(page) -> DeleteScope
get_generation(site_id, locale_id, index_page_id) -> str
bump_generation(scope, reason) -> str
```

接口只接受页面 ID、站点/语言和事件原因等最小信息；不接受正文对象和 Mongo 内容。实现必须幂等，同一事务重复收到发布信号不能造成业务错误。日志只输出 ID、事件、代次和耗时，禁止输出正文、Token、密码或私钥。

## 8. 前端渐进渲染与资源瘦身

### 8.1 解除视觉锁

`base.html` 删除全屏 `.preloader` 节点及其阻断样式。`script.js` 删除依赖 `window.load` 和 1500 ms 硬超时的遮罩处理；页面行为初始化改为 `DOMContentLoaded` 或脚本自身 `defer` 后执行。任何网络请求、图片加载或第三方资源失败都不得重新创建全屏遮罩。

主文档结构按以下顺序输出：

```text
首屏语义 HTML（标题、筛选器、前两张卡片）
首屏必要样式
列表其余卡片和侧边栏
defer 脚本与渐进增强
```

服务端响应未必能在所有 WSGI/反向代理组合下逐块 flush，因此验收重点是“HTML 到达后可立即绘制且无遮罩”，不能把网络分块当作唯一性能承诺。图片保留尺寸属性、`decoding="async"`，首张图片可 `fetchpriority="high"`，其余使用 `loading="lazy"`。

### 8.2 CSS/JS 关键路径

当前 `blog_index_page.html` 重复加载两次 `blog-index.css`，必须保留单一声明。资源治理采用渐进方式：

1. 先删除重复 CSS 和列表页不使用的页面级资源；
2. 核心 CSS 维持稳定加载顺序，避免在没有构建流水线时盲目合并造成全站回归；
3. 不依赖 jQuery 的脚本加 `defer`，依赖链按 `jquery -> bootstrap -> 业务脚本` 保持顺序；
4. 列表异步控制器、归档展开和非首屏动画使用 `defer`，不在 head 同步执行；
5. 以浏览器覆盖率和资源计时为依据，再决定是否建立页面级 bundle；
6. 每个资源保留可回滚的版本查询参数，不能把静态资源清单和缓存 key 版本混用。

目标不是单纯减少文件数量，而是使首屏渲染阻塞资源不超过 1 个页面级 CSS，脚本均不阻塞 HTML 解析，列表页不再重复请求同一个 CSS。

### 8.3 交互与降级

无 JavaScript 时，现有 GET 表单和分页链接必须继续可用；JavaScript 只负责拦截后使用 `blog_index_results_api` 替换列表片段、更新历史记录和焦点。API 失败时恢复普通链接导航，不显示覆盖页面的错误遮罩。

归档历史异步加载失败时保留年份链接；随机作者失败时隐藏该挂件；两个侧栏均不能影响主列表首屏。

如需数据库索引或 generation 持久化字段，必须另开迁移设计，先执行 `makemigrations --check --dry-run` 和 `migrate --plan` 检查；本案默认优先使用已有 `BlogPublicationState.publication_generation` 和 Redis scope generation，避免不必要 schema 变更。

### 9.2 统一上下文接口

HTML 页面和异步 API 必须共同调用一个服务接口：

```text
build_listing(request, index_page, query_params, *, output_format) -> ListingResult
```

`ListingResult` 包含：

- `payload`：可序列化列表 DTO；
- `html`：服务端片段（需要时渲染）；
- `filters`、`pagination`、`canonical_url`：与现有 API 兼容的字段；
- `cache_status`：命中、未命中、stale、旁路；
- `query_count` 和 `assembly_ms`：仅进入内部观测，不直接暴露敏感信息。

视图层负责 HTTP 状态、ETag、Cache-Control 和错误格式；服务层不直接读取模板 request，也不将模板渲染异常吞成成功响应。模板渲染错误应删除当前 generation 下的 L2 片段并 Fail-Open 回源一次，仍失败则返回现有错误处理。

### 9.3 类型和注释要求

新增 Python 服务必须使用 Python 类型标注、中文 docstring 和精准的业务边界注释。注释重点说明：为什么缓存只允许公开页面、为什么在 `on_commit` 后推进代次、为什么锁释放需要 token 校验、为什么 Mongo 正文不在列表 DTO 中。不得输出显而易见的逐行注释，也不得在文档、日志和测试夹具中写入真实凭据。

## 10. 失败降级与可回滚设计

### 10.1 功能开关

至少提供以下独立开关，默认值由 WSL2 验收后再决定：

```text
BLOG_INDEX_LISTING_ENGINE_V2
BLOG_INDEX_CACHE_V2
BLOG_SIDEBAR_CACHE_V2
BLOG_ARCHIVE_PROGRESSIVE_V2
BLOG_INDEX_COMPAT_POLYMORPHIC_QUERY
BLOG_INDEX_ETAG_V2
```

开关必须能按进程配置并在不改数据的情况下关闭。缓存 schema 版本和代码版本分离，回滚旧代码时旧代码不会读取 v2 key，也不会误读 v2 DTO。

### 10.2 故障处理矩阵

| 故障 | 处理 | 禁止行为 |
|---|---|---|
| Redis 不可用 | 旁路到批量 SQL，启用每 worker 并发上限并记录 fail-open | 不得 500、无限重试或清空全库缓存 |
| L1/L2 载荷损坏 | 删除当前精确 key，回源重建；失败返回数据库结果 | 不得反序列化任意对象 |
| Mutex 超时 | stale 优先；无 stale 时单次受控回源 | 不得死等或批量删 key |
| 失效事件失败 | 内容事务成功保留，写入补偿日志，由 reconciler 重试 | 不得回滚 Mongo/MySQL 正文或直接修库 |
| 批量导入中途失败 | 保持现有导入服务的 draft compensation 和幂等语义 | 不得以缓存失效代替正文补偿 |
| 新装配器结果异常 | 关闭 `BLOG_INDEX_LISTING_ENGINE_V2`，恢复现有查询 | 不得修改受保护正文数据 |
| 前端 JS 失败 | 普通 GET 表单、分页和侧栏静态链接仍可用 | 不得重新启用全屏遮罩 |

### 10.3 回滚步骤

1. 记录当前 generation、缓存命中率、查询数和错误率；
2. 先关闭 `BLOG_INDEX_CACHE_V2` 或 `BLOG_INDEX_LISTING_ENGINE_V2`，确认流量回到兼容路径；
3. 如只有侧栏异常，单独关闭 `BLOG_SIDEBAR_CACHE_V2`，保留列表优化；
4. 如前端资源回归，回滚静态资源版本并保留后端缓存开关；
5. 旧缓存键不需要物理删除，待 TTL 自然过期；
6. 生产回滚不得执行数据 flush、drop、批量删除或未授权迁移。

## 12. 实施顺序与发布门禁

### 阶段 A：基线和契约测试

先固定查询计数、HTML 体积、模板快照、API JSON 兼容性和发布生命周期测试。没有基线证据不得宣称“已压缩到 10 次”。

### 阶段 B：批量装配和模板减负

实现列表服务、DTO、`select_related/prefetch_related`、统计和反应聚合；接入运行时兼容字段；修改模板并在关闭缓存的情况下验证 SQL ≤ 10。此阶段不改变前端遮罩和公开缓存，便于隔离问题。

### 阶段 C：Redis 列表缓存和精准失效

接入规范化 key、generation、Mutex、stale、ETag 和生命周期服务。先灰度单个站点/语言，观察命中率、回源量、generation 推进和缓存陈旧率。

### 阶段 D：侧栏和前端去锁

接入归档/作者片段缓存、三年展开策略、历史异步接口；删除 preloader、去重 CSS、调整 defer，并执行 Playwright 双端验证。

### 阶段 E：Maker-Checker 发布

1. Sol 核对代码 diff、缓存 key、双存储影响、回滚开关和测试证据；
2. Gemini 在 WSL2 执行定向测试、`manage.py check`、CSS token 检查和浏览器验证；
3. Grok 复核并发锁、失效竞态、权限缓存、删除与批量导入边界；
4. 对话人确认发布窗口和回滚条件；
5. 生产只按批准的单步清单执行，发布后先观察，再决定是否扩大流量；
6. 未经用户明确授权，不执行 Git commit、push、生产迁移或服务重启。

## 13. 风险清单

| 风险 | 触发条件 | 预防/补偿 |
|---|---|---|
| 代次失效竞态 | 数据事务提交与缓存更新存在时间窗口 | 只在 `on_commit` 推进 generation，旧值最多存活一个 TTL；关键发布指标告警 |
| 删除后无法取得父级 | 删除完成后页面树关系已不存在 | `pre_delete` 或现有受控删除清单提前捕获 scope |
| 站点/语言串缓存 | key 只用 page_id 或语言名称 | key 强制 site_id、locale_id，并写测试做隔离验证 |
| 锁误删 | 租约过期后旧请求删除新锁 | token compare-and-delete |
| 统计陈旧 | 列表 DTO 缓存包含浏览量 | 对统计设短 TTL，或按浏览统计写入推进独立 stats generation；详情页继续实时读取 |
| 权限泄露 | `public()`、页面限制或预览请求漏判 | 缓存前固定执行 live/public/preview 门禁；受限请求一律 bypass |
| 历史混合页面语义变化 | BlogIndexPage 子节点仍被列出 | 兼容开关、数据盘点和单独指标，确认后再切换具体模型查询 |
| 图片 rendition 回源 | 缓存 miss 时每张图片创建切片 | 固定 filter spec、批量预取已有 rendition、预热任务和缺图降级 |
| 失效事件遗漏 | 非标准脚本直接更新公开字段 | 规范所有公开变更入口，增加 reconciler 和事件审计 |

## 14. 最终架构判断

本案应以“**公开列表 DTO 批量装配 + Redis 代次缓存 + Wagtail 发布后精准失效 + 原生渐进渲染**”作为主线。仅给模板加 `{% cache %}` 无法解决 N+1 和失效竞态；仅给数据库加索引也无法消除归档 DOM 与 preloader 白屏；仅把 `ORDER BY RAND()` 换成 Python 随机而不缓存候选集合，也只是把慢查询换成高频查询。

实施完成的判定标准不是某一次请求变快，而是：查询数量有硬预算、缓存 key 可解释、发布/下线/删除可追踪、正文双存储不被触碰、Redis 故障可降级、前端无视觉锁、所有改动可通过开关回滚。只有同时满足这些条件，分类与列表页优化才具备生产级可交付性。

   - 显式增加 `.defer('body')`，SQL 输出彻底排除 `body` 列，内存反序列化和数据传输开销完全归零。
2. **侧栏多站点/多语言/Public 访问限制严格隔离**：

3. **消除热缓存路径上的隐蔽 SQL**：
   - 直接从已加载的内存对象属性读取 `site_id` 与 `locale_id`，Redis 代次查询直通缓存，热缓存命中 SQL 严格保持为 **0 次**。

### 16.2 核心解答：“为什么严禁全局 cache.clear() 与代次模式的优越性”

1. **为什么严禁全局 cache.clear()**：
   - 在 Django/Redis 架构中，`cache.clear()` 默认清空整个当前 Redis 数据库（例如 DB 1）；
   - 生产环境中，Redis 不仅存放列表页缓存，还存放首页片段、详情页、侧边栏、后台任务协调凭据，甚至在某些配置下与 Session 共享连接；
   - 一旦在发布文章时调用全局清空，全站所有页面（包括并发访问的数千个请求）同时穿透回源到 MySQL、MongoDB 和 Elasticsearch，引发剧烈的缓存雪崩（Cache Avalanche）、数据库连接池耗尽与 CPU 尖刺；
   - 更严重的是，清空整个 DB 会使 Redis 在单线程上产生阻塞（Stop-the-World），造成前台高首字延迟（TTFT）。
2. **代次（Generation）模式的秒级零停顿优雅失效**：
   - 每一个分类列表页拥有一个独立整数代次控制键：`wblog:list:v2:generation:{site_id}:{locale_id}:{index_page_id}`；
   - 列表页缓存键天然包含代次信息：`wblog:list:v2:payload:{site_id}:{locale_id}:{index_id}:g{gen}:q{hash}`；
   - 当发布、下线或删除文章时，服务**只执行一次 Redis 原子的 `INCR` 指令**，将代次从 1 推进到 2；
   - 下一次读请求读取到当前代次为 2，便直接请求带有 `g2` 的缓存；旧的带有 `g1` 的成百上千个分页缓存自然失配（Miss）并在后台重新生成；旧代次数据由 Redis 根据 TTL 自动惰性逐出；
   - **零 `KEYS`/`SCAN` 遍历、零批量 `DELETE`、零加锁等待，O(1) 耗时（< 1ms）**。

### 16.3 节点 4 实现架构与安全防线

- **服务核心**：`wagtailblog3/apps/blog/services/listing_invalidation.py` (`ListingInvalidationService`)；
- **事务绑定**：所有代次推进严格绑定在 Django `transaction.on_commit()` 回调中触发，事务回滚时绝对不推进代次，保证数据库与缓存最终一致；
- **单事务去重**：利用线程局部状态 `_local_tx_state`，同一个数据库事务内多次触发的发布/修改事件自动去重，提交时每个受影响 scope 仅执行一次 `INCR`；
- **删除快照捕获**：在 `pre_delete` 阶段调用 `capture_delete_scope(page)` 捕获祖先 `BlogIndexPage` 和侧栏作用域快照，即使页面随后被从树形结构中彻底物理删除，快照依然能确保对应分类与归档代次精准失效；
- **全链路 Fail-Open**：Redis 发生任何网络超时或连接中断时，`get_generation` 安全返回 1，`bump_generation` 记录警告并平稳回退，前台读写业务绝对不抛 500 错误。
