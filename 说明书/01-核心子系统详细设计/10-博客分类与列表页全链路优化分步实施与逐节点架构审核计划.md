# 博客分类与列表页全链路优化·分步实施与逐节点架构审核计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Each milestone stops for Sol architecture review before the next milestone starts.

**Goal:** 在不触碰 BlogPage 正文、Mongo 正文、Revision 快照和发布指针的前提下，将默认 20 篇博客分类/列表页的冷缓存业务 SQL 从 182 次压缩到不超过 10 次，将侧边栏初始 HTML 从 91.2 KB 压缩到 18 KB 以下，并消除人为 Preloader 白屏。

**Architecture:** 以 `ListingService` 统一规范化参数、批量查询、DTO 装配和列表缓存；以 `ListingInvalidationService` 通过 Wagtail 生命周期在事务提交后推进 scope generation；侧边栏使用独立的归档聚合/作者候选缓存。HTML 与 JSON 继续共享同一服务入口，前端保留无 JavaScript 的 GET 降级路径。

**Tech Stack:** Python 3.13、Django 5.2.8、Wagtail 8.0、MySQL 8.4、Redis 5.2、Django templates、现有 jQuery/Bootstrap、WSL2 `wagtailblog-test` 环境。

**Spec:** `说明书/01-核心子系统详细设计/09-博客分类与列表页全链路性能优化设计说明书.md`

```python
    request: HttpRequest,
    index_page: BlogIndexPage,
    query_params: Mapping[str, object],
    *,
    output_format: Literal["context", "json"],
) -> ListingResult: ...
```

`ListingResult` 必须提供 `payload`、`html`、`filters`、`pagination`、`canonical_url`、`cache_status`、`query_count` 和 `assembly_ms`；内部 DTO 只能含标题、URL、日期、摘要、作者公开字段、标签公开字段、图片 URL/尺寸、V2/legacy 分离的统计值和完整反应类型 0 值。`body`、Mongo 文档、Revision、用户反应身份、session/IP 均禁止出现。

### 批量查询顺序与预算

1. `COUNT` 或受信任的 `total_results` 缓存最多 1 次。
2. 当前页 `BlogPage` 卡片字段 1 次，使用 `select_related("featured_image")`，默认路径明确使用 `live().public().child_of(index_page)`。
3. 作者批量预取 1 次，目标属性 `listing_authors`。
4. 标签及 through 关系批量预取 1 至 2 次，目标属性 `listing_tags`。
5. `PageViewCount` 按 page id 集合一次条件聚合，同时保持 `view_count_v2` 与旧 `count` 不相加。
6. `Reaction` 按 `page_id/reaction_type_id` 一次 `Count`，`ReactionType` 字典缓存或一次读取并补齐零值。
7. 固定 rendition spec 批量读取已有 rendition，严禁循环创建图片切片。
8. 仅在 Wagtail 上下文没有时读取一次 `BlogTagIndexPage`。

冷缓存业务 SQL 不超过 9 次，含 Wagtail 路由/站点解析的总 SQL 不超过 10 次；同一请求的 Redis 热缓存业务 SQL 不超过 2 次。测试报告必须分开记录业务 SQL、Wagtail/中间件 SQL、缓存命中状态和 assembly time。

### 固定服务接口

```python
@dataclass(frozen=True, slots=True)
class ListingScope:
    site_id: int
    locale_id: int
    index_page_id: int

@dataclass(frozen=True, slots=True)
class DeleteScope:
    scopes: tuple[ListingScope, ...]
    archive_scopes: tuple[tuple[int, int], ...]
    author_scopes: tuple[tuple[int, int], ...]

class ListingInvalidationService:
    @classmethod
    def schedule_page_publication(cls, page: BlogPage, event: str) -> None: ...
    @classmethod
    def schedule_index_refresh(cls, index_page: BlogIndexPage, reason: str) -> None: ...
    @classmethod
    def schedule_bulk_refresh(cls, scopes: Iterable[ListingScope]) -> None: ...
    @classmethod
    def capture_delete_scope(cls, page: BlogPage) -> DeleteScope: ...
    @classmethod
    def get_generation(cls, site_id: int, locale_id: int, index_page_id: int) -> str: ...
    @classmethod
    def bump_generation(cls, scope: ListingScope, reason: str) -> str: ...
```

generation key 使用 `wblog:list:v2:generation:{site_id}:{locale_id}:{index_page_id}`；首次用 `add(key, "0", timeout=None)`，推进使用 Redis 原子 `INCR`，返回字符串代次，禁止 `get()+set()` 丢更新。归档/作者使用其对应 scope generation。所有推进封装在 `transaction.on_commit()`；事务回滚不得推进。缓存不可用只记录 `blog_listing.invalidation` 和补偿日志，不回滚已经提交的 MySQL/Mongo 事务。

### 事件矩阵与验收

- BlogPage 发布/取消发布：父级列表、归档、作者候选各自 scope 只推进一次。
- 已发布文章日期、标题、作者、标签、图片变更：只在真正发布后失效；草稿保存不改变公开代次。
- BlogIndexPage 发布/编辑：只推进自身列表 scope，不触碰子文章正文。
- 受控单页/批量删除：删除前捕获 scope，提交后推进；继续走 `PageDeletionIntent`、Mongo 引用检查和墓碑流程。
- 批量导入草稿：不失效；批量发布先收集唯一 scope，提交后每个 scope 只自增一次。
- Author/Tag 公开关系变更：只失效受影响公开列表/作者候选，不清正文缓存。

必须有测试证明：同一事务重复信号幂等；并发自增无回退/覆盖；回滚后 generation 未变化；删除后仍能取得原父级 scope；源码与测试中不存在针对本功能的 `cache.clear()`、`flushdb` 或循环删除所有分页 key。
