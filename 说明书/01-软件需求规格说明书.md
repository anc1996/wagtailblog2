# 博客系统 - 软件需求规格说明书 (SRS)

## **版本: 2.0 **日期: 2025-06-13

## 1. 引言 (Introduction)

### 1.1 目的 (Purpose)

本软件需求规格说明书旨在全面定义 "WagtailBlog3" 经过底层架构深度重构后的功能与非功能性需求。本文档的目标读者包括架构师、软件开发工程师、测试工程师以及高级运维人员。它将作为项目开发、复杂架构验证、性能调优和生产级部署的基础，确保所有相关方对系统的异构运行机制有统一、精准的理解。

### 1.2 项目范围 (Scope)

本项目旨在创建一个功能丰富、极致性能、彻底解耦的现代化博客平台。系统核心基于 `Wagtail CMS (v7.1)` 和 `Django (v5.1)` 框架，并引入了企业级的分布式组件。

其主要架构与功能范畴包括：

- **异构数据存储与分离**: 采用 MySQL + MongoDB 读写分离架构，MySQL 仅维护轻量级页面骨架，大文本负载精准下推至 MongoDB。
- **混合检索与降维排序**: 摒弃单一搜索逻辑，采用 Elasticsearch 8 (ES8) 与 MySQL 双轨制引擎，支持 L1 召回与 L2 内存精排。
- **内容创作与无感重塑**: 支持多格式内容混合编排，底层通过适配器在 JSON 与 React/Draftail 渲染树（AST）之间进行跨库透明还原（Hydration）。
- **高性能数据注射**: 彻底消灭 N+1 查库瓶颈，基于单次 `$in` 批处理实现 O(1) 复杂度的无感数据注射与零 I/O 摘要提取。
- **生产级后台托管**: 全面弃用易碎的 Shell 脚本，改用 Linux 原生 `Systemd` 服务进行严格的进程隔离与环境变量守护。

### **1.3 定义、首字母缩写和缩略语 (Definitions, Acronyms, and Abbreviations)**

- **Wagtail/Django**: 系统的核心 Web 与 CMS 框架。
- **StreamField**: Wagtail核心特性，允许在页面中自由组合不同类型的内容块。
- **ES8 (Elasticsearch 8)**: 承担全文检索与 L1 召回的分布式搜索引擎。
- **MongoDB**: 面向文档的 NoSQL 数据库，本项目中专门用于承载 `body` 大文本负载与历史快照。
- **O(1) 注射**: 列表页渲染时，将关联数据的查询复杂度从 O(N) 降至 O(1) 的批处理技术。
- **惰性截流 (LazyChainedResultList)**: 针对深度分页和多态查询导致的 OOM（内存溢出）问题，采用的生成器级别延迟求值技术。
- **Systemd**: Linux 系统下的系统与服务管理器，用于配置和守护后台 uWSGI 进程。
- **AST (Abstract Syntax Tree)**: 抽象语法树，此处指前端富文本编辑器所需的严格数据结构。

## **2. 整体描述 (Overall Description)**

### **2.1 产品定位 (Product Perspective)**

本系统是一个具备生产级吞吐能力的高度定制化博客平台。它打破了传统 CMS 强依赖单一关系型数据库的局限，转型为**异构降维架构**。

- **技术栈核心**: Python, Django, Wagtail
- **数据库读写分离架构**:
  - **结构化骨架存储**: MySQL (`mysqlclient`)，仅存储 `Page` 模型的路由、元数据与轻量级字段。
  - **非结构化大文本存储**: MongoDB (`pymongo`)，负责承载庞大的 `StreamField` 数据 (`body`) 与历史版本快照，保持主表绝对轻量。
- **双轨制搜索引擎**: Elasticsearch 8 (主导全文检索) 协同 MySQL (主导无搜索词下的原生聚合排序)。
- **进程托管与生命周期**: Linux 原生 Systemd (接管 uWSGI，彻底替代 Crontab/Shell 脚本)。
- **后台任务与存储**: Celery (`celery`)，Redis (`django-redis`)，MinIO 对象存储。

### **2.2 产品功能模块 (Product Functions)**

- **`apps.blog`**: 异构模型中枢。接管了原生的页面保存与序列化钩子，将文本负载跨库路由至 MongoDB；实现了高性能的 O(1) 数据挂载机制。
- **`apps.search`**: 混合搜索大脑。封装了 ES8 召回、长短句内存精排、缓存命中机制及惰性分页逻辑。
- **系统运维与守护**: 通过独立配置的 `.service` 文件，严格管理环境变量注入、优雅启停与多项目隔离。

### **2.3 约束与部署规范 (Constraints & Deployment)**

- **进程托管绝对约束**: **严禁**使用 `start.sh` 或 `crontab (@reboot)` 启动项目。必须通过 `/etc/systemd/system/wagtailblog3.service` 前台接管 uWSGI。
- **环境变量隔离**: Systemd 必须硬编码注入网络代理（http_proxy/no_proxy）以及 Conda、MongoDB、Go 的绝对运行路径（PATH），防止环境漂移。
- **启停策略防雪崩**: Systemd 的 `Restart` 策略必须合理配置（如取消无条件的 `always` 避免报错死循环），采用 `KillSignal=SIGQUIT` 保证平滑退出。

## **3. 具体需求 (Specific Requirements)**

### **3.1 功能需求 (Functional Requirements)**

#### **FR-1: 异构解耦的内容管理**

- **FR-1.1: 零包袱存储拦截**:
  - 当内容创作者在后台点击保存或发布 (`blog.BlogPage`) 时，系统必须在视图层/表单层下方拦截动作。
  - 将大文本 (`body`) 抽离存入 MongoDB (`mongo_content_id`)，并在 MySQL 中将 `body` 字段置空（`[]`），维持 MySQL `blog_blogpage` 表的绝对轻量。
- **FR-1.2: 历史快照穿透与 AST 重塑**:
  - 系统保存草稿或生成历史记录时，快照负载必须送入 MongoDB 的专门草稿集合，并在 MySQL 的 Revision 表中刻录 OID 暗号 (`mongo_draft_pointer`)。
  - 后台编辑或预览时，必须通过 `MongoDBStreamFieldAdapter` 执行 Hydration 操作，将 MongoDB 中松散的字典对象重塑为带有 UUID 的严格 React/Draftail AST 渲染树。
- **FR-1.3: 统一视图排序下推 (Coalesce 降维)**:
  - 在异构子页面（如 `BlogPage`, `BlogIndexPage` 等）混合展示时，通过 MySQL 底层的 `Subquery` 与 `Coalesce` 注解统一生成 `sort_date` 虚拟字段。
  - 将排序逻辑从内存循环下推至数据库执行层，从根本上解决 Wagtail 多态查询时的 `FieldError`。

#### **FR-2: 混合检索架构 (FR-Search)**

- **FR-2.1: 双轨制查询路由**:
  - **无搜索词状态**: 搜索模块绕过 ES8，直接走 MySQL 原生聚合注解进行时间排序，确保日常列表浏览的极低延迟。
  - **有搜索词状态**: 严格下推给 ES8 引擎进行全文检索（权重覆盖 title, intro, 以及从 MongoDB 提取重组的纯文本 get_full_text_for_search）。
- **FR-2.2: L1+L2 缓存与精排**:
  - **L1 召回**: 利用 ES8 完成基础数据召回。
  - **L2 精排**: 在内存中针对返回的文档块进行长短句精确排序与权重修正。
- **FR-2.3: 惰性截流分页 (Lazy Loading)**:
  - 无论走 MySQL 还是 ES8，结果集必须封装为 `LazyChainedResultList`，并在视图 (`search_ajax`) 中利用生成器进行分页求值，彻底解决深度分页击穿和 OOM 内存溢出问题。

#### **FR-3: 用户互动与基础建设**

- 维持原有的评论树、反应系统 (Reactions) 和页面浏览量统计。
- 维持基础的 Wagtail 多媒体管理（StreamField 媒体块支持），但其纯文本数据必须能在存入 MongoDB 前被正确序列化，在提取时反序列化为 Wagtail 块对象。

### **3.2 非功能性需求 (Non-Functional Requirements)**

#### **NFR-1: 极限性能要求 (Performance)**

- **NFR-1.1: O(1) 复杂度防雪崩注射**:
  - 针对博客列表页，严禁使用 N+1 方式逐条向 MongoDB 请求内容。
  - 系统必须对当页截断后的 Top N 数据预提取 Mongo ID，单次跨库发起 `$in` 批量查询。
  - 获取的数据块必须动态挂载到内存 (`prefetched_mongo_data`) 中。
- **NFR-1.2: 零 I/O 摘要提取**:
  - 前端模板必须调用优化的 `get_list_preview_text()` 方法，直接从上述 O(1) 挂载的内存字典中截取摘要，实现列表页渲染阶段对 MongoDB 的零查库调用。

#### **NFR-2: 安全与隔离 (Security & Isolation)**

- **NFR-2.1: 进程强隔离**:
  - 多项目共存时，必须依托 Systemd 的 `.service` 配置文件建立独立的 socket 与工作目录，确保 A 项目崩溃或重启绝不波及 B 项目。
- **NFR-2.2: AST 语法树安全防线**:
  - 从 MongoDB 读取非结构化数据重建 Wagtail StreamValue 时，必须建立严格的空值判定（不仅仅 `bool()` 校验，需引入 `__len__` 校验）和 UUID 补齐防线，防止残缺数据导致前端 React 渲染引擎崩溃。

#### **NFR-3: 可靠性与可维护性 (Reliability & Maintainability)**

- **NFR-3.1: 分布式级联清理**:
  - 管理员在后台执行“物理删除”页面操作时，必须触发信号或重写 `delete()` 网关，级联清除 MySQL 主记录、MongoDB 中的线上正式版主内容以及所有的历史草稿快照。
- **NFR-3.2: 守护进程标准化**:
  - `uwsgi.ini` 中必须剔除 `daemonize` 参数，由 Systemd 的 `StandardError=syslog` 统一接管标准输出与错误日志。运维人员使用 `journalctl` 进行标准化排错。

- **NFR-3.3: 日志与监控体系 (Systemd 原生化)**:
  - **应用级日志**: 彻底摒弃分散在项目各处的 `.log` 文件输出（去除了 `uwsgi.ini` 中的 `daemonize=logs/uwsgi.log`）。所有 uWSGI 的标准输出（stdout）和标准错误（stderr）全部重定向至系统的 `syslog`。
  - **运维排错**: 运维人员必须统一使用 Linux 原生命令 `journalctl -u wagtailblog3.service -f` 进行实时日志流聚合与监控。
  - **业务级日志**: 针对特定业务（如 Elasticsearch 同步、Celery 异步发送邮件），保留在 `logging_config.py` 中的独立轮转日志（Rotating File Handler），并提供后台管理命令 (`clean_logs`, `view_logs`) 辅助查看。
- **NFR-3.4: 可用性**: 系统核心架构解耦后，单节点故障（如 ES8 宕机）不应导致系统整体崩溃，搜索模块应能平滑降级或提示，保证基础访问达到 99.9% 的正常运行时间。
- **NFR-3.5: 错误处理与降级防线**:
  - 系统必须在 `StreamField` 反序列化（Hydration）过程中建立异常捕获防线。若 MongoDB 数据结构损坏，必须使用 `is_lazy=True` 安全返回空列表或按字符串降级显示，绝不允许引发 500 内部服务器错误。

#### **NFR-4: 可维护性与扩展性 (Maintainability & Scalability)**

- **NFR-4.1: 异构解耦与适配器模式**:
  - 项目代码必须严格遵循高内聚、低耦合原则。关系型数据库（MySQL）与非关系型数据库（MongoDB）之间，必须通过 `MongoDBStreamFieldAdapter` 进行边界隔离，业务逻辑层绝不可直接干预底层 JSON 转换机制。
- **NFR-4.2: AST 渲染安全审查**:
  - `_hydrate_streamfield_from_mongo` 函数必须对历史遗留脏数据具备自愈能力（如自动补齐缺失的 `id` / UUID），确保前端 Draftail / React 渲染器接收到的是结构严谨的 AST 抽象语法树。
- **NFR-4.3: 多环境配置降维**:
  - 配置文件严格分为 `base.py`, `dev.py`, `production.py`。生产环境中，由于使用了 Systemd 托管，不再依赖 Shell 环境变量穿透，部分关键路径（如 Conda/Go 路径）支持直接在 Systemd 的 `.service` 中以 `Environment=` 形式硬编码注入。

### **3.3 外部接口需求 (External Interface Requirements)**

#### **EI-1: RESTful API 与惰性加载接口**

- **EI-1.1: 惰性分页检索接口 (Search AJAX API)**:
  - **接口定义**: 系统不再仅依赖传统的全量 HTML 页面渲染，针对深度检索，提供 `/search_ajax/` 端点。
  - **数据结构**: 该接口必须结合内部的 `LazyChainedResultList` 生成器，按需返回 JSON 格式的分页数据（包含 `results`, `has_next`, `total_pages` 等元数据）。
  - **前端协同**: 前端 JS 监听滚动或点击事件，发起 XMLHttpRequest，实现列表的无刷新惰性加载。
- **EI-1.2: 内部 API 文档**:
  - 系统继续利用 `drf-yasg` 提供 Swagger UI 界面，用于展示和测试所有公开的 RESTful API 接口（如评论提交、反应点赞等）。
- **EI-1.3: 搜索词补全建议 (Search Suggestions)**:
  - 提供轻量级的 JSON 接口 (`search_suggestions`)，根据用户在搜索框中的实时输入 (`q=xxx`)，调用 ES8 或 MySQL 进行分词前缀匹配，返回搜索建议列表。
