# 博客系统 - 概要设计说明书 (HLD)

**版本: 2.0 (架构重构版)**

**日期: 2025-06-13**

## **1. 引言 (Introduction)**

### **1.1 目的 (Purpose)**

本概要设计说明书旨在为重构后的“WagtailBlog3 博客系统”提供高层次的架构与技术设计方案。本文档重点描述系统在引入**混合检索引擎**、**异构存储读写分离**以及**生产级 Systemd 进程托管**后的整体架构、模块间通信机制和关键数据流转路径，作为详细设计和核心代码维护的指导性文件。

### **1.2 范围 (Scope)**

本文档涵盖了系统底层的异构解耦架构方案。重点定义了关系型数据库（MySQL）与非关系型数据库（MongoDB）的职责边界，界定了 Elasticsearch 8 (ES8) 与 MySQL 底层查询注解在双轨制搜索中的协同机制，并规范了服务在 Linux 生产环境下的进程管理拓扑。

## **2. 整体架构 (System Architecture)**

### **2.1 架构风格：异构解耦的单体架构 (Heterogeneous Decoupled Monolith)**

系统在业务逻辑层保持了成熟的 Django/Wagtail 单体架构以维持极高的开发效率，但在**数据持久层**与**检索层**实现了彻底的异构解耦。

- **骨架与负载分离**: 剥离了传统 CMS 单一数据库的负担。结构化路由与轻量级元数据由 MySQL 承载，而大体积的富文本渲染树（AST）负载被精准下推至 MongoDB。
- **双轨制检索引擎**: 打破了对单一搜索引擎的依赖，根据用户检索意图在 ES8 分布式集群与 MySQL 原生聚合引擎之间进行动态路由。
- **惰性求值与防雪崩加载**: 在视图与模板之间建立缓冲层，通过生成器（Generator）与批处理注射技术，消除深分页导致的 OOM 及 N+1 查库风暴。

### **2.2 物理部署拓扑 (Deployment Topology)**

整个系统的物理与进程拓扑如下：

- **反向代理与静态资源层**: Nginx 负责处理 HTTPS 终结、静态文件（CSS/JS）及媒体缓存，动态请求通过 Unix Socket 转发至 uWSGI。
- **进程托管层 (核心变更)**: **严禁使用 Shell/Crontab**。由 Linux 原生 `Systemd` (`wagtailblog3.service`) 前台接管 uWSGI。Systemd 负责注入严格隔离的执行环境（Conda PATH、Proxy 代理）并监听 `SIGQUIT` 信号以实现平滑重启。
- **Web 应用层**: Django 5.1 + Wagtail 7.1，承载核心业务中枢。
- **异构数据层**:
  - 主存储 (MySQL): 存储 User, Page 路由树, 评论, 反应点赞等高频关联数据。
  - 负载存储 (MongoDB): 运行独立的 `$in` 批处理查询，存储 `body` 字典与历史版本草稿。
  - 全文检索 (Elasticsearch 8): 承担倒排索引与高亮分词。
  - 缓存队列 (Redis + Celery): 承担页面片段 L2 缓存与异步任务调度。

## **3. 核心子系统设计 (Core Subsystems Design)**

### **3.1 异构存储与数据重塑子系统 (Heterogeneous Storage & Hydration)**

该子系统是本次重构的核心，负责打通 MySQL 与 MongoDB 的边界。

- **无感截流网关 (Serialization Interceptor)**:
  - 拦截 Wagtail 默认的 `serializable_data` 和 `save` 钩子。
  - 将编辑器产出的松散大文本抽离，调用 `MongoManager` 写入 MongoDB `blog_content` 集合（或草稿集合）。
  - 在 MySQL 主表的 `body` 字段中仅保留空数组 `[]`，同时刻录异构主键 `mongo_content_id` 与快照指针 `mongo_draft_pointer`。
- **AST 重塑适配器 (Hydration Adapter)**:
  - 读取时，触发 `MongoDBStreamFieldAdapter.from_mongodb()`。
  - 结合 `is_lazy=True` 绕过严格前置校验，自动为缺乏 ID 的区块补齐 UUID，将 MongoDB 散列字典重塑（Hydrate）为前端 Draftail 和 React 强依赖的 `StreamValue` 对象结构。

### **3.2 O(1) 复杂度防雪崩注射机制 (O(1) Data Injection)**

为解决列表页遍历渲染 `body` 提取摘要时引发的 N+1 数据库雪崩查询，设计了独立的注射机制：

- **收集阶段**: 在 `BlogIndexPage` 触发分页后，仅针对当前页截断后的 Top N 文章，提取所有的 `mongo_content_id` 集合。
- **批处理阶段**: 向 MongoDB 发起单次跨库 `$in` 查询，拉取所有大文本字典。
- **动态挂载**: 将拉取的字典数据构建为 Hash Map，动态挂载至内存上下文 (`prefetched_mongo_data`) 中。
- **零 I/O 摘要提取**: 模板层调用 `get_list_preview_text()`，不再触发独立的数据库查询，而是直接从内存 Hash Map 中 O(1) 定位并截取纯文本前 N 个字符。

### **3.3 混合检索与降维排序子系统 (Hybrid Search & Dimensionality Reduction)**

- **无搜索词场景 (MySQL 聚合降维)**:
  - 当没有全局搜索 `query` 时，系统严禁调用外挂的 ES8 引擎。
  - 直接利用 Django ORM 的 `Subquery` 与 `Coalesce` 函数（如：`Coalesce(blog_page_date, blog_index_page_date, first_published_at)`），将 Wagtail 的多态异构子页面时间字段统一映射为虚拟字段 `sort_date`。
  - 排序动作直接下推至 MySQL 数据库底层，实现毫秒级响应。
- **全文检索场景 (ES8 L1/L2 双重召回)**:
  - 存在搜索词时，请求路由至 Elasticsearch 8 进行 L1 召回。
  - 召回结果进入 L2 内存精排层进行二次权重修正。
- **惰性截流 (Lazy Pagination)**:
  - 组装的结果集被封装入 `LazyChainedResultList` 惰性迭代器。只有当 Ajax 接口请求指定 `page` 时，才会触发真实的数据求值，完美规避深度分页击穿和 OOM（内存溢出）。

## **4. 数据库结构设计原则 (Database Design Principles)**

### **4.1 关系型存储架构 (MySQL)**

遵循极致轻量原则，维护页面的骨架关联。

- **核心表 `wagtailcore_page`**: 维持树形路由。
- **业务表 `blog_blogpage`**:
  - 包含 `title`, `intro`, `date` 等轻量字段。
  - **关键设计**: `body` 字段物理存在，但在业务全生命周期中维持为空（障眼法），以此换取极高的表扫描性能；新增外键索引指针 `mongo_content_id`。

### **4.2 非关系型大文本架构 (MongoDB)**

作为数据的“深水区”，屏蔽一切外键约束关联。

- **正式数据集合 (`blog_content`)**: 存储最终发布的 `body` 负载集合。
- **历史快照集合 (`blog_revisions`)**: 提供无上限的历史版本堆叠能力，用于草稿对比和数据自愈穿透回滚。

### **4.3 级联清理策略 (Cascading Deletion)**

当重构了底层存储后，原生外键级联删除失效。我们在 `BlogPage.delete()` 方法中引入了**异构级联清理网关**。物理删除 MySQL `Page` 记录前，系统会自动根据指针深入 MongoDB 集群，销毁正式版内容及所有关联的历史快照，杜绝僵尸数据驻留。

## **5. 运维与部署规范演进 (DevOps & Deployment Evolution)**

配合架构重构，系统的生命周期管理从“脚本游击队”升级为“正规军”。

- **进程绝对隔离**: 每个 Wagtail 项目（如 `wagtailblog3` 与后续可能的电商模块）必须配备独立的 Systemd `*.service` 描述文件。
- **环境变量封锁**: 摒弃依赖 `.bashrc` 或 `.profile` 隐式传递路径的危险做法。Systemd 文件中必须硬编码 `Environment="PATH=..."`，确保 Conda 虚拟环境内的 `uwsgi`, `python` 二进制解释器被精准调用，实现多业务不串台、不冲突的平滑共存。

## **6. API 与惰性通信层设计 (API & Lazy Communication Layer)**

在彻底重构后，系统从传统的纯服务端渲染（SSR）演进为 **SSR + AJAX 惰性加载** 的混合模式，极大降低了服务器瞬时并发压力。

### **6.1 惰性分页接口 (`/search_ajax/`)**

- **设计意图**: 解决传统分页在多态查询和深页跳转时引发的 OOM（内存溢出）与响应超时。
- **数据流转**:
  1. 前端（或浏览器滚动事件）发起包含 `query` 与 `page` 参数的 AJAX 请求。
  2. 视图层通过 `perform_search` 从 ES8 或 MySQL 拿到召回句柄（此时不执行真实数据提取）。
  3. 句柄被推入 `LazyChainedResultList`，利用 Python 生成器（Generator）进行延迟求值，仅在当前页区间内切片。
  4. 执行 O(1) 数据库注射挂载 MongoDB 文本字典。
  5. 返回精简的 JSON 响应，包含 `results`, `has_next`, `total_pages`。

### **6.2 内部管理与业务 API**

- **评论与反应系统 (Comments & Reactions)**: 采用 RESTful 风格，依托 CSRF Token 进行跨站防护，支持用户对文章进行点赞和异步评论提交。
- **搜索建议 (Search Suggestions)**: 提供高响应频率的轻量级 API，利用 ES8 的 Edge N-gram 索引或 MySQL 的前缀匹配，实现毫秒级搜索词补全。

## **7. 缓存与异步任务调度 (Caching & Asynchronous Tasks)**

系统通过 L1/L2 缓存与异步队列的配合，确保高并发下的系统韧性。

### **7.1 双轨制缓存架构 (`SearchCache`)**

- **L1 局部片段缓存**: 针对首页、热门归档等变动极低的视图，使用 Redis 进行 HTML 片段缓存，由 Wagtail 的 `@cache_page` 装饰器接管。
- **L2 检索句柄缓存**: 针对高频的统一搜索词，`SearchCache` 不缓存庞大且容易失效的序列化对象，而是缓存检索结果的主键集合（ID Lists）与排序权重，命中后直接进入 O(1) 注射流程。

### **7.2 Celery 异步中枢**

- **邮件派发**: `base.FormPage` (如联系表单) 提交后，通知邮件与确认邮件的发送任务必须推入 Celery 队列，防止 SMTP 握手延迟阻塞 Web 工作进程。
- **日志与统计归档**: 定期执行访问量统计（PageViewCount）的持久化刷盘动作，将 Redis 内存中的实时计数落地至 MySQL。

## **8. 异常熔断与 AST 自愈防线 (Fault Tolerance & AST Self-Healing)**

异构存储最大的风险在于数据结构的不一致或网络分区。系统在底层设计了多重安全防线。

### **8.1 渲染树 (AST) 自愈重塑**

- Wagtail 前端编辑器强依赖严密的 Draftail / React 数据结构（包含严格的 `id`, `type`, `value`）。
- **防御机制**: 当从 MongoDB 中提取到历史残留的“脏数据”或结构残缺字典时，`MongoDBStreamFieldAdapter` 充当“净化器”。它会自动拦截残缺块，补齐缺失的 UUID（`uuid.uuid4()`），若结构严重损坏，则触发熔断机制，利用 `is_lazy=True` 将其降级为安全的空列表或纯文本，**坚决防止前端 React 引擎发生白屏崩溃**。

### **8.2 防雪崩穿透机制**

- 在读取博客详情 (`serve` 或 `get_latest_revision_as_object`) 时，若请求的草稿快照指针 (`mongo_draft_pointer`) 在 MongoDB 历史集合中丢失（如被手动清理），系统**不会抛出 500 错误**。
- **降级链路**: 代码会自动穿透至第二防线，基于 `mongo_content_id` 降级去线上正式表 (`blog_content`) 捞取兜底数据，确保系统具备极高的容错可用性。

## **9. 可观测性与监控矩阵 (Observability & Monitoring)**

抛弃了过去黑盒式的脚本运行模式，现在的系统运维高度依赖 Linux 原生工具链与数据化仪表盘。

### **9.1 Systemd 原生日志矩阵**

- 守护进程（uWSGI）不再自行后台化（Daemonize）并写死日志文件，而是将所有 stdout/stderr 抛给操作系统的 `syslog`。
- 管理员通过执行 `journalctl -u wagtailblog3.service -n 100 -f`，即可利用操作系统级别的日志轮转机制（Logrotate），避免业务日志撑爆磁盘，同时支持复杂的正则检索。

### **9.2 业务数据大屏 (Analytics Dashboards)**

- **访问量洞察**: `apps.blog` 提供了 `PageViewCount` 聚合大屏，精准区分并统计 UV/PV。
- **检索热度监控**: `apps.search.SearchAnalytics` 在后台捕捉用户的每一次检索动作，提供热门搜索词榜单及“无结果搜索词”预警，为内容创作者提供方向指导。

## **10. 总结 (Conclusion)**

经过架构重构，**WagtailBlog3** 已经完成从“传统内容发布系统”向“**现代化异构分布式内容中枢**”的蜕变。

- **在存储层面**，我们通过巧妙的拦截与适配器设计，将 MySQL 与 MongoDB 完美融合，享受了关系型数据库的严谨路由与 NoSQL 数据库的无感负载扩容。
- **在检索层面**，ES8 与 MySQL 的双轨降维设计兼顾了极致的全文召回能力与日常浏览的极低延迟。
- **在运维层面**，Linux Systemd 彻底根治了脚本自启引发的环境变量雪崩难题。

这份概要设计不仅是开发团队后续构建详细逻辑的蓝图，更是系统在生产环境（Production）下高吞吐、零崩溃运行的核心理论基石。
