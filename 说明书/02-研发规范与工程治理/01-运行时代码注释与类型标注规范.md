# 运行时代码注释与类型标注规范

## 1. 背景与现状证据

`wagtailblog3/apps` 同时包含运行时代码、测试和迁移文件。首批检查发现，Markdown 导入和内容搜索链路虽然已有部分中文注释，但函数参数、返回值、异常边界和类职责说明不完整；解析、批量重建、检查点、租约和失败补偿逻辑不易审阅。

本方案用于分阶段补齐运行时代码的可维护性说明。它不是一次性重写整个 `apps` 目录，也不把迁移和测试文件纳入注释改造范围。

### 员工执行绑定

本方案是仓库“员工”（所有实际修改文件的 agent）的后端运行时代码交付标准。`backend` 角色必须在编码前阅读本方案；其他角色只要修改 `wagtailblog3/apps` 运行时代码，也必须遵守本方案的中文注释、类型标注、行为不变和验证要求。该绑定不新增独立执行角色，也不改变现有专业分工或生产授权边界。

员工交付时必须能提供：模块职责说明、非显而易见函数的参数/返回/异常/副作用契约、复杂算法的不变量与失败补偿顺序、未覆盖边界，以及 `compileall`、相关测试和 `git diff --check` 的精确结果。缺少任一项时，主 agent 或审查者应退回该批次。

## 2. 目标与非目标

### 目标

- 为运行时函数补充能够由实现和调用关系确认的输入、输出类型。
- 为公开服务函数、复杂内部算法和状态类增加中文文档字符串。
- 说明解析边界、状态检查点、租约/重试、数据一致性和失败补偿等业务约束。
- 让维护者可以从函数声明和文档直接判断调用契约、异常编码和副作用范围。

### 非目标

- 不修改业务行为、数据库结构、迁移、测试断言、配置、队列或服务 unit。
- 不为简单赋值、显而易见的框架转发、生成代码和迁移文件增加逐行注释。
- 不凭猜测引入宽泛类型、改变公共接口或顺手重构相邻代码。
- 不在本任务中发布生产、执行数据修复、创建索引或修改页面内容。

## 3. 注释与类型标注规范

### 3.1 函数和方法

- 参数和返回值优先使用现有领域类型、`Mapping`、`Sequence`、`Iterator`、`tuple` 等准确类型；无法确认时保留现有接口并在文档中说明约束，不用 `Any` 掩盖不确定性。
- 中文文档字符串按需要包含“参数”“返回”“异常”“副作用”小节。
- 文档说明业务规则和调用者必须遵守的前置条件，不重复代码本身已经表达的简单分支。
- 复杂函数说明关键不变量、边界条件、失败补偿顺序及必要的时间/空间复杂度；例如倒序替换必须保持原始偏移有效，批量写入成功后才能推进 checkpoint，删除页面失败时不得继续删除其 Mongo 草稿指针和媒体依赖。

### 3.2 类和数据对象

- 异常类说明稳定错误编码的用途，不记录敏感原文。
- 数据类说明字段含义、状态所有权和生命周期，尤其是重建批次、投递租约和导入结果。
- 解析器类说明它负责观察的 HTML/Markdown 层级，以及为何忽略脚本、样式或表格外内容。

### 3.3 中文和编码

新增或修改的注释、文档字符串使用中文；保持文件现有编码，禁止把编码修复顺手扩大为无关格式化。每个 diff 均需通过 `git diff --check`。

### 3.4 标准范例：`blog/admin_image_upload.py`

后续运行时代码统一参照 [`wagtailblog3/apps/blog/admin_image_upload.py`](../wagtailblog3/apps/blog/admin_image_upload.py) 的注释密度和审阅方式。这个文件不是要求所有模块复制相同文字，而是作为结构与深度范例：

- 模块顶部用中文说明模块职责、输入到输出的主流程，以及关键派生步骤或数据边界；不写与实现无关的背景介绍。
- 每个函数和方法的声明都标注可由调用点确认的参数类型和返回类型。Django/Wagtail 动态模型或请求对象暂时只能使用 `Any` 时，必须在文档中写明实际需要的属性和调用约束，不能用 `Any` 隐藏未知契约。
- 每个非显而易见的函数都使用中文 docstring，按需要包含“参数”“返回”“异常”“副作用”“处理边界”等小节；公开入口还要说明装饰器、认证、HTTP 方法和内部权限检查之间的关系。
- 遇到算法时说明输入、输出、不变量、边界和停止条件。例如 collection 选择要说明配置/请求/单一可写集合的优先级，标题去重要说明去扩展名、长度上限、随机后缀、冲突检查和最多五次重试。
- 遇到异常补偿或多阶段保存时说明顺序和所有权。例如原图保存成功后 rendition 只是可重建派生资源，预览失败记录日志但不能让客户端重试整次上传，以免重复创建原图。
- 遇到安全边界时说明防注入、权限检查和异常转换。例如在外部请求处理入口明确标注“为什么抛出 JsonResponse 而不是直接透传异常”。
- 行内注释仅在算法分支目的、异常补偿或易误解位置增加中文行内注释；不为简单赋值、框架调用和显而易见的分支逐行复述代码。
- 注释、类型标注和 docstring 不得改变查询、事务、保存顺序、错误码、日志字段、返回结构或外部服务副作用；每个批次必须用原有测试证明行为未变。

完成一个文件后，审阅者应能只看模块说明、函数签名和关键 docstring，回答“谁调用、传什么、返回什么、何时失败、失败后是否已产生副作用、复杂逻辑为什么这样写”这六个问题。

## 4. 实施范围与执行规则

覆盖应用运行时核心链路，严格排除第三方包、生成迁移、空占位文件及前端编译输出：

1. **搜索服务链路**（`apps/search/services/`、`apps/search/views/`、`apps/search/urls.py`）：重建批次、投递租约、热词统计、ES 查询组装。
2. **Markdown 导入链路**（`apps/blog/services/markdown_*`、`apps/blog/api/`）：解析器状态机、媒体异步下载、持久化事务与 Token 鉴权。
3. **博客核心运行时**（`apps/blog/models.py`、`apps/blog/blocks.py`、`apps/blog/views.py`、`apps/blog/feeds.py`、`apps/blog/wagtail_hooks.py`）：正文渲染、统计反应、Draftail 扩展、后台钩子。
4. **可观测性与辅助应用**（`apps/observability/`、`apps/content_ai/`、全站 URL 路由配置）：日志拦截、上下文过滤、提示词服务。

## 5. 验收门禁与测试命令

在 WSL2 的 `wagtailblog-test` 环境执行：

```bash
# 1. 语法与字节码编译检查
python -m compileall wagtailblog3/apps/

# 2. Django 系统一致性检查
WAGTAILBLOG_ENV=test python manage.py check

# 3. 关联单元与集成测试（行为不变性验证）
WAGTAILBLOG_ENV=test python manage.py test blog search content_ai observability

# 4. 差异与空白字符检查
git diff --check
```

## 6. 模型与推理强度建议

- **事实收集与文档整理**：`gpt-5.6-luna` 低/中推理。
- **局部 Django/Wagtail 类型标注与业务说明**：`gpt-5.6-terra` 中推理；门禁为自动化测试完全通过且行为不变。
- **高风险升级门禁**：若标注或注释涉及跨系统并发协议、生产数据保护或复杂搜索分词逻辑时升级为 `gpt-5.6-sol` 高推理。
