## 0. 执行约束与责任

Gemini 负责每阶段代码和定向测试，Sol 按本计划逐门禁审核，Grok 在关键跨库/并发/恢复节点做对抗式复核。Windows 和 WSL2 共享 `.git`，同一时刻只在一端进行 Git 写操作。新文件责任：`wagtailblog3/apps/external_content/` 为通用正文内核；`wagtailblog3/apps/guides/` 与 `templates/guides/`、`static/guides/` 为业务；`wagtailblog3/apps/search/`、`templates/search/`、`static/search/` 为搜索集成；`settings/base.py`、主导航模板及相关测试只在对应阶段改动。开发者不得撤销其他协作者编辑，阶段交接时核对未提交工作树。

每阶段交付代码差异、实际触及文件、迁移文件、测试命令及输出摘要、残余风险。发现当前 Wagtail 8.0 Action 或现有 Blog 契约与设计不符，先反馈并修订方案，不以猜测绕开。所有新增/修改运行时代码写准确中文注释、docstring 和 Python 类型标注。每个通过审核的功能阶段在本地分支使用中文 Conventional Commit，例如 `feat(guides): 建立专题指南页面与编辑块`；Git 写操作由主控统一执行，避免 Windows/WSL2 并发写 `.git`。

### G4 基于 Wagtail 8.0 / Django 5.2.8 源码调研的方案修订（2026-10-01，未准出）

- **调研证据**：Gemini 只读核对报告 `output/external-content-g4/gemini-framework-research-followup-current.md`。报告核对了当前安装包的 Wagtail 8.0、Django 5.2.8 源码以及当前 `external_content` 接入点；该报告只证明框架调用链事实，不证明 G4 业务实现完成。另一次综合调研请求仍须以当前代理返回的报告和退出码补充，不得把代理启动当作证据。
- **发布入口修订**：Wagtail 后台 `EditView.publish_action` 直接执行 `PublishPageRevisionAction`，其 `_publish_revision()` 直接调用 `page.save()`，随后发送 `page_published`，不保证经过 `BlogPage.publish()`。因此发布冻结、Mongo 版本准备和失败关闭不能只挂在模型 `publish()`；必须同时覆盖统一 Coordinator、`save()`/`save_revision()` 前置屏障、原生 Action/Hook 或信号兜底，并用真实后台 Action 测试证明路径命中。
- **Alias 语义修订**：`CreatePageAliasAction` 创建合法 Alias Page，但通常不产生独立 Revision；`ConvertAliasPageAction` 清空 `alias_of` 后强制调用 `save_revision()`。G4 必须在创建、转换、解除共享指针三个边界显式派生目标 Page 的独立六键身份和 Manifest，明确 `published_revision_id` 与 `source_revision_id`，不得把源页可变指针当作目标页正文。
- **Copy 语义修订**：Wagtail `copy_revisions=True` 会复制历史 Revision 并重绑定目标 Page 的 Revision 对象，但不会深层重派生外置正文指针。G4 必须逐个历史 Revision 派生目标六键身份、独立 Mongo 版本和 Manifest；外部写入失败时 MySQL Page/Revision/SQL 指针必须由同一 `transaction.atomic()` 原子回滚，已写入 Mongo 的孤儿只能交给后续 GC，禁止同步 cleanup。
- **Django 事务修订**：`save_base()` 的 `pre_save`、SQL 写入和 `post_save` 均处于当前事务上下文；`transaction.on_commit()` 只在最外层事务真实提交后按 FIFO 执行，内层 savepoint 回滚会丢弃相应回调。因此 ES、Redis、Celery 等外部副作用必须延迟到 `on_commit()`；跨 MySQL/Mongo 失败补偿必须采用孤儿延迟 GC，不得在异常分支同步删除 Mongo。
- **分包顺序改为强制串行门禁**：
  1. **P0 测试凭据与环境隔离**：在导入项目 `base` settings、执行 `django.setup()`、连接任何数据库或启动容器前，完成凭据缺失失败关闭、测试库/端口/镜像/容器/卷白名单、Socket Guard、路径 no-follow、日志脱敏纯单元测试。P0 未经 Gemini 实现和 Sol 复核通过，不得进入 Django 或 Docker。
  2. **P1 Store 与身份契约**：先补六键身份、严格类型、完整 expected identity、payload 哈希、固定脱敏错误码和无写序列化的真实失败测试，再实现并通过纯单元、AST、compileall。P1 通过前不启动隔离库。
  3. **P2 Locking 与写入冻结**：实现基础 Page → State → Revision（主键升序）→ DeletionIntent 的统一锁序、PENDING 冻结和 thread-local 恢复；覆盖后台原生 Publish Action 的真实锁命中。P2 通过前不进入 Copy/Alias 和数据库矩阵。
  4. **P3 生命周期、Copy 与 Alias**：在 P2 锁屏障之上处理保存、发布、下架、删除、历史 Revision 复制、Alias 创建/转换/解除；所有跨库写入在明确 `atomic` 边界内，所有提交后副作用使用 `on_commit()`。P3 必须用真实 Wagtail Action 和事务失败注入证明原子回滚与源数据不变。
  5. **P4 只读完整性核查**：实现 `verify_external_content_integrity`，真实调用 Store 接口检查 Page/State/Revision/Manifest/Mongo 六键身份、payload_sha256、Alias、墓碑和孤儿记录；依赖不可用、索引未验证或扫描不完整必须 fail-closed，命令不得写 MySQL/Mongo/ES。
  6. **P5 冻结工作树与最终复核**：完成全量证据审计、说明书实现记录、WSL2 专用隔离矩阵、静态/迁移检查和独立 Sol 复核后，才允许精准 stage 与一次本地中文 Conventional Commit。用户人工验收前不得合并 `main`，全程禁止 push、生产访问和历史正文迁移。
