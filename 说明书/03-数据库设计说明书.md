# **博客系统 - 数据库设计说明书 (DBDS)**

**版本: 2.0 (架构重构版)** **日期: 2025-06-13** ---

## **1. 引言 (Introduction)**

### **1.1 目的 (Purpose)**

本说明书旨在详细定义“WagtailBlog3 博客系统”经历底层重构后的分布式异构数据库设计。系统彻底打破了传统 CMS（内容管理系统）强依赖单一关系型数据库的瓶颈，演进为 **MySQL（关系型骨架）+ MongoDB（非结构化大文本负载）** 的读写分离双轨制架构。本文档详述了各表结构、集合模式、索引优化、跨集群关联指针及分布式级联清理机制，为底层开发、DBA 运维及数据自愈防线提供核心规范。

### **1.2 架构背景与设计哲学**

* **结构与负载降维隔离**: MySQL 仅负责处理路由树、树形元数据、高频关系事务（如评论、PV/UV 统计、用户反应）；庞大且频繁变动的 `StreamField` 抽象语法树（AST）内容块则精准下推至 MongoDB 存储。这从根本上解决了 MySQL 单行体积过大导致的页分裂、内存碎片与全表扫描极慢的问题。
* **面向 UI 渲染的异构重塑**: 存储在 MongoDB 中松散的 JSON 字典，在读取阶段通过 `MongoDBStreamFieldAdapter` 适配器机制透明还原（Hydration）为带有严格 UUID 的前端 Draftail/React 树形渲染结构。

## **2. 数据库总体流转架构 (Data Flow Architecture)**

异构中枢的运转依赖于双向指针与拦截网关。当内容创作者在 Wagtail 后台保存文章时：

1. 系统在 `save()` 阶段触发网关拦截。
2. 提取出 `body` 中庞大的 StreamField 数据，调用 `MongoManager` 写入 MongoDB 集群。
3. 在 MySQL 的物理行中，刻录 MongoDB 返回的 ObjectId 作为外键指针（`mongo_content_id`），随后将 MySQL 的 `body` 字段物理清空为 `[]`（障眼法），以此保持 MySQL 的极速轻量。

## **3. 关系型数据库设计 (MySQL Schema Design)**

MySQL 作为主关系型存储中枢，遵循极致轻量化原则，严控宽表出现。

### **3.1 核心页面表 (`blog_blogpage`)**

承载博客文章的核心骨架与路由元数据。

| 字段名              | 物理类型      | 约束          | 索引类型      | 业务描述 / 架构备注                                          |
| ------------------- | ------------- | ------------- | ------------- | ------------------------------------------------------------ |
| `page_ptr_id`       | `INT`         | `PRIMARY KEY` | -             | 指向 `wagtailcore_page` 的外键（Wagtail 页面多态继承的核心映射） |
| `date`              | `DATE`        | `NOT NULL`    | `KEY (date)`  | 官方发布日期，建有单列物理索引以加速无搜索词状态下的按时间过滤。 |
| `intro`             | `LONGTEXT`    | `NOT NULL`    | -             | 文章的简短介绍与 SEO 描述。                                  |
| `featured_image_id` | `INT`         | `NULL`        | `FOREIGN KEY` | 关联自定义图片表 `BlogImage` 的外键指针。                    |
| `mongo_content_id`  | `VARCHAR(50)` | `NULL`        | `KEY`         | **异构主键指针**：定点指向 MongoDB 中 `blog_content` 集合的线上发布版数据唯一 `_id`。 |
| `body`              | `JSON`        | `NULL`        | -             | **物理障眼法字段**：在 MySQL 物理层中，通过 `save()` 覆写，其值永远被清空为 `[]`，彻底卸载大文本包袱。 |

### **3.2 作者与分类表 (`blog_author`, `blog_blogcategory`)**

用于文章多对多关联的维度划分。

| 表名                | 关键字段          | 类型           | 描述                                    |
| ------------------- | ----------------- | -------------- | --------------------------------------- |
| `blog_author`       | `name`            | `VARCHAR(255)` | 作者姓名                                |
|                     | `bio`             | `JSON`         | 作者简介流字段                          |
|                     | `author_image_id` | `INT`          | 作者头像指针                            |
| `blog_blogcategory` | `name`            | `VARCHAR(255)` | 分类名称                                |
|                     | `slug`            | `VARCHAR(80)`  | URL 友好的唯一标识符，建有 `UNIQUE KEY` |

### **3.3 页面访问统计聚合表 (`blog_pageviewcount`)**

承载高并发读写下的 PV/UV 异步落地。

| 字段名         | 物理类型       | 约束          | 索引类型      | 业务描述                      |
| -------------- | -------------- | ------------- | ------------- | ----------------------------- |
| `id`           | `INT`          | `PRIMARY KEY` | -             | 自增主键                      |
| `page_id`      | `INT`          | `NOT NULL`    | `FOREIGN KEY` | 关联文章的页面 ID             |
| `date`         | `DATE`         | `NOT NULL`    | `KEY`         | 统计日期，便于按月/年生成报表 |
| `count`        | `INT UNSIGNED` | `DEFAULT 0`   | -             | 每日总访问量（PV）            |
| `unique_count` | `INT UNSIGNED` | `DEFAULT 0`   | -             | 每日独立访客量（UV）          |

* **防雪崩联合索引**: `UNIQUE KEY (page_id, date)` 确保每日每页仅存在一条聚合记录，防止并发写入导致行重复。

### **3.4 用户互动反应表 (`blog_reaction`)**

记录普通读者对文章的高频互动与情感共鸣（点赞、喜欢等）。

| 字段名             | 物理类型       | 约束       | 业务描述                                     |
| ------------------ | -------------- | ---------- | -------------------------------------------- |
| `page_id`          | `INT`          | `NOT NULL` | 目标页面的 ID                                |
| `reaction_type_id` | `INT`          | `NOT NULL` | 关联 `blog_reactiontype`，标识是“赞”还是“踩” |
| `user_id`          | `INT`          | `NULL`     | 已登录读者的用户 ID                          |
| `session_key`      | `VARCHAR(100)` | `NULL`     | 匿名读者的 Session 追踪哈希                  |
| `ip_address`       | `VARCHAR(45)`  | `NOT NULL` | 读者真实 IP（兼容 IPv6 长度）                |

**防刷单复合锁**:

1. 登录用户防刷：`UNIQUE KEY (page_id, user_id)`
2. 匿名用户防刷：`UNIQUE KEY (page_id, session_key, ip_address)`

## **4. 非关系型大文本架构设计 (MongoDB Schema Design)**

MongoDB 专门作为内容与快照的深水区，全面采用无表结构约束的松散 BSON（Binary JSON）格式。

### **4.1 正式发布主内容集合 (`blog_content`)**

**设计意图**: 存放线上处于发布状态（Live）的页面真实大文本负载。用于前台详情页的定点拉取以及列表页的 O(1) 批量 `$in` 注射。

**文档模式 (Document Schema)**:

```json
{
  "_id": ObjectId("647f1a2b3c4d5e6f7a8b9c01"),
  "page_id": 12,                   // 对应 MySQL 中的 BlogPage 主键 ID
  "title": "深度重构：异构解耦单体极致性能演进",
  "intro": "探讨 Wagtail 底层序列化拦截...",
  "last_updated": "2025-06-13T10:00:00.000Z",
  "body": [                        // 强序列化沉淀的 Wagtail StreamField 负载
    {
      "id": "a1b2c3d4-e5f6-7a8b-9c0d-e1f2a3b4c5d6", // UUID 防线，防止 React 渲染崩溃
      "type": "rich_text",
      "value": "<p>引入异构架构后，主表的读写性能提升了接近一个数量级...</p>"
    },
    {
      "id": "b2c3d4e5-f6a7-8b9c-0d1e-2f3a4b5c6d7e",
      "type": "code_block",
      "value": {
        "language": "python",
        "code": "def save(self, *args, **kwargs):\n    real_body = self.body\n    self.body = []\n    super().save(*args, **kwargs)"
      }
    }
  ]
}

```

**索引规划**: `db.blog_content.createIndex({"page_id": 1}, {unique: true})`，提供 O(1) 级别的页面 ID 反向捞取能力。

### **4.2 历史快照与草稿集合 (`blog_revisions`)**

**设计意图**: 彻底接管 Wagtail 原生在 MySQL 中体积庞大的 `Revision` 历史记录流。专写无唯一性限制的草稿堆叠，提供无上限的历史版本对冲能力。

**文档模式 (Document Schema)**:

```json
{
  "_id": ObjectId("647f1a993c4d5e6f7a8b9c99"),
  "page_id": 12,
  "created_at": "2025-06-13T09:30:00.000Z",
  "draft_body": [ 
    // 存储特定时间点，处于草稿或非活跃编辑态下的 AST 完整快照结构
  ]
}

```

**索引规划**: `db.blog_revisions.createIndex({"page_id": 1, "created_at": -1})`，支撑历史快照的按时间倒序穿透检索。

## **5. 跨集群指针与数据重塑 (Hydration Matrix)**

### **5.1 异构网关双指针暗号**

由于舍弃了跨库的外键物理约束，系统通过两个核心软指针暗号打通分布式存储边界：

1. **线上 Live 指针 (`mongo_content_id`)**: 物理刻录在 MySQL `blog_blogpage` 行中。前台文章渲染时，通过该 ID 直接切入 MongoDB 主集合。
2. **快照草稿指针 (`mongo_draft_pointer`)**: 逻辑刻录在 MySQL `wagtailcore_revision` 的 JSON 序列化字符串中。当进行后台草稿编辑、对比或回滚时，系统解析出该指针，直接穿透至 MongoDB 的 Revisions 集合提取庞大快照，规避了 MySQL 的单行大文本溢出。

### **5.2 AST 动态自愈重塑数据流**

MongoDB 中提取的松散 BSON 字典，必须经过 `MongoDBStreamFieldAdapter` 处理，补齐缺失的块标识（自动 `uuid.uuid4()`），转化为强类型树：

```text
[MongoDB Loose JSON 字典] 
         │
         ▼ (拦截脏数据 / 补齐缺失 UUID)
[MongoDBStreamFieldAdapter] 
         │
         ▼ (强行注入 is_lazy=True，绕过原生严格类型前置校验)
[Wagtail StreamValue] ──► 送交前端 React UI / Draftail 进行安全渲染
```

## **6. 高性能级联清理与兜底防线 (Cascading Deletes & Fallbacks)**

由于关系解耦，传统 MySQL 的 `ON DELETE CASCADE` 对外部的 MongoDB 彻底失效。

### **6.1 物理删除异构同步解耦网关**

在后台点击“删除页面”时，代码层面重写了 `BlogPage.delete()`，构建了严格的分布式级联清理事务链：

1. **原生物理擦除**：调用 `super().delete()`，让 MySQL 安全擦除骨架行、多对多映射记录，释放表空间。

2. **跨集群定点绞杀**：提取当前页的 `mongo_content_id` 和 `page_id`，利用 `MongoManager`：

   * 调用 `delete_blog_content(mongo_content_id)`，从正式表中销毁大文本字典。

   * 调用 `delete_page_revisions(page_id)`，将历史堆叠集合中该页面的所有草稿、版本快照定点洗净，彻底杜绝“僵尸文档”。

### **6.2 防雪崩穿透降级机制**

若因网络异常或管理员强制修剪 MongoDB 数据，导致 MySQL 中刻录的 `mongo_draft_pointer` 在 MongoDB 历史表中丢失，系统被设计为**绝对不能抛出 500 崩溃错误**。

* **自愈降级链路**：拦截内部查询错误，越过丢失的历史草稿表，利用同行的 `mongo_content_id` 降级读取线上 Live 正式表中的数据进行兜底复活，最大限度保障后台编辑器的可用性与前端内容的连贯性。

## **7. 搜索引擎倒排索引设计 (Elasticsearch 8 Schema)**

作为全文检索的 L1 召回大脑，Elasticsearch 8（简称 ES8）的索引结构设计同样需要配合异构存储进行降维映射。

### **7.1 核心博客索引 (`blog_page_index`)**

由于真实的大文本存储在 MongoDB 中，ES8 并不负责存储原始内容源，只负责**倒排索引与权重打分**。当触发 `update_index` 时，系统会通过 `BlogPage.get_full_text_for_search()` 方法动态从 MongoDB 提取纯文本注入 ES8。

| 映射字段 (Field)           | ES 类型 (Type) | 权重 (Boost) | 分词器 (Analyzer)       | 架构说明                                                     |
| -------------------------- | -------------- | ------------ | ----------------------- | ------------------------------------------------------------ |
| `id`                       | `keyword`      | -            | -                       | 映射 MySQL 中的 `wagtailcore_page` 主键                      |
| `title`                    | `text`         | `^10.0`      | `ik_max_word` / `jieba` | 最高权重检索字段                                             |
| `intro`                    | `text`         | `^5.0`       | `ik_max_word` / `jieba` | SEO 简介摘要                                                 |
| `get_full_text_for_search` | `text`         | `^2.0`       | `ik_max_word` / `jieba` | **异构穿透字段**：剥离了 HTML、Markdown 标记、表格结构的纯文本集合 |
| `date`                     | `date`         | -            | -                       | 支持 `start_date` 与 `end_date` 过滤                         |
| `tags` / `categories`      | `keyword`      | -            | -                       | 用于精确的 Facet 聚合过滤                                    |

**降维策略**: ES8 仅返回命中结果的主键列表集合（ID Lists）和高亮切片。具体的全量数据重装（Hydration）依然下推给 O(1) 机制从 MongoDB 批处理完成。

## **8. 高速缓存与键值存储设计 (Redis KV Schema)**

Redis 在本架构中承担 L2 缓存（检索句柄缓存）与 Celery 任务队列的双重职责，其 Key 的命名空间实行严格的业务隔离。

### **8.1 检索惰性缓存 (Search Cache KV)**

* **设计意图**: 屏蔽高频热点搜索词对 ES8 和 MySQL 的穿透式查询。
* **Key 生成规则**: `search:{query_hash}:{type}:{page}:{start_date}:{end_date}:{order_by}`。
* **Value 结构**: JSON 序列化字符串。为了防止大对象带来的网络带宽与序列化开销，Redis 中**绝对不缓存完整的页面对象**，仅缓存该次查询命中的 ID 列表、分页元数据及总条数。
* **TTL (过期时间)**: 设定为 1-2 小时（带有一定的随机抖动防止缓存雪崩）。

### **8.2 PV/UV 异步缓冲池 (Analytics Buffer)**

* **设计意图**: `blog_pageviewcount` 若在每次用户访问时直写 MySQL 会引发极高的行锁竞争。PV/UV 必须先打入 Redis 进行增量缓冲。
* **数据结构**: 采用 Redis 的 `HyperLogLog` 结构记录当日独立 UV；采用 `INCR` 计数器记录当日实时 PV。
* **落地策略**: 依托 Celery Beat 定时任务（如每 5 分钟），将 Redis 中的聚合数据批量刷盘 (`UPSERT`) 至 MySQL `blog_pageviewcount` 表中，实现高并发下的削峰填谷。

## **9. 数据备份与容灾恢复规范 (DBA Ops & Recovery)**

由于系统是“MySQL + MongoDB”的双物理引擎架构，传统的单机 SQL 备份已无法满足要求，必须实施**分布式对齐备份策略**。

### **9.1 快照时间点对齐 (Point-in-Time Alignment)**

在进行生产环境（Production）备份时，由于业务正在持续写入，MySQL 中刻录的 `mongo_content_id` 必须与 MongoDB 中实际存在的文档保持绝对一致。

* **备份流程**: 必须先执行 MongoDB 的 `mongodump`，紧接着在秒级间隔内触发 MySQL 的 `mysqldump`。
* **运维命令范例**:

```bash
# 1. 导出 MongoDB (大文本载荷与快照)
mongodump --db wagtail_blog_db --out /backups/mongo_$(date +%F)/

# 2. 导出 MySQL (骨架与元数据)
mysqldump -u root -p wagtail_blog_db > /backups/mysql_$(date +%F).sql

```

### **9.2 灾难回滚与自愈验证**

若发生数据损坏需要回滚，必须**同时、成对**恢复 MySQL 与 MongoDB 的备份包。

* **悬空指针告警**: 若仅恢复 MySQL 而忘记恢复 MongoDB，会导致所有页面在渲染时抛出指针丢失。此时，依赖前文 `5.2 防雪崩穿透降级机制` 中的安全判定防线，系统会自动屏蔽异常块，防止发生 React 渲染白屏，等待 DBA 补齐 MongoDB 数据。
