# 系统部署与生产运行手册

## 1. 手册定位与环境拓扑

本手册为 WagtailBlog3 项目的部署、服务生命周期管理与日常运维标准基准，严格对齐仓库根目录的 `systemctl.md`。手册详细规范了测试与生产双环境的运行边界、四大应用服务编排、标准化发布发布流水线与应急排错排障指南。

### 1.1 物理与网络拓扑架构

```
[Windows 11 开发机 (192.168.20.1)]
   └── 源码编辑: F:\openclaw\workspace\wagtail\wagtailblog2
         │ (NTFS 目录穿透共享，同一份代码与 .git)
         ▼
[WSL2 测试环境 (192.168.20.5 / Debian)]
   ├── 工作路径: /mnt/f/openclaw/workspace/wagtail/wagtailblog2
   ├── Conda: /root/anaconda3/envs/wagtailblog-test
   ├── 环境配置: wagtailblog3/settings/.env.test (WAGTAILBLOG_ENV=test)
   └── 职能: Git 提交推送入口、单元与集成测试、Django Check、迁移规划验证
         │
         │ (Git Push origin main / SSH 运维受控流转)
         ▼
[生产运行服务器 (192.168.20.2 / Hyper-V 第一代虚拟机 ziliao)]
   ├── 部署路径: /home/source/Django/wagtail/wagtailblog3
   ├── Conda: /root/anaconda3/envs/wagtailblog
   ├── 环境配置: wagtailblog3/settings/.env.production (WAGTAILBLOG_ENV=production)
   ├── 接入层: Nginx (监听 6050 端口)
   └── 运行层: uWSGI (6051 / Unix Socket) + Celery (Maintenance/Beat) + Filebeat
```

> **环境隔离红线**：
> - 所有入口统一基于 `wagtailblog3.settings.dev`，由环境变量 `WAGTAILBLOG_ENV` 动态决定读取 `.env.test` 或 `.env.production`。
> - 严禁在测试环境引用或复制生产环境凭据，严禁生产环境缺省 `.env.production` 启动。

## 2. 生产四大核心应用服务编排

生产服务由 `systemd` 统一接管，服务清单及维护要求如下：

| 服务 Unit 名称 | 进程架构与组件 | 核心职能说明 | 重启/重载触发条件 |
|---|---|---|---|
| `wagtailblog3.service` | uWSGI / Django 5.2.8 | Web 应用核心，托管 Wagtail 页面树、后台管理及公共 API | Python 业务代码变更、Wagtail 模板更新、依赖升级 |
| `wagtailblog3-celery-maintenance.service` | Celery Worker (`-Q maintenance`) | 专用维护队列，消费内容检索 Outbox 投递、缩略图异步处理与数据对齐 | 搜索投递逻辑修改、异步任务定义更新、队列参数调整 |
| `wagtailblog3-celery-beat.service` | Celery Beat 调度器 | 定时任务分发、Outbox 死信重试、孤儿正文周期性审计 | `CELERY_BEAT_SCHEDULE` 配置修改、周期频率调整 |
| `wagtailblog3-filebeat.service` | Elastic Filebeat | 收集 `/var/log/wagtailblog3/` 结构化 JSON 日志并推送至 Elasticsearch | 日志格式变更、ES 日志索引模式更新 |

> **服务治理红线**：
> - 严禁新增仅消费 `email` 或 `default` 的无边界 Worker，所有高负载及搜索任务收敛至 `maintenance` 队列。
> - 若服务 unit 文件发生变动，必须先执行 `systemctl daemon-reload` 再执行重启。

## 3. 服务依赖拓扑与开机/重启依赖时序

当服务器重启或执行全系统冷启动时，必须严格遵守依赖拓扑顺序，禁止倒序或并发拉起：

```
[基础设施层]
  MySQL 8.4 (3306)  ──┐
  MongoDB (27017)   ──┼──> [应用服务器] wagtailblog3.service (uWSGI / Django)
  Redis (6379)      ──┤         │
  MinIO (9000)      ──┤         ▼
  Elasticsearch(9200) ─┘   [异步处理层] wagtailblog3-celery-maintenance.service (Worker)
                                │
                                ▼
                           [定时调度层] wagtailblog3-celery-beat.service (Beat)
                                │
                                ▼
                           [日志收集层] wagtailblog3-filebeat.service (Filebeat)
                                │
                                ▼
                           [外网接入层] nginx.service (反向代理 6050)
```

**开机恢复门禁**：
在搜索启用状态下，必须确认 MySQL、MongoDB、Redis、MinIO 及 Elasticsearch 已完全就绪，并确认只读搜索别名 `wagtailblog-prod-content-read` 真实指向当前健康内容索引后，才允许拉起应用与 Worker。

## 4. 标准化发布与上线流水线

生产代码发布必须按以下严格顺序完成闭环，严禁跨步跳跃：

### 4.1 阶段一：WSL2 验证与本地提交
1. 进入 WSL2 测试环境：`cd /mnt/f/openclaw/workspace/wagtail/wagtailblog2`。
2. 静态检查：`python manage.py check`。
3. 迁移检查：若改动模型，执行 `python manage.py makemigrations --check --dry-run` 与 `python manage.py migrate --plan`。
4. 运行相关测试：`python manage.py test <affected_app> --keepdb`。
5. 差异审查：`git diff --check`。
6. 提交与推送：
   ```bash
   git add <files>
   git commit -m "feat/fix: <清晰中文说明>"
   git push origin main
   ```
7. 确认远端同步：核验本地 `HEAD` 与 `origin/main` 指向完全一致的 SHA。

### 4.2 阶段二：生产环境安全同步
1. 连接生产机：`ssh root@192.168.20.2`。
2. 确认生产目录状态：
   ```bash
   cd /home/source/Django/wagtail/wagtailblog3
   git status --short --branch
   ```
   *要求：分支必须为 `main`，且工作树完全干净（Clean），无未跟踪或被修改文件。*
3. 预检差异：
   ```bash
   git fetch origin --prune
   git diff --name-status HEAD..origin/main
   ```
4. 快进合并（绝对禁止暴力拉取）：
   ```bash
   git merge --ff-only origin/main
   ```

### 4.3 阶段三：生产生效与服务重载
1. 执行数据库迁移（仅当有新增 migration 时，且已事先取得用户确认）：
   ```bash
   python manage.py migrate
   ```
2. 重载服务（按影响范围执行，纯文档/注释变更无需重启服务）：
   ```bash
   systemctl restart wagtailblog3
   systemctl restart wagtailblog3-celery-maintenance
   systemctl restart wagtailblog3-celery-beat
   ```
3. 验收健康状态：
   ```bash
   systemctl is-active wagtailblog3 wagtailblog3-celery-maintenance wagtailblog3-celery-beat wagtailblog3-filebeat
   curl -I http://127.0.0.1:6050/
   ```

## 5. 生产高频故障排查手册（Runbooks）

### 5.1 场景一：前台全文检索返回空或报错
1. **核验只读别名**：
   ```bash
   curl -s http://127.0.0.1:9200/_cat/aliases/wagtailblog-prod-content-read?v
   ```
   *预期：必须存在该别名且指向健康的主内容索引（如 `...-v005`）。*
2. **检查检索目标模型配置**：检查 Django 数据库中 `SearchTarget` 的 `is_enabled` 与 `role` 字段是否被意外禁用。
3. **检查 Outbox 投递堆积**：检查 `search_searchdelivery` 中是否存在大量 `status=dead` 或重试超限记录。
4. **禁止动作**：严禁在未排查原因前盲目清空或删除 Elasticsearch 索引。

### 5.2 场景二：Wagtail 后台打开博客正文变为空白
1. **排查 `mongo_content_id` 关联**：检查当前页面对应的 `BlogPage` 记录中 `mongo_content_id` 是否非空。
2. **测试 MongoDB 连通性**：
   ```bash
   mongosh "mongodb://127.0.0.1:27017/wagtailblog_prod" --eval "db.blog_page_contents.find().count()"
   ```
3. **关键保护**：若后台页面表单回显空白，**严禁点击“保存草稿”或“发布”**，否则空正文将冲刷历史版本；应立即排查 MongoDB 连接池与 `BlogPageForm` 水合逻辑。

### 5.3 场景三：异步队列任务延迟或停滞
1. **检查 Worker 进程状态**：`systemctl status wagtailblog3-celery-maintenance` 查看是否有 OOM 或僵死。
2. **检查 Redis 连通性与队列积压**：
   ```bash
   redis-cli -p 6379 ping
   redis-cli -p 6379 llen maintenance
   ```
3. **查看 Beat 调度心跳**：检查 Beat 日志是否有周期性任务投递记录；若锁未释放，排查 Redis 分布式锁租约。
