# 生产灾备、备份与恢复全书

## 1. 灾备定位与数据资产全景

本全书为 WagtailBlog3 项目的数据安全底线与灾备恢复标准。项目采用多存储引擎异构架构，正文、结构化元数据、对象附件与检索索引分别托管于不同存储介质。为确保在发生硬件故障、误操作或数据损坏时能快速、无损恢复，必须实施统一的多源灾备治理。

### 1.1 核心存储数据资产分类矩阵

| 存储系统 | 托管数据资产 | 权威级别 | 备份工具与命令规范 | 恢复容忍度 (RTO / RPO) |
|---|---|---|---|---|
| **MySQL 8.4** | Wagtail 页面树拓扑、文章元数据、分类标签、用户账户、评论数据、Outbox 投递表、搜索目标配置 | **基石级权威** (权威源之一) | `mysqldump --single-transaction --quick --triggers --routines` | RTO < 30min<br>RPO < 24h |
| **MongoDB 7.x** | 博客正文全量内容（正式正文 `blog_page_contents`、历史修订版本 `blog_page_revisions`、草稿快照 `blog_page_drafts`） | **绝对保护权威** (正文唯一权威) | `mongodump --gzip --archive=<target>.gz` (必须覆盖三大集合) | RTO < 30min<br>RPO < 24h |
| **MinIO S3** | 文章插图、作者头像、媒体视频、下载附件及静态缩略图 | **持久化权威** | `mc mirror` / 增量存储卷快照 | RTO < 1h<br>RPO < 24h |
| **Elasticsearch** | 独立全文检索索引（`wagtailblog-prod-content-v*`）、Filebeat 业务日志索引 | **派生索引** (可由 MySQL+Mongo 全量重建) | ES Snapshot API (`_snapshot`)，`include_global_state=false` | RTO < 2h<br>RPO < 1h (支持离线自愈) |
| **系统与配置** | Git 精确 Commit SHA、`.env.production`、`systemd/*.service`、`nginx.conf` | **配置基准** | 离线安全副本（凭据加密存储，严禁上传公开仓库） | RTO < 15min |

## 2. 灾难恢复全流程操作手册（Runbook）

当遭遇生产宕机、机房灾难或多库不一致时，严格按照以下六阶段实施有序冷/温恢复：

```
[阶段一: 阻断写入] ──> [阶段二: 恢复 MySQL] ──> [阶段三: 恢复 MongoDB & MinIO]
                                                        │
[阶段六: 业务验收] <── [阶段五: 启动服务]  <── [阶段四: 校验/重建 ES 别名]
```

### 2.1 阶段一：立即阻断外部写入
1. 停止上层应用服务，避免恢复期间脏数据混入：
   ```bash
   systemctl stop wagtailblog3 wagtailblog3-celery-maintenance wagtailblog3-celery-beat
   ```
2. Nginx 临时切换至维护兜底页（503 Service Unavailable）。

### 2.2 阶段二：恢复 MySQL 结构与元数据
1. 建立空数据库或确认当前数据库隔离备份已完成。
2. 导入指定日期的备份 SQL：
   ```bash
   mysql -u root -p wagtailblog_prod < /backup/mysql/wagtailblog_prod_YYYYMMDD.sql
   ```
3. 校验基础表数量与迁移状态：
   ```bash
   WAGTAILBLOG_ENV=production python manage.py showmigrations
   ```

### 2.3 阶段三：恢复 MongoDB 正文与 MinIO 媒体文件
1. 导入 MongoDB 核心三大集合归档文件：
   ```bash
   mongorestore --gzip --archive=/backup/mongo/mongodump_YYYYMMDD.gz --nsInclude="wagtailblog_prod.*"
   ```
2. 抽样验证正文完整性：
   ```bash
   mongosh "mongodb://127.0.0.1:27017/wagtailblog_prod" --eval "db.blog_page_contents.countDocuments()"
   ```
   *核对 MongoDB 记录总数是否与 MySQL `blog_blogpage` 中有效 `mongo_content_id` 匹配。*
3. 恢复 MinIO 媒体附件至目标存储桶（Bucket），验证文件权限与访问路由。

### 2.4 阶段四：恢复 Elasticsearch 索引与别名绑定
1. 若存在完备的 ES 快照，使用快照恢复：
   ```bash
   curl -X POST "127.0.0.1:9200/_snapshot/my_backup/snapshot_YYYYMMDD/_restore" \
        -H 'Content-Type: application/json' \
        -d '{"indices": "wagtailblog-prod-content-*", "include_global_state": false}'
   ```
2. 若快照缺失或版本跨越过大，直接基于权威源触发全量重建（Reindex）：
   ```bash
   WAGTAILBLOG_ENV=production python manage.py build_content_index --alias --force
   ```
3. 核验读别名指向：
   ```bash
   curl -s "127.0.0.1:9200/_cat/aliases/wagtailblog-prod-content-read?v"
   ```

### 2.5 阶段五：服务依赖顺序拉起
严格按照拓扑顺序依次启动生产服务：
```bash
systemctl start wagtailblog3
systemctl start wagtailblog3-celery-maintenance
systemctl start wagtailblog3-celery-beat
systemctl start wagtailblog3-filebeat
systemctl reload nginx
```

### 2.6 阶段六：端到端业务验收
- 验证前台首页、博客详情页 Markdown 渲染与图片加载。
- 验证后台登录、正文编辑器打开与草稿保存生命周期。
- 执行关键词检索，验证高亮与搜索结果准确返回。
- 检查 `/var/log/wagtailblog3/` 结构化日志无持续 Error 刷屏。

## 3. 灾备管理十条不可逾越红线（Red Lines）

1. **绝对禁止生产环境 `flush`**：任何情况下不得执行 `python manage.py flush`，该命令会直接清空 MySQL 全部表数据。
2. **绝对保护 MongoDB 正文**：严禁执行 `db.dropDatabase()` 或删除 `blog_page_contents` 等正文集合；正文丢失意味着不可逆的数据灭失。
3. **严禁带卷删除容器**：严禁执行 `docker compose down -v` 或 `docker volume rm` 摧毁持久化挂载的数据卷。
4. **禁止通配符删除 ES 索引**：严禁调用 `curl -X DELETE 127.0.0.1:9200/*` 这种危险通配符指令。
5. **严禁快照污染集群状态**：恢复 ES 快照时必须显式指定 `include_global_state: false`，防止快照中旧的集群路由与持久化配置覆盖当前集群。
6. **禁止明文传输与存储凭据**：备份脚本不得把数据库密码以明文形式硬编码在 Git 跟踪的文件中。
7. **数据恢复前必留隔离备份**：对出现异常的数据库进行修复前，必须先原样打包保存当前故障现场，以便追溯与反复尝试。
8. **跨库修改必须具备幂等事务**：任何对 MySQL 与 MongoDB 的同步变更，必须通过 Outbox 机制保障最终一致性，不得直接在裸脚本中双写。
9. **演练数据必须严格清理**：在灾备演练库中验证的数据与脚本，严禁与生产混用，演练后即刻安全销毁。
10. **必须留存操作审计记录**：所有重大备份与恢复操作均须记录时间、操作人、目标 SHA、文件校验和与验收结果。
