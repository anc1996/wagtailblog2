# **博客系统 - 部署与运维手册 (Deployment & Ops Manual)**

**版本: 2.0 (Systemd 原生托管版)** **日期: 2025-06-13** ---

## **1. 引言 (Introduction)**

### **1.1 目的**

本文档是 WagtailBlog3 项目在生产环境（Production）下的权威部署与运维指南。随着系统演进为异构架构（MySQL + MongoDB + ES8），本指南彻底摒弃了早期脆弱的 Shell 脚本（`start.sh`）与 `crontab` 自启方案，全面转向 **Linux 原生 Systemd 服务托管**。此举旨在实现绝对的进程隔离、环境变量防漂移以及高吞吐下的无缝平滑重启。

## **2. 基础环境与依赖矩阵 (Prerequisites)**

在进行代码部署前，请确保服务器（Ubuntu/Debian 或 CentOS）已就绪以下基础组件：

### **2.1 数据库与检索引擎**

* **关系型骨架**: `MySQL 8.0+` (负责路由表与轻量事务)
* **大文本堆叠**: `MongoDB 5.0+` (负责 Body AST 渲染树与快照)
* **检索引擎**: `Elasticsearch 8.x` (配合 IK 分词器或 Jieba)
* **缓存与队列缓冲**: `Redis 6.0+`

### **2.2 运行环境**

* **进程隔离**: `Miniconda3` 或 `Anaconda3`
* **Python**: `3.12+`
* **Web 服务器**: `Nginx`

## **3. 核心应用服务器配置 (uWSGI + Systemd)**

**【最高警告】**：严禁在生产环境使用 `python manage.py runserver` 或手动执行 `start.sh`！所有的进程生命周期必须交由操作系统内核级管理器 Systemd 托管。

### **3.1 改造 `uwsgi.ini` (剥离后台化)**

Systemd 必须在前台捕获进程状态。如果 uWSGI 自行后台化（daemonize），Systemd 会误判服务已退出，导致启动失败或无限循环重启雪崩。

编辑项目根目录下的 `uwsgi.ini`，**必须注释或删除 `daemonize` 参数**：

```ini
[uwsgi]
socket = /home/source/Django/wagtail/wagtailblog3/wagtailblog3.sock
chmod-socket = 666
master = true
processes = 4
threads = 2
vacuum = true

# ⚠️ 架构重构核心变更：绝对禁止开启以下参数，日志将交由 Systemd 的 syslog 接管
# daemonize = logs/uwsgi.log  <--- 【必须注释掉】

```

### **3.2 创建应用级 Systemd 服务文件**

在系统目录创建守护进程配置文件：

```bash
sudo nano /etc/systemd/system/wagtailblog3.service

```

填入以下生产级强隔离配置（请严格校验 `Environment` 路径与您的 Conda 环境匹配）：

```ini
[Unit]
Description=uWSGI High-Performance Instance for WagtailBlog3
After=network.target mysql.service mongodb.service elasticsearch.service

[Service]
User=root
Group=root

# 1. 强锁定项目工作目录
WorkingDirectory=/home/source/Django/wagtail/wagtailblog3

# 2. 环境变量防漂移防线：硬编码 Conda 环境 PATH，绝对解决多项目版本冲突
Environment="PATH=/root/anaconda3/envs/wagtailblog/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
Environment="DJANGO_SETTINGS_MODULE=wagtailblog3.settings.production"

# 3. 启动指令：调用虚拟环境内的 uwsgi 二进制文件
ExecStart=/root/anaconda3/envs/wagtailblog/bin/uwsgi --ini uwsgi.ini

# 4. 熔断与自愈策略：放弃 always，改用 on-failure 防止报错死循环
Restart=on-failure
RestartSec=5s

# 5. 优雅退出控制 (Zero-Downtime Reload)
KillSignal=SIGQUIT
Type=notify
NotifyAccess=all

# 6. 日志流重定向至系统内核
StandardError=syslog
StandardOutput=syslog
SyslogIdentifier=wagtailblog-uwsgi

[Install]
WantedBy=multi-user.target

```

### **3.3 激活与验证服务**

```bash
# 1. 刷新 systemd 守护进程树
sudo systemctl daemon-reload

# 2. 启动服务并设置开机自启（替代 crontab @reboot）
sudo systemctl start wagtailblog3
sudo systemctl enable wagtailblog3

# 3. 验证进程状态（必须看到绿色的 active (running)）
sudo systemctl status wagtailblog3

```

## **4. 异步队列配置 (Celery Workers)**

系统中的邮件发送与 Redis PV/UV 异步刷盘强依赖 Celery。同样，必须为其配置独立的 Systemd 守护服务。

### **4.1 配置 Celery Worker 服务**

```bash
sudo nano /etc/systemd/system/wagtailblog-celery.service

```

```ini
[Unit]
Description=Celery Worker Service for WagtailBlog3
After=network.target redis.service mysql.service

[Service]
User=root
Group=root
WorkingDirectory=/home/source/Django/wagtail/wagtailblog3
Environment="PATH=/root/anaconda3/envs/wagtailblog/bin:/usr/bin"
Environment="DJANGO_SETTINGS_MODULE=wagtailblog3.settings.production"

# 启动 Celery Worker
ExecStart=/root/anaconda3/envs/wagtailblog/bin/celery -A wagtailblog3 worker -l INFO --concurrency=2

Restart=on-failure
RestartSec=10s
StandardError=syslog
SyslogIdentifier=wagtailblog-celery

[Install]
WantedBy=multi-user.target

```

### **4.2 激活 Celery 服务**

```bash
sudo systemctl daemon-reload
sudo systemctl start wagtailblog-celery
sudo systemctl enable wagtailblog-celery

```

*(注：如有需要，同理可配置 `wagtailblog-celery-beat.service` 专门用于定时任务派发)。*

## **5. Nginx 反向代理与静态路由**

Nginx 负责静态资源承载与 HTTPS 终结。

```nginx
server {
    listen 80;
    listen 443 ssl http2;
    server_name yourdomain.com;

    # SSL 配置略...

    # Wagtail 静态资源请求
    location /static/ {
        alias /home/source/Django/wagtail/wagtailblog3/static/;
        expires 30d;
        access_log off;
    }

    # 用户上传媒体资源
    location /media/ {
        alias /home/source/Django/wagtail/wagtailblog3/media/;
        expires 30d;
    }

    # 动态请求穿透至 uWSGI 套接字
    location / {
        include uwsgi_params;
        # 指向 uwsgi.ini 中定义的 socket
        uwsgi_pass unix:/home/source/Django/wagtail/wagtailblog3/wagtailblog3.sock;
        
        # 针对长传与大负载设置超时与 body 大小
        uwsgi_read_timeout 120;
        client_max_body_size 50M;
    }
}

```

## **6. 可观测性与日志运维排错 (Observability)**

重构后，由于剔除了零散的 `.log` 文件，运维排错范式发生了根本性转变。

### **6.1 日志全景追踪 (`journalctl`)**

任何关于 500 错误、启动失败、Python 语法异常，全部通过系统日志聚合中心查看：

```bash
# 查看 uWSGI 进程的实时滚动日志
sudo journalctl -u wagtailblog3.service -f

# 查看过去 100 行日志
sudo journalctl -u wagtailblog3.service -n 100

# 查看 Celery 异步队列的实时日志
sudo journalctl -u wagtailblog-celery.service -f

# 检索特定日期的日志
sudo journalctl -u wagtailblog3.service --since "2025-06-13 10:00:00" --until "2025-06-13 11:00:00"

```

### **6.2 零停机平滑更新 (Zero-Downtime Reload)**

当进行了代码 `git pull` 或修改了 Django 配置后，**不需要**暴力 Kill 进程。只需执行：

```bash
sudo systemctl restart wagtailblog3

```

*原理解析：Systemd 会发送 `SIGQUIT` 信号，uWSGI Master 进程会等待当前正在处理的访客请求执行完毕后，安全重启 Worker 进程。此时前端 Nginx 不会报 502 Bad Gateway 错误。*

## **7. 分布式灾备与异构恢复 (Disaster Recovery)**

在 MySQL + MongoDB 异构架构下，数据备份必须执行**双库时间点对齐策略**。

### **7.1 双库同步备份**

严禁只备份 MySQL 而遗漏 MongoDB，否则会导致大量前端页面抛出 AST 指针丢失异常。备份脚本应同时执行：

```bash
#!/bin/bash
BACKUP_DIR="/data/backups/$(date +%F)"
mkdir -p $BACKUP_DIR

# 1. 秒级提取 MongoDB 大文本集合
mongodump --db wagtail_blog_db --out $BACKUP_DIR/mongo/

# 2. 紧接着提取 MySQL 骨架元数据
mysqldump -u root -p'YourPassword' wagtail_blog_db > $BACKUP_DIR/mysql_meta.sql

# 3. 压缩并发送至异地容灾服务器/OSS
tar -czvf $BACKUP_DIR.tar.gz $BACKUP_DIR

```

### **7.2 ES8 倒排索引全量重建**

当发生灾难恢复，或 MongoDB 物理迁移后，必须重新将纯文本推入 Elasticsearch。在项目目录下执行：

```bash
# 激活环境
conda activate wagtailblog
# 执行 Wagtail 原生命令重新构建倒排索引
python manage.py update_index

```
