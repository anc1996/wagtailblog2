# WagtailBlog3 搜索架构容量与演进方案

## 1. 文档信息

- 编制日期：2026-08-10
- 适用项目：`wagtailblog3`
- 当前代码版本：以实施时实际 `main` 分支和生产 commit 为准
- 当前依赖基线：Django 5.2.8、Wagtail 7.4.2、Elasticsearch Python Client 8.19.3、生产 Elasticsearch 8.17.0、PyMongo 4.11.3
- 文档性质：架构决策和实施方案，不代表已经授权执行迁移、索引重建、生产配置修改或服务重启
- 配套实施计划：`说明书/10-搜索架构实施计划.md`

## 2. 执行摘要

本项目应继续保留 Elasticsearch，原因不是 MongoDB 或 MySQL 无法保存文章，而是千万级中文全文检索需要独立的倒排索引、相关性排序、短语匹配、过滤、高亮和可横向扩展能力。

推荐的长期职责边界如下：

```text
MySQL
  └─ 页面树、发布状态、权限、分类关系、搜索同步状态

MongoDB
  └─ 正式正文、草稿正文、历史正文，属于受保护主数据

Elasticsearch
  └─ 可重建的搜索读模型，只保存检索需要的字段

Redis
  └─ 热门查询结果、搜索建议热度、异步任务协调
```

当前约一千篇文章时，现有 Elasticsearch 搜索速度和资源占用可接受；但当前 8 GiB 主机不能承担一千万篇文章的 Elasticsearch、MongoDB、MySQL、MinIO、Kibana 和应用进程。达到百万级以前必须把内容搜索迁移到独立 Elasticsearch 节点，千万级目标应按多节点集群规划。

本方案采用四条主线：

1. 先修正当前实现中的低风险浪费和错误假设。
2. 增加正文命中片段，让搜索能够定位到文章中的实际内容。
3. 将搜索同步改造成可重试、可补偿、可审计的异步投影。
4. 在数据增长前建立独立、精简、版本化的内容搜索索引。

## 3. 范围与非目标

### 3.1 本方案范围

- 博客前台全文搜索。
- Wagtail `BlogPage` 搜索字段和 Elasticsearch 映射。
- MongoDB 正文与 Elasticsearch 搜索读模型之间的数据流。
- 搜索建议、搜索缓存、深分页、命中高亮。
- 单机 8 GiB 阶段到千万篇阶段的容量演进。
- 索引构建、增量同步、故障补偿、切换和回滚。
- 与变更相关的测试、发布、服务和文档维护。

### 3.2 本方案非目标

- 不改变 `markdown_block` 存储 key。
- 不把 Markdown 转换为不可恢复的 HTML 后再保存。
- 不迁移或删除 MongoDB 正文、草稿、Revision pointer 或 `mongo_content_id`。
- 不用 Elasticsearch 代替 MongoDB 正文主存储。
- 不在本阶段引入向量检索、大模型问答或语义检索。
- 不为了搜索重写 Wagtail 页面树、发布流程或权限体系。
- 不在未压测前承诺固定的千万级 QPS。

### 3.3 前台公开搜索的内容边界

前台公开搜索入口 `http://192.168.20.2:6050/zh-hans/search/` 只能检索已经发布且允许公开访问的页面。该规则是搜索架构的硬性数据保护边界，不是仅由前端隐藏结果的展示规则。

必须满足：

- 全新创建但尚未发布的页面不得进入前台搜索结果。
- MongoDB `blog_page_revision_bodies` 中的草稿和历史正文不得写入公开内容索引。
- 已发布页面产生新草稿时，搜索继续使用上一次正式发布的正文；新草稿中的词在再次发布前不得被搜索到。
- 页面再次发布后，搜索索引才能切换到新正式正文。
- 页面取消发布或删除后，公开索引必须最终删除对应文档；同步延迟必须可监控、可补偿。
- 受 Wagtail 访问限制保护的页面不得因为 Elasticsearch 直接查询而绕过 `public()` 边界。
- 搜索 API、HTML 页面、缓存和搜索建议都必须遵守同一公开范围，不能只在模板层过滤。

Elasticsearch 可以暂时物理保存带 `live=false` 的 Wagtail 通用索引文档，但前台查询必须强制过滤；长期独立内容索引则只写入可公开搜索的正式发布版本，减少空间并降低误查询风险。

## 5. 当前真实数据流

### 5.1 保存和发布

```text
Wagtail 编辑器 StreamField
  │
  ├─ 保存草稿
  │    ├─ MongoDB blog_page_revision_bodies 写正文
  │    └─ MySQL Revision 只保存 mongo_draft_pointer 和空 body
  │
  └─ 保存/发布正式页面
       ├─ MongoDB blog_content 写正式正文
       ├─ MySQL BlogPage 保存元数据和 mongo_content_id
       └─ Wagtail 自动更新 Elasticsearch
```

`BlogPage.body_text` 在建立索引时调用 `get_full_text_for_search()`，后者按 `mongo_content_id` 从 MongoDB 读取正文、去除 HTML 和部分 Markdown 标记，再把纯文本交给 Wagtail Elasticsearch 后端。

### 5.2 搜索请求

```text
浏览器
  └─ search view/API
       └─ perform_search()
            ├─ MySQL/Wagtail QuerySet 先应用 live().public()
            ├─ QuerySet.search() 将公开范围交给搜索后端
            └─ 结果格式化前仍由 QuerySet 保持公开对象范围
```

搜索请求不读取 MongoDB 正文。MongoDB 只在索引构建、页面详情、编辑和 Revision 恢复时读取。公开搜索入口不再使用同一 Elasticsearch 后端的伪降级链路；搜索后端异常返回明确不可用状态。

### 5.3 当前搜索字段

| 业务字段 | Wagtail 定义 | ES 物理字段 | 用途 |
| --- | --- | --- | --- |
| 标题 | `SearchField(title, boost=10)` | `title` | 全文和短语搜索 |
| 简介 | `SearchField(intro, boost=5)` | `blog_blogpage__intro` | 全文和短语搜索 |
| 正文 | `SearchField(body_text, boost=2)` | `blog_blogpage__body_text` | 全文和短语搜索 |
| 标题补全 | `AutocompleteField(title)` | `title_edgengrams` | 仅供 `.autocomplete()` |
| 日期 | `FilterField(date)` | `blog_blogpage__date_filter` | 日期过滤 |
| 标签 | `FilterField(tags)` | `blog_blogpage__tags_filter` | 精确过滤 |
| 分类 | `FilterField(categories)` | `blog_blogpage__categories_filter` | 精确过滤 |

## 6. AutocompleteField 专项结论

### 6.1 官方语义

Wagtail 官方文档将 `AutocompleteField` 定义为逐字输入时的部分词匹配字段，并要求通过 QuerySet 的 `.autocomplete()` 方法查询。官方同时明确：普通 `.search()` 不应承担部分词自动补全，自动补全也不适合作为普通全文搜索替代品。

官方参考：

- https://docs.wagtail.org/en/stable/topics/search/indexing.html
- https://docs.wagtail.org/en/stable/topics/search/searching.html

### 6.2 Wagtail 7.4.2 实际实现

本机安装的 Wagtail 7.4.2 将搜索实现委托给 `modelsearch`。源码确认：

- `AutocompleteField` 与 `SearchField` 是两种独立字段类型。
- Elasticsearch 字段名自动增加 `_edgengrams` 后缀。
- 每个 `AutocompleteField` 的值既写入专用字段，例如 `title_edgengrams`，也写入全局 `_edgengrams`。
- `edgengram_analyzer` 使用 edge-ngram，当前范围为 1 到 15 个字符。
- `.autocomplete()` 默认查询 `_edgengrams`；指定字段时查询对应的 `*_edgengrams` 字段。
- 普通 `.search()` 和项目当前原生 DSL 不查询这些字段。

### 6.3 当前项目是否使用

仓库中只有一处 `AutocompleteField('title')` 声明，没有任何 `.autocomplete()` 调用。当前前端搜索建议调用 `get_search_suggestions()`，它查询的是 Wagtail `Query` 历史搜索词表，并使用 MySQL `query_string__icontains`。

因此当前 `AutocompleteField('title')`：

- 不参与全文查询。
- 不参与当前搜索建议。
- 不参与当前 API 返回。
- 会增加 `title_edgengrams` 和 `_edgengrams` 索引内容。
- 删除后需要重建 ES 索引，但不需要 Django schema migration，也不会修改 MongoDB 正文。

### 6.4 决策

建议在第一阶段删除 `AutocompleteField('title')`，前提是先增加回归测试证明仓库和实际页面没有调用 `.autocomplete()`。

未来如需“按文章标题逐字补全”，不要无条件恢复到主正文索引。优先选择：

1. 使用独立的小型标题建议索引，只存 `page_id`、标题、热度和发布状态。
2. 只收录热门或近期标题，限制建议语料规模。
3. 搜索历史热门词继续放 Redis/MySQL，不与文章正文索引混合。
4. 确认确实需要 Wagtail `.autocomplete()` 时，才恢复 `AutocompleteField`。

第三方 `wagtail-autocomplete` 库是 Wagtail 后台页面/片段选择器组件，不是当前全文搜索 `AutocompleteField` 的替代实现，不能用于判断是否保留本字段。

## 7. 当前实现的主要问题

### 7.1 公开搜索范围和降级边界

WP1 起，`perform_search()` 统一从 `Page.objects.live().public()`、`BlogPage.objects.live().public()` 或其等价 QuerySet 开始。WP2 仍先调用 Wagtail `.search()` 取得实际 QuerySet 编译器的内容类型、访问限制和日期过滤条件，再以相同过滤条件执行加权 ES 查询；ES 返回的页面 ID 必须再次通过原始 `.live().public()` QuerySet 回查，成功回查后才允许挂载标题、URL 或高亮片段。

Elasticsearch 不可用时不再调用同一后端的第二种查询方式，也不返回空数组伪装为“零结果”。HTML、AJAX 和 JSON API 返回明确的不可用状态；搜索词统计失败则只记录警告，不影响已经取得的搜索结果。

### 7.2 深分页边界

当前公开入口使用 Wagtail 搜索 QuerySet，并在 HTML 和 API 入口统一拒绝超过 10,000 条结果窗口的请求。不存在“翻到几十万页仍保持恒定成本”的承诺。

Elasticsearch 官方指出：深分页会让每个分片保存当前页和之前页面的命中数据，可能导致性能下降或节点故障；超过 10,000 条应使用 `search_after`，需要稳定快照时配合 PIT。

参考：

- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/paginate-search-results.html
- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/point-in-time-api.html

### 7.3 重复计数

WP2 的高亮结果对象对同一个质量查询只缓存一次精确总数，分页查询复用同一 query、filter 和 sort；Paginator 的总数与当前页查询仍是必要的两次 ES 读取，但不存在旧实现中独立、条件可能漂移的 `_count` 与 `_search` 组合。

### 7.4 WP2 安全高亮和查询质量

公开查询使用标题、简介和正文的实际 SearchField 映射及权重；短语命中额外加权，`minimum_should_match` 按查询词数采用 `100%`、`75%` 或 `60%`。ES 仍保持 `_source=False`，只读取 Page ID 和高亮片段，不回传完整正文。

高亮字段仅限标题、简介和正文；标题返回完整命中值，简介/正文每字段最多 3 个、目标 160 字符的片段。ES 以每次请求生成的内部标记包裹命中词，服务端随后去除原始 HTML、转义全部文本，只替换本次服务端标记为 `<mark>`；模板和 API 因此不会信任 Mongo Markdown、ES `_source` 或任意原始 HTML。

正文高亮请求设置 `max_analyzed_offset=100000`。若 ES 仍报告分析上限错误，应用写出 `search_highlight_body_offset_exceeded` 结构化告警，Filebeat 可据此聚合超限指标。`SEARCH_HIGHLIGHTS_ENABLED=false` 可在不触碰 MySQL、MongoDB 或 ES 索引的情况下回退到 WP1 的公开搜索和原摘要展示。

### 7.5 索引内容重复

Wagtail 映射确认：

- `body_text` 写入 `blog_blogpage__body_text`。
- 同一正文通过 `copy_to` 再进入 `_all_text`。
- 同一正文因 boost=2 再进入 `_all_text_boost_2_0`。
- 标题和简介也存在对应聚合字段副本。
- `_source` 默认保存原始 JSON。
- 标题补全又生成 `title_edgengrams` 和 `_edgengrams`。

这些结构是 Wagtail 通用搜索后端为 `.search()`、字段权重和 `.autocomplete()` 提供的兼容能力，但项目当前原生 DSL 只查询独立字段，未充分使用聚合字段和 edge-ngram。

### 7.6 MongoDB Revision 索引缺失

代码在读取最新草稿时使用：

```text
find({page_id}).sort({created_at: -1}).limit(1)
```

生产集合目前只有 `_id` 索引，没有设计文档中声明的 `(page_id, created_at)` 复合索引。Revision 增长后会发生扫描和内存排序。

### 7.7 全量重建存在 Mongo N+1

Wagtail `update_index` 遍历 Page，每个 `BlogPage.body_text` 都单独请求一次 MongoDB。当前约一千篇可以接受；一千万篇意味着一千万次 Mongo 往返，不能作为未来的重建方式。

### 7.8 搜索同步缺少持久补偿

正式正文先写 Mongo，再保存 MySQL，随后依赖 Wagtail 自动更新 ES。任一阶段失败都可能出现：

- MySQL 指针存在但 Mongo 正文缺失。
- Mongo 已更新但 ES 仍是旧正文。
- 页面已取消发布或删除，但 ES 文档尚未移除。
- ES 恢复后没有持久待处理记录可自动补偿。

### 7.9 搜索建议扩展性不足

当前建议词从 MySQL `Query.query_string` 使用 `icontains` 获取。随着历史搜索词增长，该查询会逐渐变慢，也无法自然处理中文前缀、拼音、热度衰减和去污策略。

### 7.10 搜索缓存失效边界不完整

搜索结果缓存 TTL 为 5 分钟，但页面发布、取消发布、删除、标签和分类变化没有明确清除对应搜索缓存。短暂陈旧可以接受，但必须被定义为产品行为而不是偶然结果。

## 8. 目标架构

### 8.1 总体拓扑

```text
                       ┌──────────────────┐
编辑/发布请求 ────────►│ Django / Wagtail │
                       └───────┬──────────┘
                               │
                  ┌────────────┼─────────────┐
                  ▼            ▼             ▼
             MySQL 元数据   MongoDB 正文   Search Outbox
                                              │
                                              ▼
                                      Celery maintenance
                                              │
                                              ▼
                                  Elasticsearch 内容读模型
                                              │
搜索请求 ──────────────────────────────────────┘
```

### 8.2 数据权威性

| 数据 | 权威来源 | 是否可重建 |
| --- | --- | --- |
| 页面树、状态、权限 | MySQL | 否，必须备份 |
| 正式正文、草稿正文 | MongoDB | 否，必须备份 |
| 搜索索引 | Elasticsearch | 是，可从 MySQL + MongoDB 重建 |
| 搜索缓存 | Redis | 是，可过期重建 |
| 搜索同步 outbox | MySQL | 否，完成前必须持久保存 |

### 8.3 内容搜索索引

长期建议建立独立于 Wagtail 通用索引的精简内容索引，并通过读写别名管理版本：

```text
wagtailblog-content-read  ──► wagtailblog-content-v003
wagtailblog-content-write ──► wagtailblog-content-v003
```

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `page_id` | keyword/long | 与 MySQL Page 主键对应 |
| `content_version` | long | 每个页面公开搜索状态的单调递增版本，用于幂等更新和失步检测 |
| `content_hash` | keyword | 正式发布内容的稳定 hash，只用于完整性校验，不承担版本排序 |
| `title` | text | 标题搜索，最高权重 |
| `intro` | text | 简介搜索，中等权重 |
| `body_text` | text | 正文全文搜索 |
| `date` | date | 日期过滤和排序 |
| `live` | boolean | 发布过滤 |
| `searchable` | boolean | 是否允许进入公开结果；tombstone 固定为 false |
| `locale_id` | integer | 多语言过滤 |
| `tag_ids` | integer array | 标签过滤 |
| `category_ids` | integer array | 分类过滤 |
| `updated_at` | date | 诊断和同步核验 |

不建议放入内容索引：

- 完整 StreamField JSON。
- 图片、文档和媒体元数据全集。
- Revision 正文。
- 页面渲染 HTML。
- 用户权限详情或敏感字段。
- 与前台搜索无关的 Wagtail 后台字段。

#### 8.3.1 生产运行时命名空间不变量

生产复用现有 Elasticsearch 单节点时，`CONTENT_SEARCH_PRODUCTION_*` 只定义受控生产目标和
门禁；前台查询、影子查询、Producer/Consumer 及 read alias 实际读取的是通用
`CONTENT_SEARCH_*` 键。两组键不能只配置其中一组，否则 Django 会把缺失的通用键回退为测试安全
默认值，造成预检与实际 alias 操作指向不同命名空间。

生产 `.env.production` 在任何独立内容搜索功能开启前，必须同时满足以下等式：

```ini
CONTENT_SEARCH_PRODUCTION_CONNECTION_NAME=content_production
CONTENT_SEARCH_CONNECTION_NAME=content_production
CONTENT_SEARCH_PRODUCTION_INDEX_PREFIX=wagtailblog-prod-content
CONTENT_SEARCH_INDEX_PREFIX=wagtailblog-prod-content
CONTENT_SEARCH_READ_ALIAS=wagtailblog-prod-content-read
```

其中连接 URL、认证信息和备份目录继续只保存在受保护的生产环境文件，不能写入本文或 Git。
`load_dotenv(..., override=False)` 不会覆盖 systemd 或交互 shell 已继承的变量，因此生产管理命令
必须在干净环境中运行，且切换前要核对 unit 的 `EnvironmentFile`、主进程白名单环境变量和
`.env.production` 三者。运行时任一独立搜索开关为 true 时，应用启动会拒绝连接名、索引前缀或
read alias 不一致的配置，宁可保持旧搜索，也不允许静默访问测试命名空间。

### 8.4 分词策略

当前所有 text 字段默认使用 `ik_max_word` 建索引、`ik_smart` 查询。`ik_max_word` 对正文产生更多词项，有利于召回但增加索引空间和噪声。

建议先在测试索引进行 A/B 基准：

| 字段 | 候选索引 analyzer | 查询 analyzer | 原因 |
| --- | --- | --- | --- |
| `title` | `ik_max_word` | `ik_smart` | 标题短，最大召回成本可控 |
| `intro` | `ik_max_word` 或 `ik_smart` | `ik_smart` | 根据评测集决定 |
| `body_text` | 优先测试 `ik_smart` | `ik_smart` | 降低正文词项膨胀 |

不能只根据磁盘大小切换 analyzer。必须比较：

- Recall@10
- Precision@10
- MRR
- NDCG@10
- 零结果率
- 索引大小
- 建索引速度
- P50/P95/P99 查询延迟

### 8.5 精确定位与高亮

第一阶段采用文章级文档，不把每个段落拆成独立 ES 文档。搜索结果由 ES 返回：

- `page_id`
- `_score`
- 标题命中片段
- 简介命中片段
- 正文 1-3 个命中片段

建议使用 `unified` highlighter，并限制：

- 每字段最多 3 个片段。
- 每片段约 120-180 字符。
- 固定 `<mark>` 或内部占位标记。
- 返回前先转义原文，只允许服务端生成的高亮标记，防止正文 HTML 造成 XSS。
- 超长正文设置合理的高亮分析上限，并记录被截断指标。

如果未来必须定位到具体 StreamField block，再增加可选的 `body_sections` 结构，包含 `block_id`、`block_type`、`order` 和纯文本。该方案会增加文档和映射复杂度，必须在文章级高亮不能满足需求时再实施。

### 8.6 搜索同步 outbox

Outbox 必须被视为 MySQL 到 Elasticsearch 搜索读模型的持久投影日志，Celery 消息只负责唤醒消费者，不能作为唯一事实来源。建议使用三个逻辑对象：

- `ContentSearchState`：每个 `page_id` 一行，保存当前单调 `content_version`、期望操作、正式正文 hash 和公开状态；页面删除后仍保留最小状态行，防止迟到的旧 upsert 复活已删除文档。
- `ContentSearchOutbox`：保存一次公开搜索状态变更，唯一约束为 `(page_id, content_version)`。
- `ContentSearchDelivery`：保存一个事件向一个索引目标的投递状态；正常时期只有当前生产目标，重建期间同时存在旧目标和新目标。

`ContentSearchOutbox` 最少包含：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 全局唯一事件 ID，用于审计和日志关联 |
| `page_id` | Page 主键 |
| `operation` | upsert/delete |
| `content_version` | 页面公开搜索状态的单调递增整数，不能使用时间戳或 hash 代替 |
| `content_hash` | 正式发布内容的稳定 hash；delete 可为空 |
| `status` | pending/processing/retry/succeeded/superseded/dead |
| `attempts` | 重试次数 |
| `available_at` | 下次允许执行时间 |
| `locked_by/lock_expires_at` | Worker 租约持有者和过期时间 |
| `last_error_code` | 脱敏错误分类 |
| `created_at/updated_at` | 审计时间 |

`ContentSearchDelivery` 最少包含 `event_id`、`target_id`、`status`、`attempts`、`available_at`、租约字段和最后错误分类，并对 `(event_id, target_id)` 建唯一约束。目标是具体的集群和物理索引代号，不能只记录可能在处理中被切换的别名。

#### 8.6.1 版本生成与事务边界

`content_version` 必须由 MySQL 在页面级锁或原子更新下递增。版本代表公开搜索状态的先后顺序，以下操作都必须生成新版本：

- 首次发布。
- 再次发布正式正文或公开元数据。
- 取消发布。
- 从公开范围变为受限访问，或从受限恢复公开。
- 删除页面。

正文 hash 只能判断内容是否相同，不能判断事件先后；时间戳也可能因精度、时钟或并发而重复，因此都不能替代单调版本。

发布流程：

1. 正文成功写入 MongoDB。
2. 在保存页面公开状态的同一个 MySQL 事务内，锁定或原子递增 `ContentSearchState.content_version`，同时写入 Outbox 事件。
3. `transaction.on_commit()` 只向 `maintenance` 队列发送唤醒任务；即使进程在提交后、发送 Celery 消息前崩溃，Beat 扫描仍能发现 MySQL 中的 pending 事件。
4. `maintenance` Worker 读取 `ContentSearchState`、MySQL 页面元数据和 Mongo 正式正文，不读取 Mongo Revision 草稿集合。
5. 生成规范化搜索文档，并再次核对 `content_version` 和 `content_hash`；构建期间如果页面已产生新版本，当前事件直接进入 `superseded`。
6. 使用 `page_id` 作为 ES `_id`，以目标文档中的 `content_version` 做条件 upsert。
7. 只有目标 ES 确认成功后，才把对应 Delivery 标记完成；所有强制目标完成后，Outbox 才进入 `succeeded`。

不得在 MySQL 页面事务提交后才创建 Outbox 行，否则应用进程可能在两步之间死亡，形成没有任何补偿记录的永久失步窗口。

#### 8.6.2 至少一次消费与 Worker 崩溃恢复

消费者采用数据库租约，而不是依赖 Celery 的“恰好一次”假设：

1. Worker 使用短事务和 `SELECT ... FOR UPDATE SKIP LOCKED` 领取到期的 pending/retry Delivery。
2. 领取时写入 `processing`、`locked_by` 和 `lock_expires_at`，随后立即提交领取事务，再执行 Mongo 读取和 ES 请求。
3. 长批次必须续租；租约到期但未完成的记录由 Beat 重新放回 retry。
4. 429、超时、连接失败和 ES 5xx 使用带随机抖动的指数退避。
5. Worker 在“ES 成功、MySQL 尚未标记成功”之间崩溃时，租约到期后会重复投递；重复操作必须返回成功或 noop。
6. Worker 在 MySQL 已标记成功、Celery 消息尚未 ack 时崩溃，重投任务只会发现没有可领取记录。

如启用 Celery `acks_late` 和 Worker lost 重投，它们只是缩短恢复时间；MySQL 租约、Beat 扫描和唯一约束才是最终恢复保证。任务不得长时间持有数据库事务或行锁执行 Mongo/ES 网络请求。

#### 8.6.3 旧版本、删除和 tombstone

旧事件不属于死信。处理前后发现 `event.content_version < ContentSearchState.content_version` 时，应标记为 `superseded`，它是正常终态，不增加 dead 告警。

ES 侧必须满足：

- 目标文档不存在，或事件版本大于当前版本时才应用变更。
- 版本相等且内容 hash/操作相同，视为重复成功。
- ES 已有更高版本时，当前 Delivery 记为 `superseded`。
- ES 返回版本冲突时读取最小版本字段判定上述三种情况，不能无条件重试到死信。

推荐 Bulk index 使用 `version=content_version` 和 `version_type=external`。`external` 只接受严格高于现存版本的写入；相同版本重投会返回 409，消费者随后用最小字段读取核对 hash 和操作并归类为重复成功。不要使用 `external_gte`，因为它允许相同版本再次覆盖，在版本生成缺陷或载荷不一致时会掩盖数据错误。

取消发布和删除建议写入轻量 tombstone 文档：保留 `page_id`、`content_version`、`searchable=false` 和必要审计字段，不保留标题、简介或正文。公开查询始终过滤 `searchable=true`。不能只依赖 ES delete 的内部版本墓碑，因为 `index.gc_deletes` 保留期过后，迟到的旧 upsert 可能重新创建文档。

tombstone 可在下一次从权威数据全量构建新物理索引时自然消失；删除旧 tombstone 前必须确认相关旧 Outbox/Delivery 已进入终态，并且不会再向该索引投递。

参考：

- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/docs-index_.html
- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/docs-delete.html

#### 8.6.4 重试、死信与积压隔离

错误必须分类处理：

| 情况 | 处理 |
| --- | --- |
| 旧版本、重复版本 | `superseded` 或 `succeeded`，不进入死信 |
| ES 429、5xx、超时、临时断连 | retry，指数退避并保留抖动 |
| Mongo 临时不可用 | retry，不用空正文覆盖已有文档 |
| live 页面正式正文永久缺失 | dead，作为主数据完整性事件告警 |
| mapping 400、规范化程序错误 | dead，修复代码或 mapping 后显式重放 |
| 单个目标不可用 | 只重试该 Delivery，不重复轰击已经成功的目标 |

达到最大自动重试次数后才进入 `dead`。Dead 记录不得自动删除，必须保留事件、目标、版本和脱敏错误分类；重放必须创建新的审计动作或显式重置 Delivery，不得直接伪造 `succeeded`。

同一页面的坏事件不能阻塞更新版本：消费者可先处理最新版本，旧版本随后进入 `superseded`。一致性检查必须报告 dead、版本落后和 tombstone 异常，即使队列总体 pending 已清零。

#### 8.6.5 Outbox 收敛条件

Outbox “已追平”不能只看 pending 数为 0，必须同时满足：

- 当前强制目标没有 pending、processing、retry 或 dead Delivery。
- processing 均未超过租约；不存在持续被回收的热点事件。
- `oldest_pending_age` 低于门禁阈值并连续稳定两个检查周期。
- ES 中每个抽检或全量核对的 `content_version` 不低于 `ContentSearchState` 期望版本。
- 公开文档数、tombstone 数以及缺失、陈旧、多余文档数符合预期。

Beat 负责扫描未被 Celery 唤醒的 pending、租约超时和失败项进行补偿，继续使用现有 `maintenance` 队列，不能新增只消费 `default` 或 `email` 队列的 Worker。

### 8.7 Wagtail 默认索引的处理

不能直接全局关闭 `AUTO_UPDATE`，因为 Wagtail 默认索引还可能服务页面管理、图片、文档和其他 chooser。

演进顺序：

1. 保留现有 `default` Wagtail 后端。
2. 建立独立内容索引和别名。
3. 仅让前台博客搜索切换到独立内容索引。
4. 验证 Wagtail 后台各类搜索和 chooser 后，再决定是否缩减默认 Page 索引。
5. 如需关闭某个后端的自动更新，只对明确的独立后端执行，不影响其他 Wagtail 索引。

## 9. 搜索查询设计

### 9.1 相关性查询

保留当前思想，但改为显式、可测试的字段配置：

```text
title match_phrase       boost 100
intro match_phrase       boost 50
body_text match_phrase   boost 20
title multi_match        boost 10
intro multi_match        boost 5
body_text multi_match    boost 2
minimum_should_match     根据分词数动态配置
```

`75%` 不应永久硬编码。建议按词项数量分段：

- 1-2 个有效词：全部命中。
- 3-4 个有效词：至少命中 75%。
- 5 个以上有效词：根据评测集在 60%-75% 之间选择。

### 9.2 排序

- 默认按相关性 `_score` 排序，追加 `page_id` 作为稳定 tie-breaker。
- 日期排序使用 ES `date` + `page_id`，不要回退到同一个后端的另一套隐式排序。
- 搜索结果回查 MySQL 时继续使用 `Case/When` 保持 ES 顺序。

### 9.3 分页

短期：

- 保留 `from/size`，但 UI 明确限制可访问结果窗口。
- `_count` 后的当前页查询设置 `track_total_hits=False`。
- 对明显超出总页数的请求立即拒绝。

长期：

- 使用 `search_after`。
- 排序字段必须稳定且包含唯一 tie-breaker。
- 需要跨页一致性时使用 PIT，并在完成或超时后关闭。
- 前端改为上一页/下一页或游标模式；不要伪装成可随机跳转到任意百万页。

### 9.4 故障降级

推荐的降级行为不是对 Mongo 正文执行 regex 全库扫描，而是：

1. Redis 中已有的短期缓存结果可继续返回，并标记可能陈旧。
2. 对标题精确值、slug、日期和分类等结构化条件，可使用 MySQL 受限查询。
3. 全文搜索不可用时返回明确的暂时不可用状态，不返回“0 条结果”误导用户。
4. 监控触发告警，outbox 保留待同步项。

### 9.5 搜索建议

建议拆成两个概念：

- 热门搜索词：来自匿名化后的历史 Query 热度，放 Redis Sorted Set 或聚合表。
- 标题补全：来自独立标题建议索引，只返回公开页面标题。

必须配置：

- 最小输入长度。
- 返回数量上限。
- 请求防抖。
- 敏感词和个人数据过滤。
- 热度衰减。
- 对恶意搜索词不进入公开建议。

## 10. 容量模型

### 10.1 当前线性基线

按当前生产数据估算：

- Mongo 正式正文平均逻辑大小约 9.4 KiB/篇。
- Wagtail Page ES 主索引平均约 19.0 KiB/文档。

该估算只用于量级规划。Lucene segment 合并、删除文档、词典复用、字段长度、中文分词、`_source` 压缩和文档结构都会导致非线性变化。

| 文章数 | Mongo 正文逻辑量 | 当前结构 ES 主索引 |
| ---: | ---: | ---: |
| 10,000 | 约 92 MiB | 约 185 MiB |
| 100,000 | 约 0.90 GiB | 约 1.81 GiB |
| 1,000,000 | 约 9.0 GiB | 约 18.1 GiB |
| 10,000,000 | 约 90 GiB | 约 181 GiB |

一千万篇使用 1 个副本时，ES 数据约 362 GiB。再考虑 segment merge、重建双索引、translog、快照和至少 25%-30% 空闲空间，内容搜索集群应准备约 450-600 GiB 可用 SSD，而不是只按 181 GiB 配盘。

### 10.2 精简索引目标

独立内容索引应以测试结果为准，目标不是承诺值：

- 删除未使用 edge-ngram。
- 避免同一正文同时进入独立字段和多个 `_all_text*` 聚合字段。
- 只保留前台检索需要的过滤字段。
- 评估 `best_compression`。
- 评估正文使用 `ik_smart` 建索引。

合理的工程目标是较当前 Wagtail 通用 Page 索引减少 30%-50%，但必须用真实文章样本重建测试索引并测量，不能把目标当作事实。

### 10.3 内存和节点建议

Elasticsearch 官方建议 JVM 堆不超过节点可用内存的 50%，为文件系统缓存、off-heap 和 JVM 开销保留空间；官方常见分片容量区间为 10-50 GiB。

参考：

- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/advanced-configuration.html
- https://www.elastic.co/guide/en/elasticsearch/reference/8.19/size-your-shards.html

建议演进：

| 阶段 | 建议拓扑 | 内存建议 | 说明 |
| --- | --- | --- | --- |
| 当前至约 10 万篇 | 当前单节点可继续 | 主机 8 GiB，ES heap 1-2 GiB | 低 QPS 前提下运行，关闭不必要常驻服务 |
| 10 万至 100 万篇 | 独立 ES 节点 | 16 GiB，heap 4-8 GiB | SSD，按实测索引和延迟扩容 |
| 100 万至 1,000 万篇 | 独立 3 节点 | 每节点 16-32 GiB | 1 副本，分片 10-50 GiB，独立快照 |
| 超过 1,000 万或高 QPS | 专用集群 | 压测决定 | 分离内容搜索和日志分析负载 |

以下任一条件出现时，不应继续等待文章数阈值，应提前迁移：

- ES heap 持续高于 75%。
- old GC 出现持续增长或长停顿。
- 搜索 P95 超过 200 ms 且无法通过查询优化恢复。
- 主机 available memory 持续低于 1.5 GiB。
- 出现 swap 活跃换入换出。
- 单主分片接近 40-50 GiB。
- 索引重建所需双倍空间不足。
- ES、Kibana 或日志查询影响网站请求。

## 11. 分阶段实施计划

### 阶段 0：建立基准和评测集

目标：任何优化都有可比较证据。

工作：

1. 建立 100-500 条脱敏中文查询评测集。
2. 为每条查询标注期望 Top 10 文章和关键命中片段。
3. 记录当前 Recall@10、MRR、NDCG@10、零结果率。
4. 记录 P50/P95/P99 延迟、ES heap、GC、索引大小和构建速度。
5. 保存当前索引 mapping、settings、aliases、文档数和主分片大小。
6. 在测试环境验证索引可从 MySQL + MongoDB 完整重建。

退出条件：基准报告可重复执行，且不包含正文、凭据或个人数据。

### 阶段 1：低风险减法和正确性修复

目标：不改变搜索产品语义，先消除已确认的浪费。

候选变更：

1. 删除未使用的 `AutocompleteField('title')`。
2. 增加测试，确保搜索建议继续使用既有历史词链路。
3. 当前页 `_search` 设置 `track_total_hits=False`。
4. 修正文档中关于深分页、高亮和降级的错误描述。
5. 为 Mongo Revision 增加 `(page_id, created_at)` 复合索引。
6. 单节点业务索引将副本数调整为 0。
7. 评估 Kibana 改为按需启动。

注意：第 5-7 项涉及生产数据库索引、Elasticsearch 设置或服务运行方式，实施前必须独立说明备份、影响和回滚并再次确认。

退出条件：相关测试通过，测试索引重建成功，结果集与基准一致，生产无数据操作。

### 阶段 2：高亮和查询质量

目标：从“找到文章”升级为“找到文章里的实际命中内容”。

工作：

1. 给标题、简介和正文增加受限 highlighter。
2. API 和模板增加安全的命中片段字段。
3. 对 HTML、Markdown、代码、表格和中文标点做安全测试。
4. 让无结果、ES 不可用和非法分页返回不同状态。
5. 根据评测集调整动态 `minimum_should_match`。
6. 验证排序稳定性和多语言行为。

退出条件：高亮不产生 XSS，不泄露草稿，不返回非公开页面，相关性指标不下降。

### 阶段 3：持久化搜索同步

目标：ES 故障不阻断内容主数据保存，恢复后能够自动补齐。

工作：

1. 新增 `ContentSearchState`、`ContentSearchOutbox` 和按目标投递的 `ContentSearchDelivery` 模型及迁移。
2. 在发布、取消发布、访问范围变化和删除的 MySQL 事务内递增单调版本并写入幂等事件；`on_commit()` 只唤醒 Worker。
3. 使用现有 `maintenance` Worker 按数据库租约消费，Beat 扫描未唤醒、失败和租约超时事件。
4. 增加 ES 条件版本写入和轻量 tombstone，拒绝旧任务覆盖或复活新状态。
5. 将旧事件归类为 `superseded`，将可重试错误与真正 dead 事件分开。
6. 增加一致性管理命令，只报告缺失、陈旧、多余索引文档和异常 tombstone。
7. 修复或 dead 重放只在独立 `--confirm` 和用户明确授权后执行。

退出条件：模拟 ES 停机和 Worker 在各提交窗口崩溃后仍可安全保存主数据，ES 恢复后自动收敛，重复任务无副作用，旧版本不会进入 dead。

### 阶段 4：独立精简内容索引

目标：摆脱 Wagtail 通用 Page 索引的重复字段，同时保留 Wagtail 后台搜索。

工作：

1. 定义版本化 mapping 和 index template。
2. 创建测试版 `wagtailblog-content-v001`。
3. 实现批量 Mongo 读取，禁止逐篇 N+1 重建。
4. 批量写入 ES，记录成功、失败和耗时。
5. 对比 Wagtail 默认索引与精简索引的大小和搜索质量。
6. 创建并注册 `SearchIndexBuild` 目标，使增量 Delivery 同时投递旧索引和新索引。
7. 使用相同的条件版本协议执行全量回填，防止旧扫描结果覆盖较新的增量事件。
8. 前台执行影子双读，只记录差异，不改变用户结果。
9. 达到追平门禁后原子切换 `content-read` 别名，并在观察期继续双投递。
10. 保留旧索引至少一个观察周期，不立即删除。

退出条件：精简索引质量不低于基准，体积显著下降，别名回滚经过演练。

### 阶段 5：深分页和建议系统

目标：消除 10,000 窗口和 MySQL `icontains` 扩展瓶颈。

工作：

1. 使用 `search_after` + 稳定 tie-breaker。
2. 必要时引入短生命周期 PIT。
3. 前端分页改为游标协议。
4. 将热门搜索词聚合到 Redis Sorted Set 或专用聚合表。
5. 如需要标题补全，建立独立标题建议索引。

退出条件：超过 10,000 条结果仍能稳定继续浏览，游标不可伪造或跨查询复用。

### 阶段 6：独立集群迁移

目标：在内容规模和负载触发阈值前，把搜索从综合业务主机分离。

工作：

1. 根据真实索引大小和压测结果确定节点数、内存和磁盘。
2. 配置 TLS、最小权限认证和快照仓库。
3. 建立新集群索引和新集群内部别名。
4. 在 MySQL 注册新集群投递目标，由应用级投影器同时写旧、新集群；ES 别名不能跨集群双写。
5. 全量回填并持续追平新集群 Delivery。
6. 影子查询对比结果和延迟。
7. 切换应用读取目标或稳定代理地址，观察期内继续双集群投递。
8. 保留旧集群回滚窗口，门禁通过后再停止旧集群投递。

退出条件：新集群健康、快照可恢复、读写追平、回滚验证通过。

## 12. 全量重建方案

千万级索引禁止继续按每篇文章单次 Mongo 查询重建，也不能采用“扫完以后根据一个最大 Outbox 自增 ID 重放”的简化方案。MySQL 自增 ID 的分配顺序不等于事务提交顺序，长事务可能在基准点之后提交一个更小 ID；仅按 `id > high_watermark` 回放会漏事件。

### 12.1 构建状态和目标注册

建议新增 `SearchIndexBuild` 或等价持久状态，至少记录：

| 字段 | 说明 |
| --- | --- |
| `build_id` | 本次构建唯一 ID |
| `target_id` | 集群加物理索引的稳定目标 ID |
| `index_name` | 新物理索引名，不是可变化的读别名 |
| `mapping_version` | mapping/template 版本 |
| `status` | created/backfilling/catching_up/ready/serving/retired/failed |
| `checkpoint` | 最近完成的 MySQL 主键游标和批次统计 |
| `started_at/ready_at` | 审计时间 |

在线构建开始顺序：

1. 创建新物理索引并验证 mapping、analyzer 和写权限。
2. 在 MySQL 把新索引注册为 `backfilling` 投递目标；消费者每次领取时读取活动目标，不长期缓存目标列表。
3. 从目标注册成功这一刻开始，新领取的 Outbox 事件为旧目标和新目标分别创建唯一 Delivery。
4. 再开始全量扫描权威数据。

这个顺序形成明确覆盖：注册前已经提交且已经处理的变化会被后续全量扫描读到；注册后的变化会通过 Delivery 持续投递新索引；注册前已提交但尚未处理的变化，要么被全量扫描读到，要么在注册后被消费者投递，两条路径最终由 `content_version` 合并。

### 12.2 全量回填

推荐回填过程：

1. 从 MySQL 以主键游标分页读取 live/public 且允许公开搜索的 Page 元数据。
2. 每批收集 `mongo_content_id`。
3. MongoDB 使用 `_id: {$in: [...]}` 批量读取正文。
4. 在进程内构建 `mongo_content_id -> body` 映射。
5. 规范化为纯文本搜索文档。
6. 使用 ES Bulk API 批量写入新版本索引。
7. 记录批次 checkpoint、成功数、缺失正文数和失败原因。
8. 中断后从 checkpoint 恢复，不重头开始。

建议从 200-1,000 篇/批开始压测，根据平均正文大小和 ES bulk 响应调整。批次上限应同时受文档数和字节数约束，不能只按条数。

全量回填和增量消费者必须调用同一个文档规范化器和同一个 ES 条件版本写入函数。每个 bulk item 都携带权威 `content_version`：

- 回填扫描到 V10，而增量已写入 V11 时，V10 必须成为 noop/superseded，不能覆盖 V11。
- 回填先写 V10，增量随后写 V11 时，最终自然收敛到 V11。
- 页面在扫描期间取消发布或删除时，增量 V11 tombstone 必须压过回填 V10 正文。
- 页面在扫描期间由私有变公开或由公开变私有时，也按新版本和 `searchable` 状态收敛。

### 12.3 增量追平与切换

重建期间：

- 旧读别名继续服务线上搜索。
- 所有内容变化继续进入同一个 MySQL Outbox。
- 旧生产目标和新构建目标各自维护 Delivery，某一目标失败不会重复请求已成功的目标。
- 全量回填完成后，将构建状态改为 `catching_up`，继续消费新目标积压，不停止内容发布。
- 新索引通过门禁后，同集群使用单次 aliases API 原子切换读别名；跨集群使用应用读取目标或稳定代理切换，不能声称跨集群别名原子切换。
- 读切换后的观察期继续向旧、新目标双投递；确认无回滚需求后，才把旧目标改为非强制并停止生成新 Delivery。
- 不使用 `rsync --delete` 或直接覆盖 Elasticsearch 数据目录。

切换不要求停止前台搜索。只要新目标在注册后始终接受增量投递，数小时的全量回填不会产生增量丢失窗口。为避免切换瞬间漏写，新目标必须先进入活动投递集合，后进入读集合，最后才允许旧目标退出写集合。

Elasticsearch 同集群别名原子操作参考：https://www.elastic.co/guide/en/elasticsearch/reference/8.19/indices-aliases.html

### 12.4 切换门禁

新索引只有同时满足以下条件才能进入 `ready`：

- 全量扫描完成，checkpoint 覆盖最后一个目标 Page 主键，所有 bulk item 均有明确结果。
- 新目标没有 pending、processing、retry 或 dead Delivery，且租约超时数为 0。
- 新目标 Delivery 的最老年龄连续两个检查周期低于阈值。
- MySQL `ContentSearchState` 与新 ES 的版本一致性扫描无缺失、陈旧和错误复活文档。
- live/public 数量、locale/分类分布、tombstone 数和抽样正文 hash 符合预期。
- 影子查询的 Recall、排序、高亮、P95/P99 和错误率达到阶段门槛。
- 新旧读结果差异已分类，不能用“总数相近”替代逐版本一致性检查。
- 回滚切换已经在测试环境演练。

流量持续变化导致一次审计发生竞态时，应在双投递继续运行的情况下重复审计到稳定，不需要暂停公开搜索。若业务要求数学意义上的瞬时全量一致快照，则需要短暂冻结发布写入或使用跨 MySQL/Mongo 的可验证快照协议；当前架构没有跨库事务，不能虚假承诺这种强一致快照。

### 12.5 失败与恢复

- 回填进程崩溃：从 checkpoint 恢复；已成功批次通过条件版本写入保持幂等。
- 新目标持续失败：将构建标记 failed，停止为它创建新 Delivery；旧读别名和旧目标继续服务，不影响主数据保存。
- 切换后发现查询回归：读别名或读取目标切回旧索引；因为观察期仍双投递，旧索引仍保持最新。
- Dead Delivery 存在：禁止切换，先修复根因并显式重放。
- 放弃构建：保留构建报告和失败 Delivery；删除生产新索引仍属于外部数据操作，必须单独确认。

## 13. 一致性与数据保护

### 13.1 必须保持的约束

- Markdown 始终以 Markdown 字符串保存。
- `markdown_block` key 不变。
- Mongo `_id`、`mongo_content_id` 和 `mongo_draft_pointer` 不因索引升级改变。
- ES 文档只引用 `page_id` 和版本，不反向成为正文恢复来源。
- 草稿和未发布页面不得进入公开内容索引。
- 删除 ES 索引不等于删除业务正文，但仍需快照和确认。

### 13.2 一致性检查

只读检查至少报告：

- live BlogPage 数。
- 有效 `mongo_content_id` 数。
- Mongo 正式正文数。
- ES live 内容文档数。
- MySQL 指针缺失数量。
- Mongo 悬空正式正文数量。
- ES 缺失、陈旧和多余文档数量。
- outbox 和各投递目标的 pending/retry/dead/oldest age。

检查默认只返回数量和 ID，不输出完整正文。

## 15. 生产发布与切换

### 15.1 发布前门禁

- 明确本次只包含哪一个阶段，不把所有阶段一次发布。
- WSL2 测试通过。
- 本地、`origin/main`、GitHub `main` 和生产目标 commit 明确。
- 生产工作树干净，分支为 `main`。
- MySQL 和 MongoDB 备份完成并验证可读。
- ES snapshot 完成并验证状态。
- 新索引空间至少覆盖新旧双索引和 merge 余量。
- 确认 outbox、Worker、Beat 和 Filebeat 的影响范围。

### 15.2 推荐发布顺序

1. 发布兼容旧索引的应用代码。
2. 应用 Django migration，仅限已经授权的搜索同步状态、outbox、delivery 和 build schema。
3. 启动或重启 Django/uWSGI。
4. 重启 maintenance Worker。
5. 重启 Beat。
6. Filebeat 仅在配置变化时重启。
7. 创建新版本索引。
8. 全量回填。
9. 追平增量 outbox。
10. 执行影子查询和一致性检查。
11. 原子切换读别名。
12. 完成首页、搜索页、后台和服务健康检查。

任何 systemd unit、队列、环境变量、端口、索引器或服务变化都必须同步更新 `systemctl.md`。

### 15.3 回滚

应用回滚：恢复到上一个已验证 commit。

索引回滚：把读别名原子切回旧索引，不删除新索引。

同步回滚：暂停内容索引 Worker，保留 outbox，不能删除 pending 事件。

数据回滚：只有确认 MySQL migration 可逆且与 Mongo 指针兼容时才执行；绝不通过删除 Mongo 正文来回滚搜索。

服务恢复后重新执行：

- Django check。
- 四项项目服务 active/enabled。
- 首页、后台和搜索页检查。
- ES cluster health 和 alias 检查。
- outbox 积压和最老事件检查。
- Mongo/MySQL/ES 数量一致性检查。

### 16.3 同步链路

- 当前活动投递目标、构建状态、checkpoint、回填吞吐和预计剩余时间。
- 新旧目标 Delivery lag 差值和双投递失败率。
- Mongo 正文缺失数。
- ES 版本落后数。

## 18. 验收标准

### 18.1 阶段 1

- `AutocompleteField` 移除后现有前台搜索和建议结果不变。
- ES mapping 不再包含项目新增的标题 edge-ngram 数据。
- 当前搜索结果一致。
- 当前页查询不重复统计总命中数。
- Mongo 最新 Revision 查询使用复合索引。

### 18.2 高亮阶段

- 正文命中能显示安全片段。
- 标题、简介、正文短语权重符合评测集。
- 草稿和私有页面绝不出现在结果中。
- 已发布页面的新草稿在再次发布前不得改变公开搜索结果或高亮片段。
- 高亮不会执行正文 HTML 或脚本。

### 18.3 异步同步阶段

- ES 停机不损坏 MySQL/Mongo 主数据。
- ES 恢复后自动追平。
- 重复任务不会生成重复文档或旧内容覆盖。
- 删除和取消发布能够最终从公开索引移除。
- Worker 在 ES 写入前后任一崩溃窗口死亡，租约恢复后都能收敛。
- 旧版本和相同版本重复事件分别进入 `superseded` 或 `succeeded`，不产生错误 dead。
- Tombstone 能阻止迟到 upsert 复活已取消发布、私有或删除页面。
- Dead Delivery 可审计、可告警、可显式重放，并且不阻塞同页更新版本。

### 18.4 精简索引阶段

- 搜索质量不低于基准。
- 索引大小相对当前结构有可测量下降。
- 全量回填无 Mongo N+1。
- 重建期间增量变化持续投递到新旧目标，无基于自增 ID 提交顺序的漏事件窗口。
- 全量回填旧版本不能覆盖增量新版本，取消发布和删除在新索引中保持有效。
- 新目标达到版本、积压、dead、查询质量和性能门禁后才能切换。
- 别名切换和回滚均成功演练。
- Wagtail 后台搜索和 chooser 无回归。

## 19. 推荐决策

建议确认以下方向：

1. 保留 Elasticsearch，作为可重建的内容搜索读模型。
2. MongoDB 继续只保存正文，不恢复 Mongo `$text`、Jieba token 或 regex 全文扫描。
3. 第一阶段删除当前未使用的 `AutocompleteField('title')`。
4. 第一阶段修复重复计数和 Mongo Revision 复合索引缺失。
5. 第二阶段优先实现安全高亮，而不是立刻拆分段落文档。
6. 第三阶段建立持久 outbox，解决 ES 故障和索引失步。
7. 数据达到迁移阈值前建立独立精简内容索引和独立 ES 节点。
8. Kibana 改为按需运行的候选优化，但需要单独确认日志运维需求。
