# 搜索架构生产部署方案

## 1. 文档定位

本文是 `18816c9` 搜索架构测试方案提交的生产部署前方案，不是生产操作授权，也不表示已经连接、同步或修改生产环境。

本方案的第一目标是保护生产 BlogPage 正文、MongoDB 正文与草稿、Wagtail Revision、MySQL 关系数据、现有 Elasticsearch 索引和线上服务。所有会写入生产 MySQL、MongoDB、Elasticsearch、Docker、环境文件、alias 或 systemd 的步骤，均必须在对应步骤前单独确认。

当前状态：

- 测试代码已在本地 `main` 提交，精确 commit 为 `18816c9`。
- 本地 `main` 比 `origin/main` 领先 1 个 commit；当前未 push。
- 测试搜索回归、Django check、迁移检查和浏览器验证已经完成，证据保留在 `output/playwright/`。
- 生产状态、生产 HEAD、生产工作树、生产备份可恢复性和生产 Elasticsearch 容量尚未在本方案阶段核实。
- 目前不执行生产 SSH、Git 同步、migration、ES 创建、Mongo 读取回填、服务重启或 alias 操作。

## 2. 关键结论

### 2.1 代码同步和搜索启用必须分开

最安全的第一步只发布兼容代码，保持以下生产开关全部关闭：

```text
CONTENT_SEARCH_PRODUCER_ENABLED=false
CONTENT_SEARCH_CONSUMER_ENABLED=false
CONTENT_SEARCH_SHADOW_READ_ENABLED=false
CONTENT_SEARCH_QUERY_ENABLED=false
CONTENT_SEARCH_CURSOR_ENABLED=false
CONTENT_SEARCH_PIT_ENABLED=false
SEARCH_SUGGESTIONS_V2_ENABLED=false
SEARCH_POPULAR_SUGGESTIONS_ENABLED=false
SEARCH_TITLE_SUGGESTIONS_ENABLED=false
CONTENT_SEARCH_RECONCILE_ENABLED=false
```

这一步不创建新索引、不读取 Mongo 正文做回填、不写新 Elasticsearch、不改变前台搜索结果、不切换 alias。它仍然是生产代码变更，需要服务重启和线上验收，但不应与首次 migration、索引回填、读切换混在同一窗口。

### 2.2 当前代码不能直接执行生产索引写操作

当前 `search_create_content_index`、`search_rebuild_content_index`、`search_switch_content_alias` 和 `search_rollback_content_alias` 的确认写路径包含 `WAGTAILBLOG_ENV=test` 保护，设计上拒绝生产执行。这是正确的安全默认值，但意味着：

- 不能把测试命令直接复制到生产执行；
- 不能用修改环境变量或伪造 `test` 前缀绕过保护；
- 生产启用前必须新增经过审查的生产安全入口，或由经过授权的独立运维流程完成等价操作；
- 生产安全入口必须要求精确目标、精确索引名、生产前缀、备份证据和显式确认，并在日志中只记录摘要，不记录正文和凭据。

因此，`18816c9` 可以作为第一窗口的代码候选，但不能宣称它已经完成生产独立 ES 的创建、回填或切换。

### 2.3 生产独立 ES 单节点不是零风险

生产主机约 6 GB 内存时，旧 Elasticsearch、MySQL、MongoDB、Redis、MinIO、Django/uWSGI、Celery、Filebeat 和 Docker 共同竞争资源。新增一个 ES JVM 会增加常驻内存、文件缓存、segment merge 和 snapshot 开销。

测试中使用的单节点和内存参数只能作为原型参考，不能直接复制到生产。必须先读取生产当前内存、swap、磁盘、旧 ES heap、MySQL/Mongo 活动和 Docker 资源，再决定是否同机部署。若资源不满足，优先把新内容索引放到独立主机，而不是压缩生产数据库的安全余量。

## 3. 发布边界

### 3.1 本次方案覆盖

- 已验证 commit `18816c9` 的生产代码同步。
- `search.0001` 至 `search.0005` migration 的生产审核、备份、执行和验证流程。
- 生产独立 Elasticsearch 单节点的容量、网络、TLS、权限、快照和数据目录设计。
- 仅发布页面进入内容索引，草稿、历史正文、未发布和受限页面不进入公开搜索。
- Outbox、Delivery、Celery producer/consumer、回填、追平、影子查询、alias 切换和观察期。
- 应用、MySQL、ES、队列和索引的分层回滚。

### 3.2 本次明确不做

- 不删除或批量修改 MongoDB 正文、草稿、Revision pointer 或 `mongo_content_id`。
- 不重建现有 Wagtail 通用搜索索引，不删除旧索引，不修改日志索引。
- 不修改 Nginx、uWSGI socket、公开端口或生产域名，除非实际预检证明必要并另行授权。
- 不在同一窗口停止旧 ES、停止旧搜索、删除旧 alias 或删除旧数据。
- 不使用 `git pull`、`rsync --delete`、数据库 flush、反向 migration 或未核验的生产脚本。

## 4. 生产部署分阶段方案

### 阶段 P0：只读预检和冻结点

**目标**：确认真正的生产目标，建立部署前基线，不写任何生产资源。

必须记录：

- 服务器 IP、SSH 目标、生产目录、当前分支、当前 HEAD、remote 和工作树状态；
- 四个项目服务及基础设施服务的 active/enabled/failed 状态；
- 当前应用、Celery、Beat、Filebeat、Nginx、Docker 和旧 ES 的监听端口、socket、容器和 PID；
- `.env.production` 的存在、权限、`WAGTAILBLOG_ENV=production` 和生产 ES/Mongo/MySQL/Redis 目标名称；只输出变量名和脱敏摘要，不输出值；
- 内存、swap、磁盘、Docker 目录、旧 ES heap 使用率、旧 ES 磁盘使用量和 MySQL/Mongo 当前负载；
- 当前旧搜索首页、后台、博客搜索、建议接口和一条不敏感查询的 HTTP 基线；
- 当前 MySQL 搜索相关表是否存在，当前数据库 migration 版本；
- 当前 ES 集群名、版本、健康状态、旧索引 alias、文档数和磁盘占用。

预检必须停止的条件：生产目录脏、分支不是 `main`、remote 不匹配、目标 SHA 不明确、`.env.production` 缺失或权限不正确、旧服务已有故障、磁盘/内存余量不足、ES 健康异常、备份目录不可写或无法验证。

### 阶段 P1：备份、恢复证据和回滚点

**目标**：在任何生产 migration、ES 写入或服务配置变化前，形成可验证的恢复点。

备份顺序：

1. 记录部署前 commit、配置摘要、服务状态、索引状态和关键计数。
2. 执行 MySQL 一致性备份，至少覆盖整个生产业务库；不得只备份新 `search` 表，因为搜索状态与 BlogPage、Revision 和业务数据需要同一时间点解释。
3. 执行 MongoDB 生产数据备份或确认最近可恢复快照；搜索部署不得以“只读 Mongo”为理由跳过正文、草稿和 Revision 备份。
4. 为现有 Elasticsearch 配置或确认可恢复 snapshot，至少保存旧索引/alias 配置、mapping、settings、文档计数和占用摘要。
5. 保存生产项目代码和配置回滚目录，环境文件只做受保护备份，不进入 Git、日志或回复。
6. 对备份计算校验和、记录大小和完成时间，并在非生产位置做最小恢复验证；不能恢复验证的备份不能作为 Gate 通过证据。

备份失败、校验失败、恢复验证失败或备份与线上数据时间点不一致时，停止，不进入 migration。

### 阶段 P2：第一生产窗口，只同步兼容代码

**目标**：先让生产运行已验证代码，但保留旧搜索行为。

执行原则：

- 只部署精确的 `18816c9`，不部署未提交工作区内容；
- 生产仓库先 `git fetch origin --prune`，检查 `HEAD..origin/main` 文件清单和工作树，再使用 `git merge --ff-only`；
- 保留生产 `.env.production`、`logs/`、`media/`、静态目录、socket 和 PID；
- 所有新搜索开关保持 `false`，不配置生产 secondary ES，不创建 target/index/alias；
- 运行生产 Conda 的 `manage.py check`、静态文件检查和依赖导入检查；
- 代码涉及 Django、Celery、Beat 和日志采集入口时，按实际影响重启四个项目服务；Nginx 不因代码-only 变更自动重启；
- 重启顺序遵守基础设施确认后：Django/uWSGI → maintenance Worker → Beat → Filebeat。

窗口验收：四个服务 active/enabled、失败 unit 为空、首页/后台/博客搜索保持旧结果、Celery maintenance 可 ping、旧 ES 日志索引仍可读、无新增搜索 outbox 错误。验收通过后至少观察一个业务周期，再进入 P3。

这一阶段即使不执行 migration，也必须由生产负责人单独确认，因为它会替换运行代码并重启服务。

### 阶段 P3：生产 MySQL migration 独立窗口

**目标**：只建立搜索状态、事件、投递和构建状态表，不启用搜索写入或读取。

执行前：

- 再次确认 P1 备份完成；
- 在生产环境运行 `showmigrations search` 和 `migrate --plan`，确认只包含预期的 `search.0001` 至 `search.0005`；
- 评估 MySQL 版本、表锁、在线 DDL 能力、当前事务和低峰窗口；
- 记录执行者、开始时间、目标 migration、预计影响和终止条件。

执行后：

- 查询 migration 记录和新表结构、索引、唯一约束；
- 确认既有业务表行数、BlogPage、MongoDB 和 Revision 摘要未发生非预期变化；
- 运行 `manage.py check` 和旧搜索验收；
- 保持所有 producer/consumer/query/shadow/title flags 关闭。

默认回滚策略不是删除新表，也不是反向 migration，而是保持新表为空或仅有明确审计记录，关闭功能并回退应用代码。反向 migration 只有在单独证明兼容、无必要审计数据且再次授权后才考虑。

### 阶段 P4：生产独立 ES 单节点和安全边界

**目标**：建立与现有日志/通用 Wagtail ES 隔离的内容搜索集群。

推荐初始拓扑：

- 单节点、独立 cluster name、独立数据卷、独立 snapshot repository；
- 内容索引使用生产专属前缀，例如 `wagtailblog-prod-content-*`，绝不复用测试前缀或旧日志前缀；
- 内容服务账号只能访问内容索引和必要的 alias，不拥有集群管理、snapshot 删除或任意索引删除权限；
- 运维管理员账号单独保管，用于创建模板、快照和恢复；
- HTTP/transport 使用 TLS，证书私钥不进 Git，ES 端口只允许应用主机和运维来源访问，不直接暴露公网；
- 单节点初始副本数可为 0，但必须明确这是无高可用状态，节点故障时由旧搜索或恢复索引承担回退；
- heap、容器上限、磁盘水位和 CPU 配额以 P0 的实测资源决定，不直接照搬测试值。

必须先完成生产安全入口或人工运维 runbook。当前测试命令的 `WAGTAILBLOG_ENV=test` 写保护不得绕过；生产入口应支持预演、精确目标、幂等、审计摘要、失败保留现场和显式确认。

P4 只创建集群、证书、权限、快照仓库和空的版本化内容索引，不创建公开 alias，不接入前台，不回填 Mongo 正文。

### 阶段 P5：目标登记和空索引验证

**目标**：让应用知道新目标，但保持不可服务。

- 在 MySQL 登记唯一的生产 `ContentSearchTarget`，角色为 `building`，`enabled=false`，`required` 按双投递策略审慎设置；
- 创建精确物理索引和 mapping/template，索引写入仅在新 cluster；
- 创建标题建议索引时使用另一个物理索引和 alias，不与正文索引混用；
- 不切换 `CONTENT_SEARCH_READ_ALIAS`，不打开 `CONTENT_SEARCH_QUERY_ENABLED`；
- 执行只读集群预检、mapping 校验、空索引写入/删除测试和 snapshot 可见性检查。

如果 ES 创建成功但 MySQL target 登记失败，保留现场并记录索引名；不得自动删除以“清理”为名的证据。反过来也一样，不能让 enabled target 指向不存在的索引。

### 阶段 P6：Producer、Consumer 和在线回填

**目标**：在旧搜索继续服务期间建立新索引，并证明增量事件不丢失。

顺序：

1. 先确保新目标存在、索引可写、snapshot 已配置、migration 已完成。
2. 打开 producer，使发布、取消发布、删除和访问限制变更进入 Outbox；旧搜索继续照常服务。
3. 观察 Outbox 是否正常创建、是否有异常增长、事件版本是否单调，确认没有误读草稿或受限页面。
4. 打开 consumer，让 maintenance Worker 消费新目标 Delivery；旧索引仍保持原有服务和写入路径。
5. 以可暂停 checkpoint 运行生产回填。回填只读取公开发布页面和对应公开 Mongo 正文，使用批量 `$in` 读取，不做逐篇 N+1 查询；Bulk 失败保留 checkpoint，允许 resume。
6. 追平期间持续接收增量事件；只有连续满足无 pending/processing/retry/dead、State 与 ES 版本一致、公开页面数量一致，才把构建状态标记为 `ready`。

回填不是“执行一次命令就完成”。必须记录批次、checkpoint、速度、ES 429、Mongo 超时、MySQL 锁等待、Worker 重启、最老 Delivery 年龄和失败原因。

### 阶段 P7：影子查询和观察期

**目标**：读取新 ES 但不改变用户看到的结果。

- 只打开 shadow read，设置低采样率、超时、最大并发和熔断；
- 旧查询继续作为用户响应来源，新查询只用于比较延迟、Top N、缺失/额外结果、过滤边界和错误率；
- 对每个差异抽样核对 `page_id`、live/public、标题、正文版本、排序和高亮安全性；
- 影子请求超时、429、认证失败或连续错误不得拖慢旧搜索；
- 观察期间保留旧索引、旧 alias、旧代码回滚点、新索引和 snapshot。

影子查询只证明新目标质量，不构成读切换授权。质量差异未解释、公开边界不一致、Outbox 有 dead 或资源水位异常时，停止并回到旧搜索。

### 阶段 P8：前台读切换

**目标**：只把博客公开搜索切换到新内容索引。

必须单独满足 Gate 5：

- 新目标连续追平，无 pending/processing/retry/dead；
- 一致性检查无 missing/extra/hash mismatch/stale/wrong tombstone；
- 发布、取消发布、删除、访问限制和旧版本不会泄漏；
- 高亮转义、代码、公式、标题渲染无回归；
- 新旧结果质量差异已人工确认，延迟和错误率达预设阈值；
- 回滚命令经过测试并由现场人员确认；
- 生产负责人在切换前再次授权。

采用原子 alias 切换；不删除旧 alias、不停旧索引、不关闭旧搜索写入。若 ES alias 已切换而 MySQL 状态更新失败，保留现场，优先按 alias 实际状态和应用开关回退，不重复盲目执行。

### 阶段 P9：观察期和停止旧目标

**目标**：在证据充分后再释放资源。

观察期建议至少覆盖一个完整业务周期，并包含发布、取消发布、删除、访问限制变更、Worker 重启、ES 重启和备份检查。只有无回滚事件、资源稳定、质量稳定、旧目标保留期限明确且再次授权，才考虑停止旧目标写入。

停止旧 ES、删除旧索引、删除旧 alias、删除旧 Delivery 或删除 snapshot 都是独立的不可逆/难恢复操作，不属于首次部署默认步骤。

## 5. 回滚矩阵

| 故障范围 | 首选动作 | 不做的动作 |
| --- | --- | --- |
| 代码启动失败 | 恢复上一已验证 commit，按受影响服务重启 | 不删除新 migration 表 |
| 前台新搜索错误 | 关闭 `CONTENT_SEARCH_QUERY_ENABLED` 或恢复旧 read alias | 不删除新索引 |
| 新 ES 不可用 | 保持旧搜索服务，停止 shadow/query，保留 Outbox/Delivery | 不把新索引当作唯一数据源 |
| Worker/ES 写入失败 | 关闭 consumer 或暂停目标，保留 pending/retry/dead，修复后精确重放 | 不批量把 pending 改成 succeeded |
| 回填中断 | 使用 build checkpoint/resume，先查版本和失败原因 | 不从头覆盖、不删除 Mongo 正文 |
| alias 切换异常 | 依据实际 alias 状态原子切回旧目标，或关闭新查询 | 不连续重复切换掩盖状态不一致 |
| migration 后发现问题 | 默认回退应用代码并关闭功能，保留新表供审计 | 不未经评估执行反向 migration |
| 新 ES 节点损坏 | 从独立 snapshot 恢复，期间使用旧搜索 | 不删除唯一 snapshot 或旧索引 |

任何回滚后都必须重新执行 Django check、四个服务状态、首页/后台/搜索、旧 ES、Redis/Worker、Beat 和日志链路检查。

## 6. 主要风险与控制措施

| 风险 | 等级 | 控制措施 | 停止条件 |
| --- | --- | --- | --- |
| 6 GB 主机新增 ES JVM 导致 OOM | 高 | P0 读取实际内存；限定 heap/容器；设置磁盘和 heap 水位告警；必要时改独立主机 | OOM、swap 激增、MySQL/Mongo 延迟异常 |
| migration 锁住业务表 | 高 | 低峰执行、先看 plan 和活动事务、分批/在线 DDL 评估 | 锁等待影响线上请求 |
| 生产新旧索引前缀混用 | 高 | 固定生产前缀、精确名称校验、禁止通配符 | 目标或 alias 指向非生产索引 |
| 草稿/受限页面进入索引 | 高 | producer、回填和查询均使用公开边界；返回前 MySQL `live().public()` 复核 | 发现任意非公开 page_id |
| Mongo 批量回填造成压力 | 高 | 批量 `$in`、限速、checkpoint、观察 Mongo 慢查询和连接数 | Mongo 延迟、连接池耗尽或错误率上升 |
| Outbox/Delivery 重复、乱序或死信 | 高 | 唯一约束、租约、external version、tombstone、Beat 补偿、按目标独立重试 | dead 增长、版本回退、最老事件超阈值 |
| ES Bulk 429 或 merge 抢资源 | 中高 | 批大小/字节上限、退避、refresh interval、回填低峰执行 | 429 持续、heap/disk 水位恶化 |
| alias 切换后质量下降 | 高 | 影子查询、人工确认、保留旧目标和一键回滚 | Top N 差异无法解释或零结果率上升 |
| TLS/权限/快照配置错误 | 高 | 最小权限账号、独立管理员入口、严格 TLS 预检、先恢复演练 | 应用账号可删除索引或 snapshot 不可恢复 |
| 代码回滚与 migration 不匹配 | 中高 | migration 默认保留；旧代码先验证可忽略新表；禁止直接反向迁移 | 旧代码启动时查询失败或 schema 不兼容 |
| Celery 服务重启造成积压 | 中 | 先确认队列、优雅重启、观察 maintenance worker 和 Beat | 消费停止、任务重复或积压持续上升 |
