# 搜索架构生产备份与恢复手册

> 当前环境事实（2026-08-12）：Windows 主机为 `192.168.20.1`；测试为 WSL2 `Debian` 虚拟机 `192.168.20.5`；生产为 Hyper-V 第一代虚拟机 `192.168.20.2`（`ziliao`），不是 WSL。所有生产恢复命令只在 `192.168.20.2` 执行。

> 当前搜索恢复边界：生产代码为 `05a4a9b38b087379cefef46d86a5226673bfbe18`，`search.0001` 至 `search.0005` 已应用，`wagtailblog-prod-content-v001` 已完成回填并正在影子观察；前台仍是旧 Wagtail 搜索。旧索引、Mongo 正文/草稿、revision pointer 与快照均不得因搜索问题自动删除。发生新搜索故障时，优先关闭 shadow 或 query feature flag，保留 MySQL 搜索审计表和 ES 物理索引供核对。

## 1. 使用范围

本文用于搜索架构生产部署前的备份和失败恢复。目标生产目录为：

```text
/home/source/Django/wagtail/wagtailblog3
```

备份根目录为：

```text
/home/source/Django/wagtail/backups
```

每次部署建立独立目录，不覆盖历史目录，不使用 `rsync --delete`，不删除旧备份。建议目录名：

```text
/home/source/Django/wagtail/backups/wagtailblog3-pre-search-YYYYMMDD-HHMMSS
```

时间戳必须使用服务器本地时间，并在备份清单中同时记录 UTC 时间、操作者、目标 commit 和部署窗口编号。

本文不保存密码、Token、API key、私钥或 MongoDB 正文。所有凭据只从生产受保护的环境文件、systemd 注入环境或运维凭据管理器读取，禁止写入命令历史、日志、Git 或聊天回复。

## 2. 备份前门禁

备份本身不修改 BlogPage、MongoDB 正文或 Elasticsearch 文档，但会读取生产数据并在服务器磁盘创建副本。执行前必须确认：

1. 当前生产低峰窗口和可接受的备份读取负载。
2. `/home/source/Django/wagtail/backups` 所在磁盘有足够空间，至少能容纳 MySQL、MongoDB 和代码/配置副本。
3. MySQL、MongoDB、Elasticsearch、Docker、systemd、Nginx 的真实服务名和连接目标已经核实。
4. 当前生产仓库分支、HEAD、remote、工作树和未跟踪文件已经记录。
5. 当前四个项目服务和基础设施没有既有故障。
6. 备份文件权限可以设置为目录 `700`、普通备份文件 `600`。
7. 备份完成后能执行归档完整性检查，并至少保留一份恢复验证证据。

以下任一项不满足时停止，不进行代码同步、migration、索引写入或服务重启：空间不足、目标不明确、生产工作树状态未知、备份命令失败、归档校验失败、ES 没有可恢复快照、或备份无法被恢复流程识别。

│   ├── mysql-migration-state.txt
│   ├── elasticsearch-summary.json
│   └── environment-names.txt
├── code/

│   ├── git-head.txt
│   ├── git-status.txt

## 4. 备份内容

### 4.1 代码和 Git 状态

代码备份必须同时保留：

- 生产当前 HEAD 和待部署目标 commit；
- `git status --short --branch`；
- `git remote -v` 的非敏感地址摘要；
- `git diff` 和未跟踪文件清单；
- 当前生产项目的受版本控制代码；
- `.env.production` 的受保护副本及权限记录；
- 项目使用的 systemd unit、Nginx、Filebeat、Docker 配置和证书路径清单；

生产独立内容搜索的任何开关、连接名、索引前缀或 read alias 修改前，还必须对
`wagtailblog3/settings/.env.production` 创建权限为 `0600` 的时间戳副本，并保存单独 SHA-256
校验记录。备份记录只保存文件名、权限和校验结果，不把环境文件正文、凭据或 API key 写入 Git、
聊天记录或普通日志。该副本用于恢复错误的运行时命名空间，不能替代 MySQL、MongoDB 或 ES snapshot。
- `collectstatic` 生成目录、socket、PID、日志和 media 的实际路径清单。

代码归档不应包含运行时日志、media 全量内容、socket、PID、缓存、Celery Beat 锁文件或临时浏览器产物。media、logs 和数据库分别由其数据备份负责；若生产回滚依赖某个静态目录，则在清单中单独归档并校验。

### 4.2 MySQL

默认备份整个生产业务库，而不是只备份 `search` app。原因是搜索状态要和 BlogPage、Wagtail Revision、权限关系及其他业务表保持同一恢复时间点。

备份要求：

- 使用一致性快照/事务方式，避免长时间锁住线上写入；
- 包含表结构、数据、触发器、事件、存储过程和必要的字符集信息；
- 记录数据库名、MySQL 版本、开始/结束时间、行数摘要和压缩文件大小；
- 备份完成后执行 gzip 完整性检查，并检查归档头和末尾是否完整；
- 不把密码写入命令参数，使用受保护环境或交互式凭据；
- 不在生产主库执行导入验证，恢复验证应使用隔离数据库或临时恢复主机。

`search.0001` 至 `search.0005` migration 的回滚默认是“保留新表、关闭功能、回退代码”，不是直接删除新表。因为新表一旦承载事件和审计状态，删除会破坏后续补偿和问题调查。

### 4.3 MongoDB

MongoDB 备份必须覆盖博客正式正文、草稿快照、历史正文、Revision pointer 和 `mongo_content_id` 相关集合。搜索回填只允许读取公开发布正文，不能因为回填而修改或删除 Mongo 数据。

备份要求：

- 使用与生产 MongoDB 版本兼容的归档方式并启用 gzip；
- 记录数据库和集合清单、文档计数摘要、归档大小和校验和；
- 不在回复、日志或手册中输出正文、草稿或完整文档；
- 恢复验证只能在隔离数据库/隔离实例执行；
- 生产恢复前必须先备份当前状态，并单独确认覆盖范围、时间点和回滚方式。

MongoDB 正文不是普通搜索缓存。代码回滚、搜索 alias 回滚和 ES 重建都不得触发 Mongo 正文恢复；只有明确的数据损坏事故才进入 Mongo 恢复流程。

### 4.4 Elasticsearch

现有 Elasticsearch 至少要保存：

- 集群名、版本、节点数和健康状态；
- 旧 Wagtail 搜索索引、读写 alias、mapping、settings 和 template 摘要；
- 日志索引及 Filebeat 使用的读写 alias 摘要；
- 每个相关索引的文档数、primary store size、磁盘余量和 snapshot 状态；
- 可恢复 snapshot 的 repository、snapshot 名称、完成状态和校验结果。

如果当前没有可恢复的旧 ES snapshot，不得把“保存 alias 配置”当成完整 ES 数据备份。此时可以先做代码-only 发布，但必须在生产新索引写入前补齐旧 ES 的快照或明确的重建能力。

新独立 ES 必须使用独立 repository、独立数据卷和独立索引前缀。新索引 snapshot 成功后，才允许进入 alias 切换 Gate。

## 5. 备份后校验

备份目录中必须生成 `manifest.txt` 和 `checksums.sha256`，至少包含：

- 文件相对路径、大小、修改时间和 SHA-256；
- MySQL gzip 归档可读检查结果；
- MongoDB archive 可列举检查结果；
- ES snapshot `SUCCESS` 状态和索引摘要；
- 代码 HEAD、工作树和配置文件权限；
- 备份是否完成恢复验证、验证环境和验证时间。

校验失败时不得继续。备份目录不得在确认前清理，历史备份不得用自动脚本删除。

## 6. 恢复手册

### 6.1 仅代码启动失败

适用于代码部署后 Django/uWSGI、Worker、Beat 或 Filebeat 无法正常启动：

1. 停止受影响的项目服务，保留失败日志和 `systemctl status` 输出。
2. 将当前生产目录移动到新的故障现场目录，不删除、不覆盖备份。
3. 从已验证的上一 commit 或代码归档恢复项目代码。
4. 恢复原 `.env.production`、静态文件路径和服务配置，核对权限。
5. 运行 `manage.py check`，再按依赖顺序启动 Django、Worker、Beat、Filebeat。
6. 检查首页、后台、旧搜索、队列、Beat、日志采集和 ES 健康状态。

代码回滚不自动反向 migration、不删除 `search` 表、不恢复 Mongo 正文、不删除新 ES 索引。

### 6.2 新搜索结果异常

优先关闭 `CONTENT_SEARCH_QUERY_ENABLED`，或把新 read alias 原子切回旧目标。保留新索引、Target、Build、Outbox、Delivery、dead 和 snapshot，便于分析和重放。旧搜索恢复后重新验收公开边界和延迟。

当前首次前台切换的最短回退步骤是：先恢复已验证的
`CONTENT_SEARCH_QUERY_ENABLED=false`，再仅重启 `wagtailblog3.service`，由旧 Wagtail 搜索重新响应。
此步骤不需要删除或修改 ES alias，也不需要回滚 MySQL migration。若故障原因是运行时命名空间配置，
从本窗口的 `.env.production` 受保护副本恢复以下键的一致集合后，再执行 `manage.py check` 和
旧搜索 HTTP 验收：

```text
CONTENT_SEARCH_CONNECTION_NAME
CONTENT_SEARCH_INDEX_PREFIX
CONTENT_SEARCH_READ_ALIAS
CONTENT_SEARCH_PRODUCTION_CONNECTION_NAME
CONTENT_SEARCH_PRODUCTION_INDEX_PREFIX
```

恢复配置后必须确认 `systemctl cat wagtailblog3.service` 仍只引用
`.env.production`，并以干净环境执行管理命令，避免 SSH shell 遗留变量覆盖文件值。不要以临时
`export`、手工 MySQL 状态更新或删除 alias 代替该回退流程。

### 6.3 新 ES 或回填失败

停止新目标 consumer 或暂停回填，保留 checkpoint 和失败批次；旧搜索继续服务。修复认证、mapping、容量或 Mongo 读取问题后，只从明确 checkpoint 或指定 Delivery 恢复。禁止批量把 pending/retry/dead 改为 succeeded，禁止删除唯一 snapshot。

### 6.4 MySQL/Mongo 数据事故

数据恢复不是普通部署回滚：

1. 先停止会继续写入受影响数据的服务并保留现场。
2. 备份当前故障状态，避免覆盖新的证据。
3. 明确恢复时间点、数据库/集合范围、是否允许覆盖和业务影响。
4. 先在隔离实例恢复并核对 BlogPage、正文、草稿、Revision 和索引指针。
5. 只有获得单独授权后，才对生产执行精确恢复。
6. 恢复后重新执行 Django、服务、搜索、Mongo 指针和 outbox 一致性检查。

禁止用全库恢复解决单个搜索索引问题，禁止删除 Mongo 正文或草稿来“清理搜索数据”。

## 7. 生产发布后的证据清单

每个窗口独立归档以下内容：

- 操作时间、操作者、授权记录和目标 SHA；
- 生产仓库同步前后 HEAD、差异文件和工作树状态；
- backup 目录、文件清单、校验和和恢复验证结果；
- migration plan、实际 migration 记录和执行耗时；
- 四个项目服务 active/enabled、失败 unit、重启时间和关键日志摘要；
- 新旧 ES 集群、索引、alias、文档数、store size、heap 和磁盘水位；
- Outbox/Delivery 状态、最老任务年龄、重试/dead 数和回填 checkpoint；
- 首页、后台、搜索、建议、公开边界和高亮验收；
- 回滚点、实际回滚演练结果、未关闭风险和下一 Gate。

## 8. 当前待确认顺序

本手册写入生产备份目录前，先确认服务器真实状态和可用空间。之后按以下顺序逐项确认：

1. 是否批准执行只读生产预检。
2. 是否批准在 `/home/source/Django/wagtail/backups/` 创建本次带时间戳的备份目录并生成 MySQL/Mongo/代码/配置/ES 备份证据。
3. 是否批准只同步 `18816c9`，全部新搜索功能保持关闭。
4. 备份和代码-only 验收通过后，再单独讨论 migration 和生产独立 ES。

在第 2 项得到明确确认前，不执行生产数据库备份、生产文件归档、ES snapshot 或任何生产写入动作。
