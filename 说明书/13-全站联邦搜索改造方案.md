# 全站联邦搜索改造方案

## 1. 文档信息

- 编制日期：2026-08-12
- 适用项目：`wagtailblog3`
- 对应工作包：WP7，全站联邦搜索（推荐模型：`gpt-5.6-terra`；推理强度：高）
- 状态：方案待用户确认；本文件不构成代码、索引、环境文件、systemd 或生产数据操作授权。
- 前置文档：`说明书/09-搜索架构容量与演进方案.md`、`说明书/10-搜索架构实施计划.md`

## 2. 问题和目标

当前三个前台入口语义如下：

| 参数 | 当前查询范围 | 当前索引/后端 |
| --- | --- | --- |
| `type=blog` | 已发布、公开的 `BlogPage` | 新独立内容索引 `wagtailblog-prod-content-read`，当前指向 v002 |
| `type=pages` | 已发布、公开且排除 `BlogPage` 的其他页面 | Wagtail Page 索引 |
| `type=all` | 已发布、公开的全部 Page，包括 `BlogPage` | Wagtail Page 索引 |

因此 `all` 目前不是 `blog + pages` 的真正联合检索，而是旧 Page 索引的一次全站查询。它仍可用，
但 BlogPage 的正文检索质量、精简 mapping 和异步内容投影没有被 `all` 使用。

本工作包的目标是把 `type=all` 改为：

```text
公开 BlogPage 的新内容索引结果
  +
公开非 BlogPage 的 Wagtail Page 索引结果
  =
统一排序、去重、分页和安全高亮的全站结果
```

完成后应满足：

1. `blog`、`pages` 的现有结果、URL、分页和开关语义不变。
2. `all` 同时包含两个互斥集合；没有重复 BlogPage，也不遗漏普通页面。
3. 默认相关性排序不能直接比较两套 Elasticsearch `_score`，必须使用可解释、可测试的统一融合规则。
4. 日期筛选和日期排序在两类页面间有明确且一致的“发布时间”定义。
5. 任何 ES 命中仍必须经过 `live().public()` 和类型范围二次回查；草稿、历史正文和受限页面不能泄漏。
6. HTML、异步片段 API、REST API、缓存、分析统计和游标分页遵循同一结果集契约。
7. 新 `all` 后端任一必需来源异常时，不得静默少返回结果或退回旧 BlogPage 索引。

非目标：不修改 MongoDB 正文/草稿/revision、`markdown_block`、MySQL schema、现有 Page 索引 mapping、
Celery 队列、Nginx、uWSGI、Filebeat 或生产 systemd unit。本工作包本身不删除 v002、Page 索引、日志索引或 snapshot。

## 3. 已核对的现状规律

### 3.1 路由分流

`search.core.perform_search()` 仅在 `CONTENT_SEARCH_QUERY_ENABLED=true` 且 `search_type == "blog"` 时调用
`build_content_search_results()`。`all` 会建立 `Page.objects.live().public()`，再通过 Wagtail 默认搜索后端查询。
这就是当前 `all` 不会自动使用新内容索引的根因。

`pages` 使用 `Page.objects.live().public().exclude(id__in=BlogPage.objects.values("id"))`；因此理论集合为：

```text
all 的公开页面集合 = blog 集合 + pages 集合
blog 集合 ∩ pages 集合 = 空集
```

联邦实现必须继续由这两个权威 QuerySet 做最终回查，不能仅依赖 ES 中的 `content_type`、`searchable` 或历史文档。

### 3.2 评分不可直接比较

Blog 内容索引的默认检索字段是 `title^10`、`intro^5`、`body_text^2`，使用精简 mapping、正式 Mongo 正文和
独立 analyzer。Page 索引的字段、analyzer、BM25 统计范围和查询编译器均不同。

例如 Blog 索引的 `_score=3` 与 Page 索引的 `_score=3` 没有共同单位；按数值直接 sort 会随机偏向某一索引，
且随着文档增长、分词器或段合并发生漂移。因此禁止把两边原始 `_score` 拼接后排序。

### 3.3 当前排序、日期和分页差异

- `blog` 当前日期筛选/排序使用业务发布日期 `BlogPage.date`；该字段已在 v002 内容索引中投影为 `date`。
- `pages` 当前使用 Wagtail Page 的发布时间字段，但现有实现实际按 `last_published_at` 过滤和排序；这与 `all` 的 `first_published_at` 口径不一致。
- `all` 当前使用 `Page.first_published_at` 语义；这与单独 `blog` 的业务日期不完全相同。
- `blog` 在游标开关打开时支持签名 `search_after`，`all/pages` 仍使用 `page=` 和 10,000 结果窗口。
- `blog` 高亮来自新内容索引；`all/pages` 高亮来自 Wagtail Page 索引。两者都在页面公开范围二次回查后才挂载片段。

因此联邦 `all` 不能简单把两份 20 条结果列表拼起来。那会导致：排序错误、第二页漏项或重复、总数错误、日期
语义混乱，以及在一侧故障时悄悄返回不完整“全部”。

### 3.4 当前内容投影缺少全站统一发布时间

v002 内容索引只保存 `date`，没有 `Page.first_published_at`。若联邦 `all` 要与 `pages` 统一“页面首次发布时间”
筛选和排序语义，不能在请求时逐篇查询 MySQL 补齐日期，也不能将 `BlogPage.date` 与普通页 `first_published_at` 混用。

请求时逐篇补齐会破坏分页和性能；混用会使“最新发布”在不同类型中含义不同。故推荐为新版本内容索引增加
`first_published_at`，把它作为 `pages` 与联邦 `all` 的统一日期筛选/排序字段。`blog` 入口仍保持原有 `date` 语义。

这意味着真实环境需要创建版本化内容索引 v003、双投递、回填、追平和 alias 切换；不需要 Django migration，
但属于 Elasticsearch 写入和生产索引切换，必须另行备份与授权。

## 4. 最终行为定义

### 4.1 类型语义

| 类型 | 结果集 | 默认相关性 | 日期筛选与日期排序 |
| --- | --- | --- | --- |
| `blog` | 公开 BlogPage | 现有新内容索引排序 | 保持 `BlogPage.date` |
| `pages` | 公开非 BlogPage | Wagtail Page 搜索排序 | 统一使用 `Page.first_published_at` |
| `all` | `blog ∪ pages`，两个集合互斥 | 联邦融合排序 | 统一使用 `Page.first_published_at` |

`pages` 与全站 `all` 的日期含义统一显示为“页面首次发布时间”。单独 Blog 的“发布日期”仍是文章业务日期，
继续使用 `BlogPage.date`。实现前应在模板的日期筛选说明中增加简短准确文案，避免把两种口径混为一谈。

### 4.2 默认相关性：加权 RRF

推荐使用 Reciprocal Rank Fusion（RRF）合并两个已排序候选流：

```text
federated_score = 1 / (60 + blog_rank)
               + 1 / (60 + page_rank)
```

由于 BlogPage 与非 BlogPage 集合天然互斥，每个结果只来自其中一个流。两边初始权重都为 `1.0`，表示
“同一查询中各自排名第 1 的博客和普通页面具有同等基础资格”；相同融合分时按 `page_id` 升序稳定打破平局。

这不是比较不可比 `_score`，而是比较每个后端内部已经确定的名次。优点是规则稳定、可复现、对 analyzer/索引
规模变化不敏感。代价是少量高匹配普通页面可能进入靠前位置；这是“全部”搜索应展示站内相关页面的预期行为，
而不是错误。第一阶段不增加人为“博客优先”权重，避免把业务偏好伪装为相关性；若人工验收证明需要偏向博客，
必须增加独立配置、测试集和明确的权重说明后再调整。

当 `order_by=date` 或 `order_by=-date` 时，`all` 不使用 RRF，按统一 `first_published_at`、再按 `page_id` 排序；
`pages` 使用完全相同的日期字段和排序规则。

### 4.3 候选查询和安全边界

每个联邦请求按相同 cleaned query、语言、日期边界和排序方向建立两个候选流。Pages 流是唯一实现，
`type=pages` 直接使用它，`type=all` 复用同一个 Pages 流后再与 Blog 流融合；不得为 `pages` 和 `all` 复制两套查询代码：

1. **Blog 流**：读取内容 read alias，仅查询 `searchable=true` 的正式内容文档；默认相关性用现有字段权重，
   联邦日期模式使用 v003 的 `first_published_at`。
2. **Pages 流**：从 Wagtail 默认 Page 索引构造公开非 BlogPage QuerySet，再复用其实际 query compiler 的
   content type、访问范围和日期 filter；`pages` 与 `all` 均调用此适配器，日期统一使用 `first_published_at`；
   不读取 MongoDB。
3. **二次回查**：Blog 命中只能由 `BlogPage.objects.live().public()` 确认；Pages 命中只能由
   `Page.objects.live().public().exclude(BlogPage)` 确认。未回查成功的命中直接丢弃，不能展示标题、URL、
   高亮或计入当前页面。
4. **去重**：合并器以 `page_id` 去重；若异常导致同一 ID 进入两流，记录脱敏错误码并优先保留 Blog 流，
   但测试必须证明正常路径不会出现此情况。
5. **高亮**：只复用两条现有安全高亮管线。ES 原始 HTML 仍先转义，仅允许服务端生成的 `<mark>`；不得把
   其中一个源的高亮附加到另一个源的页面。

### 4.4 计数契约

联邦总数为两条候选流的计数之和，因为两类页面在权威 QuerySet 语义下互斥。计数仅在两个后端均成功时返回。
页面/索引刚发生发布、取消发布或限制变更时，ES 投影存在短暂异步延迟；实际展示始终以二次公开回查为准。

实现中必须记录“候选总数”和“本页 guard 丢弃数”的脱敏指标，不能将被 guard 排除的页面标题、正文或 URL
写入日志。若持续出现 guard 丢弃，视为同步一致性告警，而不是用错误计数掩盖问题。

### 4.5 故障语义

联邦开关开启后，`all` 是完整结果集：

- Blog 内容 alias/Target 不可用、内容 ES 查询失败、Page ES 查询失败、复合游标无效或必要索引切换后失效时，
  HTML、片段 API 和 REST API 均返回既有的稳定 `503 search_unavailable` 或 `400 invalid_cursor`。
- 不允许“只返回 pages”或“悄悄回退旧 all”，因为这会把不完整结果伪装为全站结果。
- 紧急回退由独立 feature flag 完成，关闭后立即恢复当前 Wagtail `all` 查询；不删除索引、不改 alias、不改 MySQL。

## 5. 复合游标和分页设计

### 5.1 不能使用页码拼接

`page=2` 分别向两端取第 2 页再合并，会漏掉上一页未被选中的候选；分别取 20 条再排序，也无法知道第 21 条
是否应进入当前联邦页。大结果集上反复从 0 拉取会退化为深分页，不能满足现有 WP5 的性能目标。

### 5.2 新的签名复合游标

新增独立 `FederatedSearchCursor`，不复用当前仅表示单一内容索引 anchor 的 `ContentSearchCursor`。令牌使用新的
salt 和版本，签名绑定：

- cleaned query hash、`type=all`、日期范围、排序、locale；
- 联邦算法版本、RRF 参数和候选批次大小；
- 当前内容 serving Target/物理索引标识与当前 Wagtail Page 索引标识；
- 前进/后退方向；
- Blog 流和 Pages 流各自最后一个**已消费**命中的 `search_after` sort anchor；
- 两流各自已消费的排名计数，以及可选 PIT 标识。

游标不携带正文、Mongo 指针、URL、未转义高亮或凭据。alias/Page 索引切换后旧游标必须被拒绝并提示重新搜索，
不能在新旧物理索引间继续复用 anchor。

### 5.3 流式合并算法

1. 每一流从“最后已消费 anchor”开始读取有上限的候选批次；初始建议每流 `max(40, page_size * 2)`，上限 100。
2. 对候选逐项做公开二次回查。被 guard 丢弃的原始命中仍推进该流 anchor，防止下一页永久重复读取它。
3. 默认排序按 RRF 选择下一条，日期排序按统一时间字段选择下一条；选择一条才推进对应流的消费 anchor 和 rank。
4. 未选中的候选不写入游标；下一请求从该流最后已消费 anchor 重读，所以不会丢失。循环受最大拉取批次约束，
   防止大量陈旧命中导致单请求无限扫描。
5. 填满 `page_size`、两流均耗尽或达到安全扫描上限时返回；有任一流可能继续则生成下一游标。
6. 上一页使用反向排序和两个反向 anchor 重新计算，展示前恢复正向顺序；与现有 Blog 游标一致。

第一版 `all` 在联邦 flag 开启时统一使用游标，不显示页码跳转框。`blog` 保持现有游标行为；`pages` 保持旧页码行为。
传统 `page=` 可在一个发布周期内继续指向旧 all，或在 flag 开启时明确返回 400 并提示重新搜索；推荐后者，
避免两个 `all` 分页协议产生重复/漏项。规范化 URL 和前端 JavaScript 同步更新。

### 5.4 PIT 策略

默认不强制 PIT，沿用现有 `CONTENT_SEARCH_PIT_ENABLED`。若启用，Blog 和 Page 两个物理索引分别建立 PIT，
两个 PIT ID 都进入复合游标；任一 PIT 失效即拒绝令牌。PIT 会占用 ES 资源，因此先以关闭状态验证功能和
高频分页，再根据实际 P95、打开 PIT 数量和 ES heap 决定是否生产启用。

## 6. 索引与数据变更

### 6.1 v003 内容索引

新内容模板在现有白名单基础上只增加：

```text
first_published_at: date
```

`FormalContentDocument` 从 Page 元数据投影该字段；仍不写入草稿、revision、Mongo ObjectId、原始 StreamField、
HTML 或权限详情。v002 保持 serving，v003 作为 building Target 创建并参加双投递；回填使用既有 State、Outbox、
Delivery、批量 Mongo 读取、外部版本和 checkpoint 机制。

v003 连续两次追平、无 pending/processing/retry/dead、State/ES 一致性检查通过后，才允许切 read alias。切换
v003 不等于立刻开启联邦 `all`；它们是两个独立 Gate。v002 在观察期结束前不得删除。

### 6.2 Page 索引

不创建第二个全站 Page 索引，不把非博客正文复制进内容索引，也不删除当前 Wagtail Page 索引。`pages` 与 `all`
共同复用现有默认后端及其 Page 索引，并共同调用同一个公开非 BlogPage 查询适配器；这样普通页面仍由 Wagtail
管理其索引生命周期，也不会产生两套筛选、排序和公开范围逻辑。

### 6.3 缓存

新增 `federated-all` 实现命名空间和缓存代次，不能复用当前 legacy `all` 的 5 分钟结果。游标请求不进 page 缓存。
在以下事件的 `transaction.on_commit` 后清理搜索缓存：普通页面发布/取消发布/删除、BlogPage 发布/取消发布/删除、
访问限制变更，以及内容 Delivery 对 serving Target 成功写入或 tombstone 成功写入。

最后一项很重要：内容投影是异步的。如果 Delivery 成功后不失效，联邦 `all` 可能在缓存 TTL 内继续显示旧结果。
缓存清理失败只记录脱敏错误并依赖 TTL，不得影响 Delivery 成功状态；监控需统计该失败。

### 7.2 修改模块

- `search/core.py`：抽取共享的 Pages 流适配器；`type=pages` 直接调用，独立 flag 下的 `type=all` 复用后再联邦融合；保留 legacy all 路径。
- `search/services/content_query.py`：支持联邦 all 的 `first_published_at` 过滤/排序以及原始 anchor 安全推进。
- `search/services/document.py`、`search/services/content_index.py`：增加 v003 的最小日期投影和 strict mapping。

- `search/signals.py`、`blog/signals.py`：在真实发布生命周期和内容投影完成后触发缓存失效；不得对草稿保存触发。
- `search/templates`、`static/search/js/search.js`：联邦 all 使用游标导航；日期文案明确为“页面首次发布时间”。
- `settings/database.py`、`.env.example`：增加默认 `false` 的 `CONTENT_SEARCH_FEDERATED_ALL_ENABLED`；可选配置仅限
  受边界约束的批次大小/扫描上限，不能暴露任意索引名或原始查询 DSL。
- `systemctl.md`、`说明书/09`、`说明书/10`、本文件：登记配置、运行、回滚和实施事实。

原则上不修改：`settings/base.py` 的环境选择、Mongo schema、Wagtail Page 模型、现有 Page 索引的 mapping、
生产凭据、服务 unit。若实施中发现必须修改这些边界，停止并重新提出方案。

## 8. 分阶段实施与 Gate

### WP7A：代码骨架和隔离测试

- 新增 flag，默认关闭；关闭时 `all` 的代码路径、返回数、页码分页和缓存 key 完全保持当前行为。
- 用客户端替身测试候选流、RRF、日期排序、去重、guard、总数、复合游标、PIT 双锚点、篡改/过期/跨查询拒绝和 503。
- 不创建真实索引，不执行 migration，不修改测试环境常驻服务。

Gate A：定向测试、完整 `search` 测试、`manage.py check`、`makemigrations --check --dry-run`、`migrate --plan` 和
`git diff --check` 通过；关闭 flag 的旧 all 回归完全通过。

### WP7B：测试 v003 和真实联邦回归

- 仅在测试 `wagtailblog-test-*` 命名空间创建 v003 template/physical index/Target。
- 启用现有测试 producer/consumer，对公开 BlogPage 回填、双投递和追平；不读取或写入生产 MySQL/Mongo 数据。
- 切换测试 read alias 至 v003 后，开启测试联邦 all flag，真实验证 `all = blog + pages` 的集合、默认排序、日期排序、
  安全高亮、游标前后页、API 和缓存失效。

Gate B：测试 alias 唯一、v003 mapping strict、Delivery 无积压、一致性无 missing/stale/hash mismatch/ahead/extra，
且真实测试中 `all` 的可见 ID 集合等于 `blog ∪ pages`。浏览器桌面和移动端均检查无 JS error、无横向溢出、
无未转义高亮和无草稿/受限泄漏。

### WP7C：测试影子观察和人工相关性确认

- 新增联邦 all 影子观察：当前 legacy all 仍服务用户时，异步执行候选联邦查询。
- 日志只记录 query hash、有限 page ID、来源数量、差异类别、耗时和错误码；不记录查询原文、正文、高亮或凭据。
- 用 20 至 50 个代表性查询人工检查：标题命中、正文命中、中文短语、中英文混合、代码词、日期过滤和排序。

Gate C：无公开边界泄漏；联邦结果中普通页面可出现，Blog 正文命中不劣于新 `blog`；无持续 503、无异常缓存陈旧；
人工确认默认 RRF 排序可以接受。若排序不符合预期，只调整测试环境算法参数并重新观察，不在生产直接试错。

### WP7D：生产 v003、观察和受控启用

这一步会写入生产 Elasticsearch、可能更新现有 Target/Build 状态、开启双投递并重启受影响应用服务，必须单独申请授权。
执行前必须完成：生产 MySQL/Mongo/代码/配置备份、ES snapshot、磁盘和 heap 预检、v002 alias/Target/Delivery 状态记录。

顺序固定为：

1. 发布已测试代码，`CONTENT_SEARCH_FEDERATED_ALL_ENABLED=false`。
2. 创建生产 v003 building Target 和物理索引；v002 继续 serving。
3. 开启 v003 双投递并进行在线回填、追平和一致性扫描。
4. 原子切生产 content read alias 至 v003；此时仅 `blog` 使用 v003，`all` 仍为 legacy。
5. 低采样影子观察联邦 all，完成性能和人工质量验收。
6. 单独将 `CONTENT_SEARCH_FEDERATED_ALL_ENABLED=true`，仅重启 Django/uWSGI。
7. 验收 HTML、异步片段、REST API、`blog/pages/all`、缓存、Delivery 和日志；观察期内保留 v002。

生产 Gate D：四服务 active/enabled、failed unit 为 0、v003 serving/read alias 正确、Delivery 为零积压、搜索 HTTP 200、
`all` 与 `blog + pages` 在集合语义上相符、P95 不超过批准阈值、没有公开边界告警。任一项失败立即关闭联邦 flag。

## 10. 回滚

### 10.1 应用读取回滚

将 `CONTENT_SEARCH_FEDERATED_ALL_ENABLED=false`，仅重启 `wagtailblog3.service`。`all` 立刻回到当前 Wagtail
Page 索引路径；`blog` 继续使用已验证内容 alias，`pages` 不变。该操作不删除 v003、v002、Page 索引、MySQL 审计、
Outbox、Delivery 或 Mongo 数据。

### 10.2 索引回滚

若 v003 本身异常，先关闭联邦 flag，再按既有受控 alias 流程把内容 read alias 切回 v002。只在已确认 snapshot、
Target 状态和 Delivery 兼容后执行；不能把“关闭 all”与“删除 v003”混为同一步。

### 10.3 缓存和游标回滚

提升缓存代次或清除联邦命名空间，使旧联邦结果和旧复合游标自然失效。不得尝试解析、修复或手工重写客户端游标。

## 11. 风险与待确认决策

1. **排序体验**：推荐同权 RRF。请确认“博客和普通页面同等参与默认相关性排序”；若希望博客优先，必须明确期望权重和人工样例。
2. **日期口径**：推荐 `all` 与 `pages` 一律按 `first_published_at`，需要 v003；`blog` 继续按 `BlogPage.date`。请确认接受“全站/普通页面按首次发布时间，博客入口按文章业务日期”的明确区分。
3. **可用性**：推荐联邦 all 任一来源失败即 503，不显示不完整结果。请确认不接受部分成功降级。
4. **分页体验**：推荐 all 启用后仅使用上一页/下一页复合游标，不保留页码跳转。请确认接受这一行为。
5. **生产代价**：v003 需要一次新的精简索引、双投递、Mongo 正式正文回填和 alias 切换；不需要 MySQL migration，
   但必须等测试 Gate、备份、snapshot 和单独生产授权完成后才能执行。
