# AI 博客正文元数据生成方案

## 背景与现状证据

- `BlogPage.body` 是 StreamField 编辑结构，但正式正文、草稿快照和 revision pointer 受 MongoDB 数据保护规则约束。关系数据库中的 `body` 会保持为空，编辑 `BlogPageForm` 时才按 revision pointer 或 `mongo_content_id` 回填正文。
- `BlogPage` 当前使用 `AITitleFieldPanel('title')` 和 `AIDescriptionFieldPanel('intro')`。`wagtail-ai==3.1.1` 实际仅向它们绑定 `page_title_prompt`、`page_description_prompt`，模型文件中的 `PROMPT_TITLE`、`PROMPT_INTRO` 常量未参与调用；数据库中的自定义“极客标题生成”和“SEO描述生成”也不会出现在这两个受限面板中。
- 项目已有 `static/blog/js/wagtail_ai_context.js`，可从后台当前 `#body` StreamField 状态提取富文本、Markdown、代码、流程图和表格中的语义文本；它不直接读取 MongoDB，符合“以未保存编辑态为准”的需要。
- `wagtail-ai` 的 `BasicPromptAgent` 调用 `LLMService.completion()`，即 OpenAI Chat Completions 路径。当前 `any-llm` 的 OpenAI provider 虽支持 Responses API，但该 Agent 不会调用 `responses()`。
- 当前测试环境中 `WAGTAIL_AI['PROVIDERS']['default']` 与 `qwen` 均未配置 API key，因此现有魔法棒无法产生真实模型结果。

## 目标

在 Wagtail BlogPage 编辑页提供一次明确、可审阅的“根据当前正文生成文章元数据”操作：

1. 从当前未保存的 `body` 提取语义文本；
2. 通过用户确认的 OpenAI-compatible Responses API 一次生成 `title`、`intro` 和 3 至 5 个标签；
3. 校验结构化结果后显示预览，编辑者可逐项或全部应用到表单；
4. 不自动保存、发布页面或创建标签；页面原有保存/发布流程继续负责最终写入；
5. 测试和生产均使用各自独立的环境变量，不写入密钥、正文或模型响应日志。

## 非目标

- 不修改 `BlogPage.body`、MongoDB 正文、草稿、revision pointer、`markdown_block` 存储键或已有发布流程。
- 不将真实博客正文用于未获确认的外部模型调用；不批量处理已有页面。
- 不把上游模型密钥、请求正文或完整响应写入源码、Git、说明书、浏览器调试产物或应用日志。
- 不替换整个 `wagtail-ai` 包，不迁移其既有 Prompt 数据，也不新增 systemd 服务、Celery 队列或数据库迁移。

## 设计决策

### 独立元数据生成链路

不复用 `wagtail-ai` 的 `BasicPromptAgent` 作为本功能核心。原因如下：

- 用户指定的上游配置要求 Responses API，并要求关闭响应存储；现有 Agent 固定调用 Chat Completions，无法保证协议或 `store=false` 参数生效。
- 标签是 `ClusterTaggableManager` 关系字段，需要受控 JSON 结果和人工确认，不能以普通 `AIFieldPanel` 的文本替换方式处理。
- 单次模型调用生成三个关联字段，能确保标题、简介和标签基于相同正文版本，减少三次请求的成本和语义漂移。

新链路仅复用项目已验证的 StreamField 前端提取思想：浏览器将当前编辑态正文提交给受权限保护的后台端点；服务端只处理本次请求的内存数据，不按页面 ID 回读任意 MongoDB 正文。

### API 适配与预检

新增独立、环境驱动的元数据生成配置，建议变量名如下，仅在 `.env.test` 或 `.env.production` 保存实际值：

```ini
AI_METADATA_PROVIDER=openai
AI_METADATA_API_KEY=
AI_METADATA_BASE_URL=
AI_METADATA_MODEL=
AI_METADATA_REASONING_EFFORT=
AI_METADATA_RESPONSE_STORAGE=false
AI_METADATA_TIMEOUT_SECONDS=60
```

实现前先做两项不含博客正文的测试环境预检：

1. 使用配置的最小权限凭据请求模型列表，确认目标模型确实由上游提供；
2. 使用一段固定、无业务信息的短文本验证 `/v1/responses`、认证头、`store=false`、推理强度和 JSON 输出能力。

若上游不能支持上述 Responses 契约，停止实施并记录实际响应；不得静默退回 Chat Completions 或把协议差异隐藏在提示词中。

### 请求、结果与安全边界

前端只提交：当前 StreamField JSON、页面语言及防止并发误应用的正文摘要。服务端提取、归一化后再向模型发送文本，限制总长度、各块长度和允许块类型；图片、文档 ID、媒体 URL、内部 Mongo ID、revision pointer 不进入模型上下文。

模型必须返回严格 JSON：

```json
{
  "title": "不超过 50 个汉字的标题",
  "intro": "不超过 150 个汉字的纯文本简介",
  "tags": ["标签一", "标签二", "标签三"]
}
```

服务端负责解析、去重、长度检查、空值检查和标签数量检查。`intro` 作为纯文本返回，由客户端按 Wagtail RichTextField 的既有输入格式安全回填，模型输出不作为 HTML 信任。标签仅显示建议，应用到表单后仍须由编辑者点击既有保存/发布按钮；不在 AI 请求中创建或保存标签。

### 后台交互

在 BlogPage 内容编辑区增加一个有文字和图标的“生成文章元数据”命令。操作状态包括：空正文禁用、请求中、可审阅建议、单项应用、全部应用、错误与取消。按钮和每项应用操作具备可访问名称、键盘焦点和清晰错误提示；颜色不是唯一状态信息。

确认动作发生前，界面明确说明会将当前正文发送给已配置的外部 AI 服务。建议预览不写入数据库；页面离开或重新生成时丢弃未应用建议。

## 计划实施步骤

1. 完成 API 预检和模型契约记录：不发送真实正文，验证 Responses API、模型可用性、`store=false`、结构化 JSON 与超时行为。
2. 抽取共享正文归一化逻辑：将当前 `wagtail_ai_context.js` 的语义规则与服务端验证对齐，为富文本、Markdown、代码、Mermaid、表格、嵌入和 HTML 定义明确的截断、忽略和脱敏规则。
3. 新增受管理员权限保护的元数据建议端点和 OpenAI Responses 客户端适配器：不记录正文、密钥或模型全文响应；只记录请求 ID、页面 ID（如已存在）、长度、耗时、成功/失败类别。
4. 新增 BlogPage 编辑器脚本和最小后台控件：读取当前 StreamField，调用端点，展示并回填建议，但不保存。
5. 为服务端 JSON 校验、上下文提取、权限、异常、超长正文和前端回填添加针对性测试；外部调用均使用 fake client。
6. 使用合成、无敏感信息的测试页面执行浏览器验收。经用户单独确认后，才进行一次真实上游 API 的端到端测试；不使用生产正文。
7. 更新 `.env.example`、`systemctl.md` 和本方案实施记录；测试通过后，再单独申请生产配置与发布授权。

## 预计修改与不修改文件

预计修改：

- `wagtailblog3/settings/third_party.py`：增加无密钥的元数据生成配置读取和显式校验。
- `wagtailblog3/settings/.env.example`：仅增加变量名、说明和安全默认值。
- `wagtailblog3/apps/blog/` 下新增受限服务、视图和测试模块；必要时更新 `wagtail_hooks.py` 注册后台 URL/资源。
- `wagtailblog3/static/blog/js/`：新增或扩展元数据生成编辑器脚本；保留现有 `wagtail_ai_context.js` 的兼容边界。
- `wagtailblog3/apps/blog/models.py`：只在确有必要时调整面板位置或移除无效的 AI 面板绑定，不改字段、StreamField schema 或保存逻辑。
- `systemctl.md`、本方案：记录环境变量、测试、回滚与实施状态。

明确不修改：

- MongoDB 文档、revision、现有 BlogPage 正文、标签数据、页面发布状态和数据库 schema；
- 生产 `.env.production`、systemd unit、服务端口、Celery、Beat、Filebeat、Nginx；
- `wagtail-ai` 依赖版本和现有通用 Prompt 数据，除非后续另有独立授权。

## 测试与验收

- WSL2 `wagtailblog-test`：`python manage.py check`，以及相关单元/集成测试。
- API 预检：仅模型列表和合成提示词，断言不会发送博客内容，并验证密钥、响应存储、模型名和端点错误的安全处理。
- 服务端测试：没有权限为 403；空正文/非法 JSON/超长正文为可读 400；模型格式异常不回填；合法结构化结果完成长度、数量和去重校验。
- 浏览器验收：已登录测试后台，检查桌面和移动视口的控件可见性、键盘路径、加载/错误/取消/逐项应用/全部应用、控制台错误、网络请求和无横向溢出。截图、trace 和日志统一写入 `output/playwright/ai-blog-metadata/`。
- 真实模型验收：仅在用户确认并使用合成正文后执行一次；验证标题、简介和标签均与同一正文相符，且不会自动保存或发布。

## 提示词写法与版本策略

提示词使用“角色 + 输入边界 + 任务 + 硬约束 + 输出 schema”的结构。不要要求模型输出 Markdown、解释或多个候选，也不要让模型决定是否保存页面。

推荐系统提示词要点：

```text
你是中文技术博客编辑。只能依据提供的正文生成元数据，不得补造正文没有支持的事实。
标题准确、具体、不夸张；简介面向读者且不含 HTML；标签为可检索的技术主题词。
只输出符合约定 schema 的 JSON。
```

正文外的用户提示词应注明：标题最多 50 个汉字，简介最多 150 个汉字，标签 3 至 5 个、每个不超过 20 个汉字、去重且不包含泛词“技术”“博客”“教程”。提示词存放在代码常量并有测试；修改提示词时更新版本标识和测试样例，而不修改已有内容数据。

## 数据、服务与发布影响

- 测试阶段只读取当前编辑器的合成正文，不保存或迁移内容数据。
- 生产阶段会把编辑者显式选择的当前正文发送给外部 AI 服务，属于受保护数据外发，必须单独说明 provider、数据范围、留存策略、`store=false` 证据、超时与失败行为并再次获得授权。
- 不新增服务。新增环境变量或应用代码后，测试环境仅重启测试 `runserver`；生产未获授权前不修改配置或重启服务。

## 回滚点与残余风险

- 代码回滚到实施前 commit；移除编辑器资源引用即可恢复原后台，不触碰正文、标签或 MongoDB 数据。
- 环境变量可从对应环境文件移除；不得删除历史正文、草稿、revision 或标签作为回滚手段。
- 残余风险：上游 OpenAI-compatible 服务可能只部分兼容 Responses API、推理强度或 `store=false`；必须由预检证据决定是否进入实现。模型可能生成不准确元数据，故保留人工预览和应用，禁止自动保存/发布。

## 模型/推理强度建议

- 事实收集与文档整理：`gpt-5.6-luna`，低/中推理；用于读取当前接入和整理测试证据。
- Django/Wagtail 与前端实现：`gpt-5.6-terra`，中推理；用于局部服务、后台控件和针对性测试。
- 外部 API 契约、正文外发边界与生产发布复核：`gpt-5.6-sol`，高推理；仅在 Responses 协议不兼容、密钥/数据保护、生产环境或回滚风险出现时升级。
- 升级条件：需要处理真实博客正文外发、上游协议与 SDK 不一致、权限绕过风险、生产配置、服务重启或任何数据写入。
- 验证门禁：不以模型选择替代 API 预检、单元测试、浏览器验收、环境隔离、用户确认或生产回滚方案。

## V2 提示词模板与使用记录方案（待实现授权）

### 背景与现状证据

- 当前正文元数据生成服务的提示词写在 `blog/ai_metadata.py` 的 `generate_metadata` 中；标题、简介和标签共用同一份指令，不能由管理员修改、选择或回看历史版本。
- 已安装的 `wagtail-ai==3.1.1` 有自己的 `Prompt` 和 `AgentSettings`，但它面向页面标题、页面描述、富文本补全等内置 Agent，并使用不同的调用路径。它不能表达本功能要求的 JSON schema、`store=false`、正文长度边界和“标题+简介+标签”原子校验，因此不复用它作为本功能的模板存储。
- 当前元数据接口只读取浏览器提交的未保存正文，返回建议但不保存页面。本方案必须保持此边界。

### 目标与非目标

目标：

- 管理员可维护多个中文提示词模板，例如“模板一：考公资料”和“模板二：政策解读”。
- 每个模板一次生成标题、简介、3 至 5 个标签；三个字段共用同一份正文证据和一个严格 JSON 输出契约。
- 编辑页可选择模板、查看模板说明和版本号；生成后显示本次使用的模板和版本。
- 保存每次实际生成请求的可检索记录，以便追溯“哪篇页面、何时、由谁、用哪个模板版本、结果是否合规”。
- 保留当前“预览后由编辑者选择应用、页面不自动保存或发布”的行为。

非目标：

- 不让管理员编辑 API 地址、模型名、密钥、`store=false`、JSON schema、字段长度限制或重试次数。
- 不把完整 BlogPage 正文、StreamField、MongoDB 正文、草稿、模型原始响应或密钥写入模板和记录列表。
- 不替换或修改 `wagtail-ai` 既有魔法棒功能；新模板只服务“生成元数据建议”。
- 第一版不支持按用户、栏目、语言自动选择模板，不做 AB 测试、自动发布或批量重生成。

### 推荐产品设计

1. 模板数据：新增 Wagtail snippet `BlogMetadataPromptTemplate`，字段为名称、用途说明、适用内容类型、模板正文、版本号、是否启用、创建/更新时间及创建/最后修改人。名称在启用模板中唯一。
2. 固定边界：服务端将模板正文与不可编辑的系统约束拼接。系统约束仍负责正文依据、无事实补造、标题/简介/标签长度、禁用泛词、JSON schema 和 `store=false`；模板只能补充写作风格、受众、措辞和标签偏好。
3. 模板变量：仅提供受控变量 `{{ language }}`、`{{ body }}`、`{{ title_limit }}`、`{{ intro_limit }}`、`{{ tag_count }}`。保存模板前解析变量，拒绝未知变量、空模板和超长模板；正文永远由服务端插入，不能由模板覆盖。
4. 版本策略：每次保存模板正文时递增 `version`。已经被生成记录引用的模板版本不可原地覆盖，后续编辑创建下一版本；可停用旧版本，但历史记录始终保留其快照和版本号。
5. 编辑页：在“生成元数据建议”按钮前增加带标签的模板选择框，默认选中管理员设置的默认模板。生成中禁用选择和按钮，成功/失败在控件旁显示文本状态；键盘可选择，移动端不产生横向滚动。
6. 使用记录：新增只读 Wagtail snippet 列表 `BlogMetadataGenerationLog`。每次外部 AI 调用结束后记录模板 UUID/版本/名称快照、请求人、页面 ID（新建页为空）、语言、结果状态、耗时、模型标识、返回字段长度和标签数量、错误分类；成功时记录标题/简介/标签的最终建议值，失败不记录正文或原始响应。
7. 数据保留：记录只供管理员审计，默认不提供删除按钮。保留期限、是否允许人工清理和生产数据备份策略属于生产操作，实施前必须单独确认。

### 提示词写法

模板一（考公资料）建议只描述风格和受众：

```text
面向备考公务员考试的读者。标题突出资料主题、适用考试类型或复习阶段；简介说明资料能帮助读者完成什么；标签优先使用具体考试模块、政策主题、题型或复习方法。避免“必过”“内部资料”“绝密”等无法由正文证实的营销词。
```

模板二（政策解读）建议只描述证据与表达：

```text
面向需要快速理解政策文件的读者。标题优先呈现政策主体、事项和影响对象；简介用中性语言概括核心措施、时间或适用范围；标签优先使用政策名称、发布机关、领域和适用对象。不得把解读补写为正文没有出现的政策结论。
```

系统约束、JSON schema 和正文变量不放进管理员模板正文，避免被误删后导致接口契约失效。

### 实施步骤与验收

1. 建立模板与日志模型、迁移和管理员权限边界；先只在 WSL2 测试环境执行迁移计划，不应用生产迁移。
2. 建立两个初始模板作为迁移或受控管理命令，不复制真实页面正文；管理员可在后台创建后再启用。
3. 改造元数据接口：接收模板 UUID，服务端验证启用状态、渲染受控变量、保留现有字段校验和有限重试，并写入最小化日志。
4. 改造编辑器控件：选择模板、显示说明/版本及本次生成状态；保持逐项应用、全部应用和不自动保存。
5. 增加测试：模板变量校验、停用模板拒绝、版本不可变、日志脱敏、权限、生成成功/失败、现有 11 项元数据测试、桌面与移动浏览器流程。

验收标准：管理员能建立模板一和模板二、停用模板；编辑者能选择启用模板并获得符合限制的三项建议；记录列表能显示模板版本和结果但没有正文或密钥；不选择模板、选择停用模板、模板变量非法、上游失败均显示明确错误且不改页面数据。

## V2.1 需求澄清：独立提示词模板管理

本节覆盖前文 V2 中“模板只补充风格、三项共用一段提示词”的设计；以后续实现以本节为准。

### 需求定义

- 在 Wagtail Admin 增加独立的“博客 AI 提示词”列表入口，不与 `wagtail-ai` 内置 Prompt 列表混用。
- 列表中的每一行是一套完整的博客页面元数据模板，例如“提示词1”“提示词2”“提示词3”。模板可以新增、查看、编辑和停用；列表不直接展开长文本。
- 每套模板必须包含三个相互独立的提示词字段：
  - 标题提示词：一个带标签的多行编辑框，指导模型依据正文生成 `title`。
  - 简介提示词：一个带标签的多行编辑框，指导模型依据正文生成 `intro`。
  - 标签提示词：一个带标签的多行编辑框，指导模型依据正文生成 `tags`。
- 提示词编辑页底部提供“保存”按钮。保存后回到列表；模板名称、说明、三个提示词、启用状态和版本可再次查看和编辑。
- 博客页面编辑页的“生成元数据建议”区域增加模板选择器，只允许选择一个启用模板。选择“提示词1”时，标题、简介、标签三次生成都必须使用提示词1对应的三个字段；不得混用其他模板字段。
- 生成预览仍一次展示标题、简介、标签，仍由编辑者分别应用或全部应用；不自动保存草稿、不发布页面。

### 提示词与系统约束的边界

- 用户写入的三个字段是业务提示词，服务端分别注入当前正文和语言信息。
- 服务端保留不可编辑的安全与格式约束：只能依据正文、禁止补造事实、长度限制、标签数量和去重、严格 JSON schema、有限重试以及 `store=false`。
- 为保证一次请求返回三项结果，实际调用可以把三段字段组合成一个“当前模板任务”，但 JSON 输出字段仍固定为 `title`、`intro`、`tags`。模板选择只产生一套一致的三字段指令。
- 模板编辑者不能修改模型、API 地址、密钥、响应存储策略、字段校验和重试上限。

### 推荐数据结构

新增 `BlogMetadataPromptTemplate`（Wagtail snippet）：

- `name`：模板名称，例如“提示词1”。
- `description`：用途说明，可空。
- `title_prompt`：标题提示词，多行文本。
- `intro_prompt`：简介提示词，多行文本。
- `tags_prompt`：标签提示词，多行文本。
- `is_active`：是否允许在博客编辑页被选择。
- `version`：保存时递增，供生成结果和审计引用。
- `created_at`、`updated_at`、`created_by`、`updated_by`：管理记录。

第一版不新增独立“每次生成日志”功能，避免把本需求扩大为审计系统；模板本身的版本和更新时间足够支持提示词维护。生成日志另行立项。

### Admin 界面

- 左侧 Admin 菜单新增“博客 AI 提示词”。
- 列表列显示：模板名称、说明、版本、启用状态、更新时间、编辑操作。
- 列表提供“新增提示词”按钮；点击一行或编辑按钮进入详情。
- 详情页按“基本信息 / 标题生成 / 简介生成 / 标签生成”分组，每个提示词字段有明确中文标签、帮助文本和足够高度的 textarea；不使用只靠 placeholder 识别字段的布局。
- 保存后显示成功状态；非法空提示词、过长提示词和重复名称在对应字段附近显示错误。
- 博客编辑页选择器只展示启用模板；没有可用模板时显示明确错误，引导管理员先创建模板。

### 验收标准

1. Admin 中可以新增“提示词1”，分别填写标题、简介、标签三段提示词并保存。
2. 列表可以查看、编辑、停用和再次启用提示词1；编辑后版本递增，旧页面正文不受影响。
3. 新增“提示词2”后，博客编辑页只能选中一个模板；选中提示词1生成时，三项结果都使用提示词1的对应字段。
4. 预览结果与正文相关；“应用标题”“应用简介”“应用标签”“全部应用”行为保持现状。
5. 未选择模板、模板已停用、提示词为空、上游失败时显示明确错误，不写入页面、revision、MongoDB、标签关系或搜索索引。
6. superuser 权限可以增查改停用；无权限用户不能修改模板。普通编辑者是否可以查看模板内容需单独确认，默认只允许选择名称。

### 模板删除、选择和无模板规则

- 不执行物理删除。列表中的“删除”实际执行停用/归档，将 `is_active` 设为 false；历史版本、名称和已使用关系保留，避免生成记录或审计引用断裂。
- 如果管理员停用当前博客编辑页已选中的模板，页面不会自动切换到其他模板。前端会清空选择，显示“当前模板已停用，请重新选择可用模板”，并将生成按钮置为不可用。
- 如果模板在另一个编辑者页面已被选中，停用不会改写对方页面的正文或表单；对方点击生成时服务端再次校验模板状态并拒绝请求，返回明确的“模板已停用，请重新选择”错误。
- 如果列表中存在多个启用模板，页面首次加载默认不隐式选择任意一个，除非明确设置一个“默认模板”。建议第一版不设置全局默认，强制编辑者主动选择，避免误用模板。
- 如果列表中没有任何启用模板，博客页面仍可打开和编辑正文，但“生成元数据建议”按钮禁用，界面显示“暂无可用提示词，请管理员先创建并启用模板”；服务端也必须拒绝无模板请求，不能回退到代码内置提示词、`wagtail-ai` 默认提示词或任意其他模板。
- 如果模板存在但标题、简介或标签任一提示词为空、非法或超过长度限制，该模板不能启用；已启用模板被发现异常时生成请求拒绝，不产生部分结果。
- 删除/停用操作只对有权限的模板管理员开放，并要求确认对话框明确写出“停用后不会自动选择其他模板，正在编辑的页面将无法继续使用它”。
- 模板停用后可以重新启用；重新启用仍使用原版本，不修改历史生成结果。若要改变提示词内容，创建新版本或新模板，不覆盖已被使用的版本。

### 对应验收用例

1. 选中提示词1后停用提示词1：选择框变为空、生成按钮禁用、页面不回填任何字段、不会自动改选提示词2。
2. 停用提示词1后直接发送旧页面请求：服务端返回模板停用错误，不调用外部 AI，不写日志或页面数据。
3. 所有模板均停用：页面显示无可用模板提示，生成按钮不可操作，接口拒绝无模板请求。
4. 创建并启用提示词2后：页面可主动选择提示词2，选择后才允许生成；生成三项结果都来自提示词2的对应字段。
5. 启用模板缺少任意一段提示词：保存或启用被拒绝，并在具体字段附近显示错误。

### 应用边界与迁移方案

#### 结论

建议新增项目内独立应用 `content_ai`，不把提示词模型继续放在 `blog`，也不修改第三方 `wagtail_ai` 应用。`content_ai` 是项目自己的 AI 业务边界，第一阶段只实现博客元数据提示词；未来可以在同一应用下增加图片生成、摘要、翻译等功能，但每类功能使用自己的模型和服务契约。

#### 为什么不继续放在 `blog`

- 提示词模板是后台管理资源，不是 BlogPage 正文模型；放在 `blog` 会让未来图片提示词、摘要提示词继续堆到博客应用中。
- 独立应用可以拥有自己的迁移、权限、测试和 Admin 菜单，博客只负责提供当前未保存正文并消费生成结果。
- 现有 `blog` 页面、MongoDB 正文和 StreamField 结构不需要因为提示词管理而增加字段或迁移依赖。

#### 为什么不复用第三方 `wagtail_ai`

- `wagtail_ai` 的 `Prompt` 是通用编辑 Agent 的提示词，配套的是它自己的页面标题、描述、补全流程；它没有本功能的“三段字段 + 单模板选择 + JSON schema”契约。
- 直接修改第三方表或默认 Prompt 会增加升级风险，并可能改变当前已有魔法棒行为。
- `content_ai` 可以复用现有 OpenAI-compatible 客户端适配思路，但不复制密钥、不改变 `wagtail_ai` 配置。

#### 应用结构建议

```text
wagtailblog3/apps/content_ai/
  __init__.py
  apps.py
  models.py                 # BlogMetadataPromptTemplate，未来再加 ImagePromptTemplate
  admin.py                  # Wagtail SnippetViewSet、列表、详情、权限
  wagtail_hooks.py          # Admin 菜单和 snippet 注册
  migrations/0001_initial.py
  services/
    metadata.py             # 模板渲染、固定约束、调用和结果校验
  tests/
```

- `blog` 保留 `BlogPage`、正文提取和编辑页控件；生成接口可以先留在 `blog`，内部调用 `content_ai.services.metadata`，等接口稳定后再迁移 URL 归属。
- `BlogMetadataPromptTemplate` 放在 `content_ai` 的 `models.py`，使用 Wagtail snippet 管理；未来图片生成不复用标题/简介/标签字段，而是新增独立 `ImagePromptTemplate` 或图片任务模型。
- 服务层接收博客传入的受限正文文本、语言和一个模板 ID，不直接查询 MongoDB，不保存页面正文。

#### 迁移文件

- 新应用使用独立迁移：`content_ai/migrations/0001_initial.py`，不生成 `blog/0025_*.py` 来保存提示词。
- 第一张表只保存模板名称、说明、三个提示词字段、启用状态、版本、操作者和时间；不新增 BlogPage 外键，避免模板停用影响页面数据。
- 如果后续增加生成记录，使用 `content_ai/migrations/0002_generation_log.py`，与模板表分开审查；本需求第一阶段暂不增加日志表。
- 实施时先运行 `makemigrations content_ai`、检查迁移内容和 `migrate --plan`，只在测试环境应用；生产迁移必须另行确认、备份和回滚。

#### `wagtail-ai` 的保留与移除门槛

- 当前不能直接卸载：`BlogPage` 仍使用 `AITitleFieldPanel('title')`、`AIFieldPanel('tags')`、`AIDescriptionFieldPanel('intro')`，推广面板也使用 `AIFieldPanel('seo_title')` 和 `AIFieldPanel('search_description')`；项目还导入了 `wagtail_ai` 的 OpenAI backend，并注册了后台样式补丁。
- 新的 `content_ai` 模板功能只替代“根据 BlogPage body 一次生成标题、简介、标签”的自定义按钮流程；它不自动替代 SEO 字段魔法棒、富文本 AI Actions 或第三方其他 Agent。
- 第一阶段建议保留 `wagtail-ai`，将两套功能明确分工：`content_ai` 负责可选择的博客模板生成；`wagtail-ai` 负责尚未迁移的字段级辅助功能。
- 只有在浏览器和代码检查确认不再使用所有 `AI*FieldPanel`、`wagtail_ai.ai.*` backend、相关前端资源和 `WAGTAIL_AI` 配置后，才另立“移除 wagtail-ai”任务；移除时必须先把 SEO/富文本辅助功能迁移或明确下线，不能与模板应用和迁移混在同一个批次。

#### 未来图片 AI 的扩展规则

- 图片生成应新增独立 provider/service、模型和权限，不把图片尺寸、风格、分辨率等字段塞进博客元数据模板。
- 可以共享 `content_ai` 的认证读取、超时、审计接口和 Admin 菜单分组，但不能共享不兼容的输出 schema 或自动保存策略。
- 图片写入媒体库属于独立的数据写入流程，必须另行设计预览、确认、MinIO/媒体回滚和生产授权；不能因为提示词模板已经存在就默认获得写入权限。
