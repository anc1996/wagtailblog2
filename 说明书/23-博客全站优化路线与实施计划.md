# WagtailBlog3 博客全站优化路线与实施计划

## 1. 文档定位

本方案是博客产品、内容运营、前台体验、搜索、性能和运维的总路线图。它不替代以下专项文档：

- `09-搜索架构容量与演进方案.md`、`10-搜索架构实施计划.md` 及搜索生产部署文档；
- `18-Markdown本地导入实施计划与任务包.md`、`21-浏览器脚本直连Markdown导入博客方案.md`；
- `20-博客正文二级标题间距修复方案.md`、`22-运行时代码注释与类型标注方案.md`；
- `systemctl.md`、部署与备份恢复手册。

本文件回答的是“整个博客接下来往哪里建设、按什么顺序建设、怎样判断可行”，不是立即授权生产变更的操作单。

## 2. 背景与现状证据

### 2.1 已知架构事实

根据现有项目说明书，系统使用 Django 5.2/Wagtail 7.4，站点由 Wagtail 页面树驱动，博客核心模型为 `BlogIndexPage`、`BlogPage` 和 `BlogPageForm`。MySQL 保存页面、revision、元数据、评论、统计和搜索控制面；MongoDB 保存 BlogPage 正文及历史快照；MinIO 保存媒体；Redis 提供缓存、计数器和 Celery broker/backend；Elasticsearch 同时承载内容搜索和日志索引。

正文保存存在受保护的一致性边界：`BlogPage.body` 的 StreamField 序列化、`markdown_block` key、Mongo 正文、revision pointer 和 `mongo_content_id` 必须保持兼容。发布、撤回和删除通过 Wagtail 生命周期 API，并由搜索 outbox/maintenance 队列完成最终一致同步。

生产入口为 Nginx + uWSGI + systemd，相关应用服务包括 Django、maintenance Worker、Beat 和 Filebeat。生产环境还受 MySQL、MongoDB、Redis、MinIO、Docker 和 Elasticsearch 的启动顺序、read alias 和备份恢复约束影响。

### 2.2 当前仍需在实施前核实的事实

本总方案不假设“已有功能就等于已启用或健康”。第一阶段必须重新读取：

- 当前 `main` 分支、HEAD、远程分支和工作树状态；
- 实际首页、博客索引、文章详情、归档、标签、作者、搜索和后台页面；
- 生产/测试服务状态、uWSGI socket、Nginx 路由、环境文件和队列配置；
- 当前内容量、文章长度分布、媒体体积、搜索延迟、索引积压和错误率；
- 桌面与移动端的真实浏览器表现，包括溢出、遮挡、静态资源失败和控制台错误。

在这些证据完成前，性能数值只作为目标值，不作为现状结论。

## 3. 目标与成功标准

### 3.1 产品目标

1. 读者能快速找到内容、连续阅读，并在文章结束后继续发现相关内容。
2. 作者能稳定导入、编辑、预览、审核、发布和修订文章，降低正文和媒体出错概率。
3. 搜索结果可理解、可追踪、可恢复，索引异常不会破坏正文或页面生命周期。
4. 站点在移动端、慢网络和高内容量下仍保持可用、可访问和可维护。

### 3.2 工程目标

- 所有变更沿用现有 Django/Wagtail、StreamField、MongoDB、Celery 和搜索契约。
- 生产变更可观测、可回滚，且不删除 BlogPage 正文、草稿、revision 或 Mongo 数据作为故障处理手段。
- 关键页面和异步链路有自动化测试、浏览器验收和运行指标。

### 3.3 建议验收指标

指标需在阶段 0 采样后冻结基线；以下为初始目标而非现状声明：

| 领域 | 目标 |
|---|---|
| 首页/文章详情 | 移动端 LCP P75 ≤ 2.5s，CLS P75 ≤ 0.1，INP P75 ≤ 200ms |
| 页面可靠性 | 公开页面 5xx < 0.5%，静态资源 404 为 0 |
| 搜索 | 常规查询 P95 ≤ 800ms；索引延迟 P95 ≤ 5 分钟 |
| 内容一致性 | 正文、revision pointer、`mongo_content_id` 抽样一致率 100% |
| 异步链路 | pending/processing/retry/dead 有明确阈值和告警，发布事件无静默丢失 |
| 可访问性 | 键盘可完成导航、搜索和文章主要操作；无明显横向溢出；关键控件有名称 |
| 发布 | 每次发布都有精确 commit、测试证据、健康检查和回滚点 |

## 4. 非目标与硬约束

- 不更换 Django/Wagtail，不重写整套前端，不引入新的 CSS/JS 框架。
- 不改变 `markdown_block` 存储 key、既有 StreamField 序列化协议或 Mongo 正文格式。
- 不以大批量数据迁移替代渐进式兼容改造；不在未授权情况下发布页面、迁移生产数据库、重建/删除生产索引或清理数据。
- 不新增只消费 `email` 或 `default` 队列的 Worker；搜索任务继续复用 `maintenance` 队列。
- 不把 AI 推荐、复杂个性化和大规模视觉改版列入第一轮交付。

## 5. 总体建设顺序

建议按 6 个阶段、约 12 至 16 周推进。阶段可在测试环境并行准备，但生产发布必须按门禁顺序进行。

| 阶段 | 周期 | 主题 | 产出 |
|---|---:|---|---|
| 0 | 1-2 周 | 基线审计与可观测性 | 指标基线、问题清单、浏览器证据、容量边界 |
| 1 | 2-3 周 | 内容模型与发布质量 | 元数据校验、内容规范、编辑验收清单 |
| 2 | 2-3 周 | 前台阅读与发现 | 首页/文章/列表信息架构、响应式和可访问性修复 |
| 3 | 2-3 周 | 搜索与相关文章 | 查询体验、排序、高亮、相关推荐、索引运营 |
| 4 | 2-3 周 | 性能、缓存与 SEO | 图片、缓存、查询、结构化数据和站点地图优化 |
| 5 | 2 周 | 发布与运营闭环 | 健康检查、告警、备份演练、发布/回滚手册收敛 |

## 6. 分阶段实施计划

### 阶段 0：基线审计与可观测性

**目的：** 先证明问题和收益，避免凭感觉改页面。

**工作包：**

1. 建立页面清单：首页、博客索引、文章详情、归档、标签、作者、搜索、RSS、后台关键路径。
2. 用 Playwright 对桌面和移动视口采集截图、控制台、网络失败和关键交互证据；产物统一写入 `output/playwright/`。
3. 运行 Django `check`、迁移 dry-run、相关测试，并记录测试环境服务端点和依赖状态。
4. 统计页面查询数、响应时间、文章正文大小、媒体大小、缓存命中和搜索 P50/P95。
5. 核对 `ContentSearchState`、`ContentSearchOutbox`、Delivery、read alias 和 maintenance 队列积压。
6. 为 MySQL/Mongo/ES/Redis/MinIO/uWSGI/Nginx/Celery/Filebeat 建立最小健康检查表。

**进入门禁：** 工作树、分支、环境文件和测试数据库身份已核实；无生产写操作。

**退出门禁：** 形成带时间窗口和采样方法的基线报告；每个后续目标都能对应一个基线指标或浏览器证据。

**预期文件：** 主要是 `说明书/` 审计记录、测试脚本或只读检查命令；不预先修改模型、正文或生产配置。

### 阶段 1：内容模型与发布质量

**目的：** 让文章具备稳定的元数据和可运营的生命周期。

**建议需求：**

- SEO 标题、摘要、canonical、分享图、作者、主题、系列、阅读时长和更新时间的后台校验与合理默认值；
- 发布前检查：标题层级、摘要、封面替代文本、重复 slug、空正文、外链/媒体失败提示；
- 系列/主题/作者的公开页和文章末尾导航；
- 预览与 revision 对比流程文档，不自动发布、不改变既有 revision API；
- Mongo 正文写入失败、媒体失败和搜索投递失败时的明确错误、补偿和人工处理入口。

**数据策略：** 优先使用现有字段、snippet、标签和 StreamField；确需新增字段时先做模型/迁移设计，严禁把历史正文转换隐藏在普通 schema migration 中。任何批量补值都必须另立数据方案、备份和用户确认。

**退出门禁：** 新旧文章均能编辑、预览、保存、撤回和发布；正文指针不变；定向测试覆盖失败补偿和权限边界。

### 阶段 2：前台阅读与内容发现

**目的：** 围绕读者任务优化首屏、文章阅读和继续阅读。

**建议页面结构：**

- 首页：最新/精选文章、主题入口、系列入口和清晰搜索入口；减少无助于阅读的装饰区块。
- 文章页：标题、作者、更新时间、摘要、目录、正文、代码/媒体、系列导航、相关文章和分享元数据。
- 列表页：统一卡片信息、分页/游标、筛选状态、空结果和错误状态。
- 移动端：稳定内容宽度、触控区域、无非必要横向滚动；桌面端保持可扫描的正文宽度。

**可访问性门禁：** 语义标题层级、跳过导航、焦点可见、键盘路径、图片替代文本、颜色对比、图标按钮名称和 reduced-motion 行为均需验证。颜色不能作为唯一状态线索。

**实施边界：** 复用现有模板、样式 token 和组件；不在没有基线和评审的情况下替换视觉语言。涉及模板或静态资源时必须进行桌面/移动 Playwright 验收。

### 阶段 3：搜索与相关文章

**目的：** 在已有内容搜索架构上提升结果质量和运营能力。

**建议需求：**

- 标题、摘要、正文、标签、作者和系列的权重排序；中文分词、前缀/容错和高亮；
- 结果显示更新时间、作者、内容类型和匹配片段；无结果时推荐主题/系列；
- 文章页使用相关主题、系列和相似内容，先采用可解释规则，不引入黑盒推荐；
- 搜索慢查询、零结果词、索引延迟、retry/dead 数量和 alias 状态纳入运营面板；
- 继续使用新索引 + read alias，重建完成、追平和一致性检查后再切换。

**硬约束：** 不在 signal 中直接写 ES；不删除正文或 revision 处理搜索故障；不批量重置 Outbox/Delivery/State；生产重建、写入和 alias 切换必须单独授权。

**退出门禁：** 定向查询测试、权限过滤、游标分页、索引失败重试、重放和 alias 一致性均通过；搜索 P95 和索引延迟达到阶段目标或有已批准的容量计划。

### 阶段 4：性能、缓存与 SEO

**目的：** 在真实内容量下减少首屏等待和重复计算。

**工作包：**

1. 图片使用 Wagtail/MinIO 既有 API 生成合适尺寸和现代格式，限制超大原图；正文图片懒加载但不延迟首屏主图。
2. 检查列表页和首页的 N+1，按实际关系图使用 `select_related`/`prefetch_related`；列表默认不读取大正文和 `mongo_content_id`。
3. 对首页、列表、相关文章、RSS 设计可失效缓存；发布、撤回、删除和标签变化时精确失效。
4. 完善 canonical、Open Graph、JSON-LD、RSS/Atom、sitemap、robots、分页 canonical 和旧 URL 重定向。
5. 以 Lighthouse/真实浏览器和服务器指标复测 LCP、INP、CLS、TTFB、缓存命中和错误率。

**退出门禁：** 性能目标在桌面/移动测试集达到；无静态资源 404、明显布局偏移或缓存泄露未发布内容的问题。

### 阶段 5：发布与运营闭环

**目的：** 把可用性变成持续能力，而不是一次性修复。

**工作包：**

- 在 `systemctl.md` 中同步维护四个应用服务、依赖顺序、readiness、日志和验收命令；
- 为网站 5xx、队列积压、搜索 Delivery、Mongo/ES 连接、磁盘/对象存储和证书设置阈值；
- 建立每次发布的固定记录：测试 commit、远程 SHA、生产工作树、备份、重启服务、健康检查和回滚点；
- 至少完成一次测试环境备份恢复演练，验证 MySQL、Mongo、媒体、ES alias 和服务恢复顺序；
- 明确事故处理：先停止受影响写入/服务，再保留证据、恢复上一个验证版本，最后复核首页、后台、搜索、队列和日志。

**退出门禁：** 四个服务 active/enabled，failed unit 为 0；首页、后台、搜索和关键依赖检查通过；回滚步骤在测试环境演练过。

## 7. 文件与模块边界

### 预计可能修改的文件

- `wagtailblog3/apps/blog/`：模型、表单、服务、内容校验和文章上下文；
- `wagtailblog3/apps/home/`、`apps/search/`、`apps/archive/`、`apps/comments/`：按具体需求局部修改；
- `wagtailblog3/templates/`、`wagtailblog3/static/`：页面结构、样式、无障碍和性能；
- `wagtailblog3/tests/`：模型、搜索、模板、性能契约和浏览器辅助测试；
- `说明书/`、`systemctl.md`：实施记录、运维门禁和验收命令。

### 明确暂不修改的文件/对象

- 生产 `.env.production`、凭据、日志、媒体、socket、PID 和运行缓存；
- MongoDB 正文、草稿、revision pointer、`mongo_content_id`；
- 生产索引、read alias、服务 unit、数据库和页面发布状态，除非另有专项方案和确认；
- 与本路线无关的旧代码、格式和文档。

## 8. 测试与验收计划

每个阶段遵循“定向测试 → `manage.py check` → 迁移检查（涉及模型时）→ 浏览器验收（涉及 UI 时）→ 性能/服务检查（涉及运行时）”。

最低门禁包括：

```text
WSL2 wagtailblog-test:
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
相关 apps 定向测试
git diff --check
```

浏览器验收至少覆盖桌面和移动视口、首页/文章/搜索、键盘路径、控制台错误、静态资源和网络失败；所有产物写入 `output/playwright/<task-name>/`。

生产验收不以“进程 active”作为唯一证据，需按 `systemctl.md` 检查依赖、四个应用服务、socket/端口、首页、后台、搜索、队列、Beat、Filebeat、日志和 outbox。

## 9. 数据、服务和安全影响

- 阶段 0、2 的只读审计和模板验证不应产生业务数据；临时测试写入必须使用唯一标识并按精确对象清理，未获授权不得清理真实数据。
- 阶段 1 若新增字段或校验，可能涉及 MySQL 迁移和历史内容兼容；必须先备份、检查 `migrate --plan`，再单独审批生产操作。
- 阶段 3 可能创建新 ES 物理索引、写入 Delivery 和切换 alias；这是高风险操作，必须沿用搜索专项方案的备份、catch-up、一致性和回滚门禁。
- 阶段 4 可能改变缓存、静态文件和 Nginx/uWSGI 行为；需验证未发布内容隔离、缓存失效和服务重启顺序。
- 阶段 5 可能调整监控或 systemd 文档；unit 变更必须 daemon-reload、核对 enable 状态，并按依赖顺序验收。

## 10. 回滚策略

代码问题：恢复到上一个已验证 commit，按实际影响重启 Django/Worker/Beat/Filebeat，并重新执行健康检查。

模板/静态问题：恢复模板和静态文件版本，清理或更新版本化资源缓存，复测桌面/移动页面。

索引问题：停止切换或查询开关，保留失败物理索引和 Delivery 证据，恢复上一个 serving alias；不得删除 Mongo 正文、草稿、revision 或批量重置事件。

迁移问题：只有在确认兼容和有备份时才执行回滚；内容数据修复另立方案，不能用代码回滚代替数据回滚。

## 11. 需要用户确认的决策

在进入实施阶段前，请确认：

1. 是否接受 12 至 16 周、分阶段发布的总体节奏，还是只做 P0/P1 的 4 至 6 周首批。
2. 博客优先服务的读者和内容方向：技术文档、个人写作、资料归档，还是混合模式。
3. 是否允许阶段 0 进行测试环境的只读数据库/ES/Redis 指标采样和浏览器验收。
4. 是否将“相关文章/系列/标签治理”列为第一批产品需求，还是先只做性能和搜索。
5. 任何生产迁移、索引重建、alias 切换、服务重启和真实内容写入，均需在对应专项方案中再次单独确认。

## 12. 模型/推理强度建议

| 工作类型 | 建议角色 | 推理强度 | 选择理由 | 升级条件 | 验证门禁 |
|---|---|---|---|---|---|
| 基线检索、文档整理、指标汇总 | `gpt-5.6-luna` | 低/中 | 范围明确、以事实收集为主 | 发现跨服务冲突或数据风险 | 命令输出、文件和页面证据 |
| 模板、表单、局部服务和测试 | `gpt-5.6-terra` | 中 | 常规 Django/Wagtail 局部实现 | 涉及模型迁移、权限或正文兼容 | 定向测试、check、浏览器验收 |
| 搜索、Mongo/ES 一致性、迁移、生产发布回滚 | `gpt-5.6-sol` | 高 | 涉及数据保护、跨系统契约和不可逆风险 | 任何生产写入、在线重建或回滚失败风险 | 备份、dry-run、catch-up、一致性和人工授权 |

本方案编写属于文档整理和架构路线设计，实际会话使用当前可用模型完成；没有调用外部模型服务，也没有发送源码、凭据、生产日志或正文数据。

### 2026-08-23：搜索/Mongo/ES 一致性修复方案（待单独授权）

#### 根因判断

当前证据更符合“测试 MySQL、MongoDB、ES 不是同一份快照”而不是单纯消费者延迟：MySQL 中 146 个合法 pointer 在当前测试 Mongo 集合中均未命中；同时 State 有 13 个 missing、5 个 stale，Delivery 仍有 pending/retry，且 ES 单节点为 yellow。因此禁止直接 replay 或 rebuild，否则可能把错误数据集重新写入 serving 索引。

#### 分阶段解决路径

1. **冻结与身份确认（只读）**：记录测试环境文件 fingerprint、MySQL/Mongo/ES 数据源、索引前缀、serving target、read alias、State/Outbox/Delivery 汇总和时间窗口；导出不含正文的 ID/hash/版本清单。确认三库是否来自同一备份时间点和同一发布 commit。
2. **建立同快照测试环境**：使用可恢复备份把 MySQL BlogPage/State/Outbox、Mongo formal/revision、ES 目标索引放到同一测试快照；禁止把当前错位测试库直接当作修复输入。此步骤需要数据备份、恢复和用户单独授权。
3. **修复 Mongo 正文可读性**：在同快照上先只读抽样核对 `mongo_content_id`、page_id、revision pointer 和正文 hash；确认正式正文可读后，才允许对明确 target 执行受控 bootstrap/replay。Mongo 缺失的页面必须进入人工清单，不得用空正文覆盖或删除 pointer。
4. **构建隔离物理索引**：新建 test-only 物理索引，写入前执行 mapping、prefix、document count 和 content_hash 预检；优先使用 `search_rebuild_content_index --dry-run`/目标白名单，完成后执行全量 consistency check。不得直接写当前 serving index。
5. **补偿 Delivery**：只有同快照且 Mongo 正文通过校验后，才按 oldest-first 处理 pending/retry/dead；每批记录成功、失败码、版本和 hash，失败继续保留证据，不得批量清零状态。
6. **双重一致性门禁**：要求连续两次全量 `search_consistency_check --strict` 达到 missing/stale/ahead/extra/hash_mismatch/wrong_tombstone 全为 0；Delivery 无 pending/retry/dead；State、Mongo、ES 文档数与 hash 清单一致。
7. **ES 健康与 alias 演练**：测试集群先解决单节点副本策略（测试可明确 replicas=0 的一次性演练，或提供第二节点）；`search_cluster_preflight --strict` 必须通过。之后才可在测试环境执行带 expected_indices 的原子 alias 切换演练，并保留旧索引作为回滚点。
8. **生产门禁**：生产必须另行备份 MySQL/Mongo/ES、确认 green/readiness、审批 target 和 alias 变更、先双写/追平再切换；本轮不执行生产发布、服务重启、生产修复或回滚。

#### 不采用的方案

- 不直接把当前 Mongo 文档按 page_id 猜测映射到 MySQL pointer。
- 不删除 missing/stale 文档来制造“数字一致”。
- 不直接修改 State、Outbox、Delivery 或 `mongo_content_id` 绕过失败。
- 不在 serving index 上原地重建，不在 ES yellow 时切 alias。

#### 验收与回滚

- 验收：同快照 fingerprint、Mongo pointer 命中率 100%（或有人工批准例外）、两次 clean consistency、Delivery backlog 为 0、ES preflight 通过、alias 只指向新物理索引。
- 回滚：切回上一 serving alias，保留失败物理索引和 Delivery 证据；不删除 Mongo 正文、revision 或 pointer。任何迁移仅在兼容性、备份和单独授权齐备后执行。
- 模型/推理建议：数据恢复、跨库一致性和 alias 切换使用 `gpt-5.6-sol` 高/xhigh；只读核验可用 `gpt-5.6-luna` 中；常规脚本/测试使用 `gpt-5.6-terra` 中。升级门禁是数据源 fingerprint 不一致、Mongo 命中率低于 100%、ES 非 green 或出现 hash mismatch。
