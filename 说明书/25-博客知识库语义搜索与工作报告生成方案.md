# 博客知识库语义搜索与工作报告生成方案

## 1. 背景与现状证据

用户希望把某个博客索引页下的多篇 BlogPage 作为“知识库”，通过自然语言提问检索事迹，并据此生成单位简报、工作报告等草稿。

当前代码与文档核实到的事实：

- Wagtail 内容由 `BlogIndexPage`、`BlogPage` 和页面树组织；BlogPage 正文、正式内容 ID 和历史快照受保护，正式正文存放在 MongoDB，MySQL 保存页面与控制字段。
- 现有内容搜索链路为 Wagtail 发布信号 → MySQL outbox/delivery → maintenance Worker → Mongo 正式正文读取 → Elasticsearch 内容索引；失败由 Beat/Worker 补偿。
- Elasticsearch 内容文档当前包含 `page_id/title/intro/body_text/date/locale_id/tag_ids/category_ids` 等字段，已有版本化索引、read alias、重建、回滚和一致性检查命令。
- 现有搜索主要是关键词/BM25 查询；尚未发现面向知识库范围、向量字段、检索增强生成（RAG）或报告草稿持久化的完整功能。
- 项目已有 BlogPage AI 元数据生成能力和 `AI_METADATA_*` 配置，但该能力只用于受限文本的标题/简介/标签建议，不能直接扩展为正文知识库或自动发布流程。
- 现有搜索评测已提供 Recall@10、MRR、NDCG、零结果率和 p50/p95/p99 延迟等指标，并有脱敏 fixture 生成工具，可作为语义检索的 BM25 baseline。

## 2. 目标与非目标

### 目标

1. 允许用户选择一个博客索引页作为知识库范围。
2. 对范围内的已发布文章进行关键词、语义或混合检索，返回可核验的文章片段、标题、日期和链接。
3. 根据检索证据生成简报/报告草稿，逐段标注来源，不能把模型推测伪装成事实。
4. 保留人工编辑、复制、下载和审阅流程；生成结果不自动保存为 BlogPage、不自动发布。
5. 可从小规模测试知识库开始，具备索引重建、失败重试、回滚和成本/质量观测能力。

### 非目标

- 第一阶段不改写 BlogPage 正文、MongoDB 正文、revision、草稿或发布状态。
- 不默认把全站内容发送给外部模型，不在未授权时调用生产数据或生产 AI 服务。
- 不新增独立向量数据库或新的常驻 systemd 服务，除非 PoC 证明现有 Elasticsearch 无法满足容量/性能要求并另立方案。
- 不做“自动写完即发布”、事实补全、虚构数字或无来源的总结。

## 3. 推荐总体架构

采用“范围过滤 + 混合检索 + 带引用生成”的 RAG 架构，分三阶段交付。

```text
用户选择 BlogIndexPage
        ↓
范围解析（页面树后代、live/public、locale、权限）
        ↓
BM25 + 向量召回（Elasticsearch，同一 serving 版本管理）
        ↓
去重、片段截取、时间/来源元数据、证据包
        ↓
模型生成报告草稿（仅使用证据包）
        ↓
引用校验、敏感信息检查、人工编辑/导出
```

### 3.1 知识库范围

- 知识库实体首选引用现有 `BlogIndexPage`，以 page ID 和页面树路径作为稳定范围标识，不复制文章正文。现有博客索引页语义是直接子页；第一版默认 `direct_children`，如需嵌套目录再显式增加 `descendants` 模式，不能静默扩大范围。
- 查询时只允许检索该索引页的公开后代页面，并再次用 MySQL/Wagtail `live().public()` 校验，避免 ES 中的旧文档越权返回。
- 第一版可在查询前取得后代 `page_id` 集合并作为 ES filter；数据量较大时，在索引文档增加受控的 `parent_index_page_id`/`ancestor_index_page_ids` 过滤字段，必须通过版本化索引重建发布。
- 一个用户是否可以访问某个知识库，必须绑定现有 Wagtail 页面权限/后台权限；不能仅凭前端传入的 page ID 放行。

### 3.2 混合检索

- 保留现有 BM25 召回，用于人名、地名、项目名、数字和固定术语。
- 在 Elasticsearch 内容索引的后续版本增加 `dense_vector` 字段和 embedding 模型版本；正文按段落或自然语义块切分，保存 `page_id/chunk_id/content_version/content_hash` 等派生元数据。
- 查询同时执行关键词召回和向量召回，再用加权融合或 RRF 排序；先以离线评测确定权重，不能凭经验固定。
- embedding 优先采用本地部署模型，避免把单位材料发送给第三方。若使用外部 embedding/生成服务，必须单独配置、脱敏、审计和授权。
- 只索引已发布正式正文；草稿、revision、Mongo 指针和未发布内容默认不进入知识库。

### 3.3 证据包与报告生成

证据包至少包含：文章标题、页面 URL、发布日期、命中片段、page ID、content version/hash 和检索分数。生成提示词要求：

- 只能根据证据包写作；证据不足时明确写“资料未提供”；
- 每个事实段落附 `[来源: 文章标题/链接]` 或结构化 citation ID；
- 区分“原文事实”“归纳判断”“待人工补充”；
- 不生成未出现在证据中的姓名、数字、时间、成绩和因果关系；
- 输出结构化 JSON（标题、摘要、正文段落、事实清单、引用、待核实项），服务端白名单校验后再渲染 Markdown/HTML。

报告结果默认只在当前请求中返回预览，不落库。若后续需要历史报告，再新增独立的 `KnowledgeReportDraft` 模型，保存提示词版本、证据 ID/hash、模型版本和人工修改审计，不把结果写入 BlogPage 正文。

## 4. 分阶段实施

### 阶段 0：只读 PoC 与评测（建议先做）

- 选定一个测试环境 BlogIndexPage 和少量已发布文章；优先使用现有脱敏评测 fixture，再补充同义改写、实体、时间范围、索引边界和无答案问题。
- 复用现有 `content_query` 和页面树过滤，实现“指定索引页的关键词检索 + 引用片段”接口。
- 建立至少 100 条脱敏业务问题及人工相关性标注，和现有 BM25 做 A/B；记录 Recall@5/10、MRR、NDCG、引用覆盖率、事实错误率、无证据拒答率、p95 延迟和 token 成本。阈值在评测后确认，不预先硬编码。
- 用固定模型/假模型完成离线报告草稿评测，不写页面、不写 Mongo、不切换生产 alias。

### 阶段 1：混合语义检索

- 新增独立版本化索引 mapping（例如 `content-v004`，具体版本以实施时当前 HEAD 为准），增加 chunk 与 vector 字段。
- 扩展现有 outbox/delivery/rebuild 流程，保证正式正文变更最终一致；embedding 失败进入可重试状态，不阻塞页面发布。
- 增加按 BlogIndexPage 范围过滤、时间范围、标签/分类过滤和引用片段 API。
- 完成测试环境索引创建、批量回填、catch-up、一致性检查和 alias 回滚演练。

### 阶段 2：报告生成工作流

- 增加受保护的报告生成 API/后台入口：选择知识库、报告类型、时间范围、篇幅和语气。
- 先检索再生成；服务端限制最大证据数量、上下文长度、并发和超时。
- 增加引用完整性校验、敏感字段策略、失败降级（只返回证据，不生成）和人工确认。
- 仅在用户明确要求时增加报告草稿历史；不自动发布。

### 阶段 3：质量与运营增强（可选）

- 增加检索/生成评测集、提示词版本、模型版本、成本和错误率仪表盘。
- 对高风险报告增加二次复核模型或规则校验，但不能替代人工事实审查。
- 当 Elasticsearch 向量规模、延迟或运维成本不再合适时，再评估 Qdrant/pgvector 等独立向量存储；迁移必须另行设计备份、双写、切换和回滚。

## 5. 建议的数据与接口边界

### 只读查询接口（建议）

- `GET /api/knowledge-bases/`：返回当前用户可访问的 BlogIndexPage 摘要。
- `POST /api/knowledge-bases/{id}/search/`：输入 query、top_k、时间范围和过滤条件，返回证据片段及引用元数据。
- `POST /api/knowledge-bases/{id}/reports/preview/`：输入报告模板与检索问题，返回未保存的结构化草稿。

所有接口都要在服务端重新校验用户权限、页面 live/public 状态和范围，不接受客户端直接提交正文、Mongo ID 或任意 ES index 名称。

### 配置边界

新增配置应与现有 `WAGTAILBLOG_ENV` 规则一致，测试和生产分离；API key、模型名、embedding 端点和数据保留策略只放 `.env.test`/`.env.production`，不进 Git。现有 `AI_METADATA_*` 仅可作为连接配置参考，不能默认共用其上下文上限或权限。

## 6. 安全、数据保护与失败处理

- 默认只读已发布正式内容；任何草稿/历史 revision 访问都必须单独授权和审计。
- 外部模型请求前做字段白名单、长度限制和必要脱敏；不发送凭据、Mongo 指针、内部权限字段、完整日志或无关文章。
- 模型输出视为不可信文本，必须做 JSON schema、引用存在性、长度、HTML/Markdown 安全和提示词注入检查。
- 文章正文中的“忽略之前指令”等内容只能作为资料，不得改变系统提示或越权调用工具。
- embedding 是从正文派生的数据，仍按受保护内容处理；删除/撤稿必须有 tombstone 或版本失效策略。
- embedding 模型、维度、版本和 content hash 必须写入索引元数据；模型切换只能新建物理索引并通过 alias 切换，禁止原地覆盖。embedding 服务失败进入 retry/dead，不阻断公开搜索。
- 任何索引重建、mapping 变更、生产配置、服务重启和生产数据回填都要独立说明影响、备份、回滚和授权；本方案不授权生产执行。

## 7. 验收标准

### 阶段 0

- 指定 BlogIndexPage 时不会返回其范围外文章、草稿或未发布页面。
- 关键词检索能命中人名/项目名/数字，返回稳定引用链接和片段。
- 20 至 50 条评测问题形成基线报告，结果、错误和缺失证据可复现。
- AI 不可用时仍可返回检索证据；不会写入页面、MongoDB、revision 或生产服务。

### 阶段 1/2

- 关键词、语义和混合检索分别可观测，索引版本、模型版本和 content hash 可追踪。
- 发布、修改、撤稿最终能同步到语义索引；失败可重试，重建可暂停/恢复，alias 可回滚。
- 报告中的事实段落均能定位到证据；无法定位的内容进入“待核实项”或被拒绝输出。
- 桌面/移动端关键流程、权限、超时、空结果和错误状态通过浏览器验收；Playwright 产物写入 `output/playwright/`。

### 2026-08-24：多索引页范围与本地模型方案补充

#### 1. 多个 BlogIndexPage 的范围模型

用户确认知识库需要同时选择多个 BlogIndexPage，并允许选择大范围父索引页检索其后代文章。范围不能简单地把所选 page ID 做 OR，否则父子索引同时选择时会产生重复候选和重复证据。

推荐把一次查询的范围解析为“规范化根集合”：

1. 校验每个所选节点是当前用户可访问的 `BlogIndexPage`，且 `live().public()`。
2. 按 Wagtail `path/depth` 排序；若一个所选节点是另一个所选节点的祖先，则保留祖先、移除其后代作为冗余根。
3. 对每个规范化根取后代 BlogPage；默认排除嵌套的 `BlogIndexPage` 自身，只纳入其下的 BlogPage。
4. 对最终 page ID 做集合去重，并在返回前再次执行 `live().public()`、locale 和 view restriction 校验。
5. 记录 `scope_roots`、规范化后的根集合、`scope_mode` 和 query fingerprint，便于审计和复现。

例如同时选择“公文材料”和其下的“数量关系”时，最终只保留“公文材料”根；“数量关系”文章只出现一次。若用户希望排除父目录下某个子目录，应提供显式 `exclude_roots`，不能依赖多选框的偶然顺序。

第一版建议先用 MySQL/Wagtail 页面树计算 page ID 集合，再将 `terms page_id` 作为 Elasticsearch filter；避免立即改动现有 serving mapping。只有范围规模导致查询过滤过慢时，才在独立知识库索引增加 `scope_root_ids/ancestor_page_ids` 字段并重建。

#### 2. embedding 与生成模型的部署选择

“embedding 模型”和“生成模型”可以分开：

- embedding：优先本地部署，文章正文不离开内网。中文资料可评估 BGE-M3、gte-Qwen2 等模型，实际模型、维度和量化方式必须通过阶段 0 评测决定。
- 生成：支持本地模型（家用 GPU/内网推理服务）和受控第三方服务两种 provider；同一套检索与引用校验流程不依赖具体厂商。
- 外部生成服务只接收筛选后的证据片段，不接收全库、Mongo ID、权限字段或草稿；是否允许发送由环境配置和用户/管理员授权共同决定。

容量估算用于决定硬件和索引设计，不是要求用户预先知道的业务数据：

`向量原始空间 ≈ chunk 数 × 向量维度 × 每元素字节数`。

例如 10 万个 chunk、1024 维、float32 约 410 MB；加上 HNSW 图、倒排索引和副本后，通常按 2 至 4 倍预留，约 1 至 2 GB。模型推理内存另算，量化模型可降低占用。文章数量、总字数、更新量和并发量用于估算 chunk 数、批量回填时间、查询延迟、GPU/CPU 和 token 成本；阶段 0 可通过只读统计命令取得，不需要用户手工提供精确值，也不会输出正文。

#### 3. “报告”对象的定义

这里的报告不是 BlogPage，而是一次基于知识库证据生成的工作材料草稿，例如：

- 某时间段内某主题的工作事迹汇总；
- 多篇文章的时间线、项目进展或成果清单；
- 面向内部编辑的简报初稿、领导讲话素材或汇报提纲。

第一版输出建议为“Markdown 预览 + 可下载 `.docx`”，不保存为 Wagtail 页面。用户确认需要长期留痕后，再设计独立 `KnowledgeReportDraft`，保存证据引用、模型/提示词版本和人工修改记录；仍不自动发布为 BlogPage。是否使用固定模板应作为每次请求参数或可选模板，不把知识库检索和简报模板绑定。

#### 4. 推荐落地顺序

1. 先实现多根范围规范化和只读检索 API，验证父子重叠、排除目录、多语言、撤稿和权限边界。
2. 在测试环境对指定范围做 chunk 统计和本地 embedding 小规模 PoC，测量实际内存、索引大小、回填速度和 Recall/MRR/NDCG。
3. 再接入本地或第三方生成 provider，强制引用、无证据拒答、敏感信息过滤和人工确认。
4. 最后根据用户是否需要历史留痕决定 Markdown/Word 下载与独立报告草稿模型；不默认引入页面保存和发布。

### 2026-08-24：检索速度、质量与资源占用优化方案

用户要求同时优化搜索速度、语义质量、内存和存储。推荐采用“两阶段混合检索”，而不是全库直接向量搜索：

```text
查询
  -> 页面范围/权限过滤
  -> Elasticsearch BM25 召回 50~100 个候选 chunk
  -> 仅对候选做向量相似度重排
  -> 去重、时间/来源约束、证据包
  -> 交给生成模型
```

#### A. 第一阶段：BM25 负责快速缩小范围

- 复用现有 Elasticsearch 文本索引和 IK 分词，先按规范化后的 BlogIndexPage 根集合过滤。
- 标题、专有名词、数字、日期和固定术语由 BM25 保证召回；候选上限默认 100，可按评测调整。
- 对父子索引范围先在 MySQL 计算 page ID 集合，再使用 `terms page_id`，避免把大量无关向量载入内存。
- 查询结果按 `page_id + chunk_no` 去重，避免同一篇长文章占满候选窗口。

#### B. 第二阶段：向量只做重排，不做全库主召回

- 只对 BM25 候选计算向量相似度；查询延迟和 CPU/GPU 使用量与全库 chunk 数解耦。
- 第一版不把向量加入现有公开搜索 serving index，建立独立的知识库语义索引/alias，避免影响前台搜索。
- 采用较低维度的中文 embedding 候选模型，最终维度以阶段 0 评测为准；优先比较 384/512 维模型，不直接默认 1024 维。
- 向量使用 `int8` 或 `float16` 压缩存储；只有离线评测证明质量明显下降时才回退到 float32。模型版本、维度、量化方式写入索引元数据。
- 采用候选重排时，HNSW 的规模和内存压力很小；如果后续必须全库 kNN，再单独评估 HNSW `m`、`ef_search`、分片和副本。

#### C. 分块策略：减少向量数量而不损失上下文

- 以 Markdown 标题、段落和列表边界优先切块，不按固定字符硬切。
- 建议每块约 300~600 个中文字符，重叠 30~80 字；短段落合并，表格/代码/清单保持完整。
- 每篇文章最多保留有限数量 chunk；标题、日期、URL、page ID、chunk 序号和 content hash 作为元数据，不重复保存整篇正文。
- 生成时只取排序靠前的 8~12 个 chunk，并设置总上下文字符/token 上限；不要把 BM25 的 100 个候选全部发送给模型。

#### D. 存储和内存估算

单个向量的近似空间为：

```text
维度 × 每元素字节数
```

以 10 万 chunk 为例：

| 方案 | 单向量粗略空间 | 评价 |
|---|---:|---|
| 1024 维 float32 | 约 410 MB | 质量可能较好，但占用最高 |
| 512 维 float16 | 约 102 MB | 推荐的初始平衡点 |
| 512 维 int8 | 约 51 MB | 存储最低，需评测召回损失 |
| 384 维 int8 | 约 38 MB | 最省资源，中文语义效果需验证 |

以上仅是向量本体；ES 元数据、HNSW 图、倒排结构和副本需另加预留。两阶段检索的主要收益是：查询时只重排 50~100 个候选，避免把全库向量和长正文全部加载到模型上下文。

#### E. 缓存与更新策略

- 对相同的 `scope fingerprint + query + filters + index version + embedding model version` 做短时 Redis 缓存，缓存只保存 page/chunk 引用和分数，不缓存完整正文或模型报告。
- 文章内容 hash 未变化时不重复切块和 embedding；只更新变化文章的 chunk。
- 发布/撤稿沿用现有 outbox/delivery；embedding 失败只影响语义索引，BM25 和前台搜索继续可用。
- 模型升级、新维度或新量化方式必须新建物理索引，通过 alias 切换，保留旧索引用于回滚。

#### F. 推荐的默认参数（仅作为 PoC 起点）

- BM25 候选：100；每篇文章最多 3 个候选 chunk。
- 向量重排：前 50 个候选；最终证据 8~12 个 chunk。
- chunk：300~600 中文字符，重叠 30~80 字。
- 向量：先测 384/512 维 `float16` 与 `int8` 两组；不预先锁定具体模型。
- 缓存：短时、按索引版本隔离；不缓存未脱敏正文。

这些参数不能直接作为生产承诺，必须使用至少 100 条脱敏问题集，与现有 BM25 比较 Recall@5/10、MRR、NDCG、引用覆盖率、p95 延迟和索引内存；只有在质量不低于 baseline 且资源收益明确时才进入下一阶段。
