# 搜索热词与搜索分析方案

> 版本：v1.1（2026-09-01）
> 范围：Wagtail 搜索热词、趋势图、聚合搜索记录和企业化分析演进。
> 状态：方案阶段；当前仅有日粒度聚合实现，小时粒度和逐次事件尚未上线。

## 1. 背景与现状证据

- 后台 `/admin/search-analytics/` 的热门词、趋势和今日列表使用 Wagtail `QueryDailyHits`。该表只有“查询词、日期、hits”三个有效分析维度，不保存单次请求时间、搜索类型、结果数、用户或会话。
- 当前实现只能可靠回答“某日/近 N 日搜索了多少次”，不能伪造“近 24 小时按小时趋势”或“逐次搜索记录”。现有页面存在筛选控件过宽、图表与表格层级不清、移动端信息密度不合理等问题。
- 设计参考 Sub2API 使用记录页的时间范围工具栏、指标卡片、趋势图和明细表结构，但保留本项目 Wagtail 后台的视觉 token、权限和模板体系，不引入新的前端框架。

## 2. 目标与非目标

- 目标：提供近 24 小时、今天、近 7 天、本周、近 30 天和自定义范围；趋势图横轴为时间、纵轴为搜索次数；提供可筛选、可分页的聚合搜索记录表；热门词与趋势使用同一筛选口径。
- 目标：桌面端使用紧凑分析卡片和单列主趋势图，移动端自动堆叠；支持键盘、屏幕阅读器、加载中、空数据和错误状态。
- 非目标：不把 `QueryDailyHits` 伪装成逐次用户行为日志，不采集 IP、账号、Cookie、正文或未授权个人信息；不立即引入 ClickHouse、Kafka 等新基础设施；不修改文章正文、Mongo、ES 内容索引和发布链路。

## 3. 数据能力分层

1. **兼容层（P0）**：继续以 `QueryDailyHits` 支撑今天、近 7 天、本周、近 30 天和自定义日期的按日趋势；历史数据无需迁移，接口明确返回 `granularity=day`。
2. **小时层（P1）**：新增 `SearchHourlyHits` 聚合表，以 UTC `bucket_start`、规范化 `query`、`search_type` 为唯一键，保存 `hits`、`result_count_total`、`no_result_hits` 和 `updated_at`。搜索请求通过现有 Redis/Celery maintenance 通道异步累加，避免同步写 MySQL。
3. **明细层（P2，可选）**：确有逐次请求审计需求时，再增加脱敏、限期保留的 `SearchEvent` 或独立分析索引；默认只存匿名请求标识哈希、时间、查询词哈希/文本、搜索类型和结果数量，严禁存正文和认证信息。

小时层上线前，“近 24 小时”必须显示为不可用或提示“当前仅有按日数据”，不得把当天累计值伪造成小时曲线。小时层上线后，24 小时按小时、7/30 天按日自动选择粒度。

## 4. 页面结构与交互

1. 顶部工具栏：时间范围分段按钮、起止日期（自定义时显示）、粒度（自动/小时/日）、搜索类型（全部/博客）、应用和重置。移动端单列堆叠，触控区域不小于 44×44px。
2. 指标卡片：总搜索次数、活跃查询词数、无结果次数/比例、数据更新时间；只表示当前筛选范围。
3. 主趋势卡片：折线图，横轴时间桶、纵轴搜索次数；悬停和键盘聚焦显示同一数值，缺失时间桶补 0。
4. 热门词区域：增加“热词搜索次数”柱状图，横轴为规范化搜索词，纵轴为该范围内的实际搜索次数，默认显示 Top 10；超过 15 个词不全部绘制柱子。桌面端使用竖向柱状图，移动端可切换为横向条形图或横向滚动容器，避免词语重叠。
5. 搜索记录（聚合）表：时间桶、查询词、搜索类型、次数、结果数/无结果率；支持查询词筛选、排序、每页 20/50/100、分页和页码跳转。
6. 所有筛选通过 AJAX 更新指标、趋势、热词和表格；URL 同步 `range/from/to/granularity/type/q/page/page_size`，请求期间显示 loading，失败时保留旧数据并提供重试。

## 5. 后端接口与性能

- 保留现有 `view=today` 接口；新增统一 `view=dashboard` JSON 接口，返回 `summary`、`trend`、`top_queries`、`records` 和 `pagination`。
- 按时间范围先聚合再分页，禁止逐条加载正文或 Mongo 数据；对小时表建立 `(bucket_start, search_type)`、`(query, bucket_start)` 索引，复用 `QueryDailyHits` 日期/查询索引。
- 近 30 天报表可缓存 30–60 秒；查询词使用规范化字段；限制最大日期跨度和最大返回桶数；高数据量时由 maintenance Worker 预聚合。
- 当前权限要求 Wagtail staff；如需分权，再增加独立 `search.view_searchanalytics` 权限并在菜单和接口同时校验。模板和 AJAX 均必须 HTML 转义，链接由后端 URL 编码。

### 5.1 热词次数柱状图与动态时间筛选（方案阶段）

#### 5.1.1 产品口径

- 图表名称固定为“热词搜索次数”，避免与“搜索趋势”混淆。
- 默认时间范围为“近 30 天”，因为月范围既能反映近期热词，又不会像单日数据一样受偶然查询影响。
- 时间范围提供“日、周、月、年、自定义”五种选项：
  - 日：当天 00:00 至当前时间，按查询词累计；
  - 周：最近 7 个自然日，按查询词累计；
  - 月：最近 30 个自然日，按查询词累计（默认）；
  - 年：最近 12 个月，按查询词累计；
  - 自定义：用户选择起止日期，包含起止日，最长跨度由后端限制。
- 所有统计均累加真实 `hits`，不是统计聚合行数；同一词按规范化后的值合并，大小写、首尾空格和引号差异不能形成重复柱子。

#### 5.1.2 动态交互

1. 用户切换时间范围、日期、搜索类型或查询词筛选后，前端通过 AJAX 请求同一 dashboard 接口，不刷新整页。
2. 请求参数至少包括 `range/from/to/type/top_n`；后端返回 `top_queries`（词、次数、排名、占比）及实际 `from/to/granularity`。
3. 图表显示 loading 状态；请求失败时保留上一次可用图表并显示“加载失败，重试”操作，不清空已有数据。
4. 筛选条件同步到 URL，刷新或复制链接后可以恢复相同报表；切换范围时页码重置为 1。
5. 点击柱子可将该搜索词写入下方“聚合搜索记录”筛选框，但不把点击行为计入搜索次数。

#### 5.1.3 图表与可访问性

- 纵坐标从 0 开始，刻度显示整数次数；tooltip 同时显示搜索词、次数、占当前范围比例。
- 柱子按次数降序排列，颜色只用于视觉区分，排名和数值必须同时显示在表格中，不能依赖颜色传达状态。
- 搜索词较长时横轴标签自动截断并通过 tooltip/表格提供完整值；超过 10 个词时可分页或提供 Top 10/20 切换，避免标签拥挤。
- 图表下始终保留等价 HTML 表格（排名、搜索词、次数、占比、时间范围），支持键盘聚焦和屏幕阅读器；移动端不得产生非必要的页面级横向滚动。

#### 5.1.4 后端聚合与性能

- 日/周/月/年/自定义均先按日期范围聚合，再按规范化搜索词求和并取 Top N；不读取文章正文、Mongo 或 ES 文档。
- P0 继续从 `QueryDailyHits` 聚合，默认近 30 天可缓存 30–60 秒；后端限制最大日期跨度、`top_n`（建议 10–50）和返回数据点数量。
- P1 小时聚合表上线后，近 24 小时才切换到小时数据；本柱状图仍按所选范围汇总到搜索词，不能将小时数据与日数据重复相加。
- 无数据时返回空数组和明确的范围信息；非法日期、反向区间、超长跨度或非员工访问返回稳定错误，不发起无界查询。

#### 5.1.5 验收与回滚

- 验收覆盖默认近 30 天、日/周/月/年、自定义范围、搜索类型筛选、Top N、长词、空数据、越界日期、XSS 转义、键盘操作和移动端布局。
- 同一筛选条件下，柱状图、Top 查询词表和聚合明细表的次数总和一致；切换筛选后旧图表不会覆盖新结果。
- P0 仅修改模板、静态脚本和聚合查询，无数据库迁移；回滚恢复旧图表模板和接口参数，既有 `QueryDailyHits` 数据不回写、不删除。

## 10. v1.2 实施方案（2026-09-01）

### 10.1 现状证据与决策

- `core.py` 在普通 Page 搜索的 `_build_search_results_for_queryset()` 内，以及 `blog`、`all` 两个分支中分别调用 `Query.get(...).add_hit()`；调用路径变化时容易重复或遗漏。`views.py` 的 `SearchAnalytics.log_search()` 只写日志，不增加 Wagtail hit。
- Wagtail 8.0 的 `Query.get()` 使用 `wagtail.search.utils.normalise_query_string()`；项目原 `_clean_query()` 只删除部分引号，不能作为统计、检索和联想的共同口径。
- `QueryDailyHits` 仅保存 `query/date/hits`。因此 P0 的数据只能按日、全部搜索统计，不能推断小时、`search_type`、结果数或无结果率。

P0 决定只复用 `QueryDailyHits`：一次成功的 `perform_search()` 只通过集中函数记录一个规范化词；统一 `view=dashboard` 接口返回同一筛选条件下的概览、连续趋势、热词、按日聚合记录和分页。保留 `view=today` 作为兼容响应，不新增数据库表、不读取正文/Mongo/ES 文档、不改变服务。

### 10.2 P0 设计与文件范围

- 修改：`search/core.py`、`search/analytics.py`、`search/wagtail_hooks.py`、`search/services/suggestions.py`、后台模板、CSS、原生 JS 和定向测试。
- 不修改：模型、迁移、生产数据、Celery/Beat 配置、systemd、`systemctl.md`、搜索正文与索引。
- 统计函数以站点本地日期定义起止日，并生成 `[start_date, end_date]` 的每一个日桶；数据库只查询已有聚合行，服务层以零补齐，避免 SQL 递归日期序列的数据库方言差异。
- 自定义范围要求完整 ISO 日期、起止不反向且最大 366 天；`day/week/month/year` 分别对应当天、近 7 天、近 30 天、近 365 天。P0 固定 `granularity=day`、`type=all`，响应明确说明这些限制。
- Wagtail 的 `QueryDailyHits.garbage_collect()` 未配置 `WAGTAILSEARCH_HITS_MAX_AGE` 时默认保留 7 天。本仓库未发现该清理任务的调度定义，但生产若另有 cron/运维调用，月/年范围会只显示可保留的数据与补零桶。P0 不擅自修改保留期或生产清理；生产发布前必须核对真实调度、现有数据年限与容量预算，并单独授权任何保留期配置变更。

### 10.3 P1 小时聚合与 Redis 缓冲（设计，未实施）

P1 需要单独获得迁移、测试库验证和生产发布授权。模型以 UTC 小时桶作唯一键，避免本地夏令时或时区切换导致重复桶：

```python
class SearchHourlyHits(models.Model):
    bucket_start = models.DateTimeField()
    query = models.CharField(max_length=255)
    search_type = models.CharField(max_length=16)
    hits = models.PositiveBigIntegerField(default=0)
    result_count_total = models.PositiveBigIntegerField(default=0)
    no_result_hits = models.PositiveBigIntegerField(default=0)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=("bucket_start", "query", "search_type"),
                name="search_hourly_bucket_query_type_uq",
            ),
        ]
        indexes = [
            models.Index(fields=("bucket_start", "search_type"), name="search_hourly_bucket_type_idx"),
            models.Index(fields=("query", "bucket_start"), name="search_hourly_query_bucket_idx"),
        ]
```

写入路径以 `timezone.now().astimezone(datetime.UTC).replace(minute=0, second=0, microsecond=0)` 生成桶。请求成功后仅执行 Redis `HINCRBY` 到 `search:analytics:hourly:<UTC-hour>`，字段为经过 Wagtail 标准规范化并安全编码的 `query/search_type`，并在同一 pipeline 中设置有限 TTL。不能把正文、Cookie、用户身份或原始请求日志写入 Redis。

maintenance Worker 每分钟用 `RENAMENX` 将活动 key 换到带唯一 flush token 的 key 后读取并删除；失败时保留该 flush key 供重试。对 MySQL 使用参数化 `INSERT ... ON DUPLICATE KEY UPDATE hits = hits + VALUES(hits), ...`，或在事务中按唯一约束逐批 upsert。`bulk_create(ignore_conflicts=True)` 单独使用会静默丢失已存在行的增量，不能作为最终策略。Worker 结束后删除成功 flush key；不允许 Web 请求直接写小时表。

保留策略为：Redis 活动/flush key 最长 48 小时；MySQL 小时表保留 90 天。清理由 maintenance Beat 每天执行一次、每批受限的 `bucket_start < utcnow - 90 days` 删除。生产启用前必须确认备份窗口、清理批次、监控指标、队列路由为 `maintenance`，并获得单独授权；回滚先停止新 Worker/Beat 和读路径，再保留表数据，不能删除历史 `QueryDailyHits`。

3. 颗粒度

   - 颗粒度不是简单地“范围越大选项越多”，还要限制预计桶数量，避免在 2K 屏幕或移动端出现几百根不可读的柱子。
   - 基础可用规则（闭区间自然日跨度）：

     | 跨度 | 可用颗粒度 | 默认颗粒度 | 说明 |
     | --- | --- | --- | --- |
     | 1-7 天 | 日 | 日 | 短期查看明细 |
     | 8-31 天 | 日、周 | 周 | 日仍可下钻，周作为默认概览 |
     | 32-180 天 | 周、月 | 周 | 隐藏日，避免超过约 6 个月的日柱 |
     | 181-364 天 | 月 | 月 | 隐藏日、周 |
     | >=365 天 | 月、年 | 月 | 年用于长期概览，月保留趋势细节 |

   - 以上阈值还要经过桶数校验：日目标不超过 31 桶、周目标不超过 27 桶、月目标不超过 60 桶、年目标不超过 20 桶。若将来调整阈值，必须以“图表桶数上限”作为门禁，而不是只改前端显示条件。
   - 五年自定义范围的可用选项明确为“月、年”，不显示“日、周”；默认选择“月”。月桶按自然月首日，年桶按自然年 1 月 1 日，均使用站点本地日期边界。
   - 预设范围默认值优先遵循产品语义：今天、昨天、近 7 天为日；近 14 天、近 30 天、本月、上月为周（若实际跨度不足则回退到日）；本年/今年为月。自定义范围按上表和桶数规则计算默认值。
   - 用户手动选择后，只要新范围仍支持该颗粒度就保留，否则回退到新范围默认值；后端响应 `available_granularities`、`granularity`、`default_granularity` 和 `bucket_count`，前端只展示后端允许的选项，避免前后端阈值漂移。

4. 局部刷新边界

   - 范围和颗粒度应用后，仅请求 `view=dashboard`，更新概览、搜索趋势和热词环形图。
   - 聚合搜索记录继续由查询词、每页数量、列设置、分页单独请求 `view=records` 控制；上方范围改变不清空记录区，也不覆盖记录区自己的范围状态。
   - 热词点击只写入记录查询词并刷新记录区，不改变上方三块分析。

## 15. 搜索分析后台局部刷新请求模式方案（2026-09-02，待确认）

### 15.1 调研证据

- `/admin/archive/dashboard/` 首次返回完整页面；日期筛选表单由脚本拦截，使用 GET 请求 `/admin/archive/posts-filter-ajax/`，仅替换 `#posts-list-container` 内的服务端渲染 HTML。归档统计分页使用 `/admin/archive/stats-ajax/?archive_page=N`，仅替换 `#archive-stats-container`。两个区域互不刷新整页。

- 当前搜索分析页面实际上已经用 `fetch` 局部更新，但 dashboard 和 records 仍共用 `/admin/search-analytics/?view=...` 页面路径：首次加载后分别请求 `view=dashboard` 与 `view=records` JSON，前端再拼装全部 DOM；两个请求共用一个 `AbortController`，快速切换时可能互相取消。浏览器网络记录显示交互未发生整页导航，但请求形态不如归档端点清晰。

### 15.2 目标与非目标

目标：

- 保持 `/admin/search-analytics/` 只负责页面壳和初始静态结构；时间范围/颗粒度/Top N 仅刷新概览、趋势和热词区域，记录筛选/分页/列设置仅刷新记录区域。
- 采用归档相同的“专用 AJAX URL + 目标容器替换”模式，让网络请求、缓存策略、错误边界和浏览器调试更直观；交互过程中不触发整页导航。
- 保留 URL 可分享、前进/后退恢复、键盘焦点、加载状态、失败重试和 staff 权限校验。

非目标：

- 不改变 `QueryDailyHits`、MongoDB、搜索打点、统计口径、时间颗粒度规则、环形图/柱状图视觉设计或记录筛选语义。
- 不新增数据模型、迁移、Redis/Celery 写入、生产服务配置，也不把归档页面代码复制成第二套通用框架。

### 15.3 推荐设计（P0）

1. 端点拆分

   - 新增 staff-only GET 端点：`/admin/search-analytics/dashboard/`（概览、趋势、热词及范围元数据）和 `/admin/search-analytics/records/`（记录、分页及列所需字段）。请求带 `Accept: application/json` 与 `X-Requested-With: XMLHttpRequest`。
   - 暂时保留现有 `?view=dashboard`、`?view=records` 分支作为兼容包装，内部转发到同一服务函数；既有书签、测试和旧脚本不会立即失效。兼容分支稳定后再单独评估弃用周期。
   - 所有 AJAX 端点仅接受 GET，统一返回 `{ok, data, error}`；异常不返回 HTML 错误页，避免前端误把登录/500 页面当 JSON。

2. 响应和容器边界

   - dashboard 返回现有 `summary/trend/top_queries/range` 数据结构，可额外提供用于局部状态的 `canonical_url`；前端只重绘三个分析容器，不触碰 records DOM。
   - records 返回现有 `records/pagination/range` 结构；前端只重绘表体、表头可见性和分页，不触碰概览/趋势/热词。
   - 沿用当前 `textContent` 创建节点和后端 URL 编码规则，避免把查询词或错误消息拼进 `innerHTML`。如果后续要完全复用归档的服务端片段模式，再单独增加 `_summary.html`、`_trend.html`、`_top_queries.html`、`_records.html`，本批不预先引入模板复制。

3. 前端请求控制器

   - 将当前共享 `controller/requestId` 拆为 `dashboardController/dashboardRequestId` 与 `recordsController/recordsRequestId`；上方筛选取消或替换 dashboard 请求时，不取消记录请求，反之亦然。
   - 抽取 `requestJson(url, params, controller)`：设置 10 秒超时、JSON 校验、HTTP 错误转换和 AbortError 静默处理；成功后才 `pushState/replaceState`，失败保留上一次内容并显示可聚焦“重试”。
   - `aria-busy` 分别挂在分析区和记录区；更新后将焦点回移到对应标题。`popstate` 根据 URL 同时恢复两个独立状态，但不会触发整页 reload。

4. 后端代码组织

   - 从 `register_search_admin_urls` 的嵌套闭包中提取 `_dashboard_ajax`、`_records_ajax` 和页面渲染函数，统一参数收敛、staff 校验、错误码和响应头；继续复用 `SearchAnalytics.build_dashboard()` 与 `get_records()`，不重复实现聚合 SQL。
   - 保留 `analysis_q` 与 `records_q`、`range` 与 `records_range` 的隔离契约；禁止上方筛选请求改变记录区状态。

### 18.1 背景与现状分析

1. **现状菜单结构问题**：
   - 当前在 Wagtail 管理后台主侧边栏中，直接存在一个一级菜单项 **“搜索分析”**（挂在 `register_admin_menu_item`，order=800）；

3. **保护与治理边界**：
   - **底层数据模型不可废弃**：我们的搜索分析和搜索建议底层强依赖 `wagtail.contrib.search_promotions` 提供的 `Query` 与 `QueryDailyHits` 表，因此不能在 `INSTALLED_APPS` 中移除该应用，更不能删除底层表。
   - **治理方式**：应当通过 Wagtail 原生 Hook 机制，在菜单构建阶段完成“隐藏原生 Search terms 菜单项”以及“将搜索分析注册为报告子菜单项（`register_reports_menu_item`）”，实现纯展示层治理。
