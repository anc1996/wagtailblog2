## 1. 原始需求规格与业务边界 (原 01)

系统初期定位为基于 **Django + Wagtail CMS** 的技术知识库与个人/企业博客出版平台：
- **核心受众**：技术博主、知识管理者及内容审阅人员。
- **初始核心功能**：
  1. **文章发布与管理**：支持树状页面组织、富文本/Markdown 编辑、封面图设置与多分类标签绑定。
  2. **版本与历史**：支持页面草稿保存、版本历史比对与回滚。
  3. **互动与检索**：提供读者评论互动、基于 Wagtail 原生搜索的关键词查询与站内归档。
- **非功能约束**：页面首屏加载时间 < 1.5s，单实例支持日常上百并发访问，数据具备单机定期备份能力。

## 2. 早期概要与详细设计基线 (原 02, 04)

- **分层架构**：
  - **展示层**：Django 模板引擎（DTL）+ Bootstrap 基础组件，响应式栅格布局。
  - **业务层**：Wagtail Page 树状模型（`BlogIndexPage` 作为容器，`BlogPage` 作为文章实体）。
  - **持久层**：初期使用单体 MySQL 数据库承载全部页面数据与富文本内容。
- **页面生命周期**：
  - 文章状态依附于 Wagtail 原生的 `live`、`has_unpublished_changes` 与 `go_live_at` 字段。
  - 依赖 Wagtail `Page.save_revision()` 实现草稿与已发布版本切分。

## 3. 早期数据库与 API 设计 (原 03, 06)

### 3.1 初始数据库结构
- **MySQL 实体**：
  - `wagtailcore_page`：页面基础元数据（ID、路径、层级、标题、别名 slug、发布状态）。
  - `blog_blogpage`：扩展字段（副标题、发布时间、摘要、关联分类与标签）。
  - `blog_blogcategory` / `blog_blogpagetag`：分类与多对多标签表。
  - *局限*：此时正文直接存储在 MySQL 的 `body` 字段（JSON 格式 StreamField），随着富文本字数增加与修订版本累加，数据库单表迅速膨胀。

### 3.2 初始 API 契约
- 基于 Django REST Framework 暴露基础 REST 接口：
  - `GET /api/v1/posts/`：博客文章分页列表。
  - `GET /api/v1/posts/<slug>/`：博客正文详情。
  - `GET /api/v1/categories/` 与 `/api/v1/tags/`：分类和标签索引。

## 4. 早期运维与经验沉淀 (原 05, 07, 08)

### 4.1 初始部署形态
- 单台 Linux 虚拟机，采用 Nginx + Gunicorn + MySQL 部署。
- 采用本地磁盘存储媒体文件，定时脚本执行 `mysqldump` 进行冷备份。

### 4.2 早期痛点与后续重构动因（经验总结）
1. **正文膨胀问题**：MySQL 存储长文 StreamField 与频繁生成的历史 Revision 导致数据库 I/O 压力大，备份恢复耗时激增，催生后续**“MySQL 存元数据、MongoDB 存正文”**的多库异构重构。
2. **搜索瓶颈**：原生数据库模糊搜索与 Wagtail 基础索引缺乏分词智能与同义词扩展，催生后续**“自建独立 Elasticsearch 内容索引”**改造。
3. **内容录入效率**：后台手动复制粘贴排版繁琐，催生后续**“Markdown 跨端导入工具链”**研发。
