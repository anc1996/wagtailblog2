# 专题指南正文外置实现方案

> 更新日期：2026-10-15。本文维护正文外置的当前基线，以及已确认、待实施的通用回收站改造设计。
>
> 本轮交付仅为设计文档。下文新增字段、Mixin、恢复界面、物理移除搜索文档和 GC 命令均为实施清单，不代表已经上线。批次 1 优先补齐通用元数据、接口与守卫契约；禁止仅完成字段迁移就开放逻辑删除。

## 1. 当前基线与本次改造目标

### 1.1 权威数据与现有入口

| 数据 | 权威来源 | 当前入口及边界 |
|---|---|---|
| 页面 ID、具体模型行、父子树、标题、slug、权限、Locale | MySQL Page 及业务模型 | Wagtail 页面生命周期 |
| 历史草稿与版本清册 | MySQL Revision | 外置正文只保留版本凭证，不把完整正文复制进 SQL |
| 正式、草稿、审批正文指针与发布代次 | `ExternalContentPublicationState` | `page_id` 是主键；无 Page 级联外键 |
| 不可变正文版本 | MongoDB `external_content_versions` | `ContentVersionStore`；保存失败不得同步补偿删除正文 |
| 搜索期望状态与投递凭证 | `ContentSearchState`、Outbox、Delivery | SQL 事务记录事件，事务外投递 ES |
| 搜索命中 | Elasticsearch 投影 | 可重建；不能作为恢复或正文来源 |

### 1.2 必须明确的现状差异

| 项目 | 当前代码 | 本次确认的目标 |
|---|---|---|
| MySQL 删除 | `execute_safe_page_deletion()` 调用 `page.delete()`，随后标记 `mysql_deleted` | 第一阶段保留 Page、业务行及全部 Revision，改为受控逻辑删除 |
| Mongo 删除 | 保留版本；`perform_garbage_collection()` 入口硬阻断 | 初期保持阻断；未来满足保护期与引用核查才允许物理清理 |
| ES 删除 | TOMBSTONE 消费写入不可搜索墓碑文档 | 回收站事件要求物理 unindex；SQL 墓碑继续保留 |
| 恢复 | 取消待删除意图不等于恢复已删除 SQL 页面 | 新协议在原父栏目原位恢复，ID 与历史不变，统一 `live=False` |
| 通用性 | 已有通用外置 Mixin、注册表和快照适配器；部分旧搜索信号绑定 BlogPage | 通用生命周期和守卫按能力发现模型；不硬编码 GuidePage |

因此，旧文档“已实现 MySQL 软删除”“现有墓碑已满足 ES 物理删除”的描述作废。既往已物理删除的 SQL 页面不会因增加字段而重新出现，只能按已有 Manifest 提供受控快照预览。

### 1.3 保留的正文版本契约

当前页面声明方式如下，具体字段继续由业务模型定义：

```python
from external_content.mixins import ExternalContentPageMixin
from wagtail.models import Page

class ExamplePage(ExternalContentPageMixin, Page):
    content_storage = {"body": "mongo"}
    content_storage_schema = 1
    content_search = {"type": "example", "label": "示例"}
    # body 等业务字段按现有模型正常定义。
```

Mongo 以 `version_id` 唯一标识文档，同时对以下六键建立复合唯一约束：

```text
model_label, page_id, field_name, codec, schema_version, payload_sha256
```

读取、恢复及未来删除均须核对六键身份和载荷摘要。`get_raw_version_document()` 不执行完整校验，不能将其原始结果直接用于后台渲染；优先使用 `get_version(version_id, expected_identity)`。复制或别名可以合法引用源页面不可变版本，不能强制每个正文版本的 `page_id` 等于回收站目标 ID。

SQL 事务失败不能回滚已写入 Mongo 的版本；保留待对账版本，不在异常处理里删除。搜索仅取正式发布快照，不回退到最新草稿或 `Page.body`。

## 2. 已确认的生命周期与交付边界

### 2.1 状态及可见性

| 场景 | MySQL Page 与 Revision | Mongo 正文 | 前台与搜索 | 后台操作 |
|---|---|---|---|---|
| 正常草稿 | 保留 | 保留 | 不公开、不索引 | 编辑、按权限发布 |
| 正式发布 | 保留 | 保留正式与历史版本 | 仅正式快照可索引 | 按原生命周期操作 |
| 移入回收站 | 保留全部；`live=False`；冻结写入 | 全部保留 | 立即按 SQL 守卫隐藏，提交后物理 unindex | 只读预览、申请恢复 |
| 恢复草稿 | 原 ID、原父栏目、全部历史不变；`live=False` | 原版本引用不变 | 不索引、不自动上线 | 人工核对，再手动发布 |
| 满 7 天但未认领回收 | 继续保留 | 继续保留 | 持续隐藏 | 仍可恢复，直到不可逆回收认领获胜 |
| 未来物理回收 | 先清理目标 SQL 页面及其专属历史 | 再逐版本核查并清理无引用版本 | 保留 SQL 搜索围栏，ES 中无对应文档 | 不再允许原位恢复 |

7 天是最短保护期；到期只获得候选资格，不承诺在第 7 天立即释放全部空间。保护期内保留历史草稿必然占用存储，这是可恢复能力的成本。

### 2.2 通用状态转换

以下为拟新增协议 v2；旧意图仍按 v1 解释。

```text
正常页面
  └─ SQL 原子移入回收站 → TRASHED
       ├─ 校验通过且尚未进入不可逆回收 → RESTORED（该意图终态）
       │    └─ 页面状态回到 ACTIVE，但 live=False；手动发布后才公开
       └─ 到期 + 全部前置条件通过 + 独占认领 → PURGING_SQL
            └─ SQL 页面/专属 Revision 删除提交 → MYSQL_DELETED
                 └─ Mongo 逐版本核查与清理 → COMPLETED
```

同一轮重复删除返回原意图，不延长保护期。恢复后再次删除创建新 UUID 意图和新保护期。失败必须记录具体阶段；SQL 已删除、Mongo 待重试不能报成全部回收成功，也不能恢复成原位页面。

初期只实现设计中获准的批次。`perform_garbage_collection()` 及同步孤儿清理的 Fail-Closed 阻断保持不变；后续解除需要另行审核、隔离演练和明确操作授权。

## 3. 批次 1：通用元数据模型详细设计

### 3.1 设计选择

复用现有 `ExternalContentPublicationState` 作为每页唯一生命周期权威行，新增独立的纯 Python `RecycleBinPageMixin`，由现有 `ExternalContentPageMixin` 继承。不给 Wagtail Page 基表增加字段，不要求每个具体业务页面分别增加回收字段。

页面正常存在、是否处于回收站、是否允许写入，统一读取 Page 和状态表；不能只看 `live=False`，因为普通未发布草稿同样是 `live=False`。不能把任意历史删除意图存在作为永久冻结依据。

### 3.2 扩展 ExternalContentPublicationState

以下全部为拟新增字段：

| 字段 | 类型 / 默认值 | 业务语义 |
|---|---|---|
| `recycle_state` | `CharField(16)`，默认 `active` | `active / trashed / purging / purged`；与发布状态正交 |
| `active_deletion_intent_id` | 可空 `UUIDField(unique=True)` | 当前删除轮次的唯一权威指针；逻辑关联，无级联 FK |
| `requires_manual_publish` | `BooleanField(default=False)` | 恢复时置 True；只允许受控人工正式发布事务解除，阻止别名同步或自动任务重新上线 |

沿用现有 `publication_generation` 作为公开状态代次。回收站、恢复及再次正式发布均按公开状态变化推进代次；它与搜索 `content_version` 是两个不同的序列，不能混用。

约束设计：

- `page_id` 主键保证每页只有一个生命周期权威行；事务持有该行锁后才能绑定新轮次。
- `active` 必须没有活动意图；`trashed / purging / purged` 必须关联当前轮次。采用 MySQL 支持的普通 CHECK 及可空唯一索引，不使用条件唯一索引模拟“活动意图唯一”。
- 绑定时在服务内检查意图的 `page_id`、`model_label`、协议及状态。跨表一致性由受控服务和对账负责，不能宣称 CHECK 可校验其他表。
- 恢复成功清空活动指针，旧意图保留 `restored` 终态；锁服务只依据权威状态及活动轮次判断冻结。
- `requires_manual_publish=True` 时页面不得 `live=True`，SearchState 不得进入可搜索 UPSERT。普通草稿编辑不解除该锁存；“人工发布”由已鉴权的 Wagtail 发布动作上下文确认，不能信任请求中的布尔值或后台任务伪造的操作标记。
- 历史 SQL 已删除但状态行存在时，Page 缺失仍是失败关闭条件，不因默认 `active` 获得恢复或写入资格。

### 3.3 扩展 ExternalContentDeletionIntent

保留现有 UUID、Manifest、版本进度、claim 围栏、重试字段。新增如下：

| 字段 | 类型 / 默认值 | 用途与历史值处理 |
|---|---|---|
| `protocol_version` | `PositiveSmallIntegerField`，旧行默认 1 | 新逻辑删除服务显式写 2；不得将旧数据自动升级为可恢复 |
| `page_title_snapshot` | 可空 `TextField` | 删除时标题；旧数据为空显示“未记录” |
| `original_parent_id` | 可空 `PositiveBigIntegerField` | 原父栏目 ID；无级联 FK，父栏目删除不能删除审计 |
| `original_slug` | 可空 `CharField(255)` | 恢复冲突复核依据 |
| `trashed_at` | 可空 `DateTimeField` | 逻辑删除事务内记录的动作时间；与 SQL 物理删除时间区分 |
| `protection_started_at` | 可空 `DateTimeField` | 删除提交后观察到的保护期起点，见下述计时规则 |
| `mysql_deleted_at` | 可空 `DateTimeField` | 仅 SQL 真实物理删除时记录；旧行不能用 `created_at` 冒充 |
| `restored_at` | 可空 `DateTimeField` | 原位恢复时间 |
| `restored_by_id` | 可空 `CharField(255)` | 恢复人标识；不因用户删除而丢失审计 |
| `deletion_batch_id` | 可空 `UUIDField(db_index=True)` | 子树批量删除的原子闭包编号；每页仍各有意图 |
| `lifecycle_snapshot` | `JSONField(default=dict)` | 见下述版本化元数据；不含正文和凭据 |

`lifecycle_snapshot` 定义 `schema_version=1`，固定原父栏目模型、原 `url_path` 展示值、Locale/翻译身份、别名来源、原 `live` 状态、最新/正式/审批 Revision ID，以及被取消的定时发布和工作流审计标识。树的旧 `path/depth/numchild` 仅能诊断，严禁作为恢复时的写回值。

`manifest` 继续保存所有外置字段的版本、每版 `expected_identity`、`revision_ids` 和别名关系。固定默认预览对应的最新草稿 Revision，同时保留原正式 Revision 供切换查看；不能把两个版本正文拼在一起。

保护期计时采用保守确认：

1. 移入回收站事务内先填写 `safe_gc_after` 的暂定值；`protection_started_at=NULL` 表示禁止 GC。
2. 原事务提交后的短事务按当前活动轮次 CAS，一次性记录 `protection_started_at=now` 和 `safe_gc_after=now+7天`。这保证最短期限不早于原删除提交后 7 天。
3. 提交后回调中断时由后续协调任务完成初始化；初始化之前界面显示“保护期初始化中”，任何回收器均拒绝认领。重复删除或重试不重置已经确认的起点。
4. 所有时间持久化使用时区感知时间，按统一 UTC 比较；后台按用户时区展示。

状态枚举保留旧值，新增 `trashed / restored / purging_sql`。`mysql_deleted` 仍明确表示 SQL 已物理删除，不能重新解释为“仅逻辑删除”。新协议失败保留活动状态并写错误；不要让笼统 `failed` 覆盖是否已跨越 SQL 删除提交点。

索引复用 `(status, safe_gc_after)` 和 `(page_id, status)`，新增 `(protocol_version, status, safe_gc_after)`；是否增加其他索引由实际查询计划决定。

### 3.4 新增 ExternalContentRetainedRevision

仅在意图 JSON 中记录 Revision ID 无法阻止原生历史清理，因此增加显式保留关系：

| 字段 | 类型 | 约束 |
|---|---|---|
| `intent` | FK → 删除意图，`on_delete=PROTECT` | 审计意图不能在仍承担保留责任时删除 |
| `revision` | FK → `wagtail.models.Revision`，`on_delete=PROTECT` | 原生清理不得删除回收站所需历史 |
| `created_at` | `DateTimeField(auto_now_add=True)` | 保留登记时间 |

增加 `(intent, revision)` 唯一约束。删除事务固定该页全部 Revision 并登记，测试原生 `purge_revisions`、单条及 QuerySet 删除的真实保护行为，不能只测试应用自己的清理函数。

恢复时历史仍然保留；保留关系随恢复意图继续存在，不在恢复操作中顺便清理旧草稿。再次删除时新轮次覆盖当前完整 Revision 集。未来该页物理回收时，统一核查并释放该页各轮次保留关系；其他页面或独立保留责任的关系属于阻断项，不可越权移除。

### 3.5 搜索围栏的最小模型扩展

复用已有 SearchState、Outbox、Target 和 Delivery，不建立另一套搜索队列：

- `ContentSearchOperation` 拟新增 `UNINDEX="unindex"`；保留 TOMBSTONE 对旧事件的兼容解释。
- SearchState 与 Outbox 拟增加可空 `recycle_intent_id: UUID`，将物理移除请求绑定到删除轮次；恢复后仍保持 `searchable=False`，只有新正式发布才能创建 UPSERT。
- `content_version` 继续在 SearchState 行锁下严格递增，并用作 ES external version；不改成删除意图 `generation` 或 `publication_generation`。
- “搜索移除完成”按该轮事件的全部受管目标 Delivery 汇总，不在意图上新增容易失真的单一成功布尔值。

真实物理 unindex 还需要每物理目标、每页的持久写入串行化与结果未知处理，详见第 6 节。批次 1 不凭上述三个字段宣称该并发问题已经解决。

## 4. 批次 1：通用 Mixin 与服务接口

### 4.1 能力发现与继承

拟新增 `external_content/recycle.py`，承载 `RecycleBinPageMixin`、不可变结果对象和通用服务接口；`ExternalContentPageMixin` 复用它，现有业务模型保持原继承声明。

复用外置注册表及搜索 `ContentRegistry` 的模型发现。模型身份来自 `_meta.label_lower`，正文版本来自字段策略和 codec。核心不得出现 `sender=GuidePage`、`model_label=="guides.guidepage"`、Guide 专用表名或“只有 body 字段”的假定。

兼容现有外置协议的其他 Page 模型通过继承、字段声明和现有注册检查即可复用能力。仅继承一个类不能自动迁移旧 BlogPage 的存储格式；不兼容模型要提供适配器，通过系统检查前不准参与可恢复删除。

### 4.2 拟定接口

以下为接口草案，不是已落地代码。类型对象拟在同模块定义，页面实例只委托通用服务，不直接执行跨存储 IO：

```python
from dataclasses import dataclass
from typing import Literal
from uuid import UUID

from django.contrib.auth.models import AbstractBaseUser

@dataclass(frozen=True)
class RecycleEligibility:
    allowed: bool
    reason_codes: tuple[str, ...]

@dataclass(frozen=True)
class RecycleResult:
    intent_id: UUID
    page_id: int
    state: Literal["trashed", "restored"]
    search_cleanup: Literal["pending", "completed"]

class RecycleBinPageMixin:
    """声明通用回收能力；权限、锁与事务由统一服务执行。"""

    def get_recycle_eligibility(
        self, *, actor: AbstractBaseUser
    ) -> RecycleEligibility: ...

    def move_to_recycle_bin(
        self, *, actor: AbstractBaseUser, request_id: str
    ) -> RecycleResult: ...

    def restore_from_recycle_bin(
        self, *, actor: AbstractBaseUser, intent_id: UUID, request_id: str
    ) -> RecycleResult: ...
```

配套服务边界：

| 拟定服务接口 | 职责 |
|---|---|
| `build_recycle_plan(page_id, actor)` | 只读发现页面、子树、外部别名及版本闭包，返回阻断原因；不预先写意图 |
| `trash_page_tree(plan, actor, request_id)` | 获锁后重新验证闭包，在一个 SQL 事务登记元数据、保留历史、冻结页面并记录搜索事件 |
| `check_restore(intent_id, actor)` | 当前父栏目、slug、模型、Locale、权限、版本可用性预检；结果非锁定承诺 |
| `restore_page_tree(intent_id, actor, request_id)` | 获锁重验后原子恢复；每个页面均 `live=False`，不创建发布事件 |
| `get_recycle_snapshot(intent_id, revision_id, actor)` | 权限及 Manifest 归属校验，严格加载正文；只读，无初始化索引副作用 |
| `inspect_gc_candidates(filters)` | 独立只读扫描，返回候选、阻断及不完整数据；不调用真实回收器 |

`request_id` 用于脱敏追踪，不作为授权依据。恢复使用意图 UUID 与活动轮次 CAS 防止旧页面按钮恢复另一轮删除；重复提交同一轮已完成动作返回一致结果。

### 4.3 生命周期拦截覆盖面

覆盖 Wagtail 删除动作、实例删除、树 QuerySet/批量删除、上层栏目级联，以及发布、下架、保存 Revision、复制、翻译、移动、别名同步、工作流、定时发布和导入命令。

逻辑删除必须在 Django Collector 和 Treebeard 物理删除前转入通用服务；仅覆盖实例 `delete()` 或 `pre_delete` 信号不足。最终物理删除入口只允许未来受控 GC 使用，普通调用不能靠传一个公开布尔参数绕过回收流程。直接 SQL 不属于框架可拦截范围，运维账号按权限和操作流程约束。

所有写入入口共同执行当前轮次守卫：回收站页面拒绝编辑、发布、复制和移动；普通草稿可写。前台 `serve`、路由、API、sitemap、feed、菜单和搜索都排除回收站页面。后台原生页面树、选择器和编辑入口也需适配，保留行不得以“普通草稿”身份继续操作。

批次 1 只建立接口和守卫前提，不激活新的删除路由。完整写入口与读入口未覆盖前，功能开关保持关闭。

## 5. 删除、恢复、冲突和历史草稿

### 5.1 第一阶段：移入回收站

1. 校验删除权限、模型能力和整个目标子树；检查子树外依赖该页的别名、自动化任务及模型限制。不支持的混合模型或活动外部别名阻断整个操作，不能悄悄转为物理级联。
2. 按现有锁层级，对整个闭包统一排序获锁：Page → PublicationState → 按 ID 排序的 Revision → DeletionIntent；新增历史保留关系在所属层完成。之后才进入 SearchState → Outbox 的搜索子序列。所有路径保持同一顺序。
3. 获锁后复核拓扑、版本和权限，登记每页意图和保留关系。固定最新草稿、旧正式版本及全部历史引用。
4. 保留页面及树位置，设置 `live=False`、状态 `trashed`；取消定时发布和活动工作流执行，保存审计。原定时发布字段和审批状态不得在恢复后自动重启。
5. 在同一 SQL 事务推进公开代次及 SearchState 的 `content_version`，写 `UNINDEX` Outbox。SQL 回滚时这些变更一起回滚。
6. 提交后确认保护期起点、失效前台缓存并唤醒搜索投递。尝试有时限的同步 unindex；失败由持久事件继续重试，界面显示真实进度。

不移动到虚拟回收站树节点，不改写原父关系；原 slug 和栏目容量继续占用。父栏目自身后续移动时，子树按 Wagtail 当前树状态移动，恢复按父 ID 及当前树校验，不把旧路径写回。

### 5.2 恢复前的冲突检查

| 条件 | 处理 |
|---|---|
| 原父栏目已不存在、在回收站、模型不允许接收该页 | 拒绝恢复，提示原因；不自动换栏目 |
| 原 slug 被冲突数据占用 | 拒绝恢复；不自动改名或覆盖另一页 |
| 模型未安装、Locale/翻译身份冲突、别名来源不完整 | 拒绝并标注阻断项 |
| Manifest 身份错误、版本缺失、Mongo 不可用 | 拒绝恢复，保留回收状态；不返回空正文充当成功 |
| 无回收站恢复权限或无原父栏目当前新增子页权限 | 拒绝；菜单权限不能替代目标权限 |
| 该轮正在不可逆回收或 SQL 页面已物理删除 | 拒绝原位恢复 |
| 原父栏目只是移动，ID 及容纳规则仍有效 | 按当前树关系原位恢复，展示当前父栏目 |

树内已回收父子页必须按批次闭包恢复，先统一验证，全部成功或全部回滚。首版不支持从已回收父栏目中单独迁出子页。外部链接、媒体、评论等关系需要按具体模型列入预检，不能一律承诺可恢复所有第三方状态。

### 5.3 恢复提交规则

恢复事务与 GC 竞争同一权威行和活动轮次。恢复获胜后，意图为 `restored`、页面状态为 `active`、活动指针清空，页面 ID、父 ID、slug、具体行和所有历史 Revision 保持。

强制 `live=False`、`has_unpublished_changes=True`、`requires_manual_publish=True`，清空当前生效的正式/审批指针及 Page 的 `live_revision`；原正式快照只留在意图和历史中。Page 最新 Revision 及状态表草稿指针统一指向删除时固定的最新草稿。不得把旧 Revision 中的 `live=True`、工作流或计划发布时间写回运行态；历史 Revision 内容本身不改写。

搜索状态继续不可搜索，并推进版本围栏拒绝旧发布事件；恢复本身不产生 UPSERT、不从 Mongo 拉正文写进 ES。必要时补发新的 UNINDEX 以确认旧文档仍不存在。恢复后编辑人员可看全部历史，选用历史内容保存为新草稿，再手动正式发布；发布流程重新核验身份、权限和正文凭证。

持久的人工发布锁存同样约束别名同步、导入、定时任务及工作流完成回调。恢复的别名不能因来源页面再次发布而自动上线；若当前别名机制无法提供受控人工发布入口，则首版将该类恢复标为不支持并提示原因，不能绕过规则自动激活。人工正式发布成功后才在同一 SQL 事务解除锁存并生成 UPSERT。

## 6. Elasticsearch 信号守卫与物理 unindex

### 6.1 生产者与信号职责

| 入口 | SQL 事务内动作 | 提交后动作 |
|---|---|---|
| 通用移入回收站服务 | `live=False`、活动意图、递增版本、记录 UNINDEX | 唤醒投递；有时限地等待物理移除结果 |
| 通用恢复服务 | `live=False`、恢复轮次、不可搜索及新版本 | 不索引；必要时继续清除旧投影 |
| 人工正式发布动作 | 确认 `active` 和人工动作权限；同事务解除人工发布锁存、持久化 `live=True`，正式 Revision 与 Manifest 一致后记录 UPSERT | 根据正式快照索引 |
| `page_published` 通用守卫 | 拒绝回收状态及不一致的伪发布；复用当前事务上下文避免重复事件 | 只能唤醒已有事件 |
| `page_unpublished` / 删除兼容信号 | 仅做一致性校验及兼容路由，不能成为绕过受控服务的入口 | 不直接用页面内存正文索引 |

信号按通用能力或注册表分派，不绑定具体业务类。受控动作承担事务边界；非法发布在动作入口阻断，事务内信号再校验，不能指望一个发生在提交后的信号回滚已经提交的页面。非受控发布必须整笔回滚，不能只拦截搜索而留下 `live=True` 的页面。

沿用 `record_final_publication()`、`record_final_tombstone()` 的事务模式，扩展独立的 UNINDEX 生产接口。事件必须在页面变更的原始事务内写入，`on_commit` 只用于唤醒或投递，禁止在回调里补造业务 Outbox。

现有外置生命周期与这些搜索生产接口的完整接线仍需实施时补齐并验证；已有服务函数不等于全部动作已经覆盖。旧 BlogPage 兼容信号与 v2 生产者必须互斥或幂等，不能双重递增。

### 6.2 消费者共同守卫

每次 UPSERT，无论来自 Outbox、重建、回填、重放、标题建议还是 Wagtail 原生索引更新，都必须确认：

1. Page 存在、当前 `live=True`、公开权限通过，状态为 `active` 且 `requires_manual_publish=False`。
2. 事件 `content_version`、公开代次、模型身份及正式快照与 SQL 当前权威值一致。
3. 正文仅取该正式 Manifest；任何草稿、旧正式或恢复前事件均不能替代。

不满足即丢弃或标记过期，不发送正文。适配搜索结果最终 SQL 守卫，覆盖高亮、建议、统计和缓存重放；不能只从结果卡片隐藏标题，却继续在摘要、facet 或计数泄露回收数据。无法安全重算的聚合应暂不展示。SQL 权威检查不可用时失败关闭。

### 6.3 物理移除及迟到写入围栏

当前 tombstone 是 ES 文档 UPSERT，需要新增真正的删除适配器。删除按稳定文档 ID 及 `content_version` 处理，保留 SQL SearchState 和 Outbox 证据；不能删除权威状态后从 1 重新计数。

**仅将 UPSERT 改成 ES delete 不足以满足安全性。** ES 删除记录的版本记忆不能当成永久业务围栏；早先已经发出的 UPSERT 可能在删除后才执行。Worker 租约到期、调用端超时或一次“删除后查不到”均不能证明旧请求不会迟到。

实施前必须完成以下协议与故障证据：

- 所有写入路径纳入 `(ES 连接、物理索引、page_id)` 的受控顺序执行；记录持久发送尝试及其结果，事务外发送 ES，不长时间占用页面 SQL 锁。
- UNINDEX 发送前关闭该轮旧写入准入并处理已有在途写入。只有确认旧写入结束、无法再影响目标后，才能确认物理移除完成。
- 结果未知的旧请求不能仅凭租约过期视为取消。若不能确认终止，则目标保持清理待确认，阻止其作为构建完成目标切换上线；必要时隔离旧物理目标并切换到验证过的替代索引。切换是独立受控运维动作。
- 同一页未来重新发布也必须等待或隔离旧 UNINDEX 尝试，防止迟到删除移除新发布文档；幂等 404 需要结合当前版本和投递状态解释。
- 覆盖全部 serving/building 正文目标，以及实际包含该页的标题、建议和原生页面索引。不能只清服务别名、漏掉构建索引，导致重建切换后复活。
- 物理移除确认必须包含搜索可见性刷新策略及逐目标确认；当前 bulk 写入没有提供这一完成语义。不得把“请求已发出”记为“搜索文档已移除”。

上述全写入路径收口与在途请求处理，是满足物理 unindex 要求的发布阻断条件，不能在批次 1 中以伪代码锁或一次回查宣称完成。

### 6.4 故障时的准确语义

SQL 与 ES 没有共同事务。SQL 提交后立即通过权威读守卫阻止新的前台访问；ES 正常时提交后同步尝试物理移除并等待确认。ES 故障时保留不可见状态和 Outbox 重试，后台明确显示“已移入回收站，搜索清理待完成”。

只有全部受管目标确认后才能显示“搜索清理完成”。不能承诺 ES 不可用时仍瞬间完成物理删除，也不能把提交后 ES 失败伪装成 SQL 删除已回滚。逻辑隐藏与物理清理有独立确认状态，但都是最终验收必测项。

## 7. 后台回收站交互与权限

菜单名称为“外置内容回收站”。超级管理员及专门授权角色可见，列表与详情采用同一服务端查看权限；另设恢复权限，并复核目标父栏目当前权限。拟使用 `external_content.view_recycle_bin`、`external_content.restore_recycle_bin` 权限码，后台隐藏按钮不替代接口鉴权。

列表展示：标题、模型、原页面 ID、原父栏目、逻辑删除时间、保护期截止/剩余时间、删除人、搜索清理状态及可恢复状态。按 `trashed` 活动轮次展示新回收站，历史 `mysql_deleted` 作为“仅快照、不可原位恢复”分类。到期未回收记录继续可查，不能仅按 `safe_gc_after > now` 将其隐藏。

详情提供：

- 删除时最新草稿的只读正文，允许切换旧正式和历史 Revision；明确标注所查看版本。
- “恢复为草稿”操作及冲突说明；恢复成功链接到原 ID 编辑页，提示人工核对后正式发布。
- 原父栏目、原位置与当前父栏目位置的区别，7 天保护说明，以及搜索清理进度。
- 历史缺失元数据展示“未记录”，不根据当前同 ID 数据猜测删除时的标题或父栏目。

预览必须先核对意图权限、Revision 属于该意图、Manifest 身份及摘要，再使用已有 codec 和安全模板渲染；禁止原始 HTML 无条件 `safe`。页面设置私有、禁止缓存及收录，无编辑表单和发布按钮；普通前台预览链接不能访问回收正文。GET 不创建版本、claim 或索引。

恢复为 POST + CSRF + 活动轮次校验；重复点击、权限变化、超时未知结果均通过回读状态确认，界面不在未知状态下盲目重提。倒计时以服务端截止时间为准，客户端只显示。

## 8. 只读 GC 检查与未来物理回收

### 8.1 inspect_gc_candidates --dry-run

拟新增命令：

```bash
python manage.py inspect_gc_candidates --dry-run
```

默认即只读；显式 `--dry-run` 用于确认意图，不提供写模式。可增加 `--intent-id`、`--limit` 和 `--format=json`，实现时按分页扫描并输出有无下一页；单页数量不能冒充全库总数。

候选范围包括已确认保护期且到期的 v2 回收轮次，以及符合旧协议核查条件的历史 SQL 已删除意图。v1 可按原有 `safe_gc_after` 报告到期，但缺乏提交后计时证据时应单列“保护期依据待核验”，不能因为新增字段为空就伪造证明；待核验记录不能列为预计可回收，也不能进入未来物理删除。v2 的 `protection_started_at=NULL` 或仅有暂定截止时间同样不能获得回收资格。输出意图、协议、阶段、版本 ID、三类引用数量与来源标识、预计可回收/被引用阻断/检查不完整的数量；不得输出正文、凭据或敏感请求。

三道引用核查：

| 核查 | 权威来源 | 说明 |
|---|---|---|
| 当前运行引用 | 发布/草稿/审批状态及别名来源链 | 其他页面的有效指针阻断正文删除 |
| Revision 引用 | 存续 Revision 的结构化外置 Manifest | 所有受管模型；不能只全文搜索 JSON 字符串 |
| 保留与删除意图引用 | 其他有效删除轮次、显式保留关系 | 保留期内和处理中引用不可忽略 |

v2 页面仍在 SQL 中时，自身保留的运行及 Revision 引用是“随该页 SQL 删除计划释放”的内部引用，报告必须单列；不能把它们误报为已归零，也不能永久当成外部阻断。Mongo 真正删除前必须在 SQL 删除提交后再查一次三类引用。

损坏 Manifest、未知 codec、无法枚举的模型、Mongo/SQL 断连均记为“不完整，禁止回收”，不能记为 0。别名复用版本按六键身份追踪来源。

命令不得认领、改状态、建索引、写 Redis/Outbox、清理临时版本或调用 `perform_garbage_collection()`。只读连接路径也要避免 store 构造触发初始化写入。报告是观察结果，不是未来执行的授权凭证，也不消除扫描后的并发竞争。

### 8.2 后续真正回收的准备条件

以下只定义后续边界，本轮不开放执行：

1. 确认保护期、操作授权、模型能力、搜索物理移除完成和备份/回滚边界；所有待回收数据都有明确范围。
2. 按相同锁顺序争抢权威活动轮次。GC 进入不可逆状态后恢复必须拒绝；恢复先提交则 GC 必须退出。认领失败或过期不自动证明旧 Worker 不会继续执行。
3. SQL 事务内再次核查依赖和闭包，按计划释放本页各轮次历史保留关系，删除目标 Page、业务行及其专属 Revision、已取消任务的可清理关联；写 `mysql_deleted_at`、状态和持久进度。外部引用、共享资产或保护关系阻断时整笔回滚。
4. SQL 提交后重新执行三类引用检查，并针对版本建立有效的删除围栏。所有能新增引用的保存、发布、复制、别名和恢复路径必须遵循同一围栏，消除“查完无引用后又被引用”的竞争。
5. 仅对完整六键身份匹配且无引用的版本调用受控删除；逐版本记录成功、共享保留或待重试。Mongo 失败不回写假成功，不尝试伪造恢复已删除 SQL 页面。
6. 处理完毕再确认终态；共享版本仍被别页引用时保留并记录原因，不以“清该页”为由删除整集合或共享正文。旧 v1 意图不得冒认新 v2 恢复能力。

“彻底清理”指目标页面及其专属历史、无引用正文已物理移除；不删除共享图片、文档、别页版本。必要的最小审计和 SQL 搜索围栏继续保留。完成后按明确审计保留策略压缩该页各轮意图 Manifest、旧快照/事件等不再需要的载荷；不能无限保存全部过程数据，也不能提前移除迟到事件围栏。行/文档删除不等于数据库文件立即缩小，不默认执行 OPTIMIZE、compact 或磁盘维护。

## 11. 迁移、启用与回滚边界

先做向后兼容增量字段/表迁移，旧意图默认 v1，不通过推断补造 `mysql_deleted_at`、原父或标题；本轮不执行迁移。迁移执行、存量修复及真实清理均须在明确环境与范围下另行授权。

功能关闭时保留当前行为基线；启用前必须完成逻辑删除、读写守卫、ES 全写入路径收口、历史保留和故障验证。独立复核未通过，不向编辑开放可恢复删除。

启用前可回退代码且保留新增 schema。**一旦存在 v2 回收站记录，就不能直接回退到会对同一批 Page 执行物理删除的旧代码。** 此时先关闭删除/恢复/GC 写入口，保留读取及隔离守卫，按活动意图逐项对账，再制定兼容回退。禁止删除状态表或保留关系来“解除卡住”。

未来真实 GC 的不可逆边界是 SQL 物理删除提交，Mongo 删除进一步扩大不可逆范围；跨库只能依靠授权备份恢复，不能宣称 `atomic()` 可回滚整个流程。
