## 1. 状态流转与并发矩阵

### 1.1 核心状态流转模型

页面在 MySQL 关系存储与外置正文系统中的生命周期状态由 `ExternalContentPublicationState.recycle_status`（页面运行状态）与 `ExternalContentDeletionIntent.status`（删除意图生命周期）双轴定义。

```
                   [用户创建/发布]
                          │
                          ▼
                   ┌──────────────┐
                   │    ACTIVE    │ ◄────────────────────────┐
                   │ (正常在册/草稿)│                          │
                   └──────┬───────┘                          │
                          │ [软删移入回收站]                  │ [人工手动发布]
                          ▼                                  │ (清除锁存/推送ES)
                   ┌──────────────┐                          │
                   │   TRASHED    │                          │
                   │(保护期/ES下架) │                          │
                   └──┬────────┬──┘                          │
      [原位恢复草稿]  │        │ [7天到期+三道引用归零]       │
      (保持live=False)│        │ (GC Worker认领排他锁)        │
                      ▼        ▼                             │
               ┌──────────┐  ┌─────────────┐                 │
               │ RESTORED │  │ PURGING_SQL │                 │
               │(草稿锁存)│  │ (终态清理中) │                 │
               └─────┬────┘  └──────┬──────┘                 │
                     │              │ [SQL级物理删除]         │
                     │              ▼                        │
                     │       ┌─────────────┐                 │
                     │       │  COMPLETED  │                 │
                     │       │(永久Tombstone)                │
                     │       └─────────────┘                 │
                     └───────────────────────────────────────┘
```

#### 状态迁移与不变式契约表

| 当前状态 | 触发动作 (Trigger) | 目标状态 | 前置条件 (Preconditions) | 原子变更与副作用 (Atomic Actions) | 后置守卫与外置状态 (Invariants) |
|---|---|---|---|---|---|
| **ACTIVE** | `move_to_recycle_bin` (软删除移入回收站) | **TRASHED** | 1. 页面存在且 `recycle_status="active"`；<br>2. 无未完成的删除意图；<br>3. 用户具备删除权限。 | 1. Page 设置 `live=False`, `has_unpublished_changes=True`；<br>2. `PublicationState.recycle_status="trashed"`, `trashed_at=now`；<br>3. 记录原父栏目 `original_parent_id=page.get_parent().pk`；<br>4. 创建 `ExternalContentDeletionIntent` (`status="trashed"`, `protocol_version="v2"`, 标题快照，`safe_gc_after=now+7d`)；<br>5. 生成 ES `UNINDEX` 写入 SearchOutbox (`searchable=False`, `content_version+=1`)。 | 1. Page 与所有历史 Revision 完整保留在 MySQL；<br>2. MongoDB 全部不可变正文版本完整保留；<br>3. 触发写入冻结（阻止任何日常保存/发布/审批）；<br>4. ES 搜索立即物理下架。 |
| **TRASHED** | `restore_to_draft` (原位恢复为草稿) | **RESTORED** | 1. `recycle_status="trashed"`；<br>2. 关联删除意图未被 GC 认领；<br>3. 原父栏目 Page 存在且可追加子页；<br>4. 原位置 slug 无冲突；<br>5. 用户具备恢复权限。 | 1. `PublicationState.recycle_status="restored"`, `restored_at=now`；<br>2. 设置 `requires_manual_publish=True`（锁存）；<br>3. 关联删除意图标记为 `CANCELLED` (`restored_at=now`, `restore_actor_id`)；<br>4. Page 维持 `live=False`, `has_unpublished_changes=True`。 | 1. 保留原 Page ID、原父栏目、全部历史 Revision；<br>2. 恢复日常编辑保存能力；<br>3. 严禁 ES 重新索引；<br>4. 阻断一切自动化定时/工作流上线。 |
| **RESTORED** | `publish` (后台人工手动发布) | **ACTIVE** | 1. `recycle_status="restored"`；<br>2. `requires_manual_publish=True`；<br>3. 编辑在 Wagtail 管理后台显式点击“正式发布”；<br>4. 用户具备发布权限。 | 1. Page 设置 `live=True`；<br>2. `PublicationState.recycle_status="active"`；<br>3. 清除 `requires_manual_publish=False`；<br>4. 递增 `publication_generation += 1`，更新正式 Manifest 快照；<br>5. 生成 ES `UPSERT` 写入 SearchOutbox (`searchable=True`, `content_version+=1`)。 | 1. 页面重新正式对外公开；<br>2. 仅依据本次正式发布的 Manifest 生成搜索文档；<br>3. 恢复标准在册生命周期。 |
| **TRASHED** | `claim_for_gc` (GC 巡检认领并准备物理删除) | **PURGING_SQL** | 1. `safe_gc_after <= now`（满 7 天）；<br>2. 运行引用、Revision 引用、意图引用三道核查严格归零；<br>3. 成功获取 Level 1~4 全局排他锁。 | 1. `DeletionIntent.status="claimed"`, `claimed_worker`, `claim_token`；<br>2. 状态原子标记为 `PURGING_SQL`；<br>3. 准备执行 MySQL Page、Revision 及专属数据的物理级联删除。 | 1. 永久关闭原位恢复入口；<br>2. 任何并发恢复请求立即 Fail-Closed 阻断；<br>3. 物理删除具备回滚隔离日志。 |
| **PURGING_SQL** | `finalize_gc` (物理删除完成) | **COMPLETED** | 1. MySQL 物理记录完全清除成功；<br>2. Mongo 对应专属无引用正文版本删除成功。 | 1. `DeletionIntent.status="completed"`, `completed_at=now`；<br>2. 意图记录作为只读 Tombstone 永久归档留存。 | 1. 彻底物理清理完成；<br>2. 释放全部行级锁与并发围栏。 |

### 1.2 全局排他锁获取顺序 (Global Lock Hierarchy)

为杜绝跨存储死锁与并发更新冲突，所有涉及页面生命周期变更的事务，必须在同一个 `transaction.atomic()` 内严格按以下分层全序获取排他行锁（`select_for_update`）：

```
Level 1: Page 基础表行锁
  └── 契约：Page.objects.select_for_update().get(pk=page_id)
  └── 严禁：严禁调用 .specific，严禁加载正文字段，严禁触发 hydration。

Level 2: ExternalContentPublicationState 状态表行锁
  └── 契约：ExternalContentPublicationState.objects.select_for_update().get(page_id=page_id)
  └── 作用：保护 recycle_status, publication_generation 与 requires_manual_publish 标量。

Level 3: Revision 历史版本表行锁 (集合按主键严格升序)
  └── 契约：Revision.objects.select_for_update().filter(object_id=str(page_id)).order_by('id')
  └── 作用：防止软删除或恢复期间发生并发草稿保存/修订生成。

Level 4: ExternalContentDeletionIntent 删除意图表行锁 (集合按主键严格升序)
  └── 契约：ExternalContentDeletionIntent.objects.select_for_update().filter(page_id=page_id).order_by('id')
  └── 作用：排他校验活动删除轮次，防止重复软删或与 GC 巡检认领冲突。

Level 5: ContentSearchState 搜索状态表行锁 (可选：需同步更新搜索版本时)
  └── 契约：ContentSearchState.objects.select_for_update().get(page_id=page_id)

Level 6: ContentSearchOutbox 搜索事件插入
  └── 契约：以单调递增的 content_version 写入持久事件，事务提交后由 Worker 异步投递。
```

**多页操作锁序规范**：涉及别名链（Alias Closure）、跨栏目移动或整树操作时，必须先将所有目标 `page_id` 进行 `sorted(set(page_ids))` 标量升序排序，逐页依次执行 Level 1~4，严禁交叉乱序。

### 1.3 并发冲突与拦截规则矩阵

| 竞争操作 A | 竞争操作 B | 锁竞争与仲裁顺序 | 最终行为与隔离保证 |
|---|---|---|---|
| **移入回收站 (Trash)** | **保存草稿 / 发布 (Save/Publish)** | 操作 A 获取 Level 1 锁，操作 B 阻塞等待。操作 A 完成提交后，页面 `recycle_status="trashed"` 且存在未取消的删除意图。 | 操作 B 唤醒后，触发 `check_page_write_not_blocked` 检查，抛出 `ExternalContentOperationBlockedError`，事务安全回滚，草稿/发布被彻底拒绝。 |
| **移入回收站 (Trash)** | **重复移入回收站 (Trash 重复点击)** | 并发请求竞争 Level 1/4 锁。首个请求完成软删除，创建意图并将状态置为 `TRASHED`。 | 第二个请求获锁后，前置检查发现页面已处于 `TRASHED` 或存在活动删除意图，抛出幂等提示或明确错误，不产生重复意图与重复 UNINDEX 事件。 |
| **回收站恢复 (Restore)** | **移入回收站 (Trash)** | 状态互斥：恢复操作仅在 `recycle_status="trashed"` 时准入；移入回收站仅在 `recycle_status="active"` 时准入。 | 获锁后无论谁先执行，后者均因前置状态校验不通过而直接终止，绝不发生状态覆盖。 |
| **回收站恢复 (Restore)** | **GC 物理认领 (GC Claim / Purge)** | 核心高危竞争：两方均必须在 Level 4 获取 `ExternalContentDeletionIntent` 的排他行锁。 | **情况 1 (Restore 先获锁)**：意图仍为 `TRASHED`，恢复流程将意图更新为 `CANCELLED`。GC 随后获锁，检查意图已非待回收状态，安全跳过；<br>**情况 2 (GC 先获锁)**：GC 将意图更新为 `CLAIMED`/`PURGING_SQL`。恢复流程随后获锁，前置检查发现意图已锁定执行清理，抛出 `Fail-Closed` 致命错误阻断恢复。 |
| **回收站恢复 (Restore)** | **定时发布任务 / 异步工作流自动发布** | 恢复操作原子设置 `requires_manual_publish=True` 且 `live=False`。 | 定时发布或工作流执行前核验 `requires_manual_publish`；只要该标志为 True，无条件拒绝发布并记录告警日志，杜绝意外自动重新上线。 |
| **已恢复草稿保存 (Save Restored Draft)** | **正式手动发布 (Manual Publish)** | 恢复后允许日常编辑保存。保存操作按标准获取 Level 1~3 锁，更新草稿版本。 | 保存仅更新 `draft_manifest`，不清除 `requires_manual_publish`，不触碰正式 Manifest。直到编辑显式执行 Publish，方才校验权限、清除锁存并推送 ES。 |

### 2.2 字段可空性与向后兼容性确认

1. **绝对可空与安全默认值**：
   - 所有新增时间戳（`trashed_at`, `restored_at`, `mysql_deleted_at`, `protection_started_at`）及引用 ID（`original_parent_id`）一律声明为 `null=True, blank=True`；
   - 状态标量一律提供无害的安全默认值：`recycle_status="active"`、`requires_manual_publish=False`、`protocol_version="v1"`、`page_title_snapshot=""`。
2. **存量历史数据零破坏**：
   - 现有库中所有存量 `ExternalContentPublicationState` 记录自动获得 `recycle_status="active"`、`requires_manual_publish=False`，完全延续既有运行行为；
   - 现有历史 `ExternalContentDeletionIntent` 记录自动获得 `protocol_version="v1"`，新版回收站将其归类为“历史硬删意图（仅快照只读，不可原位恢复）”，界面展示“未记录”字段，不推测补造。
3. **只读 GC 巡检兼容**：
   - `inspect_gc_candidates --dry-run` 扫描时区分 `v1` 与 `v2`。针对 `protocol_version="v1"` 且缺少 `protection_started_at` 的历史记录，单列“保护期依据待核验”，不伪造通过证明，不赋予物理删除资格。

### 2.3 数据库迁移与安全双向回滚方案 (Rollback Steps)

#### 增量迁移执行步骤（批次 1 授权后）
1. 在测试环境运行 `python manage.py makemigrations external_content --name add_recycle_bin_fields`；
2. 审查生成的迁移文件，确认所有 `AddField` 均包含合法的 `default` 或 `null=True`；
3. 仅在明确授权且做好备份后，在测试库执行 `python manage.py migrate external_content`。

#### 安全双向回滚预案
1. **代码回滚优先**：若在发布新特性前发现缺陷，只要数据库中**尚无处于 `recycle_status="trashed"` 的活动页面**，可随时无害回滚应用代码至前一版本。新增的数据表字段对旧版代码完全不可见且无任何约束冲突。
2. **数据库结构回滚**：
   - 执行 `python manage.py migrate external_content <上一个迁移编号>`；
   - Django 将生成对应的 `RemoveField` DDL，安全移除新增的扩展列，核心主键、外置 Manifest 及原有 safe_gc_after 数据完全不受任何影响。
3. **回滚熔断守卫**：
   - 严禁在数据库存在 `recycle_status="trashed"` 的页面时盲目执行代码或迁移回滚！因为旧版代码缺失软删除识别逻辑，一旦对该页面触发 Wagtail 原生删除将直接引发底层硬物理删除。
   - 回滚前检查脚本必须确认：`ExternalContentPublicationState.objects.filter(recycle_status='trashed').count() == 0`。

## 3. 搜索与通用性设计确认

### 3.1 `RecycleBinPageMixin` 通用抽象基类设计

本设计基于 Wagtail 的抽象 Mixin 机制，通过将回收站生命周期与外置正文能力正交解耦，沉淀为独立的通用 Mixin。**核心逻辑严禁包含任何 `guides.models.GuidePage` 引用或其特有字段（如 `sub_title`, `steps` 等）**，保证全站任何页面模型只需继承该基类即可零成本获得全套安全回收与搜索守卫能力。

```python
# wagtailblog3/apps/external_content/mixins.py

from __future__ import annotations
from typing import Optional, Tuple
from django.db import models, transaction
from wagtail.models import Page

class RecycleBinPageMixin(models.Model):
    """
    Wagtail 页面通用回收站抽象基类 (Mixin)。

    与 ExternalContentPageMixin 协同工作，提供通用的两阶段删除、
    7天保护期、原位恢复草稿与 Elasticsearch 搜索强隔离守卫。
    零硬编码，适用于全站任意 Wagtail Page 派生模型。
    """

    class Meta:
        abstract = True

    def get_recycle_bin_title(self) -> str:
        """返回在回收站界面安全展示的标题（子类可重写，默认取 page.title）"""
        return self.title or f"未命名页面 ({self.pk})"

    def get_original_parent_id(self) -> Optional[int]:
        """返回移入回收站时的父栏目 ID"""
        parent = self.get_parent()
        return parent.pk if parent else None

    def can_move_to_recycle_bin(self, user=None) -> Tuple[bool, str]:
        """核验当前页面是否满足移入回收站的业务与权限前置条件"""
        if not self.pk:
            return False, "未持久化的页面无法移入回收站"
        # 检查是否已处于回收站
        from external_content.models import ExternalContentPublicationState, RecycleStatus
        state = ExternalContentPublicationState.objects.filter(page_id=self.pk).first()
        if state and state.recycle_status == RecycleStatus.TRASHED:
            return False, "页面当前已处于回收站中"
        return True, ""

    def can_restore_from_recycle_bin(self, user=None) -> Tuple[bool, str]:
        """
        核验当前页面是否满足原位恢复为草稿的条件：
        1. 必须处于 TRASHED 状态；
        2. 原父栏目必须存续且允许添加子页；
        3. 原位置 slug 不能与现有同父同语言页面冲突。
        """
        from external_content.models import ExternalContentPublicationState, RecycleStatus
        state = ExternalContentPublicationState.objects.filter(page_id=self.pk).first()
        if not state or state.recycle_status != RecycleStatus.TRASHED:
            return False, "页面未处于回收站状态，无法恢复"

        # 原父栏目存续核查
        if not state.original_parent_id or not Page.objects.filter(pk=state.original_parent_id).exists():
            return False, f"原父栏目 (ID: {state.original_parent_id}) 已不存在，无法原位恢复"

        # slug 冲突核查
        parent = Page.objects.get(pk=state.original_parent_id)
        conflict_qs = parent.get_children().filter(slug=self.slug, locale=self.locale).exclude(pk=self.pk)
        if conflict_qs.exists():
            return False, f"原父栏目下已存在相同 Slug ('{self.slug}') 的页面，存在路径冲突"

        return True, ""

    def move_to_recycle_bin(self, actor_id: Optional[str] = None, request_id: Optional[str] = None):
        """执行两阶段删除第一阶段：原子软删除下架与 ES 索引剔除"""
        from external_content.recycle import execute_move_to_recycle_bin
        return execute_move_to_recycle_bin(self, actor_id=actor_id, request_id=request_id)

    def restore_to_draft(self, actor_id: Optional[str] = None, request_id: Optional[str] = None):
        """执行原位恢复为草稿：原 ID/父栏目恢复，置 live=False，设置人工发布锁存"""
        from external_content.recycle import execute_restore_to_draft
        return execute_restore_to_draft(self, actor_id=actor_id, request_id=request_id)
```

### 3.2 Elasticsearch 搜索 UNINDEX 信号与防迟到版本围栏

#### 1. `ContentSearchOperation.UNINDEX` 协议扩展
在 `wagtailblog3/apps/search/models.py` 中将 `ContentSearchOperation` 显式扩展新增 `UNINDEX = "unindex"` 枚举。

```python
class ContentSearchOperation(models.TextChoices):
    UPSERT = "upsert", "写入"
    TOMBSTONE = "tombstone", "墓碑"
    UNINDEX = "unindex", "物理下架"  # 批次 1 新增
```

#### 2. 信号触发与 Outbox 事件原子生成时机
当页面执行 `move_to_recycle_bin` 时，必须在同一个 MySQL 事务内同步完成搜索状态跃迁与 Outbox 登记：
1. `ContentSearchState.objects.select_for_update().get(page_id=page.pk)`；
2. 递增 `state.content_version += 1`；
3. 变更 `state.desired_operation = ContentSearchOperation.UNINDEX`；
4. 标记 `state.searchable = False`；
5. 插入 `ContentSearchOutbox` 事件：
   ```python
   ContentSearchOutbox.objects.create(
       page_id=page.pk,
       content_version=state.content_version,
       operation=ContentSearchOperation.UNINDEX,
       searchable=False,
       status=ContentSearchStatus.PENDING,
       ...
   )
   ```

#### 3. 消费端防迟到版本围栏（Anti-Late-Arrival Version Fencing）

搜索事件投递器（`ContentSearchDeliveryWorker`）在处理任何 `UPSERT` 或 `UNINDEX` 请求前，必须执行三道围栏校验：

```
       [Outbox 事件出队]
              │
              ▼
    ┌─────────────────────┐
    │ 获取 SearchState 读 │
    └─────────┬───────────┘
              │
              ├─────────────────── event.content_version < state.content_version
              │                    (存在更新的变更轮次)
              ▼                                  │
    ┌───────────────────┐                        ▼
    │ 判定为 SUPERSEDED │ ◄──────────────────────┘
    │ (直接丢弃，不调用ES)│
    └───────────────────┘
              │
              │ event.content_version == state.content_version
              ▼
    ┌───────────────────┐
    │ 核验操作类型与状态 │
    └─────────┬───────────┘
              │
              ├─────────────────── operation == "upsert" 且 state.searchable == False
              │                    (页面已被软删移入回收站)
              ▼                                  │
    ┌───────────────────┐                        ▼
    │ 判定为 ILLEGAL    │ ◄──────────────────────┘
    │ (阻断写入，丢弃事件)│
    └───────────────────┘
              │
              │ operation == "unindex"
              ▼
    ┌───────────────────┐
    │ 调用 ES Client    │
    │ 执行物理 DELETE   │
    └─────────┬───────────┘
              │
              ▼
    ┌───────────────────┐
    │ 状态标记 SUCCEEDED │
    └───────────────────┘
```

**核心围栏契约**：
1. **防旧发布迟到**：若因网络抖动导致旧的 `UPSERT` 异步任务在 `UNINDEX` 执行后才到达 Worker，Worker 检查发现 `event.content_version < current_state.content_version` 且 `current_state.searchable == False`，无条件将该事件标记为 `SUPERSEDED` 并彻底丢弃，**绝对阻止其在 ES 中复活已删除文档**。
2. **草稿恢复零索引**：页面恢复为草稿时，状态为 `live=False`, `searchable=False`，**不向 Outbox 产生任何事件**，ES 保持完全未索引状态。
3. **防旧下架迟到**：页面后续经由人工正式发布后，`content_version` 再次单调递增。若有重试中的迟到 `UNINDEX` 此时到达，同样因版本落后被立即判定为 `SUPERSEDED` 丢弃，**绝对不会误删新发布的正式搜索文档**。
