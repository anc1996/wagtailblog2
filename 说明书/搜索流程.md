搜索没问题就好。下面把这套搜索的设计思路完整讲一遍，从架构到打分细节，方便你以后维护和扩展。

## 一、整体架构：三层职责分离

```
┌─────────────────────────────────────────────────────────┐
│  应用层 (Django/Wagtail View)                            │
│  - 接参数、Paginator 分页、模板渲染                      │
└────────────────────┬────────────────────────────────────┘
                     │ 只跟 Wagtail SearchResults 交互
                     ▼
┌─────────────────────────────────────────────────────────┐
│  Wagtail SearchResults 适配层                             │
│  - 保留 live().public() QuerySet 公开范围                  │
│  - 由 Wagtail 搜索后端执行全文检索                         │
│  - 返回前保持公开页面对象范围                              │
└────────────────────┬──────────────────────────────────���─┘
                     │ Wagtail 搜索后端
                     ▼
┌─────────────────────────────────────────────────────────┐
│  存储层 (Elasticsearch + IK 分词)                        │
│  - BM25 算分 + 字段加权 + 短语提权                       │
│  - 服务端排序、分页、过滤                                │
└─────────────────────────────────────────────────────────┘
```

**核心原则：让最擅长的层干最擅长的事。** Wagtail 先确定公开页面范围，ES 负责全文检索和排序，Python 只做参数、分页和响应格式化。

## 二、打分模型：双层加权

这是整套方案的灵魂。你要的需求是「精确句子命中分数 × 10，并按字段重要性加权」，我们用 ES 的 `bool/should` 把它拆成两组子句叠加：

### A 组：字段级精确短语（match_phrase）

每个字段单独发一个 `match_phrase`，词序严格（`slop=0`），boost = 字段权重 × 10：

| 字段 | 字段权重 | 短语提权 | 实际 boost |
|---|---|---|---|
| `title` | 10 | ×10 | **100** |
| `blog_blogpage__intro` | 5 | ×10 | **50** |
| `blog_blogpage__body_text` | 2 | ×10 | **20** |

### B 组：分词 fallback（multi_match）

只命中分词、没连贯短语命中的文章靠这一段保底，boost=1，分数远低于 A 组。

### 合并规则：should 子句分数自动相加

ES 的 `bool/should` 是分数叠加的，所以一篇文章只要在多个字段同时命中，分数就会自然累加：

```
全字段都精确命中：100 + 50 + 20 + 分词分 ≈ 顶级
仅 title 精确命中：100 + 分词分     ≈ 高
仅 body 精确命中：20 + 分词分       ≈ 中
仅分词命中（长尾）：分词分          ≈ 低
```

完美对应你说的「凡是句子里有的字段，权重 × 10」「多字段命中分数累加」。

## 三、Wagtail 搜索结果与公开范围

当前公开入口先构造 `Page.objects.live().public()`、`BlogPage.objects.live().public()` 或等价的 Wagtail QuerySet，再调用 `.search()`。这使未发布页面、直接访问限制和祖先页面限制在搜索后端执行前就成为硬边界。

```python
Paginator(es_results, 20).page(5)
   │
   └─ Wagtail 搜索后端返回当前公开范围内的结果页
```

项目只接受前 10,000 条结果窗口；超过窗口的 HTML/API 请求明确返回参数错误，不承诺无限深翻页。

## 四、保序回查：CASE WHEN 的妙用

ES 按相关性排好的顺序是 `[123, 45, 678, 9, ...]`。直接 `Page.objects.filter(pk__in=[...])` 拿回来的对象**顺序会被 MySQL 的 B+树打乱**。

解决办法：用 `Case/When` 在 ORDER BY 子句里编码 ES 的顺序：

```python
preserved = Case(*[When(pk=pk, then=pos) for pos, pk in enumerate(page_ids)])
Page.objects.filter(pk__in=page_ids).specific().order_by(preserved)
```

生成的 SQL 类似：
```sql
SELECT ... FROM wagtailcore_page
WHERE id IN (123, 45, 678, 9, ...)
ORDER BY CASE WHEN id=123 THEN 0 WHEN id=45 THEN 1 ... END
```

一条 SQL 完成「过滤 + 保序 + specific 多态」。

## 五、字段映射：理解 Wagtail 的索引规则

Wagtail 在 ES 里把所有 Page 子类塞进同一个索引（`wagtailcore_page`），用 `app_label_modelname__` 前缀区分非共享字段：

| Python 模型字段 | ES 实际字段名 | 原因 |
|---|---|---|
| `Page.title` | `title` | 父类共享字段 |
| `BlogPage.intro` | `blog_blogpage__intro` | 子类独有 |
| `BlogPage.body_text` | `blog_blogpage__body_text` | 子类独有 |
| `Page.live` (FilterField) | `live_filter` | 加 `_filter` 后缀 |
| Django ContentType | `_django_content_type` | Wagtail 自动注入的数组 |

这就是为什么必须先 `curl ... /_mapping` 确认实际字段名，否则查询全 0 命中。

## 六、过滤 vs 算分：filter 和 should 的分工

DSL 里把条件分两类：

- **`filter` 子句**：硬性过滤，不参与算分（live 状态、内容类型、日期区间）
- **`should` 子句**：软性匹配，参与算分（短语命中、分词命中）

```json
{
  "bool": {
    "should": [...],      // 算分用，决定排序
    "filter": [...],      // 过滤用，决定能不能进结果集
    "minimum_should_match": 1
  }
}
```

`filter` 走 ES 的 filter cache，性能比 `must` 高一个数量级，且不影响相关性分数。

## 七、故障契约：明确不可用

当前搜索不把同一 Elasticsearch 后端的两种调用方式称作独立降级：

```
Wagtail public QuerySet.search()
    │
    │ 搜索后端不可用
    ▼
HTML / AJAX / JSON API 返回 search_unavailable
```

搜索后端不可用不会伪装成“0 条结果”，客户端可根据稳定错误码展示重试状态。

## 八、跟旧方案的对比

| 指标 | 旧方案（内存精排） | 新方案（ES 下推） |
|---|---|---|
| 搜索公开边界 | ❌ 原生回查可能绕过 `public()` | ✅ QuerySet 先执行 `live().public()` |
| 搜索后端故障 | ❌ 同一后端伪降级并可能返回空结果 | ✅ 稳定 `search_unavailable` 错误 |
| 深分页 | ❌ 容易误导为可无限翻页 | ✅ 超过 10,000 条明确拒绝 |
| 搜索建议 | MySQL 历史词 `icontains` | 继续使用历史词，页面标题不直接暴露 |
| 正文来源 | MongoDB 正文 | MongoDB 正文只在索引构建/详情读取 |

## 九、可继续优化的方向

按性价比排序：

1. **ES highlight**：让 ES 返回命中片段的高亮 HTML，前端直接渲染（一行 DSL 配置）
2. **search_after 替代 from/size**：翻深页超过 10000 时用 search_after，无上限
3. **IK 自定义词典**：挂载业务领域词典（技术栈、产品名），提升分词准确度
4. **completion suggester**：搜索建议从 MySQL `icontains` 全表扫迁到 ES completion 字段
5. **结果缓存**：把热门 query 的前几页结果缓进 Redis，减少 ES QPS
